# 第 2 章草稿：技术可信度审计——官方数字的成立条件、Vals 评测的分裂结论与 9 类失败模式

## 论点

Jev 的技术可信度不是"高"或"低"，而是**条件性极强**：在一个狭窄但真实的区间里（单文档、证据局部、答案空间小、判断原子化）它确实达到前沿水平且便宜两三个数量级；一旦越过这个区间（需要推理链、数值计算、跨条款聚合、抗注入），它会以**不可预期的方式崩塌**，而不是平滑降级。因此本章要拆的不是"Jev 准不准"，而是"**每个数字是在什么条件下测出来的，能外推到哪里**"。

## 2.1 官方评测：一套自洽、但结构上不可外推的方法

**论据。** TypeSafe 明确**拒绝发布标准 benchmark**，创始人的理由是"公开 benchmark 极易被操纵"，并自建了一套 **workflow evals**：给定一条代码工作流，把每个模型的输出与**参考答案**比对 ([官方发布博客](https://typesafe.ai/blog/introducing-system-one-models-and-jev))。这套方法的三个关键设定决定了它的适用边界：

1. **参考答案不是 ground truth，是两个模型的共识。** 官方原文："reference labels are generated via an average of the responses of GPT-6 Astra and Claude Fable 5.1, both at **high thinking**, answering every question in the harness"，而"所有其他模型使用 provider 的默认推理档位" ([evals.typesafe.ai](https://evals.typesafe.ai/))。
2. **它放弃了标签正确性的讨论。** 原文："Instead of debating the correctness of the harness and labels, **we assume that the code is correct**, and measure against the current smartest large models"（同上）。
3. **四个 workflow 全部是"单文档 + 局部证据 + 小答案空间"形状**：Security Incidents、Agent Trace Observability、Invoice Processing、Customer Service；以 Invoice Processing 为例，官方明确"金额、日期、账号、状态**由代码计算而非问模型**" ([workflow 详情](https://evals.typesafe.ai/invoice_processing.html))。

**分析。** 这三条叠起来，意味着一件事：**这套评测测的是"与两个前沿模型共识的一致度"，而不是"判断对不对"**。官方自己也承认工作流"由我们模型能力团队的人构建，因此可能存在偏差"，且 193.6x / 444.6x "属于真实世界收益的**偏高区间**" ([发布博客](https://typesafe.ai/blog/introducing-system-one-models-and-jev))。

更值得注意的是两股**方向相反**的偏差，官方只提了其中一股。参考答案取自 Astra 与 Fable 的**最高思考档**，而被测 LLM 用**默认档**——这会让所有 LLM 显得比"它自己的最强版本"更差，从而**有利于 Jev**；官方提到的另一股是"用 Astra/Fable 的平均作参考会偏向 OpenAI 与 Anthropic 的输出分布"，从而**不利于 Jev**。两股偏差无法相互抵消，净方向不可判定。**本文认为**，这恰恰说明该评测适合做"同条件下相对排序"，不适合做"绝对能力标定"。

**「0% 幻觉」是最常被误读的一条。** 官方首页把它与结构化输出错误率并列展示（Jev 0.00%，Claude Sonnet 5 达 12.6%），但脚注写明："Jev's 0% represents its **guarantee that outputs match the defined schema**; it is **not an observed error rate from testing**" ([typesafe.ai](https://typesafe.ai/))。换言之，**它保证的是"答案一定落在你声明的选项集合内"，不是"答案是对的"**——这是类型系统的性质，不是模型能力的度量。把它读成"不会判断错"是本课题中流传最广的一处误读。

**「68%」的纵轴口径（本节核实项）。** 官方首页那张 "Workflow Intelligence vs Cost" 图的纵轴是 **Mean accuracy**，定义为"每个点把某模型配置在**四个 workflow 上等权平均**的 accuracy、cost、time 聚合"，横轴是对数刻度的单次工作流平均成本；官方并附注"These are workflow evaluation results, **not a measure of accuracy on every task**" ([evals.typesafe.ai](https://evals.typesafe.ai/), [typesafe.ai](https://typesafe.ai/))。**因此 68% 的确切含义是：在 4 个自建 workflow 上、对"两个前沿模型共识标签"的平均一致度约 68%，不是通用任务准确率，也不是通过率。** 官方在同一段里承认 Jev 是"图中成本最低的模型"，但 Terra 与 Sonnet 5 "以更高成本达到相近准确率"，Sol 与 Opus 5 "准确率与成本都更高"——**官方自己的图就承认它不是精度最优解**。

**补充核算（本文）**：首页并排示例给出的单例数字是 Jev `$0.000081 / 0.114s` 对 LLMs `$0.013880 / 8.566s`，算术比为 **171x 便宜 / 75x 快**；而标题是 **444.6x / 193.6x**。两个数不一致，说明标题是四个 workflow 的等权平均（且由差距更大的 workflow 拉高），**不是任何单个场景的实际倍数**。

## 2.2 Vals AI：同一份评测里最好的成本故事与最差的精度故事

**论据。** Vals AI（2026-10-06）是目前唯一可核验的第三方独立评测，它自建了 400 项声明核验基准（48 家美国公司最新 10-K，1,960 个段落，5 类各 80 项），外加 LegalBench 的 396 题切片（12 子任务 × 33 题）([vals.ai](https://www.vals.ai/blogs/independent-evaluation-of-jev))。结果在两端同时极端：

| 维度 | Jev 1.13.0 | 对照 |
|---|---|---|
| 声明核验准确率 | **0.975**（390/400） | 与 GPT-6 Astra、GPT-6.1 Sol、GPT-6 Luna 同分 |
| 单次成本（每 1,000 案例） | **$0.02** | GPT-6 Astra $18.00、Claude Opus 5.5 $9.64、GPT-6 Luna $0.10 |
| 延迟（32 个判断） | **0.12s** | 比 GPT-6 Astra 低 194x、比 Gemini 4 Argon 低 241x |
| LegalBench 原始准确率 | **12/12 垫底** | 其余每个系统的领先经 Bonferroni 校正后仍统计显著 |
| LegalBench 类别平衡准确率 | **0.730（12/12）** | 第一 GPT-5.6 Terra 0.932；Haiku 4.5 0.732 |
| 1% 错误预算下的自动化 | 覆盖 95%、实际错误 **1.6%** | 12 个系统中 6 个超预算，Jev 是其中之一 |
| ECE | 声明核验 **0.011（最低）** / LegalBench **0.108（最高）** | 校准不跨任务迁移 |

**分析：这个分裂不是"评测有问题"，是"任务依赖"。** 注意失败的具体形态——`contract_nli_permissible_copy` 上 **Jev 对全部 33 题答 "Yes"**，而金标是 16 yes / 17 no（常数"Yes"基线即得 0.485）；`contract_nli_confidentiality_of_agreement` 33 题答了 30 个 yes ([vals.ai](https://www.vals.ai/blogs/independent-evaluation-of-jev))。这不是"随机出错"，是**模型在它不擅长的任务上退化成常数输出**。这与官方 jaggedness 文档自述的"字面理解""多层间接推理掉精度"完全同构（见 2.4）。

两类任务的结构差异可以概括为：

- **声明核验型（Jev 强）**：证据在同一段落内、三分类、判断原子化、答案空间封闭 → 这正是官方 workflow evals 四个任务的形状。
- **法律推理型（Jev 崩）**：需要否定/例外/条件嵌套、需要跨条款聚合、需要"这句话在合同语境下是否构成许可"这类多层间接 → 超出"单次前向 + 局部证据"的能力半径。

**必须同时记住 Vals 自己给的警告**：LegalBench 只是 396/1,808 的小切片，"**不能代表整个基准上的表现**"，且 LegalBench 是公开数据集"**很可能已在 LLM 的训练数据中**"——这意味着 LLM 侧成绩可能被高估，Jev 的落后幅度也可能被放大；作者还披露原计划的 McNemar 精确检验**未执行**、只跑了 bootstrap (同上)。**因此正确读法是：Jev 在"需要推理链的法律判断"上显著弱于 LLM，这一点方向可靠；但 0.730 这个具体数值不宜外推到 LegalBench 全量。**

**第三方延迟数据的补充**：Cloudflare 在发布竞品 Clef 时给出的对照表中，**Jev 的中位延迟为 524.1ms、p95 536.0ms**，已超出官方 70–500ms 区间的上沿（同表中 Clef-flash 为 38.8ms）([Cloudflare](https://blog.cloudflare.com/clef-decision-models/))。这说明官方延迟区间应理解为"理想网络与特定 state 规模下的端到端值"，跨厂商、跨地域实测会显著偏移。

## 2.3 为什么这个品类难以用 benchmark 衡量

**论点。** "Jev 准不准"这个问法本身不成立，因为**答案空间由用户的 schema 定义**——同一个模型在"3 类工单分类"和"27 问事故编码"上是两个不同任务，换一套 criteria 就等于换一道题。官方文档把这一点写成了产品约束："Jev 不做微调或 LoRA，同一份权重服务所有账户"，领域适配只能通过 `state`、`instructions`、`criteria` 完成 ([docs: Models](https://docs.typesafe.ai/models))。

**学术侧给出了同一结论的独立验证**：德州州立大学在 500 万条警方事故叙述上的研究明确写道，**"校准性随模型而变，而非随范式而变"**，因此"每个模型都必须单独审计"（calibration is a property of the model, not of the paradigm）([arXiv:2609.24052](https://arxiv.org/html/2609.24052v1)）。这句话直接否定了"决策模型这个品类天然校准更好"的叙事：**你无法通过"选对品类"获得校准保证，只能通过"自己标定"获得。**

## 2.4 confidence 字段的实际价值：比宣传的小得多

Vals 的实测结论很直接：Jev 的 `confidence` **"几乎精确等于其概率分布，不提供额外信号"**，因此无法用它改善路由决策 ([vals.ai](https://www.vals.ai/blogs/independent-evaluation-of-jev))。配合 ECE 的跨任务反差（声明核验 0.011 → LegalBench 0.108），实践含义是：**任何从别人的博客、官方 cookbook 或模板里抄来的置信阈值都不可移植**。官方文档本身也反复要求"用你自己标注的数据标定阈值"，Vercel 的集成指南同样写明"示例阈值只是起点" ([Vercel KB](https://vercel.com/kb/guide/typesafe-jev-and-ai-sdk))。

## 2.6 结构性误差：两位小数网格设下的"校准地板"

德州州立大学的研究在 500 万条真实语料、240 万次模型答案上观察到：**Jev 的概率输出落在离散的两位小数网格上（0.01–1.00，最多 100 个取值），其中 0 从未出现过，1 只出现过 2 次**。由此推出一个纯数学的结论：若模型是校准的，则期望概率 ρ = E[p] ≥ δ(1−w₀)，其中 δ = 0.01、w₀ 为输出 0 的频次——**任何基率低于 1% 的变量在数学上都不可能被校准**，且这一误差地板**与排序质量无关**。作者明确指出"**这是接口/网格的属性，不是模型能力问题**" ([arXiv:2609.24052](https://arxiv.org/html/2609.24052v1))。

后果很具体：论文中 5 个稀有变量的期望概率被网格地板抬高，其中 `preg_mentioned` 有 **80%** 的期望概率贡献来自 p=0.01 这一档。同时该研究的正面结论也不该被忽略：Jev 在 27 问 schema 上 **F1 = 0.908**，与一个前沿 LLM 差 0.059、与另一个统计上不可区分；**实测成本 $0.154/千条**、中位延迟 0.20s、44 req/s、**0 次失败**（同上）。

## 小结

1. **Jev 的"准"是有形状的**：单文档、证据局部、答案空间封闭、判断原子化 → 前沿水平；需要推理链、数值计算、跨条款聚合 → 退化为常数输出。
2. **所有被广泛引用的数字都必须带条件读**：193.6x/444.6x 是四个自建 workflow 的等权平均；0% 幻觉是类型保证不是实测错误率；68% 是与两个模型共识的一致度不是通用准确率。
3. **校准不能继承，只能自建**：品类不提供校准保证，confidence 无增量信息，ECE 不跨任务迁移——因此**任何外部阈值都不可移植**。
4. **有一类误差调不好**：两位小数网格给基率 <1% 的变量设了数学地板，这是接口属性。

## 优先级 3（必做，一句话）：§2.5 末尾补高基数边界

**加在 §2.5 末尾**：

> 另需区分两个不同的高基数问题：**Score 的精度衰减从 K≈7 就开始**（见 2.6.2），而 **Choice 的硬上限是 255 个选项**——官方承认"Jev supports a cardinality up to 255"，超过需调用方自行两阶段降维（[发布博客](https://typesafe.ai/blog/introducing-system-one-models-and-jev)）；第三方实测也确认 Jev 在 256/384/512 选项下全部拒绝，而同批 LLM 在 512 项下仍可作答（[nibzard](https://github.com/nibzard/decision-model-benchmark)）。**两个数字相差约 1.5 个数量级，不可混用。**
