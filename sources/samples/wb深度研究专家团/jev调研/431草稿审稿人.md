## 三、`/v1/systemone`：一个已经标准化的封闭 schema

这是本章最重要的事实。契约不是"像 OpenAI 那样的自由文本接口"，而是一个**封闭的类型化 schema**，官方文档给出了完整的最小请求：

```bash
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer $TYPESAFE_API_KEY
{
  "state": "客户工单原文…",
  "model": "jev-latest",
  "questions": {
    "department": {"type":"choice","instructions":"哪个团队处理",
                   "criteria":{"billing":"付款问题","technical":"技术问题"}},
    "frustration": {"type":"score","instructions":"愤怒程度",
                    "criteria":["平静","不满","愤怒"]},
    "is_urgent":  {"type":"noul","instructions":"是否紧急"}
  }
}
```

响应按同一批 question id 回填，`choice` 返回选中项 + `probabilities` + `confidence`，`score` 返回 0–2 的期望值 + `legend` + `probabilities` + `confidence`，`noul` 只返回一个 0–1 的概率（**不返回 confidence**），另有 `usage`。注意 `questions` 是**以 id 为键的对象**，不是数组——这决定了它可以被静态类型化，也决定了它容易被标准化。

标准化程度已经有硬证据：Cloudflare 官方称 Clef "fully Jev-API compatible… you can make the swap extremely easily"；Laya 只需改 base URL；Von 宣称 byte-compatible；Kev 网关、CLM、APUS-OpenJev 都实现同一契约。**一个接口在 6 周内被 3 家大厂 + 11 个开源项目对齐，这在模型 API 史上是罕见的**——对比 OpenAI Chat Completions 用了两年才成为事实标准。

## 四、由此推出的行动建议，以及兼容性的缝隙

**建议：可以且应当按契约做抽象层**——一个 `DecisionModel` interface（`evaluate(state, questions) → answers`）+ 多 provider 适配器。厂商锁定风险显著低于常规模型采购，因为迁移成本近似于一次配置变更。

但有三道缝隙必须提前设计：

1. **OpenAI 兼容端点不支持评估调用。** Vercel 文档原文："AI Gateway exposes evaluation through the AI SDK, rather than its compatibility endpoints… OpenAI-compatible endpoints don't support Jev evaluation"。所以抽象层**不能**只做一个 OpenAI-compatible shim，必须走原生 HTTP 或 Gateway 的 evaluation 通道。
2. **同一原语有三个名字。** TypeSafe 叫 `noul`，OpenAI 叫 `Predicate`，Vercel evaluation API 映射为 `boolean`/`probability`。字段名映射错了不会报错，只会静默返回错误语义。
3. **`confidence` 与 `score` 的语义未必一致。** 官方示例中 `frustration` 返回 `score: 0.67` 而 `confidence: 0.5`——`score` 是档位上的**概率加权期望**，不是 argmax；`confidence` 是分布集中度（0 = 均匀，1 = 全集中），不是"选中项概率"。此外 Vercel 注明概率四舍五入到两位小数，分布可能合计 0.99；`probabilities` 在各 provider 中是**可选字段**，必须防御性读取。更细的差异在社区实现里：Laya 的移植版 README 明确写"Answer semantics follow rl_agent_api.py, not kev's door"，并采用四位小数 ties-to-even——**与 Jev 的两位小数不同**。

**所以本章的核心结论是：抽象层要防的是「语义漂移」，不是「接口变更」。** 接口变更会立刻抛错，好处理；语义漂移会安静地让你的阈值失效。防御手段是把"契约测试"写进 CI：固定一组 (state, questions) 黄金样本，对每个 provider 断言字段存在性、概率归一性、`score` 与 `probabilities` 的一致性、以及 `confidence` 的单调性。

## 六、邻近范式的边界（防止把非竞品当竞品）

品类边界模糊时，采购清单会被灌水。本文提出的**唯一判断标准**：该模型是否输出**"在调用方预先声明的答案空间上的校准概率"**。按此标准：

- **reward model / guardrail**（Llama Guard 系、Respan Span-01/02）——输出安全标签或分数，答案空间由模型方预设，**不是**竞品，但 Span 系列因为实现了 Choice/Noul/Score 而被收录，属边界个案。
- **router 模型**（LLM 路由 / 意图分类）——输出路由目标，答案空间可声明，**功能上是竞品的子集**，awesome-jev 里 20+ 个 router 项目正说明它是最高频用例。
- **embedding + head**（GLiNER2.5-Decide，340M encoder，Apache-2.0）——架构同源（编码器 + 头），但训练目标是抽取而非校准决策，**是近亲不是同类**。
- **「System One」概念溢出**（CUA-S1 做 computer use、OpenDecision 400M 零样本）——借用了术语，但输出空间与校准目标不同，**概念邻居**。

## 七、供应商可持续性与竞争结构

可核验事实层：种子轮 $40M @ $2 亿估值（09-15 公布）；A 轮 **$870M @ $75 亿**，a16z 领投，红杉、DCVC 跟投，Martin Casado 入董事会（10-09）。24 天内估值 37.5 倍、融资额 22 倍。同期竞争事实：Convai Innovations 在 Jev 发布后 3 天（09-18）推出 Apache-2.0 的 Laya。

**竞争结构判断**：六厂 24 天下场 + 11 个开源复现，说明**护城河在品牌与生态，不在技术**——底座可以买（微软用 Qwen3.5-9B、Cloudflare 用 Qwen3.8-27B、Together 用 Qwen3.5-4B），训练配方可以复现（RLCD + proper scoring rules 已在 Laya 开源实现中公开）。「完全兼容 Jev API」因此是双刃剑：既是标准制定者的分发优势，也是**被零成本替换的风险敞口**。

**"Jev 先发优势可持续性"评估框架**（框架，不给结论），四个可观测变量：
1. **权重是否开放**——闭源即保留议价权，但也放弃生态扩散；
2. **是否有独占能力**——当前 Jev 在模态上落后（Clef-omni 支持音视频、d1-omni 支持图像），在上下文上落后（32k vs 64k/384k/512k），若 12 个月内不补齐，差异化只剩生态；
3. **生态绑定深度**——SDK、Agent Skill、Gateway 集成、awesome-jev 2.5k 星 / 374 fork 与 290+ 依赖仓库；
4. **企业级功能**——ZDR、No Training、SLA、私有部署，这是开源复现最难对齐的一层。

## 小结与可行动建议

**可行动建议：现在就把 decision model 抽象成一个 interface（`evaluate(state, questions) → {answers, confidence, probabilities}`），后端做成可插拔适配器，同时把"契约测试"作为一等公民写进 CI——因为你真正要防的不是接口被改，而是同一个字段名在不同厂商那里意味着不同的东西。** 这样无论 12 个月后是 Jev、Clef 还是一家尚未出现的厂商胜出，你的迁移成本都是一次配置变更，而不是一次重构。
