# 第 1 章 品类边界：decision model 与 LLM 结构化输出、专训分类器、规则引擎的三角分工

## 本章论点

decision model 既不是"更快的 LLM"，也不是"更聪明的分类器"。它是一个**标签空间在推理时由请求定义、类型安全与概率校准由权重保证**的第三类组件。它的边界不是营销话术画出来的，而是由四条不可协商的约束推出来的：**不生成 token、不提供定制权重、只吃文本、只对输入计费**。本章的任务是把这条线画准，并明确指出哪些需求应当直接判出局。

## 1. 三个原语：语义差异与业务映射

decision model 的表达力被三个原语锁死，先认清"拿不到什么"比认清"能做什么"更重要。

**Choice** 回答"是这几个里的哪一个"，最多 255 个选项，返回 `choice`、覆盖全部选项且和为 1 的 `probabilities`、以及描述分布尖锐程度的 `confidence`（0–1）。它**拿不到程度**——官方明确 Choice 不适合有内在顺序的判断，那类需求应改用 Score（[Choice 原语](https://docs.typesafe.ai/primitives/choice)）。业务映射：工单路由、文档分类、智能体下一步动作选择。

**Score** 回答"落在哪个档位"，接受 **2–10 个有序等级**，返回的是**概率加权均值**，因此**可以落在两档之间**（如 1.43）（[Score 原语](https://docs.typesafe.ai/primitives/score)）。它拿不到两样东西：一是未在等级中体现的维度；二是"分布形状"——score 同为 1.0，可能是概率全压在一档，也可能是首尾各半，必须同读 `probabilities` 与 `confidence`。业务映射：严重度、优先级、置信档位、阈值判断。

**Noul** 回答"这个命题成立吗"，返回 0–1 的为真概率，**没有独立 `confidence` 字段**（[Primitives 总览](https://docs.typesafe.ai/primitives)）。它拿不到选项间比较，也不表达程度——官方特别强调 0.5 只意味着"是/否概率相等"，不意味着"中等水平"。业务映射：是否含 PII、是否要求退款、是否需要人工复核。

一个容易被忽略的机制细节：**同一请求内各问题的答案相互独立**，一个问题的答案不会成为另一问题的隐藏上下文，因此增删问题不影响其他问题的结果；问题 `id` 不发给模型，完整问法必须写进 `instructions`（[Primitives 总览](https://docs.typesafe.ai/primitives)）。这决定了它的组合方式只能是"代码里加权"，而不是"模型里推理"。

## 2. 非生成式机制与 RLCD 的后果

Jev 一次前向、并行输出全部答案，不生成任何 token。训练目标上，官方把自己与 LLM 对照得很清楚：LLM 用 RLHF/RLVR 优化"人类偏好的文字"或"可程序验证的奖励"，而 Jev 用 **RLCD（Reinforcement Learning for Calibrated Decisions）** 优化"校准过的决策"（[发布博客](https://typesafe.ai/blog/introducing-system-one-models-and-jev)）。

后果有两条，都是选型者最容易误判的地方：

**第一，它不能写报告。** 官方文档直陈：System One 模型"不写回复、不产出代码、不生成关于自身推理的解释"（[System One 概念页](https://docs.typesafe.ai/concepts/system-one)）。任何"顺便让它总结一下""让它给个人话理由"的需求，都超出了品类定义，不是调参能解决的。

**第二，它不该被要求解释理由。** 这是本章最需要提前说清的一点——很多团队第一反应是"它为什么不告诉我为什么这么判"。原因是结构性的：解释必须由生成 token 产生，而 RLCD 优化的是概率校准而非理由质量；即便在 schema 里加一个"理由"字段，那个字段也只是**又一个被分类的输出**，不具备因果解释力。可解释性在这里必须来自外部结构：**把大判断拆成原子问题（暴露判断）、读概率与 confidence（暴露不确定）、把阈值与组合写在代码里（暴露规则）**——这正是官方推荐的工作流（[How to build with System One](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)）。

需要"理由"的场景，本质上是需要 LLM 的场景，应交给第 6 章讨论的编排层。

## 3. 边界一：与传统专训分类器——不是替代，是补位

Cloudflare 发布 Clef 时给的对照表常被误读：CLINC150+OOS 上 macro-F1，Clef 97.43、**Jev 89.27**、小模型 **Laya 仅 3.19**；延迟上 Laya 中位 **5.8ms**、Jev **524.1ms**（[Cloudflare 博客](https://blog.cloudflare.com/clef-decision-models/)）。

**3.19 不是"模型差"，而是"标签空间不匹配"。** 把一个只在特定标签集上训练过的小模型，放到另一套 150 类意图标签上，它当然崩。这张表恰恰证明：**零样本决策模型与专训小模型根本不在同一条性能曲线上，不可横向比**——不能读成"Jev 比专训分类器强 28 倍"，也不能读成"专训分类器没用"（Laya 那 5.8ms 的优势，Jev 永远拿不回来，快了两个数量级）。

分界线由此清晰：

- **该训分类器**：标注数据充足、标签集稳定、延迟极敏感、单一租户单一领域。Cloudflare 的说法是，自建分类器要划算是需要长期积累的标注数据的，换来的是更准更快；而微调本身是"牺牲通用性能换取领域精度"的交易（[Cloudflare 博客](https://blog.cloudflare.com/clef-decision-models/)）。
- **该用 decision model**：标签会变、冷启动无标注、长尾类别、多租户各自一套标签体系——即"需要换标签而不重训"的那一维。

## 4. 边界二：与 LLM + structured output——差在延迟、成本、类型安全，不在精度

精度的详细证据留给第 2 章，这里只点一句：第三方独立评测显示两者在声明验证任务上已难分高下（[Vals AI 评测](https://vals.ai/blogs/independent-evaluation-of-jev)）。真正的分野在工程账上，而这笔账**最容易被算错**。

Vals AI 的实测是本章最值得记住的一个数：**要求 LLM 输出概率而非裸标签，会让成本上升 29%（GPT-6 Luna）到 101%（GPT-5.6 Sol）**，12 个系统里 11 个涨价，唯一例外是 Gemini 4 Argon 的 −3%；Jev 的输出本身就是分布，零额外成本（[Vals AI 评测](https://vals.ai/blogs/independent-evaluation-of-jev)）。只比 "$command://Mtok 单价"的选型表会系统性低估 LLM 一侧的成本，还会漏掉两笔：LLM 输出 token 单价通常是输入的 5 倍（[发布博客](https://typesafe.ai/blog/introducing-system-one-models-and-jev)），以及 schema 校验失败后的重试。

延迟结构同样不同构：Vals 实测同一长文档上问 1 到 64 个判断，Jev 从 0.10s 到 0.12s 几乎不动，而 GPT-6 Astra 到 38s、Gemini 4 Argon 到 65s；32 个判断时 Jev 中位延迟比 Astra 低 194 倍（[Vals AI 评测](https://vals.ai/blogs/independent-evaluation-of-jev)）。类型安全上，Jev 的 schema 匹配是结构保证（官方称"数学上不可能"出现类型错误），而 LLM 一侧在评测中出现了缺答案的情况，Jev 零格式错误（[Vals AI 评测](https://vals.ai/blogs/independent-evaluation-of-jev)）。

## 5. 边界三：与规则引擎——它是规则引擎的输入层，不是替代品

官方在发布博客的用例表里给自己的定位就是 **"AI-Powered Workflows / smart if-statements"**：把结构化输出当作模糊决策规则插进普通软件，"在**手写逻辑太脆**的地方做分类、路由、打分、抽取或分支"（[发布博客](https://typesafe.ai/blog/introducing-system-one-models-and-jev)）。

什么算"太脆"？给三条可操作的判据：**规则条目随表述变体爆炸**（同一意思十种说法就要写十条）、**输入本身是自然语言而非结构化字段**、**判断依赖常识而非可枚举条件**。反过来，三类东西**绝不该交给它**：金额计算、权限/授权判定、合规硬门槛。Vercel 的工程指南把这条写成一句口号："把分类与授权分开"——Jev 能判断"客户是否要求退款"，但**是否批准退款取决于它看不到的账户状态、政策与权限**，必须在代码里做第二道检查；它记录的是意图，不是批准（[Vercel 指南](https://vercel.com/kb/guide/typesafe-jev-and-ai-sdk)）。官方文档的措辞是同一件事：控制流、确定性规则、副作用留在代码里（[How to build with System One](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)）。

所以正确的理解是：**它把自然语言压成布尔/枚举/档位，再交给规则引擎**。概率是路由信号，不是判决。

## 6. 不可协商的硬约束（已核对官方 models 页，Jev 1.14）

| 约束 | 具体内容 |
|---|---|
| 无定制权重 | 不用客户数据微调、不做 LoRA，"同一份权重服务每一个账户"，只能靠 `state`/`instructions`/`criteria` 塑形 |
| 仅文本 | 只接受字符串、JSON 对象、文本数组；音频与视频不支持 |
| 语言 | 英语为主要训练语言、准确率最高；CJK 等"能处理但不等同"，官方要求自行测试 |
| 上下文 | 64k/请求、32k/问题；加 `TypeSafe-Danger-Zone-Long-Context: true` 头后两者均为 262k，**更慢更不准**，且不加价 |
| 计价 | $0.042/Mtok 输入（$42/Btok），**输出免费**；长上下文同价 |
| 版本 | Jev 1.14（`jev-1.14.0`，2026-10-14 起），`jev-latest` 与 `jev-preview` 当前都指向它 |

（以上均见 [官方 models 页](https://docs.typesafe.ai/models)。一处需要以官方为准的细节：Vercel 指南把 32k 说成"`state` 占 32k"，官方定义是 per-question context，即 `state` + 任一问题合计 32k——写 schema 时按后者算。）

## 7. 硬约束的排除效应（本章最重要的输出）

硬约束的价值不在于"知道它有限制"，而在于**据此判定出局**。以下三类需求应当直接判定为**出局，而非"调优后可用"**：

1. **需要领域定制权重的场景。** 官方明确不微调、不做 LoRA、全账户共享同一份权重。如果你的准确率瓶颈在于领域词汇或领域边界**无法用文字在 `state`/`criteria` 里描述清楚**，那它不是"再调调 prompt"能解决的，而是权重层面的缺口。
2. **需要图像/音视频输入的场景。** 官方明确"不支持（yet）"。同类替代路径存在——Cloudflare Clef 就带视觉编码器，可分类图像。
3. **需要 CJK 母语级语义判断的场景。** 官方只承诺"能处理但不等同"，并要求自测；**本章未找到任何公开的第三方 CJK 基准或评测**，因此这一维度**公开信息不足**——缺的是非英语语种上的独立准确率/校准数据。在没有自测数据前，不应把它放进中文为主的生产判断链路。

还有一条隐含代价必须写出来：**共享权重意味着全行业共用一套失败模式，你的 badcase 不会因为你反馈而改善。** 这不是推测。Vals AI 在 LegalBench 切片上发现 Jev 类别平衡准确率 0.730、在 12 个系统中排最后，且两个合同蕴含子任务退化成几乎恒定回答"Yes"（33 题全答 Yes）——这类失败模式是所有账户共有的，你既不能靠反馈修掉它，也不能靠微调绕开它（[Vals AI 评测](https://vals.ai/blogs/independent-evaluation-of-jev)）。你能做的只有两件事：在代码里检测它（低 confidence 路由人工），或用 `state`command://问题分解绕开它。**可调的是输入与阈值，不可调的是权重与模态**——这就是"调优"与"出局"的分界线。

## 8. 成本与延迟的真实结构

输出免费 + 输入计费，构成一个很硬的不对称：**多问几个问题几乎不涨价，`state` 越长越贵。** 官方也承认长上下文"同价但更慢更不准"，且不同 state 长度下准确率会抖动（[models 页](https://docs.typesafe.ai/models)）。Vercel 据此给出的建议是"只传决策依赖的字段"（[Vercel 指南](https://vercel.com/kb/guide/typesafe-jev-and-ai-sdk)）。

结构性含义有三条（具体 schema 规则留给第 6 章）：

- **决策密度应当最大化**：一个 `state` 上问满所有需要的问题，因为拆请求等于重复支付同一份 `state` 的钱。
- **`state` 是唯一成本项，也是准确率的敌人**：省钱与降噪在这里同向，都指向剪裁。
- **成本优势随"每 state 问题数"放大**：单文档单问题的场景，Jev 的价格优势远不如"高频、短 state、多问题"的形态显著。

## 小结与判据

decision model 的适用区间由四个条件共同定义，缺一即出局或换工具：**判断能写成一道"知识渊博的人几秒内答完"的单选题**（可原子化）、**标签会变或尚无标注数据**（否则专训分类器更快更准）、**输入是文本且语言以英文为主**（否则触达模态与语种硬约束）、**判决之后的动作能用代码兜住**（金额、权限、合规不得下放）。

> **一句话判据**：如果这道判断"标签会变、只有文本、答案能写成单选或档位、且错了也只是走人工复核而不是直接放款/放权"，它在适用区间内；如果它需要"领域定制权重、看图听音、或中文母语级语义"，请直接判出局，不要进入调优流程。
