# Memory 方案很多，怎样判断哪些值得投入

> 2026-09-21 · 问题研究与当前研究取舍。面向个人初期项目，优先建立能直接改善实现选择的认识。本文区分已核到的来源事实与我们的工程推断；没有运行框架对比实验，也不提供产品性能排名。对应教材设计在 [Memory 专题](../output/book-memory/design.md)。

## 先给出当前判断

值得先研究的不是最多的 Memory 框架，而是几种**会让实现选择发生实质变化的记忆机制**：保留原始经历并检索、维护紧凑的当前认识、让模型主动管理记忆、显式处理关系与时间、把反复发生的经历提炼为可复用经验。一个项目可能组合多种机制；换一个数据库或接入更多 Agent SDK，不自动增加一种值得单独研究的机制。

本项目当前适合以**可通过普通模型 API 使用的外部记忆**为主线，以原始材料和简单可修改存储为基线，先理解事实提炼、检索使用与更新，再进入关系和经验。参数记忆、隐状态记忆与训练得到的管理策略仍有研究位置，但应分别说明运行与训练前提。不能把它们混在一张“最好的 Memory 框架”表里。

这个取舍不是宣称简单检索最终最好。它让复杂方案回答一个可检查的问题：**它补上了简单方案的哪种失败，为此新增了哪些成本和能力依赖？** 简单方案失效与复杂方案有价值，都需要具体任务支持。

## 为什么这个领域尤其容易看花眼

“Memory”至少同时指向四件不同的东西：

| 层次 | 它回答什么 | 容易混淆的例子 |
|---|---|---|
| 使用需求 | 未来需要过去的什么 | 记住偏好、接续工作、解释当时原因、复用解题经验 |
| 信息机制 | 过去怎样变成未来可用的依据 | 原文检索、事实抽取、时态关系、摘要、经验提炼 |
| 实现与产品 | 哪些机制被交付成什么接口 | Python 库、独立服务、托管 API、完整 Agent 运行环境 |
| 模型与学习方法 | 能力来自推理时操作还是训练 | 文本记忆工具、训练记忆管理器、可更新隐状态、权重更新 |

事实抽取库和完整 Agent 环境不具有相同的接入边界；面向个人对话的框架和面向科学文献的检索系统也不共享天然的评分标准。论文介绍的一项机制、开源仓库某个版本与厂商服务可能不一致。把这些对象并排打分，会把任务差异、产品包装与真正的机制差异混成“谁更先进”。

更有用的区分是三种价值：**机制值得理解、实现值得借用、当前项目值得采用。** 一个研究原型可能有很强的机制价值，却不值得在个人项目里完整部署；一个普通文件方案可能没有论文新意，却提供最清楚的基线。冷门与热门都只是发现材料的线索，不能替代判断。

## 从未来用途区分记忆，而非先决定存储类型

下面是工作划分，不声称是互斥且穷尽的认知分类。同一段经历可以服务多个用途。

| 下一次需要什么 | 起步表示与读取方式 | 首先会遇到的难点 | 何时考虑更复杂的机制 |
|---|---|---|---|
| 当前有效的偏好、事实或项目约束 | 小型状态文档或结构化表，直接读取相关部分 | 错误抽取、作用范围、条件变化、旧值仍被采用 | 人工维护跟不上变化，再考虑自动抽取与合并 |
| 当时发生了什么，为什么作过这个决定 | 原始事件、来源指针、按任务与时间查找 | 精确用语被摘要抹掉、原因脱离事件、搜索用词不匹配 | 原文定位失败，再加语义检索、事件连接或更合适的切分 |
| 上次做到哪里，下一步依赖什么 | 简洁进展、未解决问题、结果位置，必要时核对外部实际状态 | 计划与实际进展不一致，压缩后丢失关键依赖 | 任务确有复杂分支时研究更丰富的状态表示；普通恢复不必先造 Memory 服务 |
| 多次经历中有什么稳定经验可复用 | 保留案例及结果，按任务相似性检索 | 成功原因误判、环境改变、经验过度泛化 | 案例反复出现且能检验迁移，再提炼规则、流程或技能 |
| 某时刻谁与什么有关，关系怎样变化 | 事件、实体标识、有效时间，先查结构化记录 | 同名实体、历史与当前混淆、关系链跨多份材料 | 查询确实依赖跨事件连接时，再比较时态图或图遍历 |

常识知识库、对话经历、项目状态之间没有绝对的存储分界。文献 RAG 可以提供 Memory 使用的证据；但“把论文放进向量库”通常还没有回答系统怎样记住用户已读什么、撤回过什么判断、为什么更换研究路线。教材应把静态资料检索和由交互积累的记忆同时放到适用任务中比较，不能只靠“RAG 不等于 Memory”一句口号划线。

当前权威事实已经可以从项目文件、数据库或工具便宜地重新获得时，额外记忆应首先保存经历、解释或定位线索。复制一份不断变化的事实，会新增同步问题。相反，用户只在过去表达过的一项约束，若无外部来源可以重新获得，保存与更正就成为核心问题。这是由信息可恢复性决定的选择。

## 一个贯穿全书的关键张力：保留材料，还是提前理解材料

原始记录把更多解释工作留给未来：写入通常便宜，来源可回查，但未来可能要检索、阅读很多内容。事实、摘要和关系图提前完成部分理解：未来可能读得更少，但写入时已经选择了哪些信息重要，以及用什么表示保存它。

因此，记忆系统实际上在对未来需求下注。若未来主要重复询问稳定偏好，小型事实集合可能很合适；若未来要问当时的精确措辞、尚未预见的细节或判断形成过程，提炼结果可能不够。这里的差异不是“结构化是否高级”，而是写入时的归纳能否服务未来问题。

这也解释了一个适合初期工程的候选组合：保留可回查的原始事件，把当前状态、摘要与索引视为可以修订的表示。它不是必须实现的双层框架：材料很小、一个文件足够时无需额外设施；原始数据不能长期保存或本就不可获得时，也不能假定可以重建。关键是明确哪些变换不可逆，后续纠错还能依赖什么。

一个构造例子：研究助手先记录“优先阅读框架 A”，一周后用户改为“只借鉴 A 的写入机制，暂停部署”。仅按相似度找到最早的推荐会答错；将两次表述压成“A 很重要”也会答错；单纯删除旧记录则无法解释为何曾考虑部署。当前选择与历史理由需要不同读取语义。这个例子说明要比较什么，并非本项目已经观测到的产品缺陷。

## 框架应怎样筛选

逐个问以下问题，比维护一个综合分数更能帮助当前决策：

1. **能走通哪条具体路径？** 从一条新经历到下一次模型实际读到的材料，哪些步骤由代码决定，哪些由模型决定？
2. **增益来自哪里？** 是提炼、召回、时间判断、关系连接，还是更多 token、更多轮模型调用、更强模型或更好的任务提示？
3. **实现需要什么？** 除模型 API 外需要哪些常驻服务、索引、训练产物或模型内部访问？示例运行起来和长期使用分别有什么前提？
4. **错误还能怎样纠正？** 错误发生在原始记录、派生事实、检索结果还是回答；是否能找到依据并修订？这决定调试成本。
5. **什么使用频率才能值得？** 写入多少、读取多少、更新多快、多久再问一次、能接受多久才读到新信息？
6. **证据对应哪个版本与产品？** 发布论文、开源实现、托管服务与本次任务是否真在比较同一个对象？

这里的依赖与纠错检查服务于可理解、可修改和个人投入，不组织成企业上线流程，也不以权限体系或安全门禁驱动教材。

## 当前值得深拆的对象，以及暂缓的原因

以下优先级是本项目的**阅读投入选择**，不是经过实验的产品推荐。版本、摘录及实现核对见 [框架一手材料](../evidence/domain/memory-frameworks-core-2026-09-21.md)。

| 对象 | 它提供的独立认识价值 | 当前如何投入 | 必须检查的边界 |
|---|---|---|---|
| 文件／SQLite、全文检索，按需加入向量检索 | 不依赖自动提炼也能保存、定位、修正材料；暴露任务究竟缺哪项能力 | 第一项基线，伴随全书 | 简单不意味着效果充分；切分、查询与任务定义仍会决定结果 |
| Mem0 | 在既有应用中插入记忆抽取与检索，适合追踪“一次 add 到一次 search” | 第一批深拆，重点读实际 OSS 写入路径 | 已核到 additive 自动写入和显式 update 共存；托管平台成绩不代表 OSS，旧论文也不能代表今天产品 |
| 当前 Letta／letta-code | Agent 自己操作常驻与外部记忆，体现文件记忆、工具访问和后台整理之间的关系 | 第一批机制对照；范围集中在记忆，避免扩展为终端产品拆解 | 当前 Letta 已指向新源码；旧 MemGPT／Letta V1 的服务架构不是当前版本说明 |
| Graphiti | 以事件形成实体与关系，并显式表达时间，适合解释“现在成立”和“当时成立”的不同 | 第二批，先有关系与时间问题再深入 | OSS Graphiti 与 Zep 托管引擎要区分；抽取、消歧与维护成本不能被图查询接口遮蔽 |
| Hindsight | retain／recall／reflect，以及多种检索与派生认识的组合 | 第二批，研究整理与使用如何配合 | reflect 是按需推理，后台 consolidation 是另一条路径；分别核对新写入和派生认识何时可读 |
| LangMem | 将记忆工具和后台处理嵌入已有应用，适合观察组件组合边界 | 使用 LangGraph 时提高优先级，否则作为短对照 | memory manager、store 与 local/remote executor 有各自边界，需要按运行环境组合 |
| A-MEM、HippoRAG 等论文方法 | 前者适合研究笔记连接与演化，后者适合研究图关联检索；分别回答不同问题 | 作为条件性深化案例，不按论文顺序逐个部署 | 不预设二者工程难度相同，也不把文章分数迁移到自己的任务 |
| 其他 Memory OS、全功能平台与新榜单项目 | 可能提供多模态、文件组织或新型管理机制 | 当前不扩张必读名单；发现独特机制再加入 | 名称、功能数量、热度与既有本地目录都不是认识增量的证明 |

这里优先选择 Mem0 与 Letta，是因为它们给出两种有辨识度的控制关系：由应用调用记忆组件，以及由 Agent 在任务中操作自己的记忆。Graphiti 增加关系与时间这一不同问题；Hindsight 增加后台形成派生认识，以及按需读取记忆进行推理这一不同问题。选择有待深拆后的修正，不保证每个对象都值得完整展开。

**版本差异已经影响这轮判断。** 2026-09-21 核对的 Mem0 README 介绍了 2026 年 4 月的 ADD-only 新算法，并明确展示的成绩来自包含专有优化的托管平台。实际读取的 OSS `Memory._add_to_vector_store` 确认了 additive 提取与插入路径；同时仍有按 ID 显式调用的 `update()`，不能把 ADD-only 解释成整个 SDK 不支持更新，也不能据此改写旧论文的实验对象。Letta 原仓库 README 则将当前实现指向 `letta-ai/letta-code`，把旧 API server 标为已退役的 V1。研究必须落到具体代码，而非维持熟悉的项目印象。

### 三个值得进入教材的具体发现

**存过原文，仍可能无法通过记忆接口找回。** Hindsight 的 Retain 文档说明，若提取目标 `retain_mission` 太窄，某文档可能不产生任何事实；原文虽然保存了，recall／reflect 搜索 memories 时却找不到它。这说明“保留原文”只是恢复条件之一，还要问检索入口能否到达。它比抽象地说“召回率很重要”更值得拆解，后续要核对来源访问的实际补救路径。

**文件记忆与专门框架可以是同一套设计。** 当前 Letta 的一份 MemFS 提示词将根 Markdown 作为常驻记忆，其他材料按需加载，并区分编辑、Git 提交和未来 Context 重新编译。文件格式并不决定系统简单或高级；真正影响行为的是谁改、怎样找、何时进入模型。这里核到的是具体提示词协议，尚未验证该模板是否为所有配置的默认路径。

**异步函数、后台整理和立即返回并非一回事。** LangMem 的基本后台示例仍先等待 `memory_manager.ainvoke` 完成再返回回答；其延迟处理示例另使用执行器提交任务。Hindsight 又区分摄入请求被接受、事实构建完成、派生认识更新完成。讨论“后台 Memory 很便宜”之前，需要先指明在等哪一步，下一次问题又依赖哪一步的结果。

以上都是可以用当前一手资料定位的机制差异，尚非任务收益的实测证据。对研究投入，可以因这些差异直接深拆，不要求先实现全部基线、证明失败才获准阅读。简单基线约束的是产品采用与效果比较的结论力度，不应成为探索新机制的门槛。

## 论文效果好，究竟在哪一步变成工程困难

至少要区分以下几类困难，避免把“长尾”当成统一理由。

| 障碍 | 具体意味着什么 | 合理的研究处理 |
|---|---|---|
| 未来问题与写入目标不匹配 | 偏好提炼用于精确事件问答，或文献方法用于持续交互 | 先查提炼丢了什么、任务是否同类；暂不归咎于检索器 |
| 强模型承担了隐形工作 | 小模型不能稳定提取、连接、操作工具或决定何时停止 | 保留构建模型与回答模型的区别；测试便宜模型是否改变行为 |
| 写入成本或新鲜度不合适 | 离线可慢慢建库，在线下一次交互却马上依赖刚写入的信息 | 把写入计入总成本；说明后台化只是移动等待位置 |
| 任务特化的表示与预算 | 某任务需要图，另一任务只需原文；多取材料本身可能提高分数 | 同时比较质量与资源，检查真正产生增益的组件 |
| 研究实现的交付缺口 | 缺版本、缺数据、复现步骤或关键实现不公开 | 可以研究思想，但不承诺本地能复现或采用 |
| 模型访问条件不满足 | 方法需要训练、修改结构或访问隐状态，而当前只有 API | 留在对应前沿路线；不是把 API 外部记忆项目也一并排除 |

特别要防止一个反向误判：A-MEM 这样的外部笔记方法不因为出自论文就必须训练基础模型；训练得到的记忆管理器也可能输出普通文本操作，推理时并不一定需要读取主模型内部。参数记忆、隐状态记忆、训练管理策略是三种不同的依赖，不应统称“工程落不了地”。本轮未逐项核查这些论文的现行复现条件，因此这里只给出辨别方向。

两篇本地论文为这些问题提供了较具体的研究线索：[2606.06448](../sources/papers/surveys/2606.06448.md)将构建、检索和生成拆开计量，讨论构建模型能力、重复读取摊销与相邻会话的新鲜度；[2607.16848](../sources/papers/surveys/2607.16848.md)在科学文献任务中检查检索体积、原文通道与预算。它们的本地版本号未知，本项目没有复现实验；后者包含作者自己的系统，前者做了任务适配并未让所有系统保有相同检索 token 数。它们足以支持“这些变量要检查”，不支持把表内排名直接变成今日框架排名。

逐段核对还发现：第二篇关闭 Graphiti 原文通道的同时改变预算，不能据此断言全部收益来自材料体积；第一篇的部分数字及同步／异步解释存在不一致。完整限制见 [论文片段与比较边界](../evidence/domain/memory-evaluation-passages-2026-09-21.md)。因此本次采用可检查的问题和条件性解释，不转录不稳固的性能数字。

## 真正需要算的是一段使用期，而非一条 search 的价格

若只计算召回和回答，提前花了很多成本提炼记忆的系统会显得格外便宜。对同一段使用期，可把货币成本记为：

```text
C = 首次构建 + 持续写入 + 整理与重建 + 检索 + 回答
```

各项用相同货币单位累计实际调用和存储费用；延迟、质量与开发时间分别记录，不随意混加成一个总分。测试中仍要保留调用数、输入输出 token、嵌入量和重复操作，便于解释成本来源。

一个用于暴露假设的算例：假定材料暂时不变，简单方案每次读取费用为 `r0`，提炼方案额外构建费用为 `B`、每次读取费用为 `r1`，回答质量相当且 `r1 < r0`。忽略共同费用后，需要 `N > B / (r0 - r1)` 次读取才会摊平额外构建费。这里没有代入真实价格，也不是选型算法。材料频繁变动、要重建、质量下降或读取次数不足时，这个条件需要重算。

后台整理可以降低前台等待，却不会使模型调用免费；新一轮任务需要上一轮结果时，写入尚未完成还会影响回答。也不能把“一次写入耗时超过会话间隔”直接解释为任何部署都不可能：并发、队列、批处理和相邻会话依赖共同决定结果。对个人项目，先测自己的写读节奏，通常比先设计分布式服务更有价值。

## 用一个小而有辨识力的任务集决定下一步

下面是检验设计，尚未实现或执行。先选一个持续研究助手场景，再用项目协作场景检查能否迁移。测试材料应包含真实会用到的名字、精确条件与改口，不只问“用户喜欢什么”。

| 情况 | 让它区分什么 |
|---|---|
| 下一次任务依赖此前明确给出的约束 | 有没有记忆的真实增益 |
| 同一对象从“考虑采用”改成“只借鉴机制” | 当前状态、历史事件与更正是否分清 |
| 问一次讨论里未经提前提炼的细节 | 保留原文是否提供实际恢复价值 |
| 同名对象或多份资料需要连接 | 直接检索的局限是否值得引入实体或图 |
| 间隔很短的新会话需要刚形成的结果 | 写入延迟是否造成读取旧认识 |
| 过去成功的方法遇到前提改变 | 经验复用的收益是否伴随过度泛化 |
| 当前任务根本不需要历史 | 额外记忆是否只是干扰与花费 |

起步对照包括无记忆、可容纳时的完整历史、当前状态文档、原文检索；在相同材料与任务下再加入一个更复杂机制。超出上下文限制的完整历史方案应记为该条件下不可行，不能偷偷截断后仍叫“完整历史”。

另加一个仅用于诊断的充分证据条件：人工把该题必要且正确的材料直接提供给模型。它不参加部署成本排名，因为它使用了任务设计者知识；作用是辨别问题究竟在记忆恢复，还是模型即使获得证据仍不会使用。不要把它当无所不知的公平竞赛选手。

公平比较也不等于强迫所有系统使用相同条目数。一个条目可以是一句话，也可以是一整段文献。保留真实产品配置作为一种比较，再增加相同实际检索 token 预算的机制对照；两种结果回答不同问题。记录写入与读取花费、最终答题质量、修正是否生效和失败实例。只有新增机制解决了可重复的缺口，才扩张下一项实现。

## 对教材与近期研究的具体影响

Memory 教材应让读者逐渐回答：过去的什么需要留下，留下什么表示，未来怎样找回并使用，认识变了如何处理，以及复杂度何时值得。Context 在“记忆怎样进入本次推理”处深入，Harness 在“谁决定写、读、整理以及何时发生”处深入。它们不再占据各自独立的大篇幅总论。

近期先完成三个有价值的认识对象：简单原文／状态基线、Mem0 的实际开源写读路径、当前 Letta 的模型主导记忆路径。随后根据暴露的问题选择 Graphiti 或 Hindsight；不为了覆盖率同时安装所有平台。论文深化分别服务关系、经验和可学习管理，不作为一条必须按年代通读的路线。

本轮产出的是筛选理由、已经核对的一手材料与教材设计。它没有把框架变成已验证方案，也没有为了填目录预造新的 Domain 主题。后续多项深拆与问题研究形成稳定关系后，再把认识综合到 Domain，允许它比教材更细、更宽。
