# pdf2md 的设计经验

## Agent 判断，脚本执行稳定操作

任务目标是把论文变成可阅读、可核对、可复用的材料。Agent 根据研究问题筛选论文、选择阅读范围、判断证据、核对原文并修改转换疑点；脚本处理下载、API 调用、资产引用、联动改名和 PDF 取证。

只有反复使用且含义稳定的操作值得固化为工具。单个段落如何修正依赖具体语境，适合现场读取、比对和编辑；把每次遇到的坏词固化成词表、正则和阈值，会使维护对象偏离论文内容。

## 保存、转换、阅读各有结果

下载得到原件；转换得到 Markdown 与资产；回答论文问题还需要阅读。先复用同一论文与版本的本地材料，只收藏时不必等待转换。转换进行中可以读 PDF 或同版本原文 HTML。

本地轮询超时不代表云端任务失败。保留批次编号续取，避免重复提交。普通 PDF URL 的来源不能从文件名恢复：分步下载与转换时，由 Agent 保留下载输出中的来源，并写入转换件的登记字段。

## PDF 文本层用于定位，页面用于解疑

`Lar<sub>g</sub>e` 可能是错误标签，`Mem0<sup>g</sup>` 可能是真实方法名，`x<sub>i</sub>` 可能是公式。标签外观不足以决定修改，文本层也可能丢失上下标、连字或阅读顺序。

Mem0（`arxiv-2504.19413v1`）PDF 第 2 页、短语 `Unlike humans` 附近可观察到：

```text
转换件：LLM<sub>s e</sub>f<sub>ec</sub>ti<sub>ve</sub>l<sub>y</sub>
PDF 页面：LLMs effectively
```

只删标签会得到少一个 `f` 的 `LLMs efectively`。修正依据是页面中的字符，而不是标签删除率。这个反例支持局部核对，不能证明全文已经校准。

哈希相等、行数不变、幂等性和测试通过各自只能证明对应属性，不能替代论文内容核对。修改应保持来源含义与表格、公式、代码、图片的关系。

## 索引保留选择，文件提供本地事实

索引中的候选、关键词和已核实日期具有独立价值：删除本地缓存不应顺带删除研究者的选择。文件名和 MD 登记块提供补录线索，已有人工字段优先保留；同一来源与版本的多个副本交给 Agent 判断，不能按扫描顺序混合字段。

查看登记、修改一篇与全库对账是不同操作范围。只读查询不扫描收录，单篇操作不重建全库，移除离线记录需要明确选择。索引不保存易失的下载状态或阅读完成标记；需要这些事实时观察文件和研究记录。

## 环境由实际操作决定

下载与转换只需标准库；读取 PDF 才需要 PyMuPDF，依赖在读取脚本中声明。使用 `uv run --script` 时，首次运行可能需要准备依赖；离线运行需要已有缓存或可用解释器。

代码位置、解释器、工作目录与凭据是不同条件。脚本绝对路径定位代码，相对资料路径仍按调用目录解析；凭据来自运行环境。排障从具体失败条件入手，skill 无需绑定宿主项目的虚拟环境或自动改动项目配置。

## 开发材料与安装内容各自完整

源码、测试、类型配置和实现笔记在同一开发空间维护。skill 子目录包含运行所需的全部文件，复制后可独立使用；研究笔记与验证材料留在外层。

本地测试保存可重复验证的行为经验，按实际改动选用。检查可移植性时，从独立副本执行一条真实流程，能发现原工作目录掩盖的路径依赖。格式、类型、离线行为、在线服务和论文理解需要各自的证据。
