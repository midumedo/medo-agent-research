# 系统样本与证据范围

系统是检验解释的样本。选样要能改变某项工程判断，而不是把产品名单逐个写成说明书。**本表记录已有证据的边界和候选理由，不是当前产品能力表，也不表示这些系统已经完成同条件比较。**

## 目前已有的材料

| 对象 | 本项目已有的材料 | 现在可以据此做什么 | 尚不能据此判断什么 |
|---|---|---|---|
| Claude Code | [上下文管理拆解](../analysis/claude-code/context-management-offload.md)与[上下文经济学拆解](../analysis/claude-code/context-economics-two-traps.md)；早期文章含待核实产品事实与过强推断 | 追踪项目如何形成旧假设，找出需要重新定位来源和验证的点 | 不能据文档顺序断定官方的策略排序；不能据建议行数推导性能悬崖；不能把价格比当策略实测收益 |
| 本地论文材料 | [已核对片段](../evidence/domain/reviewed-local-passages.md)，含控制策略与 Memory 范围定义 | 对照术语、发现原论证与本地来源的矛盾 | 不等于复现论文结果；也不证明论文覆盖所有产品或所有工程条件 |

论文的系统比较、官方文档、源码实现和本项目实验分别回答不同问题。论文报告了结果，不表示我们已经复现；源码存在分支，不表示它在当前版本和默认配置下会被执行；接口支持操作，也不表示用户通常能有效使用。

## 下一批候选如何选

以下候选来自项目已有名单。每次只选能区分竞争解释的少量样本；先确认对象身份、可访问版本和适用任务，再判断是否值得投入。名称本身不作为能力证据。

| 候选 | 选它要回答的研究问题 | 入选前需补齐什么 |
|---|---|---|
| Codex | 能否用可读实现检查“历史如何保留、何时压缩、哪些结果被重新注入”的推断？ | 实际审查的 commit、执行入口、配置和至少一条可复现轨迹；与模型或 API 的行为分开 |
| Tianshu | 管理机制较少的实现如果成本更低，收益来自更有效的信息处理，还是来自任务范围与能力的缩减？ | 先确认具体项目、版本和实现，不预先把“薄”当作已测出的系统性质 |
| mem0、Zep、Letta、memgit | 在相同的事实更新、冲突和删除任务中，状态更新与恢复行为是否不同？ | 每个系统独立定位版本、存储内容和查询方式；不能因为常被归为 Memory 就假定治理完整 |
| OpenViking | 以文件和层级组织信息的候选，是否改变精确定位、恢复与更新的代价？ | 核实实际接口和保存方式；与使用同样原文的简单文件检索基线比较 |
| 简单文件检索或全文检索基线 | 昂贵的结构化、摘要或代理控制，到底增加了什么任务收益？ | 同样的可用原文、更新事件和查询预算；记录构建与检索成本 |
| 一个非编码的持续任务 | 由编码 Agent 得出的判断，在事实更新和用户约束任务上是否仍成立？ | 明确任务、正确状态和终局成功标准，避免把编码工具行为推广为 Memory 的普遍性质 |

## 选样的停止条件

只有“名字不同”而没有关键条件差异，不构成新的交叉验证。两篇文章转引同一文档，也不是两份独立证据。若补读一个系统无法区分当前竞争解释，应先改变问题，或停止拆解。

首轮具体实验见 [研究议程](../analysis/research-agenda.md)；各解释之间的区别见 [竞争解释](disputes.md)。当前优先任务是建立最小对照、记录失败，再决定扩展哪些系统。
