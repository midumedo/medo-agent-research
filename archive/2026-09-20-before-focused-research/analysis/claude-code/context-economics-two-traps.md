## 当前回答

**上下文同时受容量约束、持续处理成本和任务效用约束。缓存影响重复输入的价格，信息长度、驻留轮数、推理和工具调用会共同决定整条路径的成本。** “负债”可以提醒读者注意持续费用，但不能取代预算模型，也不能仅凭重复计费推导出注意力阈值或某种策略普遍占优。

重复输入通常是逐次累计费用，并不自动意味着经济学上的复利。外部保存的信息若没有被送入请求，也不能只因它属于 memory 就算作每轮输入。

## 一份信息的驻留成本

先使用一个明确受限的算例模型：一份长度为 S token 的内容，完整出现在 N 次计费请求中。第一次创建缓存的有效单价为 p_write，后续命中缓存的单价为 p_read。单价单位均为货币 / 百万 token。假定没有续写或续期费用，后续全部命中，则：

    C = S / 1,000,000 × [p_write + (N − 1) × p_read]

若所考察的 N 次请求开始前缓存已经创建，并把此前费用排除在统计边界外，则这一段观察窗口的缓存读取费用才是：

    C_warm = N × S / 1,000,000 × p_read

二者回答不同的问题。实际产品还可能涉及命中条件、最小可缓存长度、保留时长、失效范围、cache write 价格和套餐口径，不能靠本算例补猜。若部分请求未命中，应按实际未缓存输入或重建缓存的计费规则逐次计入，而不是把所有请求乘一个固定折扣。

### 修正旧稿的 50 轮算例

下面的 S=3000、N=50、输入单价 2、缓存读取单价 0.2 和输出单价 10 **仅沿用旧稿数字作为假设算例，不代表本轮核实的任何模型报价**。

| 统计情形 | 计算 | 结果 |
|---|---|---|
| 50 次全部按假定普通输入价格计费 | 50 × 3000 / 1,000,000 × 2 | 0.30 |
| 已有温缓存，观察窗口内 50 次全部命中；未计创建成本 | 50 × 3000 / 1,000,000 × 0.2 | 0.03 |
| 从冷缓存开始，第一轮创建、其余 49 次命中 | 0.003 × p_write + 0.147 × 0.2 | 0.003 × p_write + 0.0294 |
| 假定 8000 个计费输出 token | 8000 / 1,000,000 × 10 | 0.08 |

旧稿没有写入单价，却把第二行情形当成整场会话成本，因此“贵 2.7 倍”只适用于排除创建成本后的特定比较，不能作为一般结论。真正的 thinking 计费量与可见输出量是否相同也要按协议核实。

在这组假设里，输出 / 缓存读取的**单位价格比**为 10 / 0.2 = 50；普通输入 / 缓存读取的单位价格比为 2 / 0.2 = 10。这两个分母不同，不能把 50 倍写成整条任务路径可节省 50 倍。缓存前后费用仍与内容长度成比例，“能缓存所以长度不重要”不成立。

## 精简上下文何时节省成本

设原表示长 L，精简后长 l，接下来驻留 T 次请求；精简一次的增量成本为 K，后续额外恢复成本的期望为 R。在有效输入单价 p 固定、精简不改变后续请求次数及其他工作量、任务效用相当的简化条件下：

    净成本节省 = T × (L − l) / 1,000,000 × p − K − R

这是暴露前提的比较式，尚未校准为实际决策算法。缓存失效、工具调用变化和返工都会破坏“其他工作量不变”的假定；漏掉关键约束造成的质量损失也不能未经定义就折成货币与费用相加。实践中应先明确质量要求，再比较满足要求的路径成本。

**推断**：信息驻留时间越长、重复输入单价越高、恢复越少，精简越可能节省费用。短任务、温缓存下的低读取价格、频繁重取或昂贵总结都可能使收益消失。因此缓存、过滤、摘要与外部寻址是联动变量，见[前置减负与压缩](context-management-offload.md)。

## 推理预算需要跨越 API 与运行框架两层核查

旧稿引用的模型/API thinking 保留规则，即使原文日后核实，也不能直接等同于 Claude Code 的最终请求轨迹。客户端可能保留、清理、重写或选择性回传内容。需要分别核查以下链条：

| 要判断的环节 | 当前缺口 | 可能改变结论的情况 |
|---|---|---|
| 增大预算是否增加实际计费 thinking | 模型版本、预算语义、实际生成量 | 更大上限没有被用满 |
| thinking 是否进入后续请求 | API 协议与客户端处理路径 | 客户端清理或不回传历史内容 |
| 总上下文是否因此增长更快 | 工具调用、对话轮数、其他输出变化 | 额外推理减少探索、重试和返工 |
| 是否更早触发压缩 | 实际触发阈值及计数对象 | 保留内容不计入同一触发口径 |
| 压缩是否降低后续任务质量 | 压缩前后关键状态及任务结果 | 压缩保留所需内容，或原文成功恢复 |

**待检验假设**：当某运行框架持续回传新增 thinking、这些 token 计入压缩触发条件，且额外推理没有减少其他路径长度时，提高预算可能更早触发压缩。即使如此，“更早压缩”与“更高失忆风险”仍需任务结果衔接，不能视为同一句话。

本稿不再保留“thinking 必然优先被压缩丢弃”及“这种取舍从未被文档提示”的无来源判断。

## 动态调整与缓存：比较额外费用，不宣布结构性矛盾

旧稿关于 budget_tokens、max_tokens: 0、reasoning.effort、configuration_update 和自动压缩的具体兼容性均待核实。即使某个设置变化会破坏部分缓存，也应确认失效的是哪个前缀、影响多少内容、持续几轮，而不是把“改一个空格”写成所有缓存全部失效。

在一次调整不改变任务质量的简化比较中：

    调整的净费用收益
      = 因调整而减少的实际输出费用
      − 新增的缓存失效或重建费用
      − 新增工具调用、重试及其他路径费用

“动态调整一定亏”与“动态调整一定省”都不能从是否破坏缓存一个事实推出。若两个产品分别存在缓存影响和某项 API 兼容限制，也只能记录各自的具体限制，不能据此推导运行时调节与自动压缩在理论上不兼容。

## 从价格隐喻回到待验证的问题

价格模型不能证明工具输出一定是所有会话的最大头；这一点需要实际 token 归因。它也不能证明约 200 行是常驻指令的性能拐点，或“卸荷严格优于压缩”。容量、注意力表现、冲突和信息有效性各有自己的观测问题。

下一步应固定一个运行框架、版本和任务集合，记录每次请求的输入组成、缓存读写、输出、工具调用和压缩行为，再比较不同推理预算的任务成功率与总费用。至少区分“额外 thinking 增长了轨迹”与“额外 thinking 缩短了探索”两种竞争解释。实际执行前先补齐计费和请求协议来源；本轮没有生成任何测量结果。
