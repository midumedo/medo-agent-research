# deepdive/ · 先把对象拆明白

这里保存对具体项目、论文及其实现的深入理解。**不要求预先锁定主线、提出竞争假设、选好教材章节，也不要求每篇都产出通用结论。** 建立对象认识、发现原来不知道该问的问题，就是这项工作的价值。

目前已建立工作入口，尚未有完整的对象深拆稿。既有 Claude Code 策略与成本文章仍在 [analysis/](../analysis/README.md)，它们不能充当已经完成源码拆解的证明。

## 拆源码时，重建它的运行方式

从项目真实入口和整体结构进入，先确认它是什么、有哪些主要部分、哪些路径承担核心行为，再沿路径深入。可以从一次任务或一项操作追踪输入、调用、状态变化与输出；不需要先映射到本项目已有的分类。

必要细节随对象展开：关键数据结构存什么，生命周期在哪里开始或结束，谁修改状态，配置怎样改变路径，工具结果如何进入下一步，错误如何恢复。未必每个项目都有这些同名模块，组织方式应跟着对象走。

解释要落到固定 commit 的路径、符号或代码片段。文档说支持、代码中存在、默认实际启用、运行中已观察到是不同事实。静态读码时明确推导依据；能运行且有必要时，用最小执行确认关键理解，而非强制跑遍项目所有测试。

不要把列出函数名当作理解。读者应能沿你的说明解释一项关键行为，知道为什么会走这条路径、状态在哪里发生变化，以及哪个环节还不能确认。“为何这样设计”若不是作者明确说明，应标作我方解释。

## 拆论文时，重建它的论证

从论文自身的问题和定义出发，理清方法依赖哪些假设、模块或推导怎样连接、实验究竟比较了什么、结果支持到哪里。算法、公式、图表、实现细节在帮助理解时充分展开；不套用后期教材压缩篇幅的要求。

区分作者声称、论文报告、我方推论与本项目复现。综述也要重建分类的依据和覆盖边界，不能直接把它的 taxonomy 当世界的真实结构。

论文有配套源码时可以在同一对象研究中互相核对；论文版本与代码版本分别记录，不因为来自同一作者就假定一一对应。发现没有控制预算、消融缺口或定义不一致，直接写在拆解中。

## “有什么说什么”怎样落地

先按对象的实际结构讲清已发现的东西，包括暂时无法归入现有 Context/Memory 框架的部分。局部质疑、解释、比较和负结果都属于深拆；忠实不等于照单全收。

完整性相对于声明的范围。可以明确写“本次已走通请求入口与消息组装，存储恢复只定位到入口”；无需为了“深度”把依赖库逐个重写成说明书，也不能把未读部分说成不存在。

一篇深拆通常需要让人找到：研究的对象和版本、覆盖范围、整体地图、核心路径或论证、证据位置和剩余盲点。这是可理解性的要求，不是固定模板、节数或完成表。

## 怎样接到其他工作

- 发现某个值得独立追问的问题，在 [analysis/](../analysis/README.md) 展开；短的解释和质疑可以直接留在深拆。
- 看清了一个可用于当前领域理解的关系，修订 [domain/](../domain/index.md) 并链接具体依据；不用等待所有项目拆完。
- 决定下一步拆什么、为什么调整研究方法，在 [notes/](../notes/README.md) 记录；拆解中的事实不搬进去。
- 原始片段和运行记录按需留 `evidence/`；对象稿引用即可，不重复复制。

对象文件按 [内容归属](../CONVENTIONS.md) 的约定建立。下一次指定或选择一个真实项目/论文时，再建它的文件或子目录；当前不预设教材章节，也不批量创建空的项目档案。
