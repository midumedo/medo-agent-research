# 领域基础：状态、可见信息与控制

研究 Memory 与上下文工程，需要先区分三个对象：过去留下的状态、本次可见的信息，以及决定如何在两者之间转换的运行过程。否则同一个词会轮流指文件、提示词、数据库、模型能力和产品功能，比较的双方实际上并没有在解决同一个问题。

以下是本项目的**工作定义**。它们用于组织工程问题，不声称整个领域已达成术语共识。引用来源使用不同定义时，应先说明差异。源码与论文研究可以暴露这些定义的遗漏，进而改写它们；初次认识对象时，先理解其自身概念与结构，再判断本项目的定义是否适用。

<a id="context-memory-harness"></a>

## Memory、Context 与 Harness

| 概念 | 工作定义 | 直接要问的问题 |
|---|---|---|
| Memory | 跨决策步骤保留、更新，并能影响后续行为的状态及其管理机制 | 过去的什么信息被保留？变化如何进入状态？之后如何起作用？ |
| Context | 本次模型调用实际可见的输入，包括指令、对话、工具结果与其他输入模态 | 这次调用究竟看到了什么，以什么顺序和表示出现？ |
| Context engineering | 选择、组织、转换与调度本次可见信息，并观测其效果的工程 | 为什么此时给这些信息？遗漏、冲突和资源代价如何被发现？ |
| Harness | 围绕模型调用组织工具、状态、控制、权限和执行的运行系统 | 谁实现上述操作？何时触发？失败后如何恢复？ |

例如，第 3 轮确定的“只改文档”约束，在第 40 轮仍应影响行动。即使没有开启新会话，这也是跨步骤状态问题。若约束只存在于已退出窗口的历史中，它仍可能被保存，但未必能在当前决策中发挥作用。因此要区分**保存、可访问、实际取回、正确使用**，不能把其中一项当作其余三项的保证。

这一范围得到本地材料的定义支持：一篇综述同时讨论任务内与跨任务的记忆作用，见 [任务内与跨任务记忆摘录](../evidence/domain/reviewed-local-passages.md#memory-scope)。引用支持的是“来源包含这两种范围”；它不能单独证明某种记忆实现有效。

三者不是简单的包含链。存储中的内容可能从未进入本次 Context；召回通常由控制策略触发，再参与 Context 组装；模型也可能在看到当前输入后决定继续读取。模型内部的参数或隐态还能通过不同于文本注入的方式影响行为。应当说明具体的数据流和控制关系，避免用“Context 决定 Memory”概括所有情况。

## 项目的研究边界

本阶段以 Agent 在任务内和跨任务如何保留与使用信息为核心，重点是可观察的外部状态与上下文组装：原始记录、摘要、结构化条目、文件、索引、技能、工具结果、指令和检索过程。

参数记忆、隐态记忆及底层缓存会改变持有成本、可编辑性或恢复条件；当它们影响当前工程选择时纳入比较。本项目暂不承担模型架构或训练方法的完整综述。缓存计算的复用也不能自动等同于语义事实已经保存或已经正确使用。

Harness 的调度、权限和多 Agent 协作在影响信息生命周期时进入研究。例如，子任务隔离改变主调用能看到什么、恢复信息需多少步骤；一般部署或界面问题则不因属于 Harness 就自动成为本项目内容。

这项边界规定领域研究的重点，不要求 [对象深拆](../deepdive/README.md) 只摘取名称包含 Memory 或 Context 的模块。为理解真实行为所需的入口、调度、工具调用、权限、配置和相关结构，可以随对象展开；理解之后再判断哪些会改变领域认识。当前工作定义不能成为剪断执行路径或论文论证的理由。

RAG 与 Memory 有交集，但问题侧重可以不同：固定资料检索主要回答当前能找到什么；持续记忆还必须处理经验写入、事实变化、历史约束和后续行为。两者可以共用索引与检索实现；是否需要专门的 Memory 管理，要由任务中的状态变化决定。

## 描述一个机制时，拆开这些维度

下面是避免误判的一组检查问题，并非追求穷尽的分类体系。问题分析选取影响当前判断的维度；对象探索则按实际实现或论文结构展开，不要求逐项套用本表。

| 维度 | 要区分的东西 | 混淆后会出什么问题 |
|---|---|---|
| 有效性与有效期 | 当前是否可信；何时、因什么事件过期或被替代 | 把经常使用的旧价格当作最新价格；把长期保存当作长期正确 |
| 使用频率与复用跨度 | 实际多久使用一次；未来多少步骤或任务可能再用 | 用访问频率替代未来价值，忽略低频但关键的约束 |
| 驻留与加载策略 | 每次自动注入、条件加载、按需读取，或只归档 | 把“重要”直接等同于“必须常驻”，或把“没注入”当作“已丢失” |
| 表示与存储位置 | 原文、摘要、结构化关系等表示；上下文、文件、索引等位置 | 把外部化当作无损，把摘要当作必然无法恢复；同一原文其实可以在多处保存 |
| 控制与授权 | 谁设目标、谁决定具体操作、谁执行、谁有权覆盖 | 将“自动执行”误读为“模型自主决定”，或让低可信信息覆盖高优先级约束 |
| 来源与恢复条件 | 谁说的、对应什么版本；原始材料能否定位、访问和重建 | 内容还在却无法确定哪个版本有效；存在原文却没有可行恢复路径 |

例如，一个每天自动注入的项目指令文件，具有常驻策略，但不因此拥有很长的有效期。一次极少召回的用户约束，访问频率低，却可能在某次任务里具有很高的违反代价。缓存命中则是运行事件：它可能降低计算费用，但并不证明内容相关、真实或新鲜。

“谁决定”是已有研究明确讨论的维度，见 [控制策略摘录](../evidence/domain/reviewed-local-passages.md#control-policy)。本项目继续拆开授权与执行角色，是为了描述混合控制：用户设边界，模型提出候选，确定性程序执行写入，工程方负责日志和回退。它不是互斥的三种系统。

<a id="control-and-flow"></a>

## 操作流程与控制策略是两回事

可以用“观察 → 形成候选 → 更新状态 → 读取 → 组装 → 行动”描述信息经过的操作，但这不是必须每步执行的固定流水线。读取可能返回空，候选可能被拒绝，写入可以延迟，行动结果可以触发重新读取。负向动作可以属于任一步的控制策略，不需要因为“拒绝注入”就另造一种系统形状。

同样，“治理”不必对应一个独立产品按钮。来源校验、冲突处理、过期失效、权限控制和删除约束，可以分别作用于写入、读取与组装。比较系统时应问这些约束在哪里得到执行、哪些没有执行，而不是先假定它们只能存在于一个集中阶段。

这只是可用于检查实现的工作模型。若真实执行轨迹显示，某种机制无法用这些操作和约束充分解释，就应调整描述；模型的价值在于暴露遗漏，而非要求产品配合它。

## 从定义走向判断

分类只能说明“是什么”，不能直接推出“该选谁”。一个有用的机制判断还要说明任务目标、必要信息、可恢复条件、控制策略、全流程成本和失败代价。[上下文留存机制](mechanisms/context-retention.md) 从同一段历史如何服务后续决策出发，展示这种推导。

当前定义中外部来源已核对本地文本，尚未独立复现所述系统；机制推论仍需通过 [研究议程](../analysis/research-agenda.md) 检验。2026-09-20 的定义调整及撤回理由见 [项目审查](../analysis/project-review-2026-09-20.md)。
