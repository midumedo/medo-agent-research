# 上下文留存：何时保留、摘要、外部化或组合

**问题：一段已经获得的信息，怎样在后续任务中继续发挥作用，又不让持有与恢复成本失控？**

当前判断是：选择取决于未来任务需要保留什么、原文能否可靠恢复、会复用多少次，以及失败的代价。直接保留、摘要和外部化改变的是不同成本与风险，没有一种操作仅凭名称就能保证更低成本或更高质量。

本文是机制推演，包含明确标注的逻辑反例与未校准成本模型，**不是产品性能报告，也没有声称本项目已经完成相关实验**。概念范围见 [领域基础](../foundations.md)。

## 四种动作到底改变了什么

| 动作 | 改变的东西 | 必须进一步确认的条件 |
|---|---|---|
| 直接保留 | 把内容继续放在后续调用可见的输入中 | 模型能否使用；内容是否仍有效；是否占用更有价值的信息空间 |
| 摘要或结构化提取 | 把原表示转换成更短或更集中的表示 | 哪些细节与关系被舍弃；摘要是否忠实；原文是否仍在且可定位 |
| 外部化后按需读取 | 让原文或派生表示退出主上下文，之后由查询恢复需要的部分 | 是否知道何时查询；能否找到正确版本；恢复花多少步和费用 |
| 过滤或延迟加载 | 暂时不让某些信息进入主调用 | 被排除的内容是否可能成为关键证据；能否发现漏取并补读 |

子任务委托还会改变观察和计算发生的位置：主调用可能只收到子任务的结论。若子任务总结了材料，它同时发生了隔离与摘要；若只返回位置指针，则把后续恢复工作留给了主调用。把这些行为统称为“卸荷”，容易掩盖真正的差别。

摘要不必删除原文，外部化也不保证原文永久可用。可恢复性取决于保存、定位、权限、版本和读取机制。相似地，确定性过滤只保证每次执行同一规则，不能保证规则保留了下一任务需要的信息。

## 从未来决策倒推留什么

同一批日志可以服务不同任务：统计某类错误，需要精确匹配；解释故障先后关系，需要时间顺序和上下文；落实已经确定的修复方案，可能只需保留诊断结论与未解决项。

因此，先问下一步决策对哪些信息敏感。不可重新获取的约束、精确 ID、条件例外和因果顺序，不能因为出现次数少就默认舍弃。反过来，大量随时可重读、近期很少复用的记录，也不必因为已经获得就每轮携带。

这仍是对未来需求的估计。需求越不可预测，越难安全地决定哪些信息永远不需要。设计应同时提供两种能力：为常见任务构造足够的信息表示，为意外任务保留可追溯的恢复入口。恢复入口本身也有成本和失效模式，不能只写“需要时再查”。

## 两个逻辑反例

**反例一：确定性过滤可以稳定地漏掉关键证据。** 假设日志先记录非 ERROR 的配置切换，随后记录 ERROR 故障。过滤器只返回 ERROR 行，下一任务要求判断故障是否由配置变化引起。规则完全确定，但它排除了区分原因需要的信息。如果原日志已不可访问，无法恢复；如果原日志还在，却没有触发补读的信号，当前行动仍可能错误。这个构造反驳“精确执行过滤 ⇒ 信息选择正确”，不说明所有过滤都不好。

**反例二：摘要可以比反复恢复原文更合适。** 假设一次排障已确认三个组件之间的依赖顺序，接下来多步任务反复需要这个已核实顺序。保留一段准确的关系摘要及原文位置，可以避免每次重新取回并重新归纳分散记录。如果摘要没有遗漏后续所需条件，那么外部化全部内容、每次再恢复，并不必然带来质量收益，却增加了调用。这个构造反驳“外部化严格优于摘要”；它的前提恰恰是摘要忠实且需求相对稳定。

两者都是人为构造的反例，尚未做模型实测。它们足以限制全称断言，但不能估计真实任务中哪种情况更常见、差异有多大。后者需要对照实验。

## 一个通常值得比较的混合策略

对当前任务保留关键约束、已核实的阶段结论和未解决项；把大体量原文放在可追溯存储中；摘要附上原文定位、版本和适用条件。精确数字、因果争议或条件例外出现时，读取相关原文再作决定。任务结束或事实改变时，更新派生表示和失效状态。

这是一项候选策略，不是默认正确的最佳实践。它也可能失败：摘要过时、位置失效、原文权限改变、查询错误、读取入口未被发现，或摘要与原文发生冲突而系统不知道该信谁。额外维护多个表示还可能超过它节省的成本。

如果信息很短、很快再次使用，直接保留可能更简单。如果下一步只需要原文中的精确片段，摘要可能是不必要的转换。如果任务经常询问出乎预料的细节，保留可检索原文的价值增加。如果删除要求覆盖所有派生表示，混合方案还必须把摘要与索引纳入删除路径。

## 成本模型只能暴露假设

设策略为 π，比较周期包含 T 次顶层决策。把为这段周期执行的所有相关模型调用——包括初始化构建、摘要、检索规划、子任务和恢复——组成集合 J；不能因构建发生在第一次查询之前就遗漏它。一个简化的货币成本表达是：

```text
C(π, T) = Σ[j ∈ J] (p_u U_j + p_r R_j + p_w W_j + p_o O_j)
          + C_index + C_storage + C_tools
```

U、R、W、O 分别表示账单口径下的未缓存输入、缓存读取、缓存写入和输出计费量；对应价格为 p。使用时必须按所选服务商的计费规则把各项拆成不重复的费用，不能把已包含在输入费中的缓存写入再算一次。索引、存储和其他工具费用只计模型费用之外的部分；不存在相应收费时可以为零。模型版本和计价规则不固定，p 也可随调用变化。

这不是服务商无关的精确计价器。它假定调用与费用可被观测，且比较周期覆盖了重要的后续复用；没有给未来任务概率赋值，也没有把错误、延迟或人工修复强行折成一个金额。缓存是否实际命中要取观测值，不能仅凭“前缀大致相同”推定。

在极简条件下，若外部化额外支付一次构建费用与多次恢复费用，它只有在这些费用小于所避免的持有费用时，才在货币成本上有利。若还改变任务结果，则不能停在这条不等式上：需要先检查任务成功、关键约束与恢复可靠性，再比较满足要求的策略成本。

因此应分别报告任务质量、总费用与延迟。费用相同但遗漏关键约束的方案，并不因 token 更少就更优；费用较高但消除了昂贵错误的方案，也可能更合适。质量无法归为同一水平时，应展示取舍，而不是强排一个总榜。

## 需要观察哪些接口

要发现静默损失，仅记录“发生了一次摘要”不够。最小观察记录应能连接以下事实：

| 接口 | 记录什么 | 能回答什么 |
|---|---|---|
| 输入进入 | 来源身份、版本、获取时间与原文位置；记录实际可保存的内容 | 后来使用的信息最初来自哪里？ |
| 表示变换 | 何时触发、使用的策略、输入与输出位置、保留原文与否 | 信息在哪次摘要或提取后发生了变化？ |
| 存储更新 | 新旧版本、冲突与失效处理、派生表示的依赖 | 旧结论是否仍可能被再次取回？ |
| 读取与组装 | 查询、候选、实际选中内容、预算截断及最终可见输入 | 信息存在却没有被取回，还是取回后没有进入调用？ |
| 行动与结果 | 任务是否完成、关键约束是否违反、证据是否被正确使用 | 问题在保存、取回还是使用？ |
| 资源使用 | 每个阶段的实际调用、费用与延迟，包括子任务和失败重试 | 是否只是把主上下文成本转移到别处？ |

这些记录只能覆盖产品或实现暴露的接口。不可见的内部压缩、隐态或服务端处理应标明观测缺口，不能据日志沉默断定它们没有发生。记录本身也要服从任务的权限、存储和保留约束。

“对比摘要前后文本”有帮助，但它并不能直接判定语义上是否丢失了必要信息：必要性与后续任务有关。应把原文、摘要和后续任务中可检查的约束联系起来，观察丢失是否真正导致错误，以及系统能否恢复。

## 当前判断的边界与下一步

本文能够通过概念区分与逻辑反例，撤回“摘要必然不可逆”“过滤确定所以选择正确”“卸荷严格优于压缩”等无条件判断。它尚不能给出真实任务分布上的策略排名、推荐压缩率或成本收益数字。

首轮应固定模型和任务目标，比较直接保留、保留原文的摘要、外部化读取与混合策略，操纵未来需求可预测性、原文恢复条件与复用次数。失败要能定位到保存、恢复或使用环节。具体执行协议见 [研究议程](../../analysis/research-agenda.md)，竞争解释见 [disputes.md](../disputes.md)。
