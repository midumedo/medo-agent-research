# domain/ · 认知论述层

> **这是本项目的一号资产。**
> `book/` 和 `manual/` 是它的编译产物，不是它的目标。产物会过时、会重写、会换形态，认知层不会。
> 本项目的实质：**构建一套 agent 领域的认知体系，再把它编译成不同形态的产物。**

> **AI 读这个目录时**：这里装的是**判断及其推导**，不是信息。
> 写在这里的每一段都要能回答「为什么是这样」——写不出理由的就不是认知，是搬运。
> **别在这里追求可摘录。** 可摘录是下一层 `entries/` 的事；为了摘录而删掉推理链，等于把审查能力一起删掉。

## 一、概念坐标系

定位任何「记忆 / 上下文」相关的东西，用三条轴：

| 轴 | 取值 | 回答什么 |
|---|---|---|
| 半衰期 | 常驻 / 热 / 温 / 冷 | 它多久失效，该不该进上下文 |
| 载体 | token 级 / 参数 / 隐态 / 外部存储 | 存在哪，能不能改，改了要不要重训 |
| 谁决定 | 系统自动 / 用户显式 / 模型推断 | 出问题时谁背锅 |

第三条轴是我们自己加的。综述都按「形态 × 功能」分，没人问「谁决定它留下来」——而后者才是工程上真正会吵架的地方。

## 二、三个概念的分工

边界不划清，后面所有讨论都会退化成「高级一点的 RAG」。

| | 一句话 | 时间尺度 | 谁在管 |
|---|---|---|---|
| Context | 每步所见 | 单次请求 | 组装方 |
| Memory | 跨时间所留 | 跨会话 | 读写方 |
| Harness | 除模型外的整套运行基建 | 项目生命周期 | 工程方 |

递进且互相包含：Harness 决定 Context 怎么组装，Context 决定 Memory 何时被召回。

## 写在这里的规矩

- **带推理链。** 这是本层与下一层的根本区别：要能看出结论是怎么来的。
- **只增不推翻。** 被撞倒的假设在 `THESIS.md` 那边处理，这里只放确认过的东西。
- **标它回答什么问题，不标它属于第几章。** 章节号随主线变而失效，问题不会。
- **证据放 `evidence/domain/`。** 论断在这里，摘录在那边。
- **允许冗余。** 铺垫和反复是论证的一部分——追求精简会伤到可审查性。
