## 第一原理

**Context 是按轮次计息的负债，不是预算，更不是仓库。**

「预算」是一次性的容量约束，它描述不出"每件东西进来之后还在持续收费"。负债观能自然推导出：为什么必须重视前缀稳定性、为什么卸荷优于压缩、为什么会存在 200 行这类限制。

预算观默认"放进去就结束"；负债观提醒你"它在后面每一轮都在收利息"。

## 已知最可疑的一段

### 「治理」在 harness 侧可能没有干净的对应物

其余五段在 Claude Code 上都有落点（对话历史 / skills 渐进披露 / system prompt 组装 / compact / subagent），唯独治理不见踪影。

harness 丢弃信息是**退化**的动作：东西没了不是因为有人判断它该没，而是因为它滑出了窗口。显式治理（抽取、冲突消解、去重、遗忘）只存在于 memory 层那侧。

若成立，「六段循环」可能只是 memory 层的循环，harness 侧是另一种形状。

### 同源的第二次撞击：卸荷不属于任何一段

Claude Code 官方给的减负手段，绝大多数不是"压得更好"，而是**让信息别进来**（Hook 预处理 / Subagent 委托 / MCP 延迟加载 / Skill 按需加载）。

它不是产生、不是召回（恰恰是阻止召回）、不是注入（恰恰是阻止注入）。它是一个**负向动作**。

推论：**骨架可能不是一条从产生到注入的流水线（默认放行），而是围绕预算做准入与拒绝的守门机制（默认拒绝）。** 这两种模型的设计取向完全不同。
