# 项目维护规则

本 skill 管的都是「动手时」才需要的规则。常驻文档里不写这些——**规则一直在场，注意力就一直在分。**

## 一、先只读，要 action 时才改

默认状态是只读。先读清楚现状、确认要改的究竟是什么，再动手。别一边读一边改——那样会在还没理解结构的时候下手，然后把没看懂的部分一起改坏。

## 二、改之前先判断改的是哪一层

| 要改的东西 | 在哪 | 改法 |
|---|---|---|
| 我们对领域的认知 | `domain/` | 只增不推翻 |
| 我们的赌注 | `THESIS.md` | 撞不上就推翻重写 |
| 证据 | `analysis/<系统>/` | 写完即定，不回头改 |
| 支撑某条论断的摘录 | `evidence/<文档名>/` | 追加 |
| 一次交流（含被否掉的选项） | `dialogue/` | 追加，不改历史 |
| 已拍板的决定 | `notes/` | 追加，不改历史 |
| 结构规则 | `CONVENTIONS.md` | **先改规则，再动结构** |

最后那行的顺序不能反：结构要变时先改 `CONVENTIONS.md` 再动目录。反过来会让目录与规则短暂不一致，而那个不一致往往被永久留下。

## 三、认知层条目必须可编译

`domain/` 是本项目的一号资产，`book/` 和 `manual/` 是它的编译产物。**能不能到时候一把梭哈，取决于条目现在是什么形状**：连贯文章 → 后期要人手重写；原子条目 → 后期 AI 挑选 + 排序 + 补连接即可。

三条硬要求：

1. **一条认知 = 一个条目。** 有小标题，摘出来就是一张卡，不依赖前后文。
2. **标它回答什么问题，不标它属于第几章。** 章节号随主线变化而失效，问题不会。认领交给编译阶段——这也是引用单向能成立的原因。
3. **证据放 `evidence/`。** 正文只留论断与指针；证据写进条目会把它撑成文章，又变回不可编译。

**检验方法**：随机抽一条问「它能直接放进手册吗」。需要重写句子 → 它是散文不是原子。

## 四、不静默删除

被推翻的说法标 `[已撞]` 并保留原句。删掉之后没人知道我们曾经相信过什么，也就没人知道那条路走不通——**走过的死路是有价值的，静默删除等于把它再走一遍的风险留给了未来的自己。**

## 五、新规则默认不进 AGENTS.md

新增规则一律写进 `CONVENTIONS.md`、`STYLE.md` 或本 skill，**不进 `AGENTS.md`**。AGENTS.md 只留每轮真正需要的那几条；它每多一条，那几条被遵守的概率就降一分。

同理：**不要在常驻文档里写论证过程。** 一个决定为什么这么定，写进 `notes/` 或 `dialogue/`；常驻文档只放结论与指针。

## 六、命名

- 目录全小写英文，连字符分词。根级常驻文档全大写。内容文件小写 kebab-case。
- **英文本身是正确性要求，不是偏好**：Windows 下非 ASCII 路径经 `.ps1` / `.bat` / 部分 Python 调用会写坏文件名。
- `claude-code` 指产品，`claude` 指模型，不要混用。

## 七、写作体例

**见 `STYLE.md`。** 不在这里重复——规则散在两处必然漂移，文体类约定统一归 STYLE.md。

## 八、放文件时的判定测试

一句话说不清一个文件该进哪个目录，就是分类错了：

| 目录 | 判定句 |
|---|---|
| `sources/papers/` | 这是一篇别人写的论文 |
| `sources/repos/` | 这是别人写的代码，我们 clone 来的 |
| `analysis/<系统>/` | 这是我们对某个外部系统的完整拆解 |
| `evidence/<文档名>/` | 这是支撑某条具体论断的原始摘录 |
| `dialogue/` | 这是我们的一次交流：问了什么、怎么推演、否掉了什么 |
| `notes/` | 这是一个已经拍板的决定 |
| `archive/` | 这是某次会话的原始快照 |

**分水岭**：`sources/` 是外部世界，其余是我们的产出。
