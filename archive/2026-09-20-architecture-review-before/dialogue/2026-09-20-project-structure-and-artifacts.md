# 2026-09-20 · 目录结构、产物形态与中间态

本轮围绕「这个项目该怎么组织」推演。按问题记，含被否掉的选项——**死路留在这，结论去别处。**

---

## Q1：文件目录结构怎么设计？各种 markdown 怎么配合？

**我的定调**：本项目目录结构是教材论点的第一个实例。不能一边写「context 是负债不是仓库」，
一边让根目录长成仓库。切分依据 = 半衰期与读取频率，不是主题（主线未锁定，按主题切即过早结构化）。

**诊断出的问题**：主线住在 AI 记忆里（会被压缩重写）· outline.md 在冒充目录 · 根目录是会话流水
· 缺 AGENTS.md。

**结论去向**：`AGENTS.md` `CONVENTIONS.md` `THESIS.md`

---

## Q2：英文命名？取舍改名？文档分工？papers 根级？加 ref？

用户拍板：目录英文为主 · 内容取舍文档改名「取舍」· 文档分工要更细宁可多写几个 ·
质疑 papers 是否根级 · 提议加 `ref/` 装 repo/papers/logs，并问「分析叫 ref 会不会歧义」。

**我否决了 `ref/`**：三重歧义（reference / git refs / 有人当 refactor），更致命的是语义污染——
**「分析」不是「参考」**，把我们的产出与外部原料塞进同一个目录，这个目录就废了。
→ 拆成两个世界：`sources/`（别人的）与 `analysis/` + `notes/`（我们的）。

**papers 不根级**：根级应表达性质差异，sources/ 内部才表达类型差异。

**英文命名的硬理由**（非偏好）：Windows 下非 ASCII 路径经 .ps1/.bat 会写坏文件名；
`pdf2md.py --out 综述` 一直带着这个雷。

**结论去向**：全部迁移已执行，`CONVENTIONS.md`

---

## Q3：四个任务？教材和手册是不是一回事？

用户指出：教材和手册不一样，学过之后复习是看手册。并列出第四个任务——
**维护「对 agent 认知的中间态」**，结合综述，需要大量分析。

**「手册不是教材的摘要」**：摘要保留路径，而复习的人不需要再走一遍路径，他手里拿着一个具体问题。
手册是打散路径、按查询重组的产物。手册独有而教材给不了的是**症状反查表**。

**结论去向**：`UNDERSTANDING.md`（新建）· `AGENTS.md` 四个产物表 · `TRADEOFFS.md` 第九节

---

## Q4：反对字数限制；手册要从认知层编译，且要多版本

**用户否决了常驻层行数上限**：「顶天了能用多少 token，但把大量注意力放在 token 数量上，
这是我难以接受的」。

我接受，并补充论证这是**指标替代**——拿可测的行数管不可测的注意力，正是我们准备写进
「评测为什么不可信」那章的毛病。**长不是问题，该拆没拆才是。**

**手册从认知层直接编译**，与教材互不为上下游：教材编译成一条路径（学的顺序），
手册编译成多个视图（用的场景）。

**结论去向**：`notes/decided-no-length-caps.md` · `AGENTS.md` · `CONVENTIONS.md`

---

## Q5：claude 还是 claude-code？症状表归哪？修改原则要不要单独写？

**我错了两处**：`claude` 指模型、`claude-code` 指产品（自己跟 `analysis/claude-code/` 不一致）；
更紧的是归档逻辑——「压缩后静默丢失」是**机制层**问题，用产品边界切机制层问题是错的。
→ 新增 `manual/troubleshooting/`。**症状不知道自己属于哪个产品。**

**用户质疑修改原则写进常驻文档「还是牵扯到注意力分散」**，并借 agent 新范式点破：
**先只读，要 action 时才改**。

→ 这是同一个 bug 第二次出现：我刚承认不该用行数管注意力，转头就把八条规矩塞进 AGENTS.md
让它每轮在场。→ 文档分两层：常驻三个（AGENTS/UNDERSTANDING/THESIS），按需五个。
AGENTS.md 硬规矩 8 条 → 3 条。

**结论去向**：`AGENTS.md` · `CONVENTIONS.md` 修改原则节 · `STYLE.md` 术语

## Q6：manual/book 是后期的事，现在该设计中间态

**用户**：「manual/ 下面不是应该很后期的东西了吗，我们急着写干嘛，我们现在重点不是该在那个
分析与交流的中间态上吗……难道交流完了，我还去自己手改吗？」

这是本轮最重的一击。真正的问题是：**中间态的形态决定了后期能不能一把梭哈。**

如果中间态是连贯文章，后期编译 = 重写（要人手改）；
如果中间态是原子条目，后期编译 = 挑选 + 排序 + 补连接（AI 可自动完成）。

→ 所以现在该做的是：把中间态设计成**可编译的**，而不是急着产出。

**结论去向**：本节即结论（可编译性三条件后经 Q7 修正）· `evidence/` 与 `dialogue/` 的新建

## Q7：认知层还要再分两层——审查层与编译层

**用户**：「这个中间层起码还要再分两层啊。就一层是类似于拆解呀这些的，第二层才是为下面那个
book 进行的……第一层 AI 人要读，机械也要读，人要审查嘛，因为我自己去审查需要一定的理解。
那再有第二层才是纯 AI 去读的，进行按点去拆的那种感觉。」

**这条纠正暴露了我一个实质错误**：我此前要求「认知层条目必须原子化，摘出来就能用」。
这条本身没错，但**不该加在第一层上**——原子化会拆掉推理链，而审查一份结论时需要看到它是
怎么推出来的。孤立论断无法判断对错。

**两层的形态要求本质冲突，同一份内容不可能同时满足**：

| | 第一层（审查层） | 第二层（编译层） |
|---|---|---|
| 谁读 | 人 + AI | 纯 AI |
| 干什么 | 判断结论对不对 | 组装成产物 |
| 形态 | 连贯论证，有推理链 | 原子条目，按点拆 |
| 冗余 | 允许（铺垫与反复是论证的一部分） | 不允许（每点只出现一次） |
| 顺序 | 有意义（推导顺序） | 无意义（可任意重排） |
| 坏掉的样子 | 推理链断了 | 条目不能独立 |

**链路因此多一环**：
`analysis/`（单系统拆解）+ 认知论述层（跨系统）→ **条目层**（提炼）→ `book/` + `manual/`（组装）

**关键设计细节**：条目层要「原子」但不能丢掉推导链——**链条不在条目里，条目指向链条**。
每条条目保留：论断 + 回答什么问题 + 证据指针（→ evidence/）+ 推导链指针（→ 第一层某段）。

**待定**：第一层认知论述层命名（候选 `atlas/` `mechanisms/` `mental-model/` `core/`）·
第二层条目层命名（候选 `entries/` `cards/` `ir/`）

**本项目教训（同类第四次）**：把两个互相冲突的要求压在同一层上。
前三次：行数管注意力 / 产品边界切机制层问题 / 规则塞进常驻文档。
**这正是「分层」这个动作的价值——冲突的要求要分层满足，不是在同一层里折衷。**
