# Claude Code · 上下文管理：卸荷优先于压缩

> 资料来源：官方 costs / context 文档（一手）。文中标 [推断] 的为我的推论，不是文档内容。
> 术语约定：项目级常驻指令文件统一称 **AGENTS.md**（CLAUDE.md、GEMINI.md 同义，已废弃统一为 AGENTS.md）。

---

## 一、一个反直觉的观察：官方给的所有减负手段，都不是"压缩"

把官方「Reduce token usage」里列的办法摊开看，会发现一件有意思的事——**没有一条是在说"怎么压得更好"**：

| 手段 | 作用在哪个环节 | 本质 |
|---|---|---|
| PreToolUse Hook 预处理工具输出 | 工具结果**进入之前** | 让信息别进来 |
| Subagent 委托 | 独立上下文 | 让信息进别的地方去 |
| MCP 工具定义延迟加载 | 系统提示 | 让它晚点进来 |
| Skill 按需加载 | 指令 | 用的时候才进来 |
| code intelligence 插件 | 检索精度 | 少试几次，少读几个文件 |
| AGENTS.md 保持精简 | 常驻层 | 常驻的少放点 |
| **auto-compact / `/compact`** | **已经进来之后** | **删减（兜底）** |

前五条是同一个动作：**让信息根本不要进入主上下文**。只有最后一条是在"已经进来了"之后做减法。

我把前者叫**卸荷（offload）**，后者叫**压缩（compaction）**。

> 这套体系的默认思路是**卸荷优先**，压缩是兜底——而且是被排在列表最后的那一项。

---

## 二、为什么卸荷严格优于压缩（这不是品味问题，是三条硬理由）

1. **压缩要付出额外成本。** 官方原话：*"compacting a large context is itself a large request"* —— 总结之前，你得先把整段待压缩的内容再读一遍。卸荷不付这笔钱。
2. **压缩不可逆，卸荷可逆。** 压缩掉的你是真没了。Hook 过滤掉的东西还在磁盘上，Subagent 里的输出还在那个上下文里——**想要还能再取一次**。
3. **压缩是意图推断，卸荷是精确控制。** 压缩要靠模型猜"什么重要"；Hook 里写的 `grep ERROR` 是确定性的，说一不二。

第 3 条最关键，引出下面这个设计决策。

## 三、为什么压缩被做成了"旋钮"而不是"策略"

CC 在压缩这件事上给了四层控制粒度，一层比一层具体：

```
自动触发        auto-compact window 达到阈值时自动总结
手动触发        /compact
带焦点的内容    /compact Focus on code samples and API usage
永久定制        AGENTS.md 里写 `# Compact instructions` 段落
```

**注意最后两条。** 官方等于公开承认了一件事：**什么值得留下来，它猜不出来。**

同样是压一个会话，做重构的人在乎"改了哪些文件和函数签名"，调 API 的人在乎"请求示例和参数格式"。这是意图，不是信息量，模型没法从上下文里推断出你在乎哪个。

所以 CC 的处理是——**不猜，把旋钮露给你**。

> 这是一个教科书级的示范：**当一个设计者意识到某件事不可判定时，正确的做法是暴露控制点，而不是假装自己能自动化。**
> 对比很多系统会硬编码一个"通用最佳实践"的压缩策略，然后把失败包装成"模型偶尔会忘"。

不过也要指出它的代价：**旋钮默认是空的**。绝大多数用户不会去写 `# Compact instructions`，于是他们拿到的就是那套通用策略——也就是谁也没定制过的那个策略。

## 四、失效现场

三种，按危险程度排序。

**① 压缩后的静默丢失（最危险）**
没有任何报错、没有 diff、没有"被丢弃了什么"的报告。会话只是往前继续了，等你发现它忘了某个早先定下的约定，可能已经过了十几轮。
*可观测证据*：压缩触发时用户能看到的现象是「一条 context warning」，官方特意说明它 **not a usage limit**——也就是说这个信号本身容易被误读成"配额快没了"，而不是"你的记忆刚刚被重写过"。

**② 常驻层的稀释**
官方要求 **AGENTS.md 保持在 200 行以下**。
这条规定本身就是一个证据：如果常驻内容不存在"越多越无效"的问题，官方就不会给数字。**超出之后代价不是成本，是注意力稀释，而且同样没有报错。**

**③ 大输出的反复重放**
每次请求发送完整对话，每次工具调用还要再带上该批工具结果。一行提问在长期会话里会因为携带全部历史而持续花钱。
→ 所以才有卸荷那套。

## 五、数量级锚点（真实数字，可直接用在书里）

| 数字 | 含义 | 出处 |
|---|---|---|
| **200 行** | AGENTS.md 建议上限，超出的详细工作流应移入 Skill | 官方明确要求 |
| **10,000 行 → 数百 token** | 一个 PreToolUse Hook 用 `grep ERROR` 过滤日志的效果 | 官方举例 |
| **每次请求发送完整对话** | 每轮都重放全部历史 | 官方说明 |
| **`MAX_THINKING_TOKENS=8000`** | 固定思考预算模型的直接下调方式（自适应推理模型忽略此变量） | 官方配置 |

这些是**真实数量级**，不是 AI 可能编出来的"合理值"——正是我们说的那类必须留在书里的东西。

## 六、只许改一处，我改这里

**把卸荷做成默认路径，而不是要求用户手工配置 Hook 和 Skill。**

理由是现状的结构性问题：官方理念上推崇卸荷，但**实现上它比压缩麻烦得多**——你得自己写 Hook、自己写 Skill、自己决定什么委托给 Subagent。压缩是零配置的自动行为，卸荷是要动手的投资。

结果就是：**默认行为（自动压缩）恰恰是官方自己认为较差的那个策略，而较好的策略需要用户先跨过一个配置门槛。**

一个务实的改法：CC 检测到某类高冗余的工具输出反复出现（比如连续几次 Read 返回大文件），就**建议**装一个对应的 Hook 或改投 Subagent——把"用户不知道有卸荷这条路"变成顺手的一步。

> 顺带说：第 6 问"你会改哪"的价值就在于此——它逼你从"它做得对"跳到"它在哪个地方偷懒了"。

## 七、拿去撞主线：卸荷在我们的循环里没有位置

这条留给教材骨架。

六段循环是：产生 → 写入 → 治理 → 召回 → 注入 →（旁路：压缩 / 隔离）

**卸荷不属于任何一段。**

- 它不是"产生"——信息已经产生了
- 不是"召回"——它恰恰是阻止召回
- 不是"注入"——它是阻止注入
- 最接近"隔离"（Subagent 那条勉强算），但 Hook 过滤和 MCP 延迟加载怎么也不像隔离

它是一个**负向动作**：整套机制的核心不是"如何放入"，而是"如何不放入"。

这和昨天发现的「治理」缺失是同源的——**我们的循环是按"信息如何流入"写的，但真实系统很大一部分工程量花在"信息如何不流入"上。**

所以骨架大概率要改的不是加一段，而是：**它可能不是一条从产生到注入的流水线，而是围绕预算做准入/拒绝的一套守门机制。** 流水线模型默认放行，守门模型默认拒绝——这俩的设计取向完全不同。
