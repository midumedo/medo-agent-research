# CONVENTIONS.md · 目录与文件约定

---

## 一、命名

| 对象 | 规则 | 例子 |
|---|---|---|
| 目录 | 全小写英文，连字符分词 | `sources/papers/surveys/` |
| 根级常驻文档 | 全大写 | `THESIS.md` `TRADEOFFS.md` |
| 内容文档 | 小写 kebab-case | `context-economics.md` |
| 临时/工具产物 | 下划线前缀 | `_scripts/` `logs/` |

### 为什么坚持英文（三条，不只是偏好）

1. **工具链正确性。** Windows 下非 ASCII 路径经过 `.ps1` / `.bat` / 部分 Python 调用时会出编码问题，文件名被写坏。`pdf2md.py --out 综述` 一直带着这个隐患——已随本次改名消除。
2. **AI 检索友好。** `sources/` `repos/` `surveys/` 这类词在模型语料里的语义密度远高于自造词，目录名本身就是给模型的一级锚点。
3. **可移植。** 哪天要上 GitHub、要做静态站、要换机器，中文路径的成本会集中爆发。

## 二、切分依据：半衰期，不是主题

根级目录表达的是**性质差异**（读取频率、半衰期不同），`sources/` 内部才是**类型差异**（性质相同、形态不同）。

主线未锁定，任何按主题分的目录都是过早的结构化——主题会变，半衰期不会。

---

## 三、各目录的判定测试

一句话说不清一个文件该进哪个目录，就是分类错了。

| 目录 | 判定句 | 半衰期 |
|---|---|---|
| `sources/papers/` | 这是一篇别人写的论文 | 冷，只追加 |
| `sources/repos/` | 这是别人写的代码，我们 clone 来的 | 冷，会漂移 |
| `sources/reports/` | 这是汇编性质的调研材料 | 冷 |
| `analysis/<系统>/` | 这是**我们**对某个外部系统的完整拆解 | 温 |
| `analysis/_cross/` | 这是跨系统的共性汇聚 | 热 |
| `evidence/<文档名>/` | 这是支撑某条具体论断的**原始摘录** | 冷，按需 |
| `dialogue/` | 这是我们的一次交流：问了什么、怎么推演、否掉了什么 | 热 |
| `notes/` | 这是一个**已经拍板的决定** | 热 |
| `book/` | 这是给读者看的正文 | 定稿即冻结 |
| `archive/` | 这是某次会话的原始快照 | 冷，允许重复 |

### `evidence/` 与根级文档同名配对

根级每个结论性文档，在 `evidence/` 下有一个同名目录：

```
domain/index.md          → evidence/domain/
THESIS.md                 → evidence/THESIS/
```

**论断写在 md 里，证据放在同名目录里。** 用命名配对代替显式链接——链接会失效，同名关系不会。

三层的分工要分清：

| 层 | 装什么 | 颗粒度 |
|---|---|---|
| `sources/` | 外部材料的**全集**（可能还没读） | 整篇论文 / 整个仓库 |
| `analysis/` | 一次完整的拆解推演 | 一篇论证 |
| `evidence/` | **已被引用**的那一小段 | 一段摘录 / 一个数字 / 一条命令输出 |

`evidence/` 里存「锚点 + 摘录」，不是复制整篇推演。它与 `analysis/` 的重叠是引用式的，不是复制式的。

### `dialogue/` 与 `notes/` 的区别

**交流是过程（含死路），结论是结果（只含活路）。**

合并会让结论文件被过程污染——你只想查「我们定了什么」，却得先读完三轮推演。分开之后，
`dialogue/` 保留「我们为什么否掉了 X」，`notes/` 只留活下来的那条。**死路是有价值的，
但它不该占着结论文件的位置。**

### 关于 `sources/repos/` 的四条约束

1. clone 完立刻在 `analysis/<系统>/` 记下 commit sha 与日期，否则引用无从对证。
2. 只读、不改。
3. 目录已 `.gitignore`，不入版本控制。
4. **不 grep 全仓**——对着一个带 `node_modules` 的仓库全量 grep，几千行直接灌进上下文。要查就限定目录，或走锚点文件。

### 为什么没有 `ref/`

`ref` 有三个常见读音：reference（参考资料）、git refs（引用指针）、少数人当 refactor。更麻烦的是语义污染——**分析不是参考**。把我们的产出和外部原料塞进同一个 `ref/`，这条目录就废了。

所以拆成两个世界：`sources/`（别人的）和 `analysis/` + `notes/`（我们的）。这条分界线是本架构里最重要的一条。

## 四、不建空目录

`sources/docs/`、`sources/specs/`、`book/`、`manual/` 暂时都不建。需要时再建——空目录会骗人，让结构看起来比实际完整。

## 五、修改规则

修改文档、放文件、往认知层加条目的操作规则，都在 **`project-maintenance` skill**，不在本文档。

理由：**这些规则只在动手时才需要。** 写进常驻或半常驻文档，它们就一直占着注意力——这和常驻层不设长度上限是同一个道理，问题不是规则有多少条，是它们是不是每轮都必须出现。

（原本写在下面的「修改原则」与「中间态必须可编译」两节已移入该 skill。）

## 六、手册长什么样（`manual/` 将来如何使用）

手册从认知层（`domain/` + `analysis/`）**直接编译**，与教材并列，不是教材的下游产物。认知层是源文件，两者是不同的编译目标。

### 多版本，每个版本内部逻辑不同

| 版本 | 读者当时在干什么 | 内部逻辑 |
|---|---|---|
| `manual/claude-code/` | 正在配、正在调 Claude Code 这个产品 | 按配置与调参的动线组织 |
| `manual/memory/` | 正在选或正在搭一套记忆层 | 按「我要做哪个决策」组织 |
| `manual/harness/` | 正在从零搭一套 harness | 按「搭建顺序」组织 |
| `manual/troubleshooting/` | 我的 agent 行为不对劲，但说不清是哪层的问题 | **按症状反查，跨系统** |

划分依据是**使用场景**，不是知识主题。所以同一个知识点（比如压缩）会在多个版本里都出现，但**位置、详略、配什么决策卡都不同**——这不是重复，是不同编译目标的正常产物。别为了"去重"把它们合并。

### 为什么症状反查表单独成一版

**症状不知道自己属于哪个产品。** 「压缩之后 agent 忘了早期约定」「常驻文件加了没效果」这类现象在 Claude Code、Codex、自建 harness 上都成立——它们是**机制层**的问题。

把它们塞进 `claude-code/` 就是用产品边界去切机制层问题，读者在别的栈上遇到同一个症状时根本不会去翻那一版。所以单独成版，按症状组织，每个症状下面再标「在哪些系统上被观察到」。

### 三类体例

| 体例 | 形态 | 例子 |
|---|---|---|
| **条目** | 概念 + 一句话 + 数量级锚点。只放结论与坐标，论证留给教材 | 「卸荷：让信息不进入上下文。与压缩的分界是作用点在进入前还是进入后」 |
| **决策卡** | 场景 / 候选 / 各自的失效模式 / 选择依据 / 诊断信号 | 已有体例，直接复用 |
| **症状反查表** | 现象 → 可能原因 → 去哪验证 | 「agent 反复问同一个问题 → 早期约束被压缩掉了 → 查 compact 触发点」 |

**不编号。** 教材用 `ch-01` 是因为顺序即知识；手册打散才好查，编号反而误导。

**按问题索引组织**，不按知识结构组织。可参照 `sources/papers/surveys/README.md` 的第 4 层「按问题索引」——那套模式已经在项目里验证过。

### 认知层的结构

`domain/` 已从单文件拆成目录——坐标系、系统定位、分歧这三类内容从不需要同时被读，放在一起只会让查概念的人被迫看系统表。

```
domain/
├── index.md        坐标系 + 导航
├── systems.md      各系统的定位（结论；证据在 analysis/）
├── disputes.md     分歧与盲区
└── mechanisms/     机制库 —— 认知层的主体，待建
```

**`mechanisms/` 是认知层真正的大头**：每条机制一张原子卡（是什么 / 解决什么 / 什么时候坏 / 数量级锚点 / 在哪些系统上被观察到）。教材与手册的绝大部分素材从这里出。等第一张卡落地时建目录。**结论在这里，证据在 `analysis/`，两边不互相复制。**
