# ARCHITECTURE.md · 这个项目是怎么设计的

> **本文供外部审查。** 假设读者对本项目的对话历史一无所知，所有术语都在文中解释。
>
> 建议审查重点：**第二节（五个核心判断）** 与 **第八节（已犯过的错）**。
> 前者是设计的地基，后者能看出推理的实际质量。

---

## 一、项目是什么

写一本《Memory 与上下文工程》教材。面向已了解 LLM 与 Agent 的进阶读者，重点是工程化与记忆的深度讲解。

**实质不是写书，是构建认知体系**：

> 构建一套 agent 领域的认知体系，再把它编译成不同形态的产物。
> 认知层（`domain/`）是本体，教材与手册是它的投影。

产物会过时、会重写、会换形态；认知层不会。**当前阶段只做认知层，`book/` 与 `manual/` 是后期的事。**

## 二、五个核心判断

每个判断都附「如果它错了会怎样」——这是给审查者的抓手。

### 判断 1：目录按半衰期切，不按主题切

根级目录表达**性质差异**（读取频率、半衰期不同），`sources/` 内部才表达**类型差异**（形态不同）。

理由：教材主线尚未锁定。主题会变，半衰期不会。按主题切目录是过早的结构化。

> **如果错了**：目录会随主线调整而反复重构。检验方法——看过去一个月目录结构改了几次，如果每次都是因为主题变了，这条就是错的。

### 判断 2：认知层分两层，因为可审查性与可编译性本质冲突

| | 第一层 `domain/`（论述层） | 第二层 `entries/`（条目层，待建） |
|---|---|---|
| 谁读 | 人 + AI | 纯 AI |
| 目的 | 审查结论对不对 | 组装成产物 |
| 形态 | 连贯论证，**带推理链** | 原子条目，按点拆 |
| 冗余 | 允许——铺垫是论证的一部分 | 不允许——每点只出现一次 |
| 顺序 | 有意义（推导顺序） | 无意义（可任意重排） |

理由：人审查一份结论时需要看到推导链，否则无法判断对错；而机器组装需要条目可独立摘取。
**同一份内容不可能同时满足两者**，所以必须分层，不是在同一层里折衷。

关键设计：**链条不在条目里，条目指向链条**——条目保留推导链指针，可自由组装又随时可回溯。

> **如果错了**：`entries/` 建成后发现它和 `domain/` 高度重复，说明两层切得不对，应该合并成一层加双形态。

### 判断 3：目录命名以「AI 会激活什么先验」为第一标准

目录名是给 AI 的一级 prompt，会影响模型的思维空间偏移。选词标准：在资深工程师 / 架构师的语料里有无歧义的稳定含义。

**已排除的名字及理由**：

| 排除 | 理由 |
|---|---|
| `core/` | 工程师语料里几乎总指核心**代码**模块，AI 会以为里面是源码 |
| `atlas/` | 纹理图集（游戏）/ 监控 Atlas（Netflix）/ 医学图谱——激活「图」的先验 |
| `knowledge/` | RAG 知识库，会被当成待检索的文档堆 |
| `spec/` | 规范性条文，会诱导写成规范而非描述 |
| `agent/` | 按主题命名，违反判断 1；且整个项目都是关于 agent 的，无区分力 |
| `ref/` | 三重歧义（reference / git refs / 有人当 refactor），且「分析」不是「参考」 |

最终定 **`domain/`**：DDD 里的领域层专指「核心、与基础设施无关的那层」，AI 看到即知是跨系统的本体知识。

> **如果错了**：观察 AI 实际使用时是否仍会放错文件。如果频繁放错，说明名字激活的先验还是不对。

### 判断 4：引用单向——原料标「回答什么问题」，不标「属于第几章」

流向 `book/` → `entries/` → `domain/` → `analysis/` → `sources/`，**反向引用一律不写**。

理由：章节号随主线变化而失效，问题不会。认领工作交给编译阶段。

> **如果错了**：编译时发现无法判断某条素材该去哪一章，说明纯靠「问题」描述不足，需要加一层弱分类。

### 判断 5：规则按需加载，不进常驻文档

操作规则做成 skill（`.workbuddy/skills/project-maintenance/`），动手时才加载。
常驻文档只有三个：`AGENTS.md`、`domain/index.md`、`THESIS.md`。

理由：规则一直在场，注意力就一直在分。问题不是规则有多少条，是它是不是每轮都必须出现。

> **如果错了**：AI 频繁违反规则（因为不知道要加载 skill），说明按需的触发条件设计得不够显眼。

## 三、目录结构

| 目录 | 判定句（一句话说不清该不该进这里，就是分类错了） | 半衰期 |
|---|---|---|
| `domain/` | 这是我们对领域的**认知论述**（带推理链） | 活，只增不推翻 |
| `sources/` | 这是**别人**写的材料 | 冷，只追加 |
| `analysis/` | 这是我们对**单个外部系统**的完整拆解推演 | 温 |
| `evidence/` | 这是支撑某条**具体论断**的原始摘录 | 冷，按需 |
| `dialogue/` | 这是我们的一次交流：问了什么、怎么推演、否掉了什么 | 热 |
| `notes/` | 这是一个**已拍板**的决定 | 热 |
| `book/` | 这是给读者从头读到尾的教材 | 定稿即冻结 |
| `manual/` | 这是给读者用时查的手册 | 局部可替换 |
| `archive/` | 这是某次会话的原始快照 | 冷，允许重复 |

**分水岭**：`sources/` 是外部世界，其余都是我们的产出。

## 四、编译链路

```
sources/            别人写的材料（论文 / 仓库 / 报告）
   ↓ 拆解
analysis/           单系统的完整推演（人审查）
   ↓ 提炼
domain/             跨系统的认知论述（人审查）── 第一层
   ↓ 原子化
entries/            按点拆的原子条目（纯 AI 读）── 第二层，待建
   ↓ 组装
book/ + manual/     教材（一条路径）+ 手册（多个视图）
```

**教材与手册互不为上下游**，都从认知层直接编译。教材回答「学的时候按什么顺序」，手册回答「用的时候我在什么场景」。

手册按使用场景分多个版本，每版内部逻辑不同：`claude-code/`、`memory/`、`harness/`、`troubleshooting/`。
同一个知识点可在多版出现，位置、详略、配什么决策卡都不同——**这不是重复，别为去重而合并**。

其中 `troubleshooting/` 单独成版，因为**症状不知道自己属于哪个产品**——用产品边界切机制层问题是错的。

## 五、证据三层（颗粒度不同，不互相复制）

| 层 | 装什么 | 颗粒度 |
|---|---|---|
| `sources/` | 外部材料的**全集**（可能还没读） | 整篇论文 / 整个仓库 |
| `analysis/` | 一次完整的拆解推演 | 一篇论证 |
| `evidence/` | **已被引用**的那一小段 | 一段摘录 / 一个数字 / 一条命令输出 |

`evidence/` 与根级文档**同名配对**：`STYLE.md` → `evidence/style/`，`domain/` → `evidence/domain/`。
用命名配对代替显式链接——**链接会失效，同名关系不会**。

## 七、两条值得单独说的产物设计

### 教材 vs 手册不是同一内容的两份排版

| | 教材 | 手册 |
|---|---|---|
| 目的 | 建立认知 | 支持检索 |
| 组织 | 按因果，一条路径 | 按使用场景，多个视图 |
| 顺序是不是知识 | **是**，顺序本身就是产品 | 不是，打散了更好用 |
| 过时方式 | 结构性过时 | 局部可替换 |
| 主力体例 | 论证 + 决策卡 | 条目 + 决策卡 + **症状反查表** |

**手册不是教材的摘要。** 摘要保留路径，而复习的人不需要再走一遍路径——他手里拿着一个具体问题。

症状反查表是手册独有、教材给不了的东西：教材按因果组织没法反查，而东西坏掉时人手里只有症状。

### AI 思维定向写进了 markdown

`AGENTS.md`、`STYLE.md`、`domain/index.md` 都写了「AI 读到这里时应该怎么想」。
例：`domain/index.md` 头部写着「这里装的是判断及其推导，不是信息；**别在这里追求可摘录**」——
防止把第二层的要求压到第一层上。

## 八、已犯过的错（供审查者看推理质量）

同一类错误今天出现了四次：**拿一个好操作的边界，去替代一个理解不了的判据。**

| # | 错误 | 好操作的边界 | 理解不了的判据 |
|---|---|---|---|
| 1 | 给常驻文档设行数上限 | 行数 | 注意力是否被用在正确的地方 |
| 2 | 用产品边界归置症状反查表 | 产品名 | 这是机制层还是产品层的问题 |
| 3 | 把八条规则塞进常驻文档 | 文档在场 | 规则是否每轮都必须出现 |
| 4 | 要求论述层条目原子化 | 可摘录 | 结论是否可审查 |

第 1 条尤其值得注意：我们正准备写「评测为什么不可信」这一章，一边批判指标替代，一边亲手干了一遍。
第 4 条直接催生了判断 2（分层）。

**这类错误的共同形态**：用一个可测的代理量，去管一个不可测的目标。

## 九、未决与已知取舍

**未决**（主线未锁定，这些是待撞的假设，不是结论）：

- 「治理」在 harness 侧是否真的没有对应物——其余五段在 Claude Code 上都有落点，唯独治理不见踪影
- 骨架是流水线（默认放行）还是守门机制（默认拒绝）
- 卸荷不属于六段循环任何一段，它是个负向动作

**已知取舍**：

- 目录全英文。不只是偏好，是**正确性要求**：Windows 下非 ASCII 路径经 `.ps1` / `.bat` 会写坏文件名（`pdf2md.py --out 综述` 曾带着这个隐患）
- 不建空目录。空目录会骗人，让结构看起来比实际完整
- 不建中央索引文件。导航靠各目录入口，中央索引会与内容漂移
- 状态靠目录位置表达，不给文件加 `status` 字段
- 不静默删除。被推翻的说法标 `[已撞]` 保留原句——**走过的死路有价值**

**已知违规（尚未处理）**：

- `sources/以前的/pass.md`：中文目录名，且疑似私人文件，待用户决定
- `archive/` 里的 `outline.md` 尚未提到 `notes/candidate-outline.md`
