# 文档模型：从需要完成的工作推导，而不是从文件名推导

> 作者：Codex / GPT-6 · 2026-09-26。本文是可修订的主题研究，不是给所有仓库颁布的新规范。证据、取样过程与旧稿修正见 [本地材料审阅](research/local-material-audit.md)。

仓库文档的价值，是让下一次行动获得原本缺失的信息：知道目标、找到实现、遵守约定、理解理由、继续未完工作，或判断某个结论究竟来自哪里。文件名只是一个定位线索。`AGENTS.md`、`CLAUDE.md`、`MEMORY.md` 可能被某个客户端特殊处理，但这种运行语义来自客户端及其配置；`ARCHITECTURE.md`、`README.md` 也不会因为标题正确就自动成为当前事实。

由此得到本文的工作选择：**把文档模型定义为一组反复出现的信息责任与维护方式，把文件视为模型的容器。** 同一文件可以承担几种责任，同一种责任也可以由一个章节、一组文件、一个外部问题板或一份结构化数据承担。是否拆分，由实际读取和更新需要决定。这个选择吸收了 [手写草稿末尾转向文档模型的想法](../01docsclassify/draft1.md)，没有保留“坐标决定全部治理属性”的强要求。

## 一、从一次使用推导需要描述的东西

设想 Agent 接到“更换存储实现”的任务。它需要知道现在用什么、接口在哪、哪些性质不能破坏、过去为什么没选另一种方案，以及此次任务实际授权改到哪里。这些问题不会自然收敛成“读所有架构文档”。一份现行架构说明、一条旧 ADR、一份接口定义可能分别提供不同前提。旧 ADR 解释历史，不能自行证明现行接口；接口源码证明某个版本如何实现，不能自行证明这次允许怎样修改。

这给出五个可以逐项问、但不要求制成全仓字段表的问题：

1. **下一次谁要用它完成什么动作？** 人的审查、Agent 的实施、脚本的解析、用户的上手，需要不同的内容密度与精确程度。“给 Agent 看”还不足以区分这些任务。
2. **它怎样被找到和送入使用现场？** 客户端加载、目录探索、搜索命中、入口链接、显式点名、代码调用解析，是不同路径。写下“默认读取”只是作者意图，运行轨迹才说明是否发生。
3. **读到之后应把它当什么？** 当前要求、事实说明、拟议方案、历史理由、原始观测、来源原文，承担不同证明责任。它们可以同页存在，但不能靠读者自行猜测身份。
4. **什么变化会使它失效？** 代码变化、任务阶段变化、用户纠正、指标口径变化、上游新版本、决定被替代，分别触发不同维护动作。“长时间没改”不等于稳定有效。
5. **错误会怎样传播，怎样发现？** 一段每次加载的错误约定可能反复影响行动；一条很少读取但关键的迁移说明也可能造成重大错误。读取频率只是审查优先级的一部分。

这些问题不是相互独立的正交轴。加载方式可以随客户端改变，读者可以重合，生命周期也会转换。它们的作用是暴露具体选择的依据，不是为任意未来文件计算唯一坐标。尤其要保留“作者、维护者、使用者”的区别：AI 起草不等于 AI 已验证，人不亲自编写也仍可能是审查者；一个文件同时服务人和 Agent，并不需要把受众权重凑成 100%。

**作用范围也不能被加载范围替代。** 某个子目录的规则可能因为搜索而被读到，但只适用于该子目录；全项目约定可能要到实施阶段才读取。读入上下文是信息可见性，适用范围是解释条件。这是对 [draft0 的辖域问题](../01docsclassify/draft0.md) 的直接回应。

## 二、可复用的文档模型

以下模型是设计工具，不是穷尽分类。每一节都给出责任、读取与更新触发、失败方式和反例；不要求每个仓库建出全部文件。例子中的文件名表示常见或题中候选容器，不承诺行业统一含义。

### 1. 入口与定位：README、BRIEF、THISIS

**责任。** 帮助首次进入的人或 Agent 判断“这里是什么、能做什么、这次要往哪里走”。定位、最短可用路径和任务导航可以放在同一份 README。`BRIEF` 可以是给决策者看的短简介，也可能是一项设计任务的简报；`THISIS` 如果只是重复 README 的开头，就没有独立维护的必要。

**读取触发。** 首次进入、项目目标不清、要运行或交付、需要确认边界时。不是所有子任务都需要重读整份 README；模块级 README 可以服务局部任务。

**更新触发。** 定位、安装或启动条件、支持范围、主要入口改变。定位段与安装段可以由不同变化触发，但未出现读取或维护冲突时，不必据此拆成两份文件。

**失败与反例。** “README 对外、内部架构对内”只是一种安排。研究项目的 README 可以主要服务未来自己；库的 README 可以解释设计限制；子目录 README 可以是索引。不能把“长 README”与“短 BRIEF”定义成不可交叉的类型。本项目 [README](../../../README.md) 与来源里的 [Agent Notes README](../../../sources/repos/deepseek-harness/.agents/notes/README.md) 已服务明显不同的工作，后者的本次核查见 [L6](research/local-material-audit.md#本次抽核的局部实例)。

**最小可复用写法。** 先说对象与适用范围，随后给能行动的入口。只在另一个受众确有独立交付需要时保留单独 BRIEF，并说明简介事实从哪里维护。

### 2. 协作入口与运行时适配：AGENTS、CLAUDE、GEMINI、部分 local 文件

**责任。** 把当前项目的工作要求、必要背景及进一步读取的路由送给协作者。某些项目把入口限制成硬规则；另一些把它用作架构地图。二者都确实出现在本次样本中：Raven 的 `AGENTS.md` 自述只放硬约束，Tianshu 的同名文件以架构地图开头；这是各项目约定，不能提升为文件名的通用定义。[L1、L5](research/local-material-audit.md#本次抽核的局部实例)

**读取触发。** 由实际客户端的发现机制与项目工作流程决定。需要分别确认客户端版本、起始目录、路径范围、名字与配置，再判断哪些文本进入模型请求。入口中的链接也不等于链接正文已经加载。文件写着“必须读”能表达约定，不能单独证明客户端做了什么。

**更新触发。** 常用操作、适用规则、关键路径、工具接口或客户端适配发生变化。项目事实有一份负责正文即可；多个客户端需要不同入口时，可以采用适配文件、原生导入、生成副本或少量手工镜像，取决于客户端真正支持什么。不要在未确认加载能力前把一种写法称作兼容方案。

**失败与反例。** 把 `CLAUDE.md` 普遍定义成 `AGENTS.md` 的副本，会漏掉两种真实结构：MemOS 的文件明确只管运行时适配；EverOS 的文件直接承载项目概览、架构与工程说明。`GEMINI.md` 也可以自己承担项目入口。这些内容观察不证明各客户端当前自动加载了它们。[L2—L4](research/local-material-audit.md#本次抽核的局部实例)

**最小可复用写法。** 保留这类任务开始前必须知道的少量规则和路由；把需要解释的规则连到负责正文。先分清内容责任与加载入口，再选择“单份正本＋适配”是否值得。多个名字同时存在，不必然意味着重复；不声明副本，也不自动证明它就是权威正本。

### 3. 当前系统解释：ARCHITECTURE、CONTEXT、DESIGN、部分 GLOSSARY

**责任。** 让读者形成足以定位修改影响的系统模型：组件如何协作、状态怎样流动、哪些边界决定行为、哪些约束源于设计理由。架构正文可以保留理解现状不可缺的理由；只有独立追溯价值较高的长篇备选方案和历史争论才需要外置。

**读取触发。** 跨模块改变、首次进入陌生子系统、理解异常、需要判断某条局部规则为何存在。局部修改可以从对应模块说明开始，不要求每轮加载总架构。

**更新触发。** 描述的系统关系发生变化，或新的证据推翻了原说明。修改负责该事实的章节；纯用户文案决定不必同步架构文件。架构若是未来设计，明确标成 proposed、target 或计划状态，不能用文件名伪装成已实现。

**失败与反例。** “架构只写 what/how，绝不写 why”会拆掉理解边界所需的前提。本项目的 [ARCHITECTURE](../../../ARCHITECTURE.md) 就包含结构理由。Raven 的 [CONTEXT-MAP](../../../sources/repos/Raven/CONTEXT-MAP.md) 同时导航与解释关系，不能只当术语表。[L9](research/local-material-audit.md#本次抽核的局部实例)

**最小可复用写法。** 描述一条实际路径，保留关键边界、必要理由及实现定位。图、树和术语表只是辅助手段：只列目录的 TREE 不能替代组件关系解释；有叙事的地图则可能已经承担架构责任。

### 4. 当前约定与判断准则：CONVENTIONS、STYLE、GLOSSARY、部分 TRADEOFFS

**责任。** 保存仍在执行的选择，帮助多次工作保持一致。CONVENTIONS 可以回答内容归属、命名与协作方式；STYLE 可以回答代码或论证表达；GLOSSARY 可以固定本项目术语及与外部用法的差异。TRADEOFFS 若讲“以后怎样取舍内容或方案”，承担的是当前判断准则；若讲“那次为什么放弃 A”，承担的是后面的历史理由模型。

**读取触发。** 将要开展对应写作、修改、命名、组织或选择时。把所有约定置于默认入口，只有在它们经常同时需要时才有收益。

**更新触发。** 采用了新约定、旧约定出现反例、适用范围变化，或实现工具改变。能由既有 formatter/linter 精确决定的格式细节，可以把配置作为负责对象；“何种论证算充分”“为何保持这条边界”等内容仍需要自然语言。

**失败与反例。** 规则不“永恒”；工具配置也不能替代全部写作风格。GLOSSARY 只列同义词而不说明对象，可能掩盖版本或语境差异。把本项目 [TRADEOFFS](../../../TRADEOFFS.md) 当成通用历史日志，会误读它面向后期成品取舍的职责。

**最小可复用写法。** 讲清规则、作用范围、必要理由及有意义的例外。只有一条有用规则时，放入现有负责章节即可；不为拥有 `STYLE.md` 而造一个样式体系。

### 5. 路由与库存：INDEX、TREE、registry、outline、llms.txt

**责任。** 降低找到相关材料的成本，但这些容器仍有不同任务：INDEX 给阅读入口；TREE 展示层级位置；registry 保存稳定标识和可筛选属性；outline 可能安排一篇产物的论证或教学次序。后者若描述未完成内容，还承担计划责任，不能统称“时不变的元导航”。

**读取触发。** 不知道相关材料在哪、要筛选一组对象、要确认缺项或某份产物的组织次序时。已知道唯一目标文件时，可以直接读正文。

**更新触发。** 对象增删、路径迁移、职责变化、入口改变、查询字段口径改变。纯文件树优先从文件系统生成；人工导航主要增加“为什么来这里、何时需要它”的信息。规模并非唯一标准：十条复杂来源也可能需要身份字段，几千份可按路径查找的记录也未必需要另一份手工总索引。

**失败与反例。** deepseek-harness 的 Notes 目录要求用生命周期树和搜索替代中央 INDEX，Tianshu 则有实际索引；这是针对不同本地结构的选择，不能投票得出一个普遍最佳答案。[L6—L7](research/local-material-audit.md#本次抽核的局部实例) `llms.txt` 是帮助 Agent 导航网站内容的提案；本次读取的是 v2。发布这样的文件，不构成某个客户端会读取、优先信任或遵从它的证据。[W3](research/local-material-audit.md#外部一手校准)

**最小可复用写法。** 只保留改变查找行动的说明与属性，链接负责正文。registry 的标识、值域与空值口径比列数重要；把结论再压缩成一张“全局真相表”会产生第二套维护责任。

### 6. 待完成工作与未决问题：PLAN、ROADMAP、PROBLEMS、部分 LIMITATIONS

**责任。** 让协作者区分想做什么、当前执行到哪、被什么问题阻碍。PLAN 通常靠近一次任务的行动和验收；ROADMAP 通常表达优先方向或交付意图；PROBLEMS 表达尚未解决的问题及其条件。它们不是靠过去／现在／未来三个互斥标签来区分。

**读取触发。** 接续任务、判断优先级、估计修改范围、复核承诺或诊断已知问题时。任务结束后，计划可作为历史留存；下一次默认读取应指向当前计划，不能让过期勾选项继续驱动行动。

**更新触发。** 执行进展、授权范围、依赖、优先级、证据或验收结果改变。未来承诺和当前状态要保持可区分；不一定需要建立新状态机。

**失败与反例。** LIMITATIONS 可能是当前能力缺口、暂缓工作、设计上不支持，甚至仅对某个版本成立，不能统一解释成“永远不做”。本次读到的 deepseek 历史记录明确把 Known Limitations 与 Deferred Work 放在同一节。[L8](research/local-material-audit.md#本次抽核的局部实例) Gemini CLI 的 ROADMAP 既有当前原则，也指向动态问题板，并声明不是交付保证。[L4](research/local-material-audit.md#本次抽核的局部实例)

**最小可复用写法。** 对计划说清目标、必要步骤、完成证据与当前阻塞；对问题说清可观察现象、影响条件和已知依据。把项目级问题放文档还是问题板，由协作和查询入口决定，不用“高层问题不能进 Issues”作为规则。

### 7. 决定及其历史理由：DECISIONS、ADR、部分 TRADEOFFS、records

**责任。** 保留当时的问题、约束、采用的方案、重要备选及后果，帮助后续判断应继续、重访还是替代。这里保存的不是“过去说过，所以现在不可违背”，而是“过去在这些条件下怎样判断”。

**读取触发。** 准备推翻旧选择、遇到看似多余的约束、重试被放弃方案，或当前说明不足以解释边界时。

**更新触发。** 提案被接受或拒绝，决定被替代，实施事实需要校正，或发现记录错误。是否保留正文不可变、允许修正路径、还是迁入冻结历史，是项目的历史保留约定。ADR 原始提议本身包含 proposed、accepted、deprecated、superseded 状态，后来的记录可以替代先前决定。[W2](research/local-material-audit.md#外部一手校准)

**失败与反例。** `decisions/` 的名字不授予硬约束地位。单文件适合数量少、常一起读的决定；独立文件适合独立引用、更新和审查，但并不能保证永远没有编号、索引或相同路径的冲突。deepseek active Notes 要更新事实，archived Notes 才冻结；Tianshu 的 ADR 允许改为 superseded。[L6—L7](research/local-material-audit.md#本次抽核的局部实例)

**最小可复用写法。** 记录问题与当时条件、选择及重要替代、后果、当前状态与替代指针。已能由变更本身和现有正文解释的小调整不必再写 ADR；需要长期保留的理由也不能只留在一次会话里。

### 8. 证据与研究过程：EXPERIMENTS、sources、records、原始观测

**责任。** 使后来的人能区分“材料说了什么”“我们做了什么”“据此能推什么”。sources 保存外部对象及版本；实验记录保存问题、设置、操作和结果；分析连接证据与结论。它们可以通过链接组成一条可复查路径，无须把每个引用全文复制进自己的报告。

**读取触发。** 验证关键论点、迁移到不同条件、解释异常、修正已失效结论，或复用方法时。它们是按问题读取的证据，不等于低优先级的“仅供参考”。

**更新触发。** 获得新版本、新观察、复现实验，或发现原记录错误。冻结的实验观测不覆盖；更正与追加观察显式区分。可更新的本地 checkout 则需要版本身份，不能把 sources 目录整体推断成永久不变。

**失败与反例。** 实验不仅包括被废弃的方向，也包括支持当前方案的实验、未成功复现和无区别结果。文件存在只证明存在；“verified”若只核对名字和首行，就不能自动升级为机制或效果已经验证。版本字段相互矛盾时，必须缩小引用范围；本轮已经遇到这一真实问题。[审阅记录](research/local-material-audit.md#样本边界与版本问题)

**最小可复用写法。** 保留待区分的问题、材料或输入身份、实际动作、可检查结果、解释边界和下一次复用入口。这是保存研究过程所需的公开轨迹，不要求保存所有临时检索噪声或每段内部思考。

### 9. 个人与会话连续性：MEMORY、USER、SOUL、local

**责任。** 在需要时把与用户、助手、任务有关的信息带到下一次行动。必须先确认这里写的是运行时数据，还是解释记忆／用户模型的设计文档；同名文件可能承担二者之一。`SOUL` 也可能是助手行为设定，而非仓库规范。

**读取触发。** 由实际持久化与装配机制决定，也可能由显式读取发起。仅把文件命名成 MEMORY，不证明跨会话使用；把 USER 放仓库，也不证明它是所有用户的统一模型。

**更新触发。** 用户纠正偏好、任务状态变化、原信息过期或适用范围缩小。声明是谁的信息、在哪个范围有效，比把它笼统标成“长期记忆”更有用。本项目的会话记忆采用日期、动作与指针，由 [项目入口](../../../AGENTS.md) 规定；这是本地职责选择，不能当作其他系统的普遍结论。

**失败与反例。** 文件内的临时推测可能被反复读取成稳定偏好；项目规则如果同时复制到记忆中，会出现两个现行版本。`.local` 是名字，是否被发现、忽略或版本控制要看具体实现与项目配置；它既不必然临时，也不必然不入 Git。原草稿把 MEMORY 限定成设计说明，与后续定义稿允许存内容相矛盾，不能通过词义争辩解决。[旧稿修正 8—9](research/local-material-audit.md#逐条修正旧稿断言)

**最小可复用写法。** 对真实持久化内容说明主体、来源与适用条件，纠正时修改负责项；对设计说明说明具体存取路径。是否单列 USER，取决于用户信息是否需要独立维护，不由名字清单决定。

### 10. 操作与参考：SKILL、CONTRIBUTING、QUICKSTART、教程、接口手册

**责任。** 支持重复执行某项操作，或精确查询接口和约定。教程为了建立能力，操作指南为了完成既定任务，参考为了查询细节，解释为了理解理由；这是 Diátaxis 可以贡献的区分。[W1](research/local-material-audit.md#外部一手校准) 它不能替代加载策略、历史状态和证据身份的分析。

**读取触发。** 用户正在做某项任务、需要某个准确字段，或需要学习前置技能。SKILL 的发现与加载还依赖其客户端；一份步骤文档并不会仅因改名成 SKILL 就获得自动执行能力。

**更新触发。** 命令、接口、依赖或被支持工作流程改变。实际使用暴露遗漏步骤，也构成修改依据。

**失败与反例。** CONTRIBUTING 可以同时供人和 Agent 使用；安装指南不一定只是 README 的剪短版；法律声明、许可证和漏洞报告政策还有独立消费者与要求，不能因为不常进入 Agent 上下文就归为“旧时代可忽略文档”。这不是要求本研究扩建合规体系，而是拒绝把 Agent 读取频率误作全部文档价值。

**最小可复用写法。** 对操作给前提、步骤与成功判断；对参考给准确字段与版本；对解释保留因果与条件。只有真实任务要求一种独立入口时才拆分。

## 三、容易混淆的几组边界

| 看似相近 | 实际需要问的问题 | 可合并的条件 | 值得分开的条件 |
|---|---|---|---|
| README / BRIEF / THISIS | 是否服务同一个首次进入任务？ | 定位短、维护事实相同 | 独立交付或读者前提明显不同 |
| AGENTS / CLAUDE / GEMINI | 是同内容入口、互补适配，还是彼此独立？ | 客户端支持同一负责正文 | 客户端能力、装配规则或适配内容不同 |
| ARCHITECTURE / ADR | 正在解释现状，还是保留当时选择？ | 理由短且理解现状离不开 | 长期历史、替代关系、独立复查需要 |
| TRADEOFFS / DECISIONS | 当前准则、尚在比较，还是已作决定？ | 同一个决策的完整推理 | 一个是现行原则、另一个是带日期历史 |
| CONVENTIONS / STYLE | 是否有独立读取与更新节奏？ | 少量风格属于同份协作约定 | 写作与代码分属不同工作流，内容已独立 |
| GLOSSARY / CONTEXT | 只需查词，还是必须理解对象关系？ | 词义解释与关系很短且互相依赖 | 术语查阅与架构推理分别频繁发生 |
| PLAN / ROADMAP / PROBLEMS | 行动、优先方向和问题状态是否混为承诺？ | 小项目同页能清楚分段 | 任务执行、对外路线和缺陷跟踪独立变化 |
| INDEX / TREE / registry / outline | 导航、物理结构、查询库存还是产物次序？ | 信息少且每次共同使用 | 有固定字段查询或不同编辑责任 |
| records / sources / evidence | 是来源对象、原始观测，还是作者解释？ | 一次小研究可同页明确身份 | 原件保留、复用或版本需求不同 |

区别责任不等于必须分文件。两项材料分开后，如果每次都需要互相跳转才能理解同一条推理，拆分可能增加了成本。反过来，当前事实、未采纳设想和旧理由长期混在一页且不标身份，会把维护问题转给每个读者。

## 四、格式由读写工作负载决定

以下是选择条件，不是格式排行榜。先看消费者原生支持什么，再看主要操作是连续阅读、字段筛选、嵌套配置、追加事件还是关系查询；最后考虑差分、编辑和复核成本。

| 格式 | 通常适合的工作负载 | 得到什么 | 实际代价与改选条件 |
|---|---|---|---|
| Markdown | 连续论证、例子、代码片段、按章节阅读 | 理由与条件可相邻，链接易导航 | 任意排版不构成稳定机器 schema；固定字段筛选多时用结构化数据 |
| CSV / TSV | 固定列的库存、实验参数或结果；先筛行列再送入上下文 | 表头与记录集中，标准解析器容易选择字段 | 类型、空值和分隔符口径要另定；CSV 可含引号内换行，不能把任意记录当一物理行。[W4](research/local-material-audit.md#外部一手校准) |
| JSON | 机器交接、嵌套结果、客户端原生消费的配置 | 对象、数组和基础值有明确语法 | 重复键名与漂亮打印会改变体积；正文注释不属于标准 JSON 语法；大量连续论证不宜硬塞字符串。[W5](research/local-material-audit.md#外部一手校准) |
| YAML | 人经常编辑、已有消费者接受的层次配置与元数据 | 映射、序列、标量及注释等表达方式 | 解析器和 schema 选择会影响值解释；使用既有消费者需要的子集，别为省几个符号引入复杂技巧。[W6](research/local-material-audit.md#外部一手校准) |
| SQL / SQLite | 多表关联、反复条件查询、索引、事务性更新 | 把过滤和一致性工作交给数据库 | SQL 是语言，SQLite 数据库是存储；数据库文件不适合普通逐行文本审查，必要时提供可再生导出。没有查询或事务需求时不必建库。[W7](research/local-material-audit.md#外部一手校准) |

CSV 的分隔符少，不推出任意 tokenizer、任意数据、任意任务下 token 最低；JSON 键名重复，也不推出总任务更贵。一次可靠的程序过滤可能远比全量读入更重要；一次错误过滤带来的漏读、修复和重试也要算进成本。比较时保持语义和选中信息相同，记录 tokenizer、工具返回包装、查询、读入量、编辑差分与正确性，才知道省掉的是哪一段成本。

同理，XML 标签是语法与解析结构，不是模型“注意力硬边界”。本次没有实验证明 XML 相对 CSV 的通用幻觉改善或固定倍数开销。若消费者原生要求 XML，就按其契约使用；不必为了推测的心理效果把简单清单转换成标签树。

`.xlsx` 在以文本差分为中心的代码审查中存在摩擦，但“所有合并必损坏”“必须依赖 Python”不是成立的排除理由。若实际工作要求电子表格中的公式、原生图表和业务人员交互，保留这种工作界面可能合理；若当前只是固定字段库存，文本表格通常更直接。这里不替既不存在的电子表格需求搭建额外流程。

本地就有一种有用分工：本研究的 [文件清单](../00docslist/index.csv) 用 CSV；[仓库抓取事实](../../../sources/repos/_commits.json) 用 JSON；论证留在 Markdown。这证明混合格式能够表达不同责任，不证明当前三份材料已保持一致——本次还发现版本账本漂移，详见审阅记录。

## 五、把模型用于实际治理，而不再制造一层治理

对一个准备新增的文件，先写一句“缺少它，会使哪次实际工作缺什么信息”。接着去看现有材料是否已经承担这项责任。若有，修它；若没有，再选读者最容易到达的容器。只在材料需要独立读取、引用、更新或交付时拆分。记录一个局部决定，也不要求先创建完整文档注册中心。

当前说明与历史理由可以采用“负责正文＋必要历史链接”。负责正文保留足以理解当前选择的理由，历史记录保留当时的完整取舍与替代状态。改变事实时更新对应正文；不是每追加一条记录都要改 ARCHITECTURE，更不要求同步 README、AGENTS、MEMORY 和 INDEX 中的多份同义摘要。

审查投入由错误的后果、传播范围、变化概率和可发现性共同决定。常读入口值得简洁准确，少读的迁移说明也可能需要细审；“来源只增加”不免除引用准确性检查，“已进 Git”也不把草稿变成事实。必要的结构检查可以发现坏链接和缺字段，却不能证明论证完整或约定合理。

本文给出的是可复用判断顺序，而不是要实施的新规章。下一次真实任务若发现某模型遗漏了必要责任，应改模型；若两份模型在实际使用中没有产生不同选择，就允许合并。模型是否有用，看它能否减少错读、重复维护或信息缺失，不能用文件命名整齐、表格填满或分类轴更少来验收。
