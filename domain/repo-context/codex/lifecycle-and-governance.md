# 怎样维护当前解释、规则理由和历史状态

> Codex / GPT-6 · 2026-09-26。本文是从任务需求与本轮证据推导的工作方法，未通过长期维护对照验证；不作为本项目新增强制规则。

治理的目标不是让每一份文件都有相同表头，而是使变化发生后，下一次使用仍能找到足够且适用的信息。一项维护动作必须接到真实责任：修正事实、改变约定、继续任务、保存理由或复核来源。没有相应任务的元数据，不必仅为“完整”而添加。

## 当前正文与记录：分开的是用途，不是把 why 全部搬走

考虑一个构造例子：项目最初为单用户选择本地文件，后来加入并发更新需求，决定换成 SQLite。现在的系统解释要说实际存储路径、事务边界和迁移状态；历史决定要保留原条件、备选方案和改变的原因。读者不该遍读历代 ADR 才知道现在用什么，也不该为了理解“为什么需要事务”必须跳出当前正文。

因此主文保留**理解和行动所需的当前理由**；记录保存**独立追溯所需的当时条件和选择过程**。是否拆分取决于读写任务。短理由直接同页；历史较长且经常独立引用时再外置。该例是逻辑构造，不是本项目实际采用数据库的建议。

同名目录 `records/architecture/` 可以降低一次查找的解释成本，但不是唯一解。跨主题决定通常不能一一归属到同名树。把它复制到多个目录会制造多个历史版本；一条记录由受影响正文分别链接即可。日期适合表达发生时间，稳定序号适合引用次序，两者都不自动代表现行状态。文件命名规则只需符合实际引用与排序需求。[模型七、八](document-models.md)

## 一条规则的生命周期

这里给出可复用过程，而不是所有规则必须填写的表单。

**出现问题时，先还原失败路径。** Agent 用错命令，可能因为文档过期、工作目录不对、依赖缺失，也可能确实缺少非标准命令提示。在未区分这些解释前追加“永远先读完整手册”，可能修错位置。工具能可靠承担的检查交给工具，文档保留操作入口、适用范围与必要理由；能程序化的约定也可能需要文字帮助发现和解释，不必重复维护完整算法。

**新增时，保留能支持未来修改的理由。** 最少说清适用范围和为何需要。完整的失败复现、被排除解释和试验结果可以放本次记录，并从负责正文按需定位。不是每条拼写约定都需要 ADR；也不应把有决定性价值的理由只留在对话里。E07 的受控维护实验提醒我们区分维护信息和执行信息，但不能据此要求所有客户端把 HTML 注释隐藏或逐条生成注释。[E07 原文条件](research/empirical-evidence.md)

**执行中，看它是否改变了应改变的行为。** “Agent 引用了这条规则”只说明可见或被复述；是否避免原故障，还要检查实际结果。若一条规则使无关任务也触发全仓测试，先缩小触发条件；若漏掉必要任务，修复条件或加载路径。这里的取舍是召回必要前提与避免无关要求之间的任务性选择。

**环境变化时，判断保留、修改还是撤回。** 触发可以是相关代码变更、工具升级、模型替换、用户修正或原条件消失。无需所有文件每月统一审查；长期无人碰但作用广的入口可以另设复核节奏。日历是发现变化的一种办法，不是有效性的来源。

**撤回时，更新下一次会读取的位置。** 只在历史日志写“旧规则已废弃”，却保留现行入口原句，不会自然阻止再次使用。删除当前条目后检查直接入链和仍传播的副本，保留必要的替代指针。记录可以说明撤回，不把当时发生过的事改写成从未发生。

规则生命周期可以结束；并非每个异常都值得变成永久要求。另一方面，“现在看不懂用途”也不是删除依据，应先查它所负责的路径。这两个条件共同阻止无限加规则和无证据删规则。

## 审查怎样分配，而不靠“默认加载就重审查”的单轴

同一段错误的影响取决于它被用到的概率、适用范围、错误后果以及发现和修复难度。下面是推导出的对照，而非量化风险算法。

| 信息 | 可能的传播方式 | 相应复核重点 |
| --- | --- | --- |
| 每次加载的项目入口 | 反复影响很多任务 | 触发范围、是否与当前授权及其它规则冲突、链接是否可达 |
| 很少使用的迁移说明 | 一旦使用影响深且可能难恢复 | 前提、版本、操作结果和恢复路径 |
| 当前架构地图 | 引导定位和修改边界 | 描述是否匹配实现、关系和必要理由是否完整 |
| 历史实验结果 | 经综合后影响后续选择 | 原条件、分母、指标、负结果与外推边界 |
| 可生成的文件树 | 提供位置提示 | 生成方式和新鲜度；不逐项手工重复维护 |

频繁读取不是唯一价值指标。错误传播也不要求引入新门禁：普通文字更正、定向查源、已有测试、链接检查，通常足以覆盖眼前责任。检测坏链接不证明链接内容支持正文；来源哈希相等也不证明论证正确。

## 事实、约定、意图和历史冲突时怎么办

“代码优先”或“文档优先”都太粗。先问冲突句子在做什么：

- 代码实现 A，当前要求 B：可能是待修缺陷，也可能文档已过期。确认当前任务与负责约定，再决定改哪一端。
- 历史 ADR 写 A，当前系统写 B：查替代关系与实施状态；历史真实性不要求今天继续 A。
- 两份来源账本 SHA 不同：不能凭文件名选一份当事实，应回到抓取记录或固定上游内容。
- 计划说“将迁移”，架构说“已迁移”：需要实施观察，不能按“较新文件”自动裁决。

本轮正遇到了第三种冲突，并选择记录而不擅自修复：[六处元数据差异](experiments/results/2026-09-26.md)。该例说明“唯一负责项”是减少重复维护的设计，不是把责任声明当成对真实性的证明。

## 命名：先保护接口，再优化发现

文件名有三种不同作用。

1. **程序接口。** 某个加载器明确匹配文件名、路径或 frontmatter。这类名字的修改必须核对消费者；不能因更好听就换掉。
2. **协作约定。** 本项目把 STYLE 定位为论证规则，把 TRADEOFFS 留给后期成品。这些含义可由正文说明，不需要声称行业都一样。
3. **检索线索。** 文件名、目录名、标题和链接描述帮助选择材料。准确、可区分、贴近任务词汇通常是合理起点，但比较效果仍应测试。

“模型训练中见过所以一定更好”缺少本轮可查依据。可以检验同一正文使用熟悉名称、语义准确名称、任意名称三组后的发现与误解差异；但必须使加载机制相同，否则测试的其实是程序识别而非模型语义先验。这个区分也说明为什么不能把所有指令文件统一改名成 AGENTS。[命名实验](experiments/README.md#行为实验二命名与结构的解混)

目录同样如此。把内部文档都移入 docs 不自动更好；位于根目录也不天然应常驻。是否提供入口、何时加载和谁更新，才决定实际使用。

## 计划、问题与会话连续性

计划是带目标的当前状态，可以由意图变成执行过程，再作为历史保留。无需机械地每变一次时态就搬文件。重要的是让当前入口指向未完成工作；完成时写明结果和未完成项的去处，而不是让未来 Agent 继续执行已完成步骤。

问题记录保存现象和条件，不必提前写死解决方案。路线图表示方向或承诺强度，不能用清单存在推断承诺已定。LIMITATIONS 可以是现有局限、设计排除或待补能力，应逐项说明。[模型六](document-models.md)

会话连续性也应按承担责任定位：短记录可以只存日期、动作与指针；需要恢复的中间状态则要有实际可恢复信息。本项目选择前一种会话记忆约定，研究结论在研究正文维护，避免记忆成为第二份规则库。此处只解释现行分工，不创建或修改个人记忆。

## 一个无需重构全仓的使用示例

假设接到“重构 AGENTS，使以后少读无关文件”的任务，可以先在独立草稿列出每条现有内容负责的行为，抽取一项真实任务，查看实际加载文本与读取轨迹。发现重复加载来自自动 import 时，删一句提示未必改变读入；发现短路由使关键前提漏读时，一味继续缩短也无效。

然后只实施有依据的变化：保留任务开始即需要的前提，把具有明确触发条件的细节连到现有正文；将不可重建的修改理由留到一次记录；核对实际输入，再执行有代表性的任务验收。若没有受控比较，只能报告“结构和可达性已改变”，不能报告“准确率已提高”。本轮为该后续任务准备了方法和对照，未替用户重构现有 AGENTS。
