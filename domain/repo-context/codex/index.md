# Repo-context：让仓库中的信息在正确时点影响行动

> Codex / GPT-6 · 2026-09-26。AI 研究与暂定综合，可纠错；不是新的全仓规范。研究对象包括代码仓库与文档仓库。`codex/` 表示本轮产出者，研究范围不只限于 Codex 产品。

本研究的当前回答是：**repo-context 的核心责任，是在持续变化的仓库与一次具体行动之间，保持一条可发现、可解释、可更新的信息路径。** 文档分类、命名、索引、加载、记忆与历史记录，都是这条路径的不同设计问题。只有先明确什么任务需要什么信息、谁负责它的当前含义、它怎样进入实际输入，才有依据决定文件怎样拆合。

这比“所有仓库应有哪十份 Markdown”更接近用户的原始问题，也让设计有被推翻的可能：如果增加文档没有补足信息、减少查找、支持纠错或保存不可重建的理由，文件数量增加本身不构成改进。反过来，若删去一段长解释使后续反复误解关键边界，仅仅缩短入口也不是进步。下面先建立推理，再给出本轮证据能支持到的位置。

## 一、第一性起点：信息为什么需要被组织

先不假设有 AGENTS、README、记忆库或索引，只有四个前提。

**第一，任务的成功取决于行动与当前目标、实际环境相符。** 一个 Agent 即使流畅遵守文档，也可能实现了旧接口。反之，它可能从代码直接推知结构，根本不需要另读一篇架构说明。文档的贡献必须相对于本来能获得的信息和能力判断。

**第二，仓库状态不等于一次调用的可见信息。** 文件存在于磁盘、被程序读入、被渲染成工具结果、仍保留在当前输入、被模型正确使用，是不同事件。本轮三种 harness 的加载、裁剪和保留方式确实不同，详见 [H02–H16](research/harness-evidence.md)。把它们统称“上下文已加载”会隐藏故障位置。

**第三，信息随时间改变用途与有效性。** 某条规则可能仍在执行，也可能已经由工具保证；某个决定曾经合理，但约束后来改变。历史文件保留当时理由，当前文件解释今天怎么做，两种责任都可能必要。只记录结果无法重建全部理由；只保存历史又让每个读者重新做一次现状归纳。这是后文当前解释与记录分工的起点，不是要求复制两套结论。

**第四，获取、理解、维护和错误恢复都消耗资源。** 文件少不一定易找；文件多不一定少读；字节少不一定模型输入少；模型输入少也不一定任务总成本低。必须把资源单位和任务结果拆开。

由这四点，研究单元应从“某个名字的文件”变成“**某条信息在某类任务中的使用链**”。一个文件可含现行规则、事实与历史例子；一条信息也可在源码、文档、索引和会话里出现。容器边界未必等于语义边界，更未必等于运行时加载边界。[本地实例 L1–L10](research/local-material-audit.md#本次抽核的局部实例) 提供了同名异责和异名互补的反例。

## 二、一个够用而非穷尽的分析模型

把时刻 t 的仓库及外部环境记作 R_t，当前任务记作 q，历史对话与工作状态记作 H_t。加载策略 P 包含客户端版本、配置、工具和检索行为。模型实际获得的输入可写成：

```text
C_t = Assemble(P, q, R_t, H_t, 工具观测)
行动 a_t = Model(C_t)
后续状态 = Execute(a_t, R_t)
```

这是暴露变量的工作模型，不是对所有 Agent 的架构规定。它的用处是提醒研究者：只替换文档却同时改变模型、任务难度和客户端，不能把结果归因于文档；只检查 Assemble，也不能推出 Model 或 Execute 的正确性。

评价 P 时，至少保留一个结果向量：任务完成质量、依据可追溯性、获取与推理成本、延迟、后续维护量。若需要作总体选择，可写出未校准目标：

```text
在实际任务分布 Q 下，使预期任务损失与全生命周期成本可接受。
```

这里故意不给固定权重。一次研究审阅、简单拼写修正、接口迁移对于遗漏、耗时与证据的要求不同。不存在本轮已证明的“最优 100 行”或“固定四轴决定所有治理操作”。也不能把代价简单相加后假装不同单位已经换算。

这个模型导出三个条件判断。

1. **保存多少，不等于默认加载多少。** 完整实验记录值得保留，但可以只在复核时取用；当前必需前提可能很短，却应尽早可见。
2. **路由也是信息。** 指针若没有适用条件，Agent 不知道何时跟随；若条件列得比正文还长，拆分可能没有收益。
3. **文档价值取决于反事实。** 应问“没有这条信息，当前任务会缺什么”，以及“它是否能从更直接、更新鲜的来源低成本得到”。静态重复的目录树与独特的历史约束，价值来源并不相同。

第三点不是“代码能查到就删文档”。代码可能能给出局部实现，却很难直接给出跨模块关系、设计意图或未采纳方案。文档可以提供有损压缩，但压缩的目标是保留任务相关差异。什么差异不能丢，随任务改变；不能从一般信息论直接推导某种文件结构最优。

## 三、分类应能改变行动，但不必替每个文件分配唯一身份

原始材料经历了从“正交轴”到“实用文档模型”的转向。本轮采用后者，并把读取、更新、适用范围、内容身份作为检查角度。[文档模型](document-models.md) 给出十类开放模型，而不是十个必建文件：入口定位、协作适配、系统解释、当前约定、导航库存、待完成工作、历史理由、证据研究、个人连续性、操作参考。

例如，ARCHITECTURE 的核心是帮助理解系统关系，ADR 的核心是保存某次选择的条件和后果。两者可以部分重合，因为必要理由本来就是理解现状的一部分。是否把长历史外置，取决于独立读取与更新需要，不取决于强制的 what/how/why 分割。

同样，PLAN 从意图走向执行记录，并没有在每个阶段都换掉全部内容；INDEX 会随对象和路径变化；sources 中的冻结原件与可刷新 checkout 也不是同一种生命周期。分类应该暴露这些变化，而不是用“永恒”“仅供参考”“只追加”等静态标签掩盖它们。[旧稿修正](research/local-material-audit.md#逐条修正旧稿断言)

本研究也不采用“人已经不读，所以读者不重要”的前提。作者、维护者、使用者、审查者可以不同；人的低频审查仍可能决定一项长期规则是否合理。读取频率影响传播，但不能独立决定审查投入。

## 四、加载机制给出可行边界，不能替我们决定效果

本轮挑选的三个源码对象覆盖不同机制，不代表市场排名：Codex 的项目祖先链与 shell 工具面、Gemini CLI 的专用工具和访问时 JIT、Tianshu 的按节选择与多文件预算分摊。[机制正文](harness-mechanisms.md)

这些差异产生实际约束。沿同一 Codex 祖先链拆分指令，不能绕开累计项目预算；Gemini 的专用读取与 shell 读取可能带来不同附加上下文；Tianshu 的章节结构可以影响裁剪时保留哪些段落。因而“拆文件”“改成表格”“一次并行读完”不能脱离消费者分析。[H03、H09–H15](research/harness-evidence.md)

另一个直接纠偏是：read 工具没有列参数，不等于整个工具面不能投影 CSV。本轮实际解析 134 条账本记录，选出 22 条入口文件后，统一 CSV 序列化由全表 10,579 字节降为 1,750 字节，再选 `id,path` 得 423 字节。这个观察证明了一条可行获取路径，不证明模型会自主选对查询，也没有测 token 或任务成本。[本地结果](experiments/results/2026-09-26.md)

一次读取是否足够，要问保留了哪些任务前提；不是只数工具调用。拆分既可能减少无关材料，也可能使必要理由不可发现。合并既可能消除跳转，也可能使关键内容被裁剪。批处理还能改变每文件预算。因此应先检查最终输入，再做行为比较。

## 五、实证证据为何没有给出一个通用最佳模板

[E01 与 E02](research/empirical-evidence.md) 看似都在研究 AGENTS.md，实际主要结果和任务范围不同。E01 v2 比较任务成功、成本和行为；E02 v2 在受限的小修改任务中报告耗时与输出量变化，却没有完成全面功能正确性评估。二者可以同时成立：“某些任务更快”不等于“所有任务更正确且更省总成本”。本轮不把不显著结果写成已证明完全等价，也不把均值差直接称作因果机制。

长上下文研究给出“输入长度和位置可能影响使用”的理由，但没有为本项目推导出一个跨模型安全行数。RepoCoder、Repoformer 展示检索策略可改变补全表现与成本；其任务、模型与评估范围不等于任意 Agent 修改仓库。它们用于形成假设，不直接决定根目录应有哪些文件。[E03–E06](research/empirical-evidence.md)

维护研究 E07 更贴近“过程要留下什么”：作者在受控环境中测试让维护者获得规则理由；其中维护通道和执行通道被刻意区分。这支持继续研究“保留理由能否改善修改”，不证明把全部历史内联进 AGENTS 会更好。[E07](research/empirical-evidence.md)

当前可以作出的综合推断是：**文档既可能补足任务信息，也可能增加不相关工作；维护理由既可能帮助纠错，也可能增加执行噪声。** 收益方向依赖内容、任务、加载与评价方式。最有解释力的后续对照应区分“找不到信息”“没读到完整信息”“误解其身份”“无法完成实现”，而不只比较有没有一个 AGENTS.md。

## 六、治理的基本单位：负责正文、使用路径与失效触发

从前面的关系出发，治理不需要先建立一座分类数据库。对于一项实际要维护的信息，能够回答以下问题通常已足够：

- 当前含义在哪里负责？若有导出或镜像，怎样从负责项更新？
- 谁在何种任务下需要它，通过什么路径找到？
- 它描述现状、要求、拟议选择还是历史观测？
- 哪种变化会使它需要重新核对？

这里的“负责正文”不是宣称整仓只有一个真相源。实现行为由固定源码及运行观测支撑，目标和约定由当前授权与项目选择确定，历史由当时记录支撑；三者有时会不一致，研究工作正是定位并解释这种不一致。不能用“code is truth”消除意图，也不能用“文档是正本”否认实际行为。

当前正文与历史记录可采用伴随目录，但同名不是强约束：一条决定可能同时影响架构、成本与写作约定。依靠稳定路径、说明和链接即可表达关系，不必复制到三棵历史树。关于规则新增、变更、删除与计划结束的具体流程，见[生命周期与治理](lifecycle-and-governance.md)。

命名需要另作两层处理。客户端识别的名字是接口，不能随意改；普通标题是帮助人和模型找信息的线索，效果仍需检验。本轮找到同名异责，足以反驳名字决定职责；没有训练语料与控制实验，不能断言 THISIS、BRIEF 或 CONTEXT 中哪个天然更适合模型。

## 七、用本项目作例子，但不把研究建议直接改成项目规则

本轮有两项具体观察。文件清单的真实分母是 133 条 verified 文件记录，加一条 absent 占位；来源两个版本元数据文件有六处冲突。本地测量重新检查了 133 个文件的存在与字节数，都与旧账本相符，但字节数相同不证明版本身份正确。JSON 保留了本次完整文件哈希。[测量记录](experiments/results/2026-09-26.json)

这说明库存一致性与内容正确性是不同问题。对于当前研究，足够的处理是缩小受冲突项目结论的范围并保存文件身份；下一次专门维护来源时，再追溯抓取过程并修复负责字段。为研究顺手改写来源账本，会混淆观察时的状态。

同理，本轮在独立 codex 工作区记录旧稿修正，不把其它模型稿原地改写成当前结论。未来整合时可以沿修正记录定向处理入链；本轮已给出可用的主题综合、机制与文档模型，无需先迁移整个既有目录。

## 八、现在可复用什么，下一步怎样推进

可以直接复用的有：按责任分析文件的模型、固定版本机制取证路径、识别论文比较条件的方法、带输入指纹的确定性测量脚本、实例化的实验方案和任务卡。它们都指向能够核查的对象，而不是只留一句“未来应实验”。

尚待检验的关键问题有三个：任务路由能否在保持正确性的同时减少无关读入；怎样保存规则理由才能帮助后续修正而不拖累执行；同一正文不同命名、拆分与加载方式是否改变漏读和误读。对应的干预、对照、结果口径和撤回条件已写入[实验方案](experiments/README.md)。

本轮工作的完成点是把这套解释、证据、修正路径与可复跑材料交付出来。它不是研究终局。若后续对照显示某类任务需要较完整的常驻地图，或者按需路由经常失败，应改策略；不能为了维护“薄入口”的偏好把失败归咎于使用者。
