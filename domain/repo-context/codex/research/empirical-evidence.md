## 研究问题与取证边界

要判断仓库上下文是否值得保留，首先要分开三个问题：它是否改变行为，改变是否完成了真正要求，以及完成要求的总成本是否下降。行为更符合指令、运行更快、通过更多测试是不同结果，不能互相替代。

本轮选择七份原始研究，分别覆盖项目指令文件、输入信息选择、代码检索和维护依据。筛选依据是能否识别实验单位、输入变化、对照与评判方式；不按支持某一架构的程度筛选。这是针对问题的代表性核验，不是系统综述，也不声称穷尽截至访问日的全部研究。

## 七份证据卡

### E01 · 项目指令文件不等于更高的任务通过率

Gloaguen 等，*Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?*，`arxiv:2602.11988v2`，2026-06-23。[版本](https://arxiv.org/abs/2602.11988v2) · [正文](https://arxiv.org/html/2602.11988v2) · [PDF](https://arxiv.org/pdf/2602.11988v2)。定位：§3.2、§4.1–4.2、Table 2–3、§5。

- **设计**：SWE-bench Lite 300 任务/11 仓库；CTXbench 138 任务/12 仓库。Claude Code/Sonnet-4.5、Codex/GPT-5.2 或 GPT-5.1 Mini、Qwen Code/Qwen3-30B-Coder，每条件一次；比较无文件、初始化生成文件、开发者提交文件，后者仅用于 CTXbench。主要结果是补丁通过测试的比例。
- **结果**：无文件对生成文件，两基准分别 `p=.87/.37`；CTXbench 无文件对开发者文件 `p=.21`，开发者对生成文件 `p=.038`。生成文件的平均推理成本分别增加 20%/23%。
- **边界**：Python、指定任务和配置；部分描述/测试由模型构造并人工审核。开发者提交不保证纯人工编写。统计未显著不等于证明等效；也没有衡量所有非功能要求。
- **本研究判断**：它支持把“写了指令”与“任务更成功”分开测；不能据此删除真实的项目约束。必须固定 v2，不能把检索到的 v1 摘要当现行结果。

### E02 · 更快与正确，是两个不同的证据问题

Lulla 等，*On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents*，`arxiv:2601.20404v2`，2026-03-30。[版本](https://arxiv.org/abs/2601.20404v2) · [正文](https://arxiv.org/html/2601.20404v2) · [PDF](https://arxiv.org/pdf/2601.20404v2)。定位：§3.1.1–3.1.8、Table 1、§5。

- **设计**：10 仓库、124 PR；单根 AGENTS.md，任务限 ≤100 改动行、≤5 文件。固定 pre-PR 快照与任务，用 gpt-5.2-codex 配对比较有/无文件。
- **结果**：运行时间中位数 98.57→70.34 秒；输出 token 中位数 2,925→2,440。表中作者定义的总 token 中位数却是 223,707→226,582，不能改写为各类 token 普遍减少。
- **边界**：只抽查 50 任务排除空或明显不完整输出，明确未全面评估功能正确性；文件内容经过筛选，不能代表所有文件。
- **本研究判断**：这是限定条件下的效率证据，不能与 E01 的测试通过率当作同一个因变量，也不能自动换算成总体金钱成本。

### E03 · 位置可以影响读取，但不是通用的字数上限

Liu 等，*Lost in the Middle: How Language Models Use Long Contexts*，`arxiv:2307.03172v3`，2023-11-20。[版本](https://arxiv.org/abs/2307.03172v3) · [正文](https://arxiv.org/html/2307.03172v3) · [PDF](https://arxiv.org/pdf/2307.03172v3)。定位：§2.1–2.3、Figure 5、§3、§4.2。

- **设计**：2,655 个 NaturalQuestions-Open 问题；保持问题与含答案文档，移动其位置、改变干扰文档数量；另测合成键值检索。模型包括 GPT-3.5-Turbo 0613、Claude 1.3、MPT 与 LongChat。
- **结果**：多文档问答出现中部较弱的位置曲线。将查询前后重复，可明显改善键值检索，却未同样消除问答趋势。
- **边界**：这是问答/检索而非现代编码 Agent 任务；信息位置实验不等于项目指令优先级实验。
- **本研究判断**：可复用的是控制位置与长度的方法；它不直接给出“AGENTS.md 必须少于多少行”。

### E04 · 干扰、长度、任务匹配需要分别控制

Hong、Troynikov、Huber，Chroma 技术报告 *Context Rot: How Increasing Input Tokens Impacts LLM Performance*，官方更新日期 2025-07-14，无不可变版本号。[正文](https://www.trychroma.com/research/context-rot) · [发布日期入口](https://www.trychroma.com/updates/research)。定位：Details、Needle-Question Similarity / Results、LongMemEval / Experiment / Results。

- **设计**：18 个模型；扩展 NIAH 采用 8 种长度、11 个位置。另筛得 306 个 LongMemEval_s 问题，比较约 300-token 相关片段与约 113k-token 全历史，使用 GPT-4.1 评判。
- **结果**：相关片段条件更好；该 NIAH 设置下却没有明显位置差异。
- **边界**：相关片段由已知标注及人工调整得到，没有把实际检索失败纳入成本。技术报告不是仓库文档治理实验。
- **本研究判断**：它不能支持统一的“窗口用到 50%/75% 就失效”阈值。与 E03 的位置差别要求保留任务和模型条件，不能都简称为同一种退化。

### E05 · 缺失的跨文件信息确实可能值得取回

Zhang 等，*RepoCoder: Repository-Level Code Completion Through Iterative Retrieval and Generation*，`arxiv:2303.12570v3`，2023-10-20。[版本](https://arxiv.org/abs/2303.12570v3) · [正文](https://arxiv.org/html/2303.12570v3) · [PDF](https://arxiv.org/pdf/2303.12570v3)。定位：§3–5、Table 1–3。

- **设计**：RepoEval 来自 14 个 Python 仓库，行/API 各 1,600 样本、函数 373 样本；比较单文件输入、检索及迭代检索生成。模型为 GPT-3.5-Turbo 与 CodeGen 系列。
- **结果**：GPT-3.5 行补全精确匹配率从单文件的 40.56%，到一次检索 55.31%、两次 56.81%；函数单测通过率 23.32%→38.34%→42.63%。
- **边界**：检索对象是代码，不是治理说明；评测是补全，不是开放的多步修改。Oracle 使用目标真值帮助检索，不能作为部署方案。
- **本研究判断**：反对把“少输入”独立当目标；相关信息的补足与无关信息的削减必须一起考虑。

### E06 · 选择是否检索，与默认总是检索不同

Wu 等，*Repoformer: Selective Retrieval for Repository-Level Code Completion*，`arxiv:2403.10059v2`，2024-06-04。[版本](https://arxiv.org/abs/2403.10059v2) · [正文](https://arxiv.org/html/2403.10059v2) · [PDF](https://arxiv.org/pdf/2403.10059v2)。定位：§3–5、Appendix E.3、Table 8。

- **设计**：训练代码模型判断检索价值，比较不检索、总检索和选择检索；测试包括 RepoEval、CrossCodeEval、CrossCodeLongEval。§4.2 的 RepoEval 写为 32 仓库，与 E05 口径不一致；本轮未对照底层样本，不能合并数字或断定差异来源。
- **结果/核验差异**：Table 8 的 1B 稠密检索 API 补全中，贪心选择加速 71%，ES 却从 71.69 降至 70.82；阈值选择加速 33%，ES 为 72.39。同页正文把“超过 70%”归给阈值选择，与表不一致；此处采用表格条件。
- **边界**：专门训练的策略、代码补全与硬件延迟，不能推出通用 Agent 已能可靠判断何时读文档。
- **本研究判断**：这是测量条件检索收益的先例，不是“按需加载必然更优”的证明。

### E07 · 保留维护依据可能有用，执行输入未必应该一起增长

Chakrabarti，*Why Does CLAUDE.md Keep Growing? Catastrophic Remembering in Agentic Coding*，`arxiv:2608.11095v1`，2026-08-11。[版本](https://arxiv.org/abs/2608.11095v1) · [正文](https://arxiv.org/html/2608.11095v1) · [PDF](https://arxiv.org/pdf/2608.11095v1)。定位：§2–4、Table 2、Limitations、Appendix B.3 / C.6 / D.4。

- **观测**：1,867 仓库的指令演化；重写/迁移规则删失 77.3% 的消亡记录。有限历史观察与形式模型不能证明真实仓库必然无界增长，也不能唯一识别遗忘的因果作用。
- **干预**：inverse IFEval，Haiku 4.5 为维护者/执行者；2–3 条约束、184 worlds×3 seeds、15 轮，51 轮仅 1 seed。注释只供维护者读取；C.6 的不剥除注释消融仅 1 seed。
- **结果**：WildIFEval 的 64 worlds 被人为加入 16 条干扰；3 轮后，对照/注释组的**逐条约束满足率**为 50.4%/62.0%，即 +11.6 百分点，按 Haiku 4.5 判分。无干扰时未见一致增益。
- **关键条件**：B.3 通过搜索找到五项共同条件才产生组间差异：模糊失败、通过反馈删失、隐藏约束 ID、不要求简短、至少 10 轮。完整披露验证规则则差异消失。
- **本研究判断**：这支持检验维护通道和信息缺失的作用，不能要求所有项目逐条加注释；“最小覆盖”与指数删除成本仍依赖建模假设。

## 结果为何看似冲突

以下为本研究的解释框架，不是论文共同声称的结论。

**先核对比较的问题。** E01 与 E02 在模型、任务大小、文件筛选、指标和验证方式上不相同。它们暂时不能作“谁推翻谁”的二选一：更快完成一项未全面验证的修改，与更高概率通过独立测试，本来就可同时不成立或只成立其一。将“有无文件”做配对干预，比横向比较采用/未采用文件的仓库更接近因果问题，但仍只识别该处理包在选定条件中的效应；无法从中拆出每条指令的作用。[E01](#e01--项目指令文件不等于更高的任务通过率) [E02](#e02--更快与正确是两个不同的证据问题)

**再核对是否增加了任务所需的信息。** 用已知答案位置构造短输入，是理想选择器；实际按需读取还可能漏读。反之，单文件缺少定义时，取回跨文件代码可能补上完成任务的必要前提。因此“输入越少越好”与“上下文越全越好”都遗漏了相关性和选择误差。该解释与 E03–E06 相容，但不是它们已验证的仓库文档组织方案。[E03](#e03--位置可以影响读取但不是通用的字数上限) [E04](#e04--干扰长度任务匹配需要分别控制) [E05](#e05--缺失的跨文件信息确实可能值得取回) [E06](#e06--选择是否检索与默认总是检索不同)

**最后核对谁读取维护记录。** 保留一条约束的由来，可以服务日后的修正；执行者此刻是否需要该由来，是另一个问题。E07 把二者在实验中分开，提供了值得测试的设计，但不能自动证明本项目应采用某种注释语法或每次加载全部理由。[E07](#e07--保留维护依据可能有用执行输入未必应该一起增长)

## 可复用的核验方法

### 从一句主张退回一个可检验问题

1. 把“提高效果”换成可观察结果：任务通过率、需求违背、查找时间、总 token、墙钟时间或后续维护工作量。
2. 写明处理的最小单位：一份文件的存在、某段内容、加载位置、读取触发规则，还是整套 Agent。文件名相同不代表处理相同。
3. 给出未接受该处理时的对照。对照本身若缺少任务必需信息，需说明比较到底在测信息量、组织方式还是路由。
4. 确定推断单位。任务、仓库、模型调用、指令、world 和 seed 不互换；同仓库的任务也不能自动当作相互独立。
5. 先看方法、表注和附录，再读作者解释。记录原始分母、单位、均值/中位数、百分比/百分点，并核对最优数字对应哪一行。
6. 寻找最直接的替代解释。更短是否只是提前放弃？更多测试是否是要求的一部分？“选择有效”是否依赖真值标签？维护效果是否依赖特殊输入通道？
7. 比较版本。标题相同但版本不同，结论口径、数据集和显著性可能改变。固定所用版本，不以搜索摘要覆盖正文。
8. 在新证据无法区分解释时保留分歧；写出下一项能区分它们的观察，不以更多转述代替实验。

可复制的证据卡模板：

```text
编号 / 作者 / 标题 / 固定版本 / 日期 / 原文定位：
研究问题与纳入理由：
实验单位、数量、抽样限制：
模型 + Agent/harness + 解码/预算条件：
处理与对照；哪些条件保持相同：
指标及判断器；是否有独立正确性验证：
结果（单位、分母、区间、表格位置）：
作者解释：
本研究可接受的较窄解释：
替代解释与反例；什么证据会推翻/缩小它：
阅读范围；未核部分；作者报告/本项目复现：
```

不要求每项都填一个猜测；未报告、未读取、未复现应保留为空缺。卡片是防止混淆的阅读工具，不是增加一道必须过完的项目门禁。

### 将文献启发变成后续小实验

下面是**实验建议，未执行**。先选择一种真实任务与一个当前模型配置，完成最小配对试验；只有出现可解释差异时再扩大。

| 待检验命题 | 最小对照 | 需要同时保留的结果 | 使解释失败的观察 |
|---|---|---|---|
| 项目独有约束能减少重复纠正 | 当前说明 / 仅删去该约束；任务确会触发它 | 功能结果、约束违背、人工纠正次数、成本 | 保留约束不减少违背，或只是增加无关工作 |
| 入口指针可用更少读取完成定位 | 全文内联 / 短入口＋链接；信息源相同 | 是否找到必要材料、实际读取内容、完成质量、总调用成本 | 路由频繁漏读，或多跳读取成本抵消节省 |
| 历史理由帮助后继维护者删除过时规则 | 规则正文相同，有/无附带原始原因与观察记录 | 删对/删错、残留规则、维护时间；执行输入另行控制 | 只压短文件，却使有效要求丢失 |
| 任务无关内容会干扰本项目任务 | 相同关键依据，加/不加固定的无关材料 | 证据引用正确率、遗漏、成本；保持难度与预算 | 增加材料并未造成差异，或改变的是任务难度 |

报告必须包括失败和无差异任务；不能只保留有利演示。对模型采样、缓存、任务顺序和同仓库相关性作与实验规模相称的控制。若还没有稳定的正确性判断器，先记录逐项可审查结果，不生成一个貌似客观的总分。

## 本轮留下的可改写判断

本研究目前采用的工作判断是：仓库上下文的价值应按它补足了什么、改变了什么行动、产生了什么可验证结果来判断；压缩、检索和记录理由都是可选手段。七份材料不足以把任何一种固定目录、固定行数或固定加载比例确立为普遍最优方案。

下一轮优先检验本项目真实任务中的必要信息是否能被找到，以及约束的由来是否能帮助正确修正；无需为了复刻论文的规模而先构造庞大的评测设施。
