# 实验：已完成的确定性测量与待执行的行为比较

> Codex / GPT-6 · 2026-09-26。已完成与待执行严格分开。未调用付费模型，未运行三个完整 Agent 客户端，未声称任务成功率提升。

## 已完成：账本、查询与格式测量

[probe_repository.py](probe_repository.py) 只读现有来源与清单，使用 Python 标准库，保存输入哈希、Git 基线、运行时间、逐文件哈希与结果。它回答四个可确定的问题：

1. 现有清单的记录分母和状态分布是什么？
2. 同一数据先筛行再选列，实际输出减少多少？
3. 同样的选中字段在四种表示中占多少字节？
4. 两个来源版本文件是否一致，清单中已登记文件是否存在且大小相符？

另有两个构造示例：带引用字段的 CSV 不可用裸逗号/物理行解析，字符数与 UTF-8 字节数不等。这些只涉及确定性表示与工具能力，没有测模型理解。

从仓库根复跑，选择一个未使用的输出前缀以保留原观察：

```powershell
python domain/repo-context/codex/experiments/probe_repository.py --output domain/repo-context/codex/experiments/results/replication-01
```

也可用 `--root` 指定另一份保持同样输入布局的仓库。脚本不刷新 checkout、不修复账本；新结果变化应先比较 `inputs.sha256`。运行时间与 Git HEAD 随运行变化，其余确定性值仅在输入相同时可比较。Python 内置 `assert` 检查格式往返与构造反例，因此复跑不使用 `python -O`。

本次结果见 [可读报告](results/2026-09-26.md) 与 [原始 JSON](results/2026-09-26.json)。最重要的观察：134 条记录含 133 个 verified 文件与一条 absent 占位；文件存在与字节数复核均通过，但两份版本元数据仍有六处不一致。格式小样本的 CSV 更短，只能归于这 22 条两字段记录；不是 CSV 的通用性能证明。

## 行为实验一：路由收益还是必要信息丢失

**问题。** 同样可用的项目知识，默认全文加载与任务路由读取，在什么任务上产生差异？

**实验单位。** 一项任务在一个固定仓库状态、固定模型与客户端配置下的一次独立尝试。不同重复 seed 不当作独立仓库样本。避免在同一持续对话先跑一种条件再跑另一种，让历史泄漏答案。

**第一阶段三组。** A 为不添加项目专用说明，保留相同代码、任务与工具；B 为同一份说明全部默认可见；C 为短入口加条件路由，完整说明仍可获取。A 用来估计新增信息的总效应，B/C 比较路由策略。第一轮不同时改命名、格式和规则内容。无项目说明不意味着删除系统提示、工具契约和测试要求。

**挑选任务。** 从 [五个任务卡](tasks.jsonl) 开始；它们是可实现的设计样例，不是已经存在的评测数据集。先给每个任务建立隔离 fixture、参考实现/答案和功能测试，再执行 Agent。包括一个简单负对照、一个需非标准约定、一个跨模块关系、一个历史理由和一个纠错任务；这种有目的取样只能分析机制，不能代表真实任务频率。

**固定比较。** 记录任务输入与仓库 commit、模型准确标识、客户端版本、配置、工具、预算、测试方式。将条款身份与内容保持一致，内容变化用哈希检查。组间仅改变默认入口和取得正文的方式；C 新增的路由文字本身属于干预成本，不能从费用中扣掉。

**主要结果。** 先看任务实际正确性：代码任务跑功能测试并检查必要行为，文档研究任务按预定义事实与引用标准审查。再分别报告完成用时、input/output/cached tokens、实际计费、读取回合、无关操作和关键前提覆盖。不将“少输出”当成功，不把因失败提前退出的低成本当效率。

**统计与解释。** 按任务配对比较；成功率给成对差异与区间，成本保留所有尝试并另列成功尝试。多仓研究以仓库/任务聚类，避免把 seed 数量当新增任务。先小规模确认 fixture 和评分有效，再按目标最小实际差异与观测方差决定样本数，不凭空规定一个万能 n。报告每项任务差异，避免总体均值掩盖简单任务获益、复杂任务受损。

**撤回条件。** 若 C 反复漏掉必要前提并损害正确性，撤回这类任务的“短入口优先”；若 B 并未增加无关读取且更可靠，保留整体说明可能更合适。若 A 已能低成本恢复同样信息，入口摘要的价值应缩小到确有缺口处。若置信区间宽，则报告不确定，而非证明等价。

**失败诊断。** 对失败轨迹依次区分：材料不存在／未发现／未选择／被裁剪／身份误解／已有信息却实现失败。这个分类只解释观察，不替代成功指标。必要时做一次后续干预“明确提供缺失信息”来区分获取瓶颈和能力瓶颈，不能凭模型自述猜根因。

## 行为实验二：命名与结构的解混

**问题。** 熟悉名称是否帮助找到并正确使用信息，还是仅因客户端识别特殊名字？

先固定客户端不会自动处理的普通文档，正文与位置深度相同，分别用熟悉名称、语义明确名称、任意名称。文件名是唯一命名干预，随机分配任务版本，清除上一条件历史。评估发现成功、首次正确定位用时、无关读取和身份误解。

再做第二个单独比较：相同内容一个文件与按任务拆分两种结构，提供等价导航说明，记录全部正文是否真正可达。不要一次把 `AGENTS.md` 改成随机名字再得出“模型偏爱 AGENTS”，因为自动发现已经改变了实验条件。也不要把文件数的效果与少了一半正文的效果混为一谈。

**撤回条件。** 名称差异在固定工具面下消失，说明此前差异更可能来自加载机制；结构优势只在少量特定任务存在，则限定到该任务范围，不宣布全仓统一命名或分片规范。

## 行为实验三：保留规则理由能否改善后续维护

**问题。** 上下文改变后，维护者能否正确删改规则，且执行者是否受到无关历史干扰？

用同一组明确规则和可检查的约束变更，比较：只有当前规则；规则加可按需取得的理由记录；规则与理由全部常驻。维护任务与执行任务分开评分。每条规则的实际需要由 fixture 中的版本与测试确定，不由维护 Agent 自己判断自己对。

维护结果看该删是否删、该留是否留、适用范围是否更新；执行结果看新任务正确性和多余工作。记录维护者是否真的读取理由。若理由被程序剥除，应明确其只对维护者可见；不能一边采用这种人为瓶颈，一边外推到所有普通项目文件。[E07 的适用条件](../research/empirical-evidence.md)

**撤回条件。** 理由没有改善修改，或增加噪声使执行明显受损，说明当前内容/获取设计不适用。应继续区分理由质量、可发现性与模型能力，而非用更长记录机械修补。此实验不要求每条规则都产生永久 ADR。
