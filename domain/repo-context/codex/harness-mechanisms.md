# Repo-context 如何真正进入模型：三种 harness 的固定版本机制

作者：Codex / GPT-6 · 日期：2026-09-26

性质：AI 研究稿；以静态读码为主，另做一次本地 CSV 投影观测。未运行三个 harness，未做模型行为、token 计费或任务成功率实验。

本文回答一个比“应该写哪些文档”更先行的问题：**一个文件必须经过什么路径，才可能影响一次 Agent 行动？** 在本轮核对的实现中，文件名只是入口条件之一；工作目录、工具选择、信任状态、已加载集合、预算和历史保留方式都会改变最终输入。因而 repo-context 的组织单位不能只按磁盘上的文件计算，还要按实际加载路径计算。

来源定位、实际命令、失败查询和判断修正见[机制研究记录](research/harness-evidence.md)。本文中的 H 编号链接到该记录，不将旧稿当作机制依据。对照范围为 Codex `75e0e0aad97a86138b8b1ec87d9b544b4a35ecbf`、Gemini CLI `bedef96ef42905bd84a86dbec021c706168e7e2f`、Tianshu-harness `79c10d30ba4fff8aaccfed30410d75050cecb451`；不是三者的无版本产品承诺。[H01](research/harness-evidence.md#h01-版本与本地文件核对)

## 1. 第一性拆解：读取不是一个动作

这里采用一个工作分解，而非声称行业存在统一管线：

1. **发现**：枚举哪些文件、技能或资源可能相关。
2. **选择**：依据作用域、名字、用户点名、工具参数或策略留下哪些候选。
3. **读取**：把磁盘字节或远端资源取入程序。
4. **裁剪与渲染**：按行、字符、字节、预算或结构形成返回内容。
5. **注入**：内容进入项目指令片段、系统提示、普通工具结果或其他消息位置。
6. **继续保留或失效**：随后是否重读、去重、替换、摘要、压缩或丢弃。

最后才是模型是否注意、正确解释并据此行动。前五步的源码可以证明信息有机会进入输入，不能证明第六步后的有效使用。反过来，程序曾读完整文件，也不能证明完整内容曾发给模型：Codex 先读取项目文档再按累计字节预算截断；Gemini 的文本读取先得到完整字符串再选行和裁长行。[H03](research/harness-evidence.md#h03-codex-项目指令累计预算)、[H10](research/harness-evidence.md#h10-gemini-read_file-的两种截断)

这一分解给出两个可复用判断。第一，磁盘 I/O 成本、工具往返成本、模型输入量和任务错误成本必须分开；只观察其中一项不能替代其他项。第二，“已加载”的含义必须附着于位置与时点：进程内存中存在、当前提示里出现、较早工具结果里出现，都是不同状态。

## 2. 项目指令：三种作用域与裁剪方式

| 环节 | Codex | Gemini CLI | Tianshu-harness |
|---|---|---|---|
| 发现与选择 | 从项目根到当前工作目录，每层按候选文件名优先级取一个 | 初始化按 workspace roots 向上发现；访问更深路径时还可 JIT 发现 | 此处核对的 loader 读取当前 `cwd` 下 `AGENTS.md` 与 `.rivet.md` |
| 文件名 | `AGENTS.override.md`、`AGENTS.md`、配置的 fallback 顺序 | 默认 `GEMINI.md`，实际名称由配置集合提供 | 上述两个固定名字 |
| 读取与组合 | 选中的路径按祖先到子目录读取并组合；普通分支加入分隔标记 | 读内容并处理 import；初始化分组，JIT 结果另行返回 | 两文件读取后连接；可先去除与 codebase-index 重复的首张表 |
| 本轮确认的预算 | 项目文档合用 `project_doc_max_bytes`，默认 32 KiB | 所读初始化 loader 内未见同型累计字节限额；这不等于全系统无限制 | standard 项目指令块 8,000 字符，子代理覆盖为 4,000；profile 可改变 |
| 裁剪策略 | 用剩余额度保留当前文件前缀，额度耗尽停止后续文件 | 初始化正文与工具输出是不同路径；JIT 若附在工具结果，受结果路径约束 | 按章节优先级挑选、恢复原顺序，再做最终块截断 |
| 注入位置 | `AgentsMdState` 构造上下文用户片段，状态变化可产生替换/移除片段 | 初始化内容进入系统提示的 context 段；JIT 内容附于工具结果 | `<project-instructions>` 进入稳定前缀块 |

表中事实分别见 [H02–H04](research/harness-evidence.md#h02-codex-祖先发现与每层择一)、[H08–H09](research/harness-evidence.md#h08-gemini-初始化与-import)、[H13–H14](research/harness-evidence.md#h13-tianshu-本目录两文件读取)。

### 2.1 Codex：拆到子目录改变相关性，不解除累计预算

Codex 的 `load_project_instructions` 先设置一个 `remaining`，传给各环境的读取过程，并在得到条目后递减。每个环境内部也逐文件递减同一份剩余预算。预算是项目文件内容的累计量，不是每文件赠送一次 32 KiB；用户/线程指令走单独字段，不能把这个数推广成整个 prompt 的上限。[H03](research/harness-evidence.md#h03-codex-项目指令累计预算)

**逻辑算例，未运行 harness：** 如果已选中的根级文件恰好用完项目预算，后续子目录文件不会因“更具体”而自动获得额外空间。把同样的 40 KiB 内容拆成祖先链上两份 20 KiB 文件，累计预算仍会截断。拆分可以在不同 `cwd` 下减少无关分支被选中，但只有选择集合改变时才获得这种收益；沿同一链全部注入时，文件数增加本身没有节省正文。

本轮官方网页也出现了值得保留的表述差异：AGENTS guide 说 combined，advanced config 说 each。固定源码支持累计解释。不要依据网页中“拆到嵌套目录”的建议，推断拆分能绕过同一路径的累计上限。[H17](research/harness-evidence.md#h17-官方文档表述差异)

另一个边界是更新。该版本 `AgentsMdManager` 用环境选择与项目信任状态判断是否重新发现仓库指令，并缓存已加载结果；状态渲染还会比较前后快照。它不是“每步无条件把磁盘全文再加一遍”。仅修改磁盘文件是否在某个宿主里立即生效，需要继续检查宿主如何刷新或重建会话，不能从文件保存成功推出。[H04](research/harness-evidence.md#h04-codex-缓存与注入)

### 2.2 Gemini CLI：访问路径能触发新指令

该版本 `read_file` 在完成文件读取后调用 `discoverJitContext`。JIT 选择包含目标的最深 trusted root，从访问路径所在目录向上查到边界，再用已加载路径/文件身份去重，将新发现的项目内容附加到当前工具结果。`read_many_files` 也会对涉及目录顺序发现，避免共同祖先重复注入。[H09](research/harness-evidence.md#h09-gemini-jit-与已加载状态)、[H11](research/harness-evidence.md#h11-gemini-多文件与工具结果裁剪)

因此，项目指令的实际集合不仅由会话起点决定，还可能受 Agent 的探索路线影响。**推断：** 根文件需要提供可发现的导航；仅把内容放到更深目录，不保证 Agent 会走到那里。反过来，一旦某次工具调用触发 JIT，新增的指令与文件数据一起进入结果，下游结果裁剪也需要被纳入覆盖检查。

“JIT 去重”也不等于“后续始终可见”：这里的集合记录发现/装载状态，不是对每一轮模型输入的全文可见性证明。本轮没有运行压缩或恢复实验，不据此断言加载集合和保留历史之间不存在缺口。

### 2.3 Tianshu：标题和表格结构可以改变被保留内容

它提供了与前缀截断不同的样本。项目指令在预算不足时按 `#` / `##` 分节，将章节分为 Gate、Prose、Reference，再按优先级选择，最后恢复原文顺序。分类器先检查表格比例，随后检查标题/正文中的规则词。这不是语义完备的重要性判断，而是一组固定启发式。[H14](research/harness-evidence.md#h14-tianshu-按节选择与真实预算)

**逻辑反例，非模型实验：** 一个表格占比达到 40% 的章节，即便含“必须”，仍可能归入 Reference；把同一规则改写成散文，可能改变其保留优先级。因此，文档结构有时会改变传输选择，而不仅改变模型阅读体验。应先用真实裁剪器检查最终保留文本，再讨论哪一种排版更好。

旧稿引用的 6,000 字符是诊断函数生成建议的条件。真正渲染预算位于另一处：standard 为 8,000，子代理 4,000，完整配置还可调整。诊断阈值、传输裁剪阈值和模型性能阈值是三类东西。[H14](research/harness-evidence.md#h14-tianshu-按节选择与真实预算)

## 3. 专用读工具与 shell：比较完整工具面

Codex 此次核对的 core 工具注册路径包含 `exec_command` / `write_stdin`，未见内建通用 `read_file` 的注册。该说法限定在已检索的 core，不能扩成“Codex 永远没有文件工具”：MCP、扩展与特定宿主可以增加工具；技能还有专用的资源读取路径。[H05](research/harness-evidence.md#h05-codex-shell-工具面)、[H06](research/harness-evidence.md#h06-codex-技能分来源加载)

有 shell 时，模型可以先调用现有解析器投影字段，再把选中的输出返回。因此，“原生 read schema 没有列参数”只说明这一个接口不提供列投影，不能证明系统必须返回 CSV 每列。本轮使用项目账本的三行做了可复核观测：同样用 `ConvertTo-Csv` 序列化，六列为 509 UTF-8 字节，两列为 99 字节。这个结果只证明本机 PowerShell 可以完成该投影；不证明 Agent 会稳定选对命令，也不把字节差当作 token 或总成本差。[H18](research/harness-evidence.md#h18-本地-csv-列投影观测)

专用读工具仍然提供不同的机制价值。Gemini `read_file` 暴露 `start_line` / `end_line`，会生成续读提示并触发 JIT；已检索的 `shell.ts` 未见 JIT 调用，且可按配置将 shell 输出交给摘要器。即使两条路径打印同一文件，也不能默认两者进入上下文的内容与附带状态相同。[H10–H11](research/harness-evidence.md#h10-gemini-read_file-的两种截断)

读取限制也必须沿调用链读到底：

- Gemini 文本默认返回最多 2,000 行；显式 `end_line` 在该函数里不再受默认行数限制，但单行仍截到 2,000 字符。随后 scheduler 对字符串或数组中的单个文本 part 使用 64 KiB 上限。前者不是全局模型输入上限，后者也不能简化成“整次多文件调用只有 64 KiB”。[H10–H11](research/harness-evidence.md#h10-gemini-read_file-的两种截断)
- Tianshu 多文件读取最多取传入列表的前 5 个，将本次模型读取预算除以文件数后逐文件应用。少一次调用不保证每个文件得到同样完整度；文件大小不均时，均分预算也可能留有未被大文件使用的份额。[H15](research/harness-evidence.md#h15-tianshu-read_file-的状态和分摊)
- Tianshu 的重复读取还可以依配置返回引用；若引用已经服务一次而模型仍重读，则退回内容。这说明“读过”与“模型现在还能看到”在实现中被当作需要恢复的状态差异，而不是天然等同。[H15](research/harness-evidence.md#h15-tianshu-read_file-的状态和分摊)

## 4. Skill 的渐进披露发生在哪一层

三者都能先向模型展示描述、再给正文，但“渐进”不等于程序只在激活后才读磁盘。

| 系统 | 发现阶段 | 正文进入模型的路径 | 不能从名称推断的事 |
|---|---|---|---|
| Codex | 元数据目录与来源 locator；加载器可已读取文件以解析元数据 | 显式提及的 host skill 可由 core 构成指令片段；executor/cloud 有条件注册 `skills.list` / `skills.read`，后者可分页 | 不是统一“无工具”，也不是一个任务文本匹配函数包办 |
| Gemini CLI | loader 读取并解析 SKILL.md，包括 body；系统提示先列名称、描述、位置 | `activate_skill` 返回 body 与资源树，并把技能目录加入可读 workspace | 进程已持有 body，不代表模型已收到 body |
| Tianshu | 注册表存技能；发现块按触发词排序并在描述预算内挑选 | `skill` 返回 body，已调用技能还可出现在动态附录；`complete=true` 停止后续重新注入 | 描述预算允许省略候选，不能保证所有技能都在可见清单 |

具体实现见 [H06–H07](research/harness-evidence.md#h06-codex-技能分来源加载)、[H12](research/harness-evidence.md#h12-gemini-skill-加载与激活)、[H16](research/harness-evidence.md#h16-tianshu-skill-目录与重新注入)。

需要特别修正旧稿对 Codex `detect_implicit_skill_invocation_for_command` 的解释：该函数分析 shell 命令中的技能文档读取与脚本路径，不是在这里对任务描述做语义匹配。模型收到的使用说明可以要求它按描述选择技能，那是另一种选择机制。把可见目录、选择提示、显式提及注入、命令访问检测混成“skill 自动匹配”，会掩盖应该验证的不同环节。[H07](research/harness-evidence.md#h07-codex-隐式检测的真实含义)

## 5. 单文件与多文件的成本能推到哪里

令一个任务需要的材料总量为 `R`，进入输入的无关量为 `N`，路由/边界/工具返回包装为 `O`，补读与错误恢复成本为 `E`。这只是拆解记账口径，不是已校准的优化公式。文件拆分只有改变 `N`、`O` 或 `E`，才会改变读取效益；同样正文全部拼入时，无法凭文件数推出节省。

可从本轮机制得到的条件判断是：

1. **自动拼接场景**：按作用域拆分能让不同任务命中不同集合；同一祖先链全部命中时，正文仍合计且共享预算。
2. **按需读取场景**：索引加任务路由可以少取无关内容，但路由必须可发现、规则描述足以选择，遗漏关键前提会转化成补读或错误成本。
3. **多文件批量场景**：批处理减少的可能是工具往返，不必然减少输入量；它可能均分预算，也可能逐 part 裁剪，应核对具体实现。
4. **重复任务场景**：稳定前缀、缓存命中、历史裁剪、引用恢复会改变总成本；本轮没有请求级 token/缓存记录，不能判定哪个样本便宜。
5. **表格与长行场景**：长字段既可能被一行截断，也可能通过解析器选列避免传输；格式选型要同时考虑消费者可调用的工具和任务查询方式。

由此，暂不采用“拆分零成本”“固定 N 行最优”“没有 read_table 就无法投影”“某个阈值就是性能悬崖”四种结论。适合当前研究的下一步是：为具体任务固定 harness、版本、配置与读取策略，检查最终模型输入，再测成功率、证据覆盖、补读次数和真实计费。[研究记录中的复核步骤](research/harness-evidence.md#可复用复核步骤)可作为机制检查模板；模型实验应另列实验方案并保存请求与结果。

## 6. 本文边界

本轮重建了三种可读实现的项目指令、主要文件工具和 skill 路径，没有覆盖所有宿主、插件、自定义配置或模型。只对三个代表文件做了上游固定 commit 内容比对，其余文件使用本地已登记快照；没有把仓库测试的存在说成测试已通过。历史压缩后的指令存活、实际选择错误、缓存计费和同任务性能尚待运行观测。已有旧稿的修正只在本研究中明确记录，未改写旧稿或来源元数据。
