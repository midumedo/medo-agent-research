# 证据缺口与重开条件

本文件把“已经能从 00 说什么”和“还不能说什么”分开。缺口不是模型失败，也不是把未检查的材料判为不存在；它们是下一轮研究的入口。

## 当前证据边界

### 已能确认

- `00docslist/index.csv` 在 2026-09-25 的取证范围内登记了 133 条 `verified` 实例和 1 条 `claude-code` `absent` 占位；字节数与首行摘要可由 00 的脚本和快照规则复核。
- 00 的仓库明细和研究报告足以支持若干正文组织观察：DeepSeek 的翻译 sidecar、Tianshu 的入口/索引/双仓 PR 说明、Raven 的 CONTEXT-MAP、ZCode 的 DESIGN 与架构策略、goose 的治理/维护者文档等。
- 同名不等职、同一文件多职责、目录与横幅表达时态、复制/指针/互补别名并存，这些是 00/01 已记录的边界事实。

### 不能从 00 单独确认

- 文件是否被某个 harness 发现、读取、注入本次模型输入，或在后续步骤继续可见。
- `architecture-policy.yaml` 是否有执行器，`marketplace.json` 是否被安装器消费，`.rivet.md` 是否被 Rivet 解析，`.i18n.yaml` 是否由校验脚本实际读取。
- README 语言/平台变体之间是否完整对齐；存在相似文件不等于派生内容等价。
- 一条规则是否提高任务成功率、降低成本或延迟；静态体量、命名和存在性不能推出这些效果。
- `claude-code` 的真实根目录文档形态；`absent` 只表示本次没有本地 checkout。

## 消费者与版本缺口

01 的运行系统研究已经提醒：读盘、描述展示、激活、持续提供和模型实际使用可以分离。要把本阶段的 T02/T03/T04/T07/T08 从“文本组织模型”推进到“运行关系模型”，需要为每个声明选择固定版本、配置和执行路径，记录：发现入口、选择条件、读取范围、投递时点、失败处理和后续修正。没有这些证据时，mapping 中的 T 模型只说明材料组织了某种可重复任务，不声称任务已被系统执行。

## 反例与模型重开条件

出现以下任一情况，应保留原材料和失败原因，重新检查 `models.md`：

1. 两个当前同属一个模型的实例，在正文、使用关系或演化条件上存在会改变正确行动的差异，而现有 C/T 模型无法表达。
2. 一个新实例只能靠不断增加“特殊情况”才能解释，说明它可能引入了独立使用任务或机器关系。
3. 把一份混合文档拆成多个 C 模型后，读者已经无法判断哪些内容必须共同取得、哪些结果尚未验证或哪些状态仍然有效。
4. 新的消费者版本改变了文件名的发现接口、字段解析或投递路径，使当前 T 模型的关系不再成立。
5. 正文核读推翻了 00 的首行/`kind` 推断，例如文件名看似是手册，正文实际是生成元数据或临时工作稿。

反过来，单纯出现新文件名、语言后缀、目录位置或表示格式，不足以重开模型；先检查它是否改变了任务和关系。

## 暂定状态规则

只有实例存在、正文职责、边界反例和必要消费者关系都能由当前证据说明时，才可把模型或映射标为“已核定”。在此之前使用“暂定映射”；不要用旧 `ds.md` 的 `[LOCKED]` 记录替代本阶段证据。
