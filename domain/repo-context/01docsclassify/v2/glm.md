# 仓库文档分类与治理方法（定稿）
**文档说明**：本文是此前全部讨论的最终整理，自成一体，不依赖此前任何一轮的用词。全文只用两类词汇：日常用语，以及首次出现时就地定义的少量术语。此前讨论里出现过的缩写代号（如"受体 M/D/H"）和比喻（如“中毒”“死刑”“闸门”“门面”“物化视图”）全部停用，一律换成功能描述，文末附新旧用词对照。

## 一、两个根本事实
整套方法只建立在两个事实上，后面所有规则都能追溯到它们。
**事实一：agent 每次会话都从零开始，并且读到什么就执行什么。**
它对项目没有记忆，不知道团队历史和口头约定。它获得项目知识的途径只有两个：读文档，或用工具当场查（列目录、搜代码、读文件、看提交历史）。更关键的是：它不核实。人读到可疑文档会本能地对照现实起疑，agent 不会——它把读到的内容当作操作依据直接执行。它能发现自己被过期内容误导的唯一机会，是命令运行失败、构建报错这类“错误自己发出声音”的时刻。
**事实二：文档内容会与仓库现实脱节。**
代码每天都在变，文档不会自己变。一份与现实不符的文档（下文统称“失效”），对人类读者是困惑，对 agent 是错误行动——并且由于事实一，这个错误会在每一次会话里重复发生。
由此得出治理的三个任务：
1. 让每份文档在需要时能被找到；
2. 让该保持准确的内容保持准确；
3. 让失效能被发现，或者让内容本身具备“错了会报错”的性质。
以及一条总的存在判据：**一份内容值得成为文档，当且仅当存在一类真实缺少它的读者，且没有更便宜的补法。** 凡是 agent 用工具当场能查到的信息，都不满足这条判据——这也是后文所有“建议删除”的唯一理由。

## 二、角色：谁在读、谁在写、谁在维护
### 2.1 按“关系”分类，不按“文档属性”分类
如果问“README 的读者是谁”，会卡住：外部评估者读它，新成员读它，多数 agent 工具也默认读它。这说明“读者”不是文档的单值属性。正确的问题不是“这份文档归谁”，而是：agent 与它是什么关系、developer 与它是什么关系、它由谁写。分类的单元从“文档”换成“关系”之后，这类卡壳全部消失。
### 2.2 agent 的四个特征
1. **零起点**：每次会话对项目一无所知（除预载内容外）。
2. **不核实**：读到即执行。
3. **有工具**：能列目录、搜索、读任意文件、看提交历史——相当一部分知识可以当场查。
4. **纠错只靠报错**：只有“错误自己发出声音”时它才有机会自我纠正。
### 2.3 developer 的三个特征
1. **高语境**：项目历史在脑内，团队文化在口头。
2. **会核实**：拿文档对照现实，是天然的错误过滤器。
3. **唯一有写权限的群体**：整个文档体系里，人的核实是唯一的纠错来源。所有维护制度——发布前评审、定期整理、周期对账——本质上是同一件事：安排这种稀缺的核实该花在哪条内容上。
### 2.4 外部读者为什么不算一类角色
判据：一个角色值得在分类里占一席，当且仅当它对应的关系会产生其他角色推不出来的规则。外部读者只产生“写得清楚”这类要求，用固定模板解决（README 的段落结构），不进分类。
一个必须记住的例外：主流 agent 工具（Claude Code、Codex 等）默认会读 README。这不是外部读者关系，这是 **agent 关系**。所以 README 里的安装命令必须按“给 agent 的标准”维护。**一份文件是否进入 agent 的上下文，由工具的默认行为决定，与作者意图无关。** 建议维护一份“主流工具默认读取清单”，清单内文件的事实性段落一律从严。
### 2.5 agent 的两种工作范围
- **项目范围**：注意力指向项目本身——AGENTS、CONVENTIONS、ARCHITECTURE 属于此。
- **个人范围**：注意力指向 agent 自己和使用者——MEMORY、USER、SOUL 属于此。
判定方法（**脱离仓库检验**）：想象把内容挪到本仓库之外，是否仍有意义。MEMORY、USER、SOUL 换个项目依然成立；AGENTS 离开这个项目就是无用信息。
两个易混点：
1. AGENTS.local 是个人文件、不入库，但它讲的是“在这个项目里怎么干活”——按内容属项目范围，按存放属个人范围。**内容指向和存放位置是两个独立的选择。**
2. USER、SOUL 与 MEMORY 同属个人范围，但前者是人写的、后者是 agent 写的——这个差别决定治理方式（见 2.7 和记忆类）。
这个区分为什么重要：两种范围的语境性质不同，坏法也不同。
- 项目范围的内容，每次会话靠重读即可恢复；它的问题是**会过期**——对策是随代码变更同步更新。
- 个人范围的内容是**积累的**，只增不减；它的问题是膨胀，以及（当由 agent 自写时）错误自我强化——对策是定期整理和存放隔离。
### 2.6 阅读关系与维护关系是两条独立的关系
谁读、读多频繁，是一条关系；谁维护、维护到什么严格程度，是另一条关系。二者的连接公式：
> **维护的严格程度 = 这份文档被消费的频率 × 消费一方出错的代价。与维护者自己读不读无关。**
例：AGENTS.md 的作者几乎从不“阅读”它（内容就在他脑子里），却必须重度维护——因为它每次会话都被 agent 消费，错误会被原样执行。推论：判断该为一份文档投入多少维护精力，看它的读者，不看它的作者。
补充：检查节奏应当跟随阅读时机——agent 每次会话读的（AGENTS）随每次变更检查；只在发布时读的（CHANGELOG）随发布检查；只在出事故时读的（ADR）平时免检；只在入职时读的（入门文档）绑定入职事件检查。
### 2.7 写者与读者的四种组合
| 谁写 → 谁读 | 风险 | 对策 |
|---|---|---|
| 人写 → agent 读 | 错误被无条件执行，每会话重复 | 发布前必须过人审；维护标准最高 |
| **agent 写 → agent 读** | 唯一中间没有任何人核实的通路；一条错误教训每被读取一次就更可信一分，自我强化 | 隔离（不入团队仓库）+ 定期人工整理 |
| 人写 → 人读 | 读者自己会核实 | 常规评审即可 |
| agent 写 → 人读 | 人本身就是过滤器 | 无需额外制度，应鼓励 |

## 三、三条分类轴
三条轴就是三个依次回答的问题。
### 轴一：读者关系（不单选）
每份文档分别回答：对 agent 是什么关系（是否自动加载、靠什么被找到、读来干什么）；对 developer 是什么关系（什么场景读、要不要维护）；由谁写（人／agent）。不设“主读者”，不折算权重。AGENTS 对 agent 是“每次会话自动加载、直接执行”，对 developer 是“几乎不读、重度维护”——两条关系并存，描述的是同一份文件。
### 轴二：获取承诺
为什么按“承诺”分级而不按“agent 行为”分级：agent 什么文件都能读，行为没有区分度；有区分度的是仓库承诺了什么。
| 取值 | 仓库承诺 | 兑现方式 | 违反形态 |
|---|---|---|---|
| 常驻 | 每个相关会话中自动在场 | 预载 | 该在场而缺失、或内容超预算 |
| 可达 | 需要时找得到 | 在导航文件登记，或在指令里放链接 | **无入口文档**：声明可达却没有任何路径能发现它 |
| 无承诺 | 不做保证 | — | 无（归档、证据、被取代的记录，允许自然消失） |
每份文档必须三选一。两种违反都能机器检查：行数超限；对账两份清单（声明可达的集合 vs 实际被索引的集合）。
附带删除规则：**凡是 agent 用只读工具一秒能当场得到的信息，不值得设任何一级承诺**——目录树（列目录命令）、变更文件清单（提交历史）、格式规范（格式化工具配置）、接口文档（从接口定义文件生成）。
### 轴三：时间指向
沿用四个值：**事前 / 事中 / 事后 / 永恒**。每个值的含义是“内容以什么为准”：
| 取值 | 以什么为准 | 失效方式 |
|---|---|---|
| 事前 | 计划中的未来 | 未来变成了别的样子 |
| 事中 | 当前现实 | 现实变了，文档没跟上 |
| 事后 | 事件发生的那一刻 | **不失效**——历史不会变错，只会被后来事件取代；唯一义务是被取代时标注 |
| 永恒 | 项目原则 | 原则被现实推翻；必须走显式撤销（写新记录说明），不许悄悄改 |
说明：此前讨论曾另设第五个值“元”（描述文档系统自身的文档）。检验后并入事中——导航文件描述的“现状”，就是文档体系本身的现状，性质与 ARCHITECTURE 描述代码现状相同。四个值够用。

## 四、七类文档
先看总表，再逐类展开。
| 类型 | 一句话定义 | 内容以什么为准 | 代表 |
|---|---|---|---|
| 指令 | 告诉 agent 现在该怎么干活 | 人的现行意志 | AGENTS、CONVENTIONS |
| 记录 | 已发生且不可撤销的事件 | 事件发生的那一刻 | ADR、CHANGELOG |
| 记忆 | agent 自写自读的跨会话积累 | 经验（可修订） | MEMORY |
| 入口 | 给第一次接触者的项目介绍 | 借自指令类的事实 | README |
| 导航 | 只装“去哪找”的检索目录 | 文档体系的当前布局 | INDEX |
| 现状 | 可由记录重建的当前状态描述 | 当前现实 | ARCHITECTURE、GLOSSARY |
| 计划 | 尚未发生、可能永不发生 | 计划中的未来 | ROADMAP、TRADEOFFS |
每类按统一结构展开：是什么 / 为什么存在 / 怎么坏 / 怎么管 / 怎么判断 / 与邻近类型的边界。
### 4.1 指令类
**是什么**：人写的、约束 agent 当下行为的命令性内容，回答“现在该怎么干活”。时间指向：事中（规则部分）与永恒（原则部分）。
**为什么存在**：agent 无法从代码推导操作事实——这个项目用哪个包管理器、哪些目录绝对不能动、改完必须跑什么测试。工具查得出“是什么”，查不出“你要我怎么办”。
**怎么坏**：过期指令被原样执行，agent 自信地做错事，每次会话重复发生。
**怎么管**（全体系最严格的一类）：
1. 随代码变更在同一提交里更新，不允许“文档稍后补”。
2. 内容优先选“错了会报错”的形式：可执行命令 > 有检查工具兜底的约定 > 没有验证手段的散文断言。安装命令过期会当场报错，agent 有机会自纠；“我们用四个空格缩进”这类断言过期了没有任何声音。
3. 自动加载的指令文件设行数上限（约 200 行：这是当前前沿模型能稳定遵循的指令量级，且每条每次会话都占上下文容量）。
4. 不写代码文件路径——路径是最容易失效的信息；写能力不写位置（“认证逻辑在 auth 相关模块”优于具体路径）。
5. 禁止用 AI 批量生成指令文件。已有实测：自动生成的上下文文件降低任务成功率、增加约两成成本；人工维护、只写不可推断的内容才有净收益。
**两个变体**（按 2.5 的工作范围分）：
- 项目指令：AGENTS.md、CONVENTIONS.md。
- 个人交互指令：USER、SOUL、AGENTS.local——规定 agent 与特定使用者的相处方式。人写、agent 读，不构成 agent 自写自读的循环，所以只需个人存放，不需定期整理。
**CONVENTIONS 的内部结构**：分原则段（永恒，低频维护）与规则段（事中，随版本维护）。可执行的格式条款不写在文档里，写进格式化与检查工具的配置；文档只保留工具表达不了的语义约定（如“接口层不抛异常，一律返回结果对象”——没有这条，agent 会给每个调用都包一层异常处理）。
**怎么判断**：这段内容是在告诉 agent 现在该怎么干活吗？
**边界**：与现状类的区别在语气与效忠对象——命令语气、以人的意志为准是指令；陈述语气、以可重建的事实为准是现状。指令与某条旧记录冲突时，人的现行意志优先（要么人改了主意，要么补一条新记录说明为什么改）。
**方言问题**：不同工具读不同文件名（CLAUDE.md、.cursor/rules 等）。做法：维护一份 AGENTS.md，其余做符号链接。分别维护必然产生两份逐渐分道扬镳的指令。
### 4.2 记录类
**是什么**：对已发生且不可撤销事件的条目，只增不改。时间指向：事后。
**为什么存在**：developer 的高语境也有洞——“当年为什么这么定”不在新成员脑内，也已从老成员记忆里蒸发。出事故、做重构时需要回溯决策背景；agent 提议方案时也需要知道哪些路走过且放弃了。
**怎么坏**：几乎不坏。历史不会过期，只会被取代。剩余风险只有两种：链接失效；被取代了却没标注。
**怎么管**：免日常维护——这是结构性的（对历史而言“过期”这个概念不成立），不是偷懒。仅有的义务：
1. 被取代时显式标注并指向取代者；
2. 写法 = 结论 + 关键理由 + 证据存放位置的链接；证据允许消失，链接断掉不算事故；
3. 被否决的决策同样记录——“考虑过 X、因 Y 放弃”是防止日后重提旧案的关键知识。
**怎么判断**：内容描述的是已经发生且不可撤销的决定吗？
**边界**：与计划类互为镜像（同一件事，定前在计划类，定后进记录类）；与记忆类的区别在写者与可变性——人写的不可变档案 vs agent 写的可修订经验。
**代表**：ADR 目录（含被否决条目；轻量决策直接写短条目，不另设平行文件）、CHANGELOG（只写为什么变与影响面，“改了哪些文件”由提交历史承担）、废弃机制流水。
### 4.3 记忆类
**是什么**：agent 自己写、跨会话读取的积累性内容。时间指向：事后（累积）。
**为什么存在**：agent 每次会话清零重启，需要一个跨会话延续的层。
**怎么坏**（比指令类的坏法更隐蔽）：
1. 膨胀：只增不减，占用无界增长；
2. 错误自我强化：agent 对自己写下的内容不是普通的“不核实”，而是当作经验信任——一条错误教训每被读取一次就更可信一分。这是自我放大的循环，不是一次性错误。
**怎么管**（全体系维护成本最高的一类：变化最频繁 × 要求最严格）：
1. **隔离**：放个人范围、不入团队仓库。理由不是隐私，而是“agent 写 → agent 读”这条通路中间没有任何人的核实，必须先圈起来；
2. **定期整理**：周期性由人过一遍；反复出现的教训升级为正式的指令条款或词表条目——升级必须过人审，这是往循环里插入核实的唯一办法；
3. **每条带日期**：让“这条还新鲜吗”可以判断。
**怎么判断**：脱离本仓库仍有意义，且由 agent 撰写——两者都成立。
**过程性材料**（会话记录、草稿笔记）是记忆类的临时形态：用完即删，默认不入库。
### 4.4 入口类
**是什么**：写给第一次接触项目的人看的项目介绍；同时事实上被多数 agent 工具默认读取。时间指向：事中。
**为什么存在**：陌生评估者要在半分钟内判断“这是什么、值不值得用、怎么装”。
**怎么坏**：隐性失效。快速上手里的安装命令过期了，没有人把它当指令维护——但 agent 工具默认读它、照跑不误。入口类的风险恰恰来自“大家不觉得它需要严格维护”。
**怎么管**：按段落分治——
- 叙事段（这是什么、为什么存在、给谁用）：自由，写给人；
- 事实段（安装、版本要求、快速上手命令）：按指令类标准维护，且单一来源——AGENTS.md 持有事实，这里放链接；至少保证两处在同一次提交内同步。
- 凡在“默认读取清单”上的文件，事实段一律按此标准。
**怎么判断**：这是写给不了解项目的人的一次性入口吗？
**平台变体**：SECURITY、CONTRIBUTING、LICENSE、行为准则等，格式由托管平台与社区规范决定，登记进体系、照标准写即可。
### 4.5 导航类
**是什么**：不装知识、只装“去哪找”的检索目录。每个条目 = 话题（或意图）→ 文档与位置（可细到小节）。时间指向：事中（它描述的现状是文档体系的布局）。
**为什么存在**：agent 的搜索是字面匹配——搜 "auth" 命中五百处代码；真实需求是按话题找文档——“认证相关的约定在哪”。把同义词归并到同一条目（auth／鉴权／认证），是搜索工具做不到、只有人工目录能做到的事。
**怎么坏**：链接断；或者该登记的文档没登记，成为无入口文档，永远无人发现。
**怎么管**：
1. 链接有效性进自动检查；
2. 定期对账两份清单：声明可达的文档 vs 实际被索引的文档；
3. **只索引文档，不索引代码文件**。文档目录是几十个低频变动的文件，索引成本可控；代码路径天天变，写进索引就是持续制造失效。
**怎么判断**：内容只是指向其他内容吗？
**与“agent 自己查”的三层分工**：文件在哪儿（物理位置）→ agent 用工具当场查；知识在哪儿（话题到文档的映射）→ 导航类；为什么这样设计（意图与理由）→ 现状类与记录类。一份静态目录树想兼干第一层的活，而第一层已被工具当场查询完全替代——这就是 TREE 类文件被删除的全部理由。
### 4.6 现状类
**是什么**：对项目当前状态的描述。关键性质：**原则上可以从记录类文档推导重建**——它存在只是为了让读者省去逐条翻阅历史的时间。
**为什么存在**：agent 和新成员都不该为了知道“现在长什么样”去读一百条决策记录。同时，模块边界的“为什么这样划”无法从目录结构推导——工具能查到代码在哪，查不到为什么这么分。这是它逃过“工具替代检查”的原因。
**怎么坏**：与现实脱节。代码重构了、决策被取代了，描述没跟上——此时它比没有更糟：一份语气自信的错误陈述。
**怎么管**：周期对账（现状描述与记录层或代码比对，可逐步做成自动检查）；意图部分必须由人写入并随架构变更维护。
**怎么判断**：这是原则上可从历史重建的当前状态描述吗？
**三个子形态**：结构现状（ARCHITECTURE）；词汇现状（GLOSSARY——吸收 CONTEXT，因“上下文”一词在 AI 语境里有歧义；领域术语比文件路径稳定得多，适合成文）；边界现状（LIMITATIONS——“我们不支持什么”，即当前能力的负空间；注意与问题清单分工：这里放长期如此的设计边界，具体故障归问题追踪系统）。
### 4.7 计划类
**是什么**：承载尚未发生、可能永不发生之事的活文档。时间指向：事前。
**为什么存在**：agent 和人都需要“接下来往哪走、哪些方案还在桌面上”的语境，避免提出已被放弃的方向。
**怎么坏**：
1. 信息价值随时间衰减——半年没人确认的条目，信息量趋近于零，却还占着位置；
2. 写下来的计划变成没人敢删的包袱。
**怎么管**：
1. 每条带最后确认日期，超期强制处理（重新确认，或标记放弃）；
2. 承诺分级：确定要做（锚定到版本号）vs 探索中（随时可弃）。明确允许“放弃”这个状态，是防止包袱化的机制；
3. 两个出口都接好：做成 → 转入记录类（CHANGELOG 对应版本下记一条）；放弃 → 标一句原因，重要的放弃升级为一条被否决的决策记录（“曾计划做 X，因 Y 放弃”）。
**怎么判断**：描述的是尚未发生、且可能永远不发生的事吗？
**子形态**：路线图（ROADMAP）；待权衡的选项集（TRADEOFFS——记“为什么暂时不做某事”，防止 agent 好心翻案）；实验记录（EXPERIMENTS——为澄清选项而做的验证，原始产出放证据层）；问题清单（PROBLEMS——若仓库托管在 issue 平台且 agent 能读 issue，则被外部系统整体替代，应迁出）。

## 五、判断流程与全量归位
### 5.1 判断流程
```
拿到一份文档（新增或存量），依次问：
1. 把内容挪到本仓库之外，还有意义吗？
   有 → 由谁写？
        agent 写 → 记忆类（个人存放 + 定期整理）
        人写     → 指令类 · 个人交互变体（个人存放）
   没有 → 继续
2. 内容只是指向其他内容？           → 导航类
3. 描述已发生且不可撤销的事？       → 记录类
4. 描述尚未发生、可能不发生的事？   → 计划类
5. 描述当前状态：
   写给陌生人的一次性介绍           → 入口类
   命令语气，以人的意志为准         → 指令类 · 项目变体
   陈述语气，可从历史重建           → 现状类
```
### 5.2 归位总表（对最初列举的全部文档）
| 文档 | 归类 | 补充说明 |
|---|---|---|
| AGENTS | 指令 · 项目 | 自动加载；行数上限 |
| AGENTS.local | 指令 · 项目内容 · 个人存放 | 内容属项目范围，存放属个人 |
| CLAUDE 等工具方言文件 | 指令 | 符号链接到 AGENTS.md，禁止分别维护 |

| MEMORY | 记忆 | 唯一的 agent 自写自读；隔离 + 整理 + 日期 |
| dialogue/、NOTES/ | 记忆 · 临时 | 用完即删，默认不入库 |
| README | 入口 | 事实段按指令标准，来源单一 |
| SECURITY、CONTRIBUTING、LICENSE 等 | 入口 · 平台变体 | 按平台规范 |
| INDEX | 导航 | 吸收 registry、outline |

| PROBLEMS | 计划 | 满足条件时迁往 issue 系统 |
### 5.3 建议删除或合并清单（附理由）
| 对象 | 处置 | 理由 |
|---|---|---|
| TREE | 删除 | 列目录工具当场可得，静态快照必然失效 |
| STYLE | 删除 | 可执行的格式条款迁入格式化/检查工具配置；工具表达不了的并入 CONVENTIONS |
| THISIS、BREIF | 并入 README 开头 | 与 README 是同一知识按详略拆成的多份，没有同步机制，必然分道扬镳 |
| registry、outline | 并入 INDEX | 同为“只装指向的内容” |
| USER | 并入 AGENTS.local | 使用者画像就是个人指令的理由：“我是中文使用者”与“回复用中文”是同一件事的两种说法 |
| DECISIONS | 并入 ADR | 与 ADR 是同一类型的两种容量形态；轻量决策写短条目即可 |
| CONTEXT | 并入 GLOSSARY | 完全同义，且命名有歧义 |
| 手写接口文档（有接口定义文件时） | 改为生成 | 从定义文件生成，禁止手编 |
一条总原则贯穿：**同一信息只在一处维护；允许存在多份呈现的前提是读者不同（README 给人、AGENTS 给工具），绝不允许按详略拆分。**

## 六、维护制度
### 6.1 各类维护节奏（检查频率跟着阅读时机走）
| 类型 | 更新/检查时机 | 严格程度 |
|---|---|---|
| 指令 | 随代码变更，同一提交 | 最高 |
| 入口 · 事实段 | 随指令同步 | 同指令 |
| 入口 · 叙事段 | 随重大变化 | 低 |
| 记录 | 仅在被取代时标注 | 免日常维护 |
| 记忆 | 固定周期整理 | 高 |
| 导航 | 文档增删时；链接自动检查 | 中 |
| 现状 | 周期对账 | 中 |
| 计划 | 周期确认（条目带日期） | 中 |
### 6.2 状态转换（文档的一生，共五种）
1. **草稿 → 正式**：合并进主干前的评审即是全部检查——用分支与合并实现，不需要额外制度。草稿放草稿目录或留在分支上。
2. **计划 → 记录**：决定作出时，把选项与结论写成记录条目。
3. **讨论过程 → 记录**：会话结束时提炼结论入记录，原始材料删除。
4. **记录 → 原则**：标志是引用方式变了——从“根据第 42 号决策”变成直接当作前提陈述。升级需人确认。
5. **原则 → 撤销**：原则被现实推翻时，必须写新记录说明并取代，不许悄悄改。
（关于给 AI 生成内容加作者标记：要紧的不是谁写的，而是过没过人的审——人审过的 AI 草稿无害，没审的人写草稿同样危险。用位置和分支表达状态，用日期表达记忆的新鲜度。）
### 6.3 结论、证据、过程三层存放
- **结论层**：记录正文（结论 + 理由 + 证据链接）——长期保存；
- **证据层**：实验输出、基准数据——体积大、允许消失、断链不报警（不入主库或用大文件存储）；
- **过程层**：对话、草稿——默认不入库，用完即删。
理由：三者寿命完全不同（近乎永久／随时间贬值／即时作废），混放必然互相拖累；且原始证据的体积会淹没结论——agent 读记录要的是结论，不是三百行基准输出。
### 6.4 可落进自动检查的五项
1. 自动加载文件行数上限；
2. 导航链接有效性；
3. 无入口对账（声明可达 vs 实际索引）；
4. 现状对账（渐进实现）；
5. 计划条目日期超期报警。

## 八、自检与遗留
**自我归类**：本文（治理方法本身）= 人写、双方按需读取、事中（它描述的现状是文档体系本身）→ 放 docs/，在 INDEX 登记。一套分类方法必须能给自己归类，否则不完备。
**两句总述**：
1. 七类文档的全部差别只在“内容以什么为准”：指令以人的现行意志为准，现状以可从历史重建的事实为准，记录以事件发生时刻为准，记忆以经验为准，计划以尚未到来的未来为准，入口以借自指令的事实为准，导航以文档布局为准。
2. 失效的统一定义：依据变了，文档没跟上。治理的统一定义：按依据的变化速度安排更新频率，按消费一方的错误代价安排严格程度。
**附属材料**（另行成文，不塞进本文——它们随工具版本快速变化，与稳定的方法本体寿命不同）：
1. agent 工具如何读取文件：各工具默认读取清单、嵌套目录的拼接规则（根到叶拼接、越近越优先、累计字节上限）、读取工具行为差异；
2. 类型两两对比的展开（何处需要详细辨析再写何处）。
**待办问题**：记忆整理的周期与细则；问题清单迁往 issue 系统的条件量化；现状对账的自动化实现；个人交互指令的推荐格式。
**研究方法一句话**：网状的研究内容写进线性文档时接缝不可避免，规则是——某话题第一次被别处引用时原地留一句带链接，第二次被引用时才抽成独立章节。
**新旧用词对照**（仅为衔接此前讨论，此后一律用右列）：
| 此前讨论的说法 | 本文用词 |
|---|---|
| 受体轴（机器/双读者/人类） | 读者关系（分别描述，不单选） |
| 真理锚定 / 锚定物 | 内容以什么为准 |
| 腐烂 / 中毒 | 失效；agent 依据失效内容行动 |
| 孤岛 | 无入口文档 |
| 闸门（G0–G6） | 状态转换及其检查 |
| 蒸馏 | 定期整理、提炼 |
| 门面 | 入口类 |
| 视图 / 物化视图 | 现状类 |
| 正典化 / 去正典化 | 升级为原则 / 撤销原则 |
| 出仓存续检验 | 脱离仓库检验 |
| 轻信读者 / 怀疑读者 | 不核实就执行 / 会对照现实核实 |
| 事件溯源管线 | 记录按时间追加，现状可由记录重建 |

| 死刑 / 处决 | 建议删除（附理由） |
