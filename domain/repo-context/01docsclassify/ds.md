# 文档分类法改造：从"单值受体"到"角色-强度矩阵"

> 属于 `domain\repo-context\` 研究，阶段 **02docsclassify** · 产出者 **ds**
> 上游：`drafts\总览.md`（草案）、`02docsclassify\glm.md`（另一 AI 的分类法草案）、`01docsdefine\ds.md`（定义）
> 本文立场：**上面两处都是草稿，不是教条。** 本文只做两件事——诊断现有分类法为何不好用，然后提出一个我认为更可用的替代骨架。所有判断都标注依据；没有依据的地方写"待验证"。

---

## 0. 一句话结论

现有分类法（glm 的"受体 / 时向 / 嬗变 / 辖域"四轴）的核心病根，是把**受体当成单值标签**（M / D / H 三选一）。
但一个文档和角色的关系不是"它属于谁"，而是**"每个角色读它多深、维护它多深"**——是一张**矩阵**，不是一枚标签。
把这一轴从"标签"换成"矩阵"，其余问题（维护被吞掉、空格空置、登记成本高）会连带松解。

---

## 1. 诊断：现有分类法为什么不好用

### 1.1 病根一：受体轴是单值，无法表达"多角色"

`glm.md` 的轴 1 原文：

> 轴 1｜受体轴（Reader）——谁是第一读者
> 机器优先 `M` / 双读者 `D` / 人类优先 `H`

它给出的定位是 `README → H`、`AGENTS.md → M`。但现实是：

- **README 也会被 agent 默认读**（你说的）——标 `H` 就把这条丢了；
- **AGENTS.md 被 developer 高频维护**——标 `M` 就把这条也丢了。

glm 自己其实察觉到一半：它在对比章节里写"**二元契约对象丢失 D（双读者）**"，于是补了一档 `D`。但 `D` 只是把三选一变成"三个枚举值里选一个"，**没有解决本质问题**——`D` 意味着"人和机器都高价值"，可它仍然回答不了"谁读、谁维护、各到什么程度"。

更根本的是：**"谁是第一读者"这个问法本身就预设了一个排序**，而现实中不同角色在同一份文档上做的是**不同的事**（一个读、一个维护），不存在统一的"第一"。

### 1.2 病根二：读取与维护被压进同一个标签

glm 把维护收编成了"审查规则 = f(受体)"：`M` 类 → 行数计量 / 漂移审计 / 禁止 LLM 批量生成；`H` 类 → 无需为机器优化。

但你的原话点破了它：

> 一份 `agents.md`，确实是 agent 的一等公民，每次默认加载，但是因为很重要，所以对 developer 来说，维护也极其重要。

`受体 = M` 这个标签里，**装不下"developer 维护它是一等大事"**。而恰恰是这条维护事实，决定了它要走 review、要与代码同 PR、要防漂移——这些规则 glm 只能挂在"受体 = M"下面，于是一份"机器优先"的文档自动获得了机器审查规则，而**人类维护者那一侧的需求没有任何位置可放**。

**读取和维护是两件独立的事**，理由很直接：读完之后的动作不同（读 → 加载进上下文；维护 → 修改、评审、承担一致性责任），参与的角色往往也不同（README 的读者是 user，维护者是 developer）。

### 1.3 病根三：轴的有效性不均，空格大量空置

glm 自己标注了两处空格：

- `M × F`（机器可读的未来意图）——原文："**尚无成熟实践**"；
- `H × X`（人类专属导航）——原文："无需新文件"。

12 格里至少 2 格是空的/预留的。这说明 4 轴 × 3 值的划分中，**有一部分是为了对称整齐，而不是因为现实中真有区分**。

### 1.4 病根四：glm 违反了自己的判据一（可验证的自洽性破绽）

glm 的判据 1 原文：

> 判据 1｜正交性 —— ❌ 排除的反例：**按"目录位置"分类（root / docs /）——位置是治理的输出而非本质属性，循环论证**

它据此排除了"按位置分类"。但它的**轴 4「辖域轴（Scope）」**原文是：

> 轴 4｜辖域轴（Scope）——生效范围：仓库根 `R` / 子树 `S` / 个人 `P`

`R / S / P` 恰恰就是目录位置（根 / 子树 / 个人目录）。**glm 用自己的判据一否定了自己的轴 4。** 这不是笔误——它说明"位置"确实不该是独立轴，而应是**由别的属性推导出的输出**（比如"要常驻 → 必须放根"）。

### 1.5 病根五：登记成本高、推导链长

登记一个文档要填 4 个轴值，再查 4 个函数（加载 / 更新 / 审查 / 位置），外加"同格合并"和"禁区"两张表。对一个要长期反复使用的分类法来说，**每登记一次要跑一遍决策树，成本太高**——这是"不好用"最直接的含义。

## 2. 改造：读者不是"是谁"，是"读多少 × 维护多少"

### 2.1 角色集

先定义角色（你说三个，我同意，并补一个候选）：

| 角色 | 定义 | 判定线索 |
|---|---|---|
| `agent` | AI 执行者，把文档**注入上下文**来完成工作 | 文档是否被 harness 自动加载 / 被 agent 主动检索 |
| `developer` | 人类工程维护者，**修改**仓库与文档 | 谁会提 PR 改这份文档 |
| `reader` | 使用者 / 外部读者，**消费**项目但不改它 | 谁克隆下来照着跑 |
| `tooling`（候选） | 确定性脚本：CI、链接检查、行数门禁 | 是否有脚本读它做校验 |

> `tooling` 是否该单列，见 §7 开放问题。它与 agent 的区别是：agent 是"理解后行动"，tooling 是"机械规则匹配"。

### 2.2 每个角色有两个独立强度

对每个角色 `r`、每份文档 `d`：

- **`read(r, d)`** —— 它如何进入这个角色的工作流；
- **`maint(r, d)`** —— 这个角色对它承担多少维护责任。

**读取强度（4 档，按"如何进入工作流"判定）**

| 档 | 名称 | 判据 |
|---|---|---|
| `r0` | 常驻 | 每次会话/任务默认加载（agent 注入 / developer 打开仓库先读） |
| `r1` | 按需 | 有明确触发条件时主动拉取（"改接口时读 ARCHITECTURE"） |
| `r2` | 检索 | 只在搜索/排查时命中 |
| `r3` | 无 | 该角色不读 |

**维护强度（4 档，按"谁改它、改时走什么流程"判定）**

| 档 | 名称 | 判据 |
|---|---|---|
| `m0` | 一等 | 该角色是文档的主人，变更需走严格流程（review / 门禁 / 与代码同 PR） |
| `m1` | 参与 | 会改，但不是主人 |
| `m2` | 偶改 | 偶尔更新（补一行链接、改个措辞） |
| `m3` | 无 | 不改 |

> 分档不是为了精确打分，而是为了**可判定**：每一档都对应一个能直接观察的事实（"谁提的 PR""是否默认加载"），不依赖主观判断。

### 2.3 为什么它是矩阵而不是标签

给你清单里四个代表文档填一遍（**这张表是全文的核心**）：

| 文档 | agent.read | agent.maint | developer.read | developer.maint | reader.read | reader.maint |
|---|---|---|---|---|---|---|
| `README` | `r1` 按需（多数 agent 默认读） | `m2` | `r1` | `m1` | **`r0` 常驻** | `m3` |
| `AGENTS.md` | **`r0` 常驻** | **`m0`** | `r1` | **`m0`** | `r3` | `m3` |
| `CONTEXT.md` | **`r0`** | `m1` | `r1` | **`m0`** | `r3` | `m3` |
| `CHANGELOG` | `r3` | `m3` | `r2` | `m0` | `r1` | `m3` |
| `ADR`/`decisions\` | `r2` | `m2` | `r1` | **`m0`** | `r3` | `m3` |

这张表立刻显出单值标签丢掉了什么：

- `README` 在 glm 里是 `H`，但这里 `agent.read = r1`（不是 `r3`）——**agent 确实会读它**，`H` 掩盖了这一点；
- `AGENTS.md` 在 glm 里是 `M`，但这里 `developer.maint = m0`——**developer 是它的维护主责人**，`M` 掩盖了这一点；
- `CONTEXT.md` 出现了一种 glm 无法表达的形态：**两个角色的读取都高、维护主责在 developer**（agent 读它但不大改它）。

**并且它顺手解释了 glm 的"空格"**：所谓 `M × F` 空格（机器可读的未来意图），用矩阵语言说就是"`agent.read = r1`、`agent.maint = m1`、时态 = 未来"的文档——**不是不存在，是还没人需要它**。空格的成因从"轴划错了"降级为"这类文档尚未出现"。

## 3. 从矩阵推导治理（保留 glm 最有价值的思想）

glm 最值得继承的一点是：**治理规则是坐标的函数，不是要背的清单**。矩阵版继续用它，但把函数挂到"强度"上——比挂在抽象的轴值上更直观。

### 3.1 加载与预算 = f(agent.read)

| 条件 | 规则 | 依据 |
|---|---|---|
| `agent.read = r0` | **有硬预算**（行数/字词上限）+ 防漂移审计 | 常驻内容每次请求都占 token，是稀缺资源 |
| `agent.read ∈ {r1, r2}` | 无硬预算，但必须**可被检索**：标题稳定、术语与 CONTEXT 一致 | 按需/检索靠"能找到"，不靠"总在眼前" |
| `agent.read = r3` | agent 零预算，纯人类优化 | agent 无行动价值 |

### 3.2 变更流程 = f(任一角色的 maint)

| 条件 | 规则 | 依据 |
|---|---|---|
| 存在 `maint = m0` | 变更走 review + 与代码同 PR；禁止无人值守批量生成 | 有明确主人 → 有明确责任 → 有明确门禁 |
| 最高只有 `m1` | 变更需 owner 知会 | 无主责文档最容易漂移 |
| 全部 `≤ m2` | 低流程，定期巡检即可 | 低风险 |

### 3.3 位置 = f(read 的最高强度)

```
若某角色的 read = r0（常驻） → 必须放在"最先被读到"的位置（根 / 近端），并占据稀缺门面位
若最高 read = r1 或 r2      → 可放 docs\ 子树，靠链接可达
若全为 r3                   → 不建（或归档）
```

**这一条正是 glm 判据 1 想表达的意思**：位置不是独立轴，而是 `read` 的**输出**——常驻才能占据根目录。区别在于，矩阵版把"位置"正确地降级成了函数，而 glm 一边这么论证、一边又把它当成了轴 4。

### 3.4 语言与格式 = f(read 的分布)

| 条件 | 规则 |
|---|---|
| agent 侧 read 高 | 需要机读友好结构（稳定标题 / frontmatter / 机器可校验） |
| reader 侧 read 高 | 人类可读叙事优先 |
| 两者都高（如 `README`） | **双轨**：结构化骨架 + 可读正文，绝不能只照顾一边 |

## 4. 与 glm 四轴的处置

| glm 轴 | 处置 | 理由 |
|---|---|---|
| 轴 1 受体 `M/D/H` | **替换** → 角色-强度矩阵 | 单值标签丢多角色（§1.1）、丢维护维度（§1.2）；矩阵信息量更大且直接对应治理动作 |
| 轴 2 时向 `P/N/F/X` | **保留** | 事前/事中/事后/永恒是真实区分；glm 承认的"永恒"盲区正是你草案贡献的 |
| 轴 3 嬗变 `I/L/E` | **降级为派生** | 它可由"成熟度 × 时向"推出（记录类→追加，现状类→活文档）；glm 自己也说层级→嬗变是"机制→现象" |
| 轴 4 辖域 `R/S/P` | **降级为派生** | 位置由 `read` 强度推出（§3.3）；glm 的判据 1 已经预告了这个结论 |

一句话：**矩阵版把一个轴换成矩阵（信息量增加），把两个轴降为函数（登记成本下降），保留一个轴（时向）。**

## 5. 还需要哪些维度（你说"还有其他的"）

除角色矩阵与时向外，我认为以下维度**独立于角色**、且各自能推出治理规则：

### 5.1 成熟度 / 权威等级（草稿 → 受控 → 正典）

- 同一个知识会**在角色矩阵不变的情况下沿这个轴移动**：`TRADEOFFS` 的讨论（草稿）→ `ADR` 的结论（受控）→ `CONVENTIONS` 的原则（正典）。
- 这是**静态坐标表捕捉不到的"知识相变"**——文档会换文件、换位置、换治理规则，而它的"角色-强度"可能全程不变。
- 判据（可观察）：引用它时是否需要标注来源。需要溯源 = 事后知识；被当作先验前提直接陈述 = 正典。

### 5.2 载体 / 格式（md / csv / json / yaml）

- `drafts\结构设计.md` 已在讨论（"大规模数据 + 需要条件过滤" 是否该用 csv）。
- 它**与角色正交**：同样是"索引"（`read(agent)=r1`），md 适合叙事、csv 适合行级增删。判据应是"行级增删频率 + diff 友好度"。

### 5.3 公共性（internal / public）

- 决定语言、语气、能否暴露内部细节。`SECURITY.md` 是 public 的、`docs\postmortem\` 多半是 internal 的——但两者的角色矩阵可以完全相同。

### 5.4 生命周期 / 保质期

- glm 的 `E`（阅后即焚）本质是"**带保质期**"。它可以并入 5.1 成熟度（草稿态常带保质期），也可以单独作为"是否需定期清理"的开关。

## 6. 这套分类法买到什么

1. **可判定**：每一档都对应一个能直接观察的事实（谁提的 PR、是否默认加载），不需要"理解 25 个文件的历史沿革"。
2. **不丢信息**：`README` 与 `AGENTS.md` 这类"多角色"文档第一次被如实描述。
3. **维护进入一等公民**：你指出的"AGENTS.md 对 developer 的维护极重要"有了位置。
4. **登记成本下降**：从"填 4 轴 + 查 4 函数"降到"填一张 3×2 表 + 查 4 条函数"。
5. **自洽**：位置作为输出而非轴，避免了 glm 判据 1 与轴 4 的矛盾。

## 7. 开放问题（待验证，不假装已解决）

1. **角色集是否完备？** `tooling` 该不该单列？——CI 确实"读"文档（链接检查、行数门禁），但它是机械匹配而非"阅读"。倾向单列，但需在 `03docscompare` 用真实例子检验。
2. **4 档强度够不够？** 或许 `r0/r1/r2/r3` 应压缩成 3 档——观察是否有文档卡在 `r1`/`r2` 之间无法判定。
3. **矩阵会不会太贵？** 每份文档一张 3×2 表，长期维护成本未知。可能的压缩记号：`a=r0m0 | d=r1m0 | u=r3m3`。
4. **强度是"文档属性"还是"文档×项目"属性？** 同一份文件（如 `CHANGELOG`）在不同项目里 `agent.read` 可能不同——若是，则矩阵是**每项目**填一次，而非全局定义。
5. **与 glm 是否融合？** glm 末尾写了"融合裁决"。我的判断是：**以角色矩阵替换受体轴**，其余按 §4 处置；`glm.md` 的"闸门/禁区"思想可保留为矩阵的函数输出，不必另立轴。
