# Agent 开发中的文档模型

> Codex（GPT-6），2026-10-12。本文展开可复用的文档职责、读取与维护方式，供设计和研究时参考。具体项目可以合并、细分或采用不同组织方式。

## 模型在描述什么

文档模型是对反复出现的信息职责和使用关系的描述。它可以解释材料保存什么，何时会被需要，读到后应该怎样使用，什么变化使它失效，以及怎样维护。模型不等于文件名；同一个名字在不同项目里可以承担不同责任，同一份文件也可以组合几种模型。

可以从三个层次建模。**内容职责**回答“它为哪种判断保存什么”；**读取与维护原型**回答“它怎样进入工作、演化和结束”；**文档实例**回答“实际用哪个文件、章节、工具结果或服务承载”。三个层次可以组合，不要求其中一层唯一决定其他层。

例如“当前架构说明”描述内容责任；“进入相关子系统时取得、随实现更新”描述使用和维护；`ARCHITECTURE.md` 的某一节是实例。同样的架构可以被默认提供、从入口找到或搜索命中。路径变化不必立刻产生一个新内容模型，但如果它带来独立的可靠性和维护责任，也值得进一步细分。

一个有用的模型应使读者更容易回答具体问题。撤去这类材料，Agent 会失去哪一种判断、操作、核验或恢复能力？能从现有代码、工具或别处低成本补回吗？这是一种反事实检查，不是认定每个候选都不可替代。单个实例足以提出一种候选，更多实例和反例帮助判断它的可复用范围。

## 项目定位、工作入口与导航

### 项目定位与目标说明

定位说明帮助开发者判断项目是什么、服务谁、为什么存在、当前优先问题和不准备承担的范围。它可以包含愿景、使命、原则、产品边界和阶段目标，但需要区分稳定方向与当前任务承诺。

它通常在初次进入、目标不清、形成方案或交付时有用。README、项目简介、VISION、MISSION、PRINCIPLES、VALUES、IDENTITY、BRIEF 或 THISIS 都可能承载这项责任；名称本身不证明需要独立文件。简短定位可以放在现有入口，面向不同接收者的独立交付则可能值得另写。

项目目标、受众、范围或主要能力变化时，需要更新相关说明。当前没有采用的愿景可以保留为设想；不能把未来方向写成已实现能力。人类审查在这里主要决定目标和优先级，Agent 可以据此组织具体工作。

### 协作入口与客户端适配

协作入口给出开始工作所需的背景、有效边界、常用操作入口和进一步读取线索。AGENTS、CLAUDE、GEMINI、Cursor 规则或 Copilot 指令文件可能承担这类工作，但它们被何种客户端发现、优先级如何、是否支持导入，属于具体实现。

多个入口可以有四种关系：各自保存独立内容；互补地保存项目事实与客户端差异；共同引用负责正文；由一个来源生成多个适配表示。选择要看消费者支持和维护成本，不能默认一个名字永远只是另一个的别名。

入口的内容应足以使开发者选对最初动作。项目特有词义、影响理解和方案的限制可以直接出现；大量具体规则和接口细节可以给明确条件后再取得。默认入口与用户消息的实际权限关系由运行系统确定，不能因名字叫 AGENTS 就称其拥有系统提示的地位。

### 导航、库存、文件树与大纲

这些内容都帮助定位，但回答的问题不同。**导航**将问题或任务连到材料；**文件树**展示物理层级；**库存或注册表**保存稳定身份和可筛选属性；**大纲**安排某项论证、教材或产物的次序；**资产清单**还可能包含图片、数据集和脚本。INDEX、TREE、registry、outline、MANIFEST、CATALOG、CHEATSHEET、SKILLS 清单、MINDMAP 或 llms.txt 可以承担其中一种或多种责任。

如果已经知道唯一目标路径，直接读取可能最有效。若材料多且用途不明显，问题式入口、少量描述和触发条件可以减少试读。目录和搜索足够时，不需要另一份人工总表；有固定字段查询、稳定标识或跨目录对象时，结构化库存可能更合适。

导航的更新触发来自对象增删、职责或路径变化，库存还受字段含义变化影响。生成的目录树能减少人工同步，但人工说明仍可以补充“何时来这里”。大纲若安排尚未完成的内容，也承担计划责任，不能统一称为不随时间改变的元数据。

## 当前对象的解释与契约

### 系统结构与设计说明

当前说明使开发者形成足以定位改动影响的理解：组件怎样协作、状态与数据怎样流动、关键边界是什么、哪些关系决定行为。架构图、结构正文、模块说明、性能说明和兼容性说明都可以服务这一责任。

ARCHITECTURE、DESIGN、OVERVIEW、DIAGRAMS、systemPatterns 或某份 SPEC 的结构章节，可能描述当前系统，也可能描述目标方案。状态应由正文说明，不能由标题推定。进入陌生系统、跨模块改动和诊断异常时常需要关系解释；局部任务也可以只从相关模块开始。

实现关系发生变化或新证据推翻解释时更新。能够从代码生成的依赖视图可以直接生成，难以从局部源码看出的设计理由和边界仍用文字解释。只有目录树通常不足以说明组件关系，但一份带有数据流和语义的地图可能已承担架构说明。

### 术语、概念关系与用词约定

术语表解释某个词在当前语境中的含义，概念模型解释对象及其关系，用词约定表达以后应采用什么说法。三者可相邻，也可在独立查询和维护需求明显时分开。GLOSSARY、LEXICON、DOMAIN-GLOSSARY、DOMAIN-MODEL、MODELS、命名词典和缩写表都可能是载体。

如果“会话”在项目中表示跨调用的持续任务，应说明它与连接、用户和当前模型输入的关系。一个定义加例子或反例，往往比堆积同义词更能辨认边界。新造词、通用重载词和来源中采用不同义项的词，都可能需要解释；不必给所有常识重新编词典。

理解其他内容离不开的核心定义应能提前取得，全量词表可以用于按需查询。词义变化时保留必要的替代说明；若引用的是外部作者术语，先说明语境差异，不为了统一名称改写来源所说的内容。

### 当前能力、限制与技术环境

能力说明表达现在支持什么、不支持什么，以及成立条件。限制可能是当前缺陷、版本约束、设计上不支持、未来待补能力或当前决定不做；它们会带来不同的行动。LIMITATIONS 里的一个条目可以同时关联问题记录、设计解释与有效约束。

技术环境说明保存工具链、依赖、平台、存储、环境变量和启动条件。TECH_STACK、DEPENDENCIES、ENVIRONMENT、techContext 或模块 README 都可以承载。清单可从配置恢复，但非标准命令、版本冲突、部署限制和选择理由未必由清单表达。

当前环境或能力变化时修订。操作前可以核对与本次任务相关的条件，不必每次读完全部环境史；稳定说明也不能仅因长期未改就被视作新鲜。个人目录里的环境文件可能只适用于一个项目，不能由位置推定它是通用个人偏好。

### 接口、数据和业务契约

接口契约规定调用者与实现者共同依赖的行为：参数、返回值、错误、类型、状态变化和版本条件。OpenAPI、GraphQL Schema、gRPC Proto、类型定义、API 参考或生成说明可能分别提供其中一部分。原生定义能直接表达的内容不必再手抄一份独立真相；行为语义和重要例外仍可能需要解释。

数据契约关注实体、关系、存储约束、序列化、迁移与兼容。Prisma 的结构定义、对象关系映射（ORM）中的实体、SQL 数据定义语句、实体关系图和 DATA-MODEL 是不同承载方式。修改字段时，解析器、序列化器、存储和外部调用者可能共同依赖它，不能只凭局部类型检查判断兼容性已保持。

业务规则和需求说明表达使用场景、对象含义、优先级、行为边界和预期结果。产品需求文档（PRD）、BUSINESS_RULES、领域说明或实例化验收条件都可能提供信息。它们往往在方案选择前就有用；当前实现不能唯一推导用户真正要求。

这几类契约可以作为独立模型研究，也可以视作“当前说明＋有效要求”的具体内容分支。值得独立的条件是使用、版本、责任或校验方式有明显差异，而非仅因为技术领域不同。

## 当前约定、操作方法与完成判断

### 当前约定与选择准则

约定保存当前采用的规则、默认选择、例外和必要理由，帮助多次工作保持一致。它可能涉及代码风格、内容组织、命名、依赖、兼容、提交、审查或论证质量。CONVENTIONS、STYLE、CODING-STANDARDS、GUIDELINES、CODE-REVIEW、VERSIONING 或相关政策章节，都可能承担责任。

硬要求、建议和经验应能辨认。代码格式可由工具精确执行，什么证据足以支持研究结论则需要语义判断；两者即使同叫“风格”，也不必用相同维护方式。短规则可以同页，只有独立读取和变化需要明显时才拆文件。

读取发生在第一次受其影响的判断前。会改变设计空间的要求不能统一推到写代码时才给；与当前任务无关的格式细节也不必全部提前展开。变更来自新的采纳决定、适用范围变化、反例或工具机制变化。

冲突处理应结合当前任务、来源、实际范围和负责选择。局部规则可以是例外，也可能仍受全局条件约束；历史记录可以解释原因，却不天然覆盖今天的要求。按文件名排出固定高低顺序，通常不足以表达这些关系。

### 操作规程、脚本与技能

操作规程帮助在明确前提下完成重复工作：安装、启动、测试、调试、迁移、发布、测量或资料处理。它通常需要前置条件、实际步骤、资源、成功判断和有意义的失败处理。RUNBOOK、PLAYBOOK、OPERATIONS、INSTALL、SETUP、DEBUGGING、TROUBLESHOOTING、MIGRATION、RELEASE 或 BENCHMARK 说明，可能承担这项责任。

步骤可以引用可执行脚本、准确接口和当前规则。工具能承担的机械工作交给工具，文字保留决定怎样使用工具的条件。比如生成文件不应直接改结果，而应修改源定义再重建，这会改变实施顺序，值得说明。

Skill 可以把发现描述、触发条件、操作步骤、适用规则引用、资源和结果检查组织在一起。规则继续由负责来源维护，技能在需要时调用或引用。普通步骤文档改名成 SKILL.md 不会自动产生发现和执行能力，具体触发、资源访问、正文展开和结束后保留由运行系统决定。

维护 Skill 的职责也可以直接研究：它识别什么变化，找哪份负责正文，怎样修改或重建，检查什么结果。若只是把现有清楚步骤再包装一次，收益可能很小；若反复减少漏项和重复操作，就有独立复用价值。规程的实际使用反馈、工具升级和必要演练，都是更新依据。

### 测试策略与验收说明

这类内容帮助判断什么算完成。应区分测试目标和要求、怎样运行、实际运行结果。TEST_STRATEGY、TESTING、验收标准、端到端测试场景，以及按“给定条件—触发动作—预期结果”（Given-When-Then）表达的用例，分别可能提供这些内容；它们可以同页，但不能互相替代。

验收条件可能影响方案和测试设计，因此不一定只在最后读。已执行什么测试、哪些条件未覆盖、失败来自环境还是实现，需要明确。通过一组现有测试不自动证明用户的新需求完整满足。

操作说明随工具和环境维护；验收要求随目标和契约维护；一次执行记录保留当时条件与结果。三个责任的更新触发不同，是可以拆分的理由；一次小任务也可以在同一段清楚说明。

### 教程、操作指南、参考与解释

这四种写法分别侧重建立能力、完成已知任务、精确查询和理解原因。例如初学者教程安排一条学习路径，迁移指南帮助执行具体变更，API 参考提供字段与行为，设计解释说明为什么存在这些边界。

它们可以帮助组织内容，却没有回答何时加载、是否已采纳或怎样维护。开发 Agent 往往更常需要项目特有操作和准确参考；在学习陌生系统或交付教程时，完整教学材料也可以成为主要内容。这个区别来自任务，不来自“人类文档”与“Agent 文档”的永久划分。四种使用需求的外部框架可参见 [Diátaxis](https://diataxis.fr/)。

## 目标、计划、探索与持续工作

### 路线、问题与优先级

路线说明保存方向、候选工作、优先级和承诺强弱；问题记录保存现象、影响条件、已有观察和仍待解决的部分。ROADMAP、PROBLEMS、KNOWN-ISSUES、BACKLOG、RISKS、MILESTONES、TODO、METRICS 和任务板可以承担这些责任。

问题不必预先绑定解法，路线项目不必全是交付承诺。能力限制可能是已知问题，也可能是有意不支持；是否值得继续由当前目标、条件和代价决定。文档还是外部问题板，由协作、查询和更新需要决定，不存在“高层问题不能进 Issues”的通用要求。

持续变化的方向和状态需要能区分当前与历史。完成、放弃或被替代的事项，不应继续以未完成任务的身份驱动 Agent；对未来有价值的理由和结果仍可保存。

### 当前任务与工作状态

任务工作材料保存当前目标、范围、计划、进展、未决项、已排除路径、验证状态和下一步。TASK、PLAN、PLANS、WIP、STATUS、activeContext、TASK_QUEUE、阶段任务板或简短工作笔记，都可能实现这一责任。

它在形成方案、执行、观察反馈和恢复时使用，通常随实际进展改写。计划可以表达未来意图，也可以记录正在执行的状态，完成后又有历史价值；这不要求每改一次时态就迁移一次文件。

简单任务如果已有对话与工具状态足以稳定保留进度，就不必另建工作文件。跨会话、执行者切换或长任务中，外部工作状态可以减少反复重建。重要的是下一次能恢复到什么程度，而非必须写固定格式。

任务结束时，当前事实回到负责说明，仍有效的选择回到当前约定，重要理由进入可复查记录，原始观察保留必要条件。临时内容可以结束、归档或删除；不是所有草稿都应自动成为长期知识。

### 提案、研究与未定方案

提案保存问题、前提、比较方向、候选方案、尚未核实之处和可能的检验。意见征求稿（RFC）、PROPOSALS、研究稿、设计草图、未定规格说明（SPEC）、实验计划和 TRADEOFFS 都可能承载。它们提供一个能够继续修正的思考对象。

未采纳是状态，架构、需求或操作方案是职责。未审架构仍可以供比较，读一份提案也不意味着接受它的全部要求。方案被接受后，仍需区分实施进度和对现状的描述。

短任务可以把提案放在当前工作页；长期独立评审、多个分支、稳定引用或单独交付的方案，可能值得成为独立原型。单例也可以提出新的组织方法，是否泛化再由后来任务判断。没有内容的占位字段或没有定义的术语，不需要为了“完整”硬写成模型。

### 交接与恢复

交接说明是面向接续者的工作状态表示。它需要足以恢复目标、实际进展、依赖、未完验证、阻塞、必要依据和下一步。HANDOFF 可以独立，也可以是任务页的一节；名字不决定恢复质量。

日期动作索引只告诉读者发生过什么，不一定足够继续任务。完整对话保存更多过程，但寻找关键条件可能成本较高。摘要与可检索原文可以组合，前提是关键理由没有只剩模糊指针。

恢复后应核对现在的代码、环境和任务目标。其他主体的修改可能使旧状态部分失效。若存在跨团队签收、长期移交或固定机器交接接口，交接会形成独立维护责任，届时可以从一般工作状态中细分。

## 决定、证据与来源

### 当前短理由与完整决策记录

当前短理由解释一个有效选择为什么影响今天的判断；完整决策记录保存当时的问题、约束、采用方案、重要备选、结果和替代关系。两者可以服务不同读取需要，但不必物理分成两份文件。

例如项目曾为单用户选择本地文件，现在因并发要求改用数据库。当前说明保留实际存储路径、事务边界和“为什么现在需要事务”的简短理由；历史记录保存旧条件、当时排除的方案和变化原因。未来重访选择时，条件比一句“当年决定如此”更有价值。

架构决策记录（Architecture Decision Record，ADR）、DECISIONS、已定 RFC、decisionLog、部分 TRADEOFFS、复盘结论，都可能承担记录责任。DECISIONS 也可能只是索引；TRADEOFFS 也可能是当前取舍原则或尚未结束的比较。文件名不能裁决身份。

记录可以经历提案、采纳、拒绝、实施、弃用、被替代等状态。活动中的实施事实可以更新；保留当时选择的记录可追加替代说明；发现错记时需要明确更正。是否冻结正文、怎样命名和归档，是维护选择，不是“记录”一词的必然含义。[Nygard 的 ADR 提议](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)以背景、决定、状态和后果为基本内容，也允许以后将旧决定标为被替代。

跨主题的一个决定可以被多个正文引用，不必复制到多个同名目录。少量短理由可以直接留在当前说明；需要独立追溯的完整取舍再单独保存。并非每个细小修改都要形成长期决定记录。

### 原始事件、实验与复盘

事件记录保存实际发生的动作和观察。CHANGELOG、RELEASE-NOTES、LOGS、MEETING-NOTES、STANDUP、事故时间线、会话导出、实验原始结果、BENCHMARKS 与 DATASETS 都可能属于这一范围，但消费者和精度要求不同。

实验至少涉及问题或计划、输入与设置、执行结果、分析与结论；复盘还可能产生决定和行动项。它们可以在一篇小研究中分段，也可以分别保存。原文件状态变化与从原始结果生成新结论，是两种关系；不能在“转成结论”时覆盖原始观察。

观察冻结在当时条件下，不代表记录不会错。更正应能区分错记、新观察和解释改变。实验也不只包括失败或废弃方案：支持当前方案、无区别结果、未成功复现都可能帮助以后判断。

事件历史可以从工具生成，重要理由却未必能从提交差分恢复。保留哪些原始材料，取决于要支持的结论、恢复成本和复用需要。完整过程并非永远必要，只有最后一句结论也可能不足。

### 外部来源与技术参考

来源材料包括论文、标准、外部 API 文档、第三方仓库、厂商说明、数据和其他作者的研究。sources、PAPERS、THIRD-PARTY 或 vendored 文档只是位置线索；里面既可能有固定快照，也可能有会刷新的检出目录。

需要判断技术细节、验证解释或复用方法时，取得相关内容及其版本。固定快照可以并列保存不同版本，动态来源可以在使用时确认条件；本地解释与原文身份保持可辨。无需先把每一段外部原文复制成自己的笔记，才允许引用。

来源归属与历史职能可以重叠。外部论文可以是证据，内部实验同样可以是证据；外部原文不由本项目修改，但本项目仍负责准确引用和判断适用性。长期保存也不证明内容永远正确。

## 经验、个人设定与对外交付

### 项目经验与跨会话记忆

经验材料保存后来仍可能使用的事实、纠偏、教训、有效方法和失败条件。MEMORY、LESSONS、日期笔记或宿主记忆库可能承担责任。它需要实际保存与取回机制，命名为 MEMORY 不会自动带来跨会话使用。

持续任务的进度应优先作为工作状态；普遍适用于项目的当前事实可以进入说明；有效要求进入约定；某次选择的理由进入决策记录。经验的放置可以按其当前用途变化，不必全部堆进一个记忆文件。

提炼经验时保留主体、来源、条件和可修正性。模型自己产生的解释可能在以后被反复读取，因此有必要区分观察与推断；也不必把所有模型生成内容统一视为低可信。验证和反馈如何进入后续更新，比作者标签更能说明可靠性。

### 用户偏好与助手设定

USER、SOUL、PERSONA、IDENTITY、LOCAL、AGENTS.local 或个人配置，可能保存用户事实、交流偏好、助手行为设定，也可能只是这些机制的设计文档。应先读实际内容和消费者，不从同名直接推定它是运行数据。

项目经验与跨项目偏好有不同范围。用户偏好在某个场景有效，不一定应成为整个团队的规定；个人目录里的项目要求也不因此能跨仓使用。纠正、缩小范围、合并和删除都是可能的维护方式，隐私和共享边界按实际信息处理。

自述身份在持续助手中可能是重要输入，在某个局部开发任务中也可能几乎无关。可以把它单独作为研究角度，而不用它限制所有开发文档的分类。

### 面向用户、社区和外部协作的材料

README、QUICKSTART、教程、发布说明、SUPPORT、CONTRIBUTING、SECURITY、CODE_OF_CONDUCT、LICENSE、NOTICE、AUTHORS、CITATION、FUNDING 和供应商条款，各自服务上手、协作、支持、分发、引用或归属等任务。

Agent 可能读取它们来理解有效要求，也可能负责制作它们作为交付物。发布库时，支持范围、依赖许可和用户迁移说明可能直接影响工作；普通局部修复中，则不一定需要主动展开。原受众不能决定资料永远不进入开发输入。

同一对外文件常有多职责：SECURITY 可含内部政策、披露步骤和公共接口，CONTRIBUTING 可含约束与操作，README 可含定位、架构、安装和业务说明。是否拆分，取决于独立使用、更新与交付，而不是要维持文件唯一归类。

## 读取与维护可以形成另一组原型

内容职责之外，还可以研究以下稳定的使用方式。它们相互组合，不要求把所有组合预先枚举成文件类型。

| 使用与维护方式 | 它解释什么 | 适用条件与容易忽略的部分 |
|---|---|---|
| 开始时默认提供 | 工作开始就需要的定位、语义、边界和下一步线索 | 适合缺失难察觉或反复必需的前提；预算与真实加载机制决定实际供给。 |
| 阶段前按条件提供 | 设计、修改、验证、发布等活动前的必要内容 | 时点依赖具体判断；阶段可跳过或返回，约束不天然只在写前使用。 |
| 进入子域时提供 | 模块、目录、接口或环境的局部事实与规则 | 适用范围与发现范围不同；访问路径未触发加载时，局部说明仍可能未取得。 |
| 入口引导后取用 | 先给问题、条件或材料描述，再跟随到正文 | 需要维护路由与负责内容的关系；只给路径可能不足以选择。 |
| 自主判断后查找 | Agent 发现信息缺口，利用搜索、目录、查询或外部工具取得 | 有足够线索和访问能力时很灵活；对难以察觉的缺失可能需要早期提示。 |
| 当前正文随对象更新 | 持续描述有效事实或当前选择 | 修改负责项并处理受影响表示；历史仍可独立保留。 |
| 提案逐步形成与采纳 | 从未定想法、比较、接受到实施或拒绝 | 采纳不等于实现；拒绝原因和重新考虑条件可能有复用价值。 |
| 工作状态持续改写 | 目标、进度、阻塞与下一步在任务中更新 | 结束时需要区分可复用结果与临时状态；恢复后核对现实。 |
| 事件追加与显式更正 | 保存发生过的观察及后来纠错关系 | 追加策略有助于留痕，但错误记录仍需可识别地更正。 |
| 固定来源按版本保存 | 让后来知道当时依据的是哪份外部材料 | 新版可并列或替换当前入口；原件身份和解释分别维护。 |
| 从负责来源生成视图 | 根据代码、数据或正文生成接口、树、摘要、索引 | 生成方法、源版本和刷新条件决定新鲜度，自动生成不等于永久正确。 |
| 概览与全文分层使用 | 默认给短定义或骨架，需要时取正文与依据 | 摘要必须保留其服务判断的关键条件；概要、全文不必各自成为独立真相。 |
| 跨任务持续与纠正 | 保存个人偏好、项目经验或长期状态 | 需要明确主体、范围和恢复方式；长期保存不等于所有任务都要加载。 |

如果某个差异长期改变读取可靠性、更新责任或使用身份，可以据此细分原型。反之，仅仅改了具体触发时刻或展示格式，而责任未变时，保持一个模型加条件描述可能更清楚。两种建模方法都可研究，选择由要解决的问题决定。

## 组合实例怎样处理

文件名经常隐藏组合。ARCHITECTURE 可以同时有当前关系、有效边界与简短理由；GLOSSARY 可以同时有定义与用词约定；TESTING 可以同时有验收目标、运行步骤和结果入口；EXPERIMENTS 可以同时有计划、观察和解释。

处理组合至少有四种方式：同页明确分段；按独立责任拆成文件；保留一个负责来源而生成多种视图；按任务只选择相关片段。选择时比较共同理解、独立更新、引用和交付的收益，以及拆分后的跳转、发现和同步成本。

例如同一份能力限制中，一条写“当前只支持单用户”，另一条写“本次不得改变旧格式”。前者是现状，后者是要求；它们可能与同一个迁移任务有关。可以在同页说明身份，也可以分别放当前说明和任务约定。关键是读者能分辨，不是必须建出两份文件。

决策摘要也有两种价值：帮助现在快速了解有效选择，帮助未来定位完整理由。前者需要足够的条件和当前效力，后者需要可用的检索线索；只列标题不一定完成前一种责任。概览与原文的分工应按实际判断需要设计。

## 格式与查询方式怎样配合模型

| 表示 | 适合的主要工作 | 需要一起考虑的条件 |
|---|---|---|
| Markdown 和连续正文 | 定义、理由、步骤、例子、关系解释 | 能保持必要前提相邻；自由排版不等于稳定机器字段。 |
| CSV 或 TSV | 固定字段清单、筛行选列、实验参数与结果 | 类型、空值、引用和多行字段需要明确；应使用标准解析，不按裸逗号或物理行猜记录。 |
| JSON | 机器交接、嵌套数据、接口原生结构 | 重复键名和格式化改变体量；标准语法不支持普通注释，长篇解释放字符串未必好用。 |
| YAML | 人经常编辑、消费者支持的层次配置 | 解析器、类型解释与支持的子集会影响含义；无需为省几个符号引入复杂特性。 |
| XML | 明确的标签结构与消费者契约 | 标签是语法和解析边界，不自动构成模型注意力隔离。 |
| 数据库与查询 | 多表关联、反复筛选、索引和事务更新 | 查询与导出有成本；SQL 是语言，数据库文件是载体，不能混成一种文本格式。 |
| 图、网页、PDF 和电子表格 | 关系、排版、公式、图表及特定用户交互 | 要看读取工具、定位、版本、编辑和输出需求；文本差分不方便不足以证明载体没有价值。 |

CSV 的相关语法可参见 [RFC 4180](https://www.rfc-editor.org/rfc/rfc4180)，JSON 参见 [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259)，YAML 的版本化说明见 [YAML 1.2.2](https://yaml.org/spec/1.2.2/)。这些规范说明格式能表达什么，不直接说明模型任务效果。

名字和格式应服务消费者及读写工作。一个来源清单可以用 CSV，获取事实用 JSON，论证用 Markdown；多种载体同时存在并不证明同步已完成。需要程序执行、字段查询或精确契约时，结构化表示有优势；需要解释条件和理由时，正文仍有作用。

## 让模型用于新的研究

对一份准备新增或重写的材料，先用几句话说明它帮助完成的工作、使用身份、需要时点、依据、变化和恢复方式。已有位置可以承担时，改已有内容；需要独立阅读、引用、更新或交付时再拆分。文件数量、字段数量和模型数量都不是价值本身。

比较模型时，可以使用小修改、跨模块变更、未完任务恢复、重访历史选择和对外交付等不同任务。一个分类在所有样本上都能填满，不等于信息得到正确使用；一个混合实例也不表示分类失败。模型的作用是让重要差异变得可理解，并帮助识别新的问题。

当前材料可以形成明确主张，也可以留下不同方案。新的证据或更好的解释出现时，重新研究即可。没有必要为了维护现有类别，让后来的工作先接受它的全部边界。
