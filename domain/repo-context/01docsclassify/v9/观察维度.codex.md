# Agent 开发中的文档：观察维度

> Codex（GPT-6），2026-10-12。这里展开可用于理解和比较文档方案的观察角度。按研究问题取用，不要求每份材料填写全部属性，也不要求所有维度互斥或相互独立。

## 先确定观察的对象

同一个属性，放在不同对象上可能含义完全不同。“频繁使用”可以指经常打开文件，也可以指只读过一次、但其内容反复随模型输入提交；“已经接受”可以指方案获采纳，不表示已经实现；“在子目录”描述位置，不证明规则只对该目录有效。

可以分别观察一条信息、一份文档、一次读取、一次模型调用、一个开发任务或一组协作主体。许多维度属于关系：某项资料在任务甲中必须提前提供，在任务乙中完全不需要；同一文件由 Agent 阅读、工具解析、人维护，并不要求在三者之间分配总和为百分之百的受众权重。

文档也可能有多种表示。一个负责正文可以产生概览、检索片段、结构化清单和对外说明；这些表示承担不同使用任务。比较前先说清所指的是正文、派生视图还是本次实际输入，才能知道差异发生在哪里。

## 内容在讲什么，帮助完成什么

| 观察角度 | 含义和可能区别 | 例子与判断用途 |
|---|---|---|
| 内容指向 | 项目实现、运行系统、用户、环境或某项产物，是被描述的对象。它与阅读者不同。 | Agent 读取一份用户需求，阅读者是 Agent，内容指向用户问题；不能据保存目录推定对象。 |
| 内容职责 | 定位、解释、定义、约束、操作、导航、意图、状态、理由、证据、历史和偏好，承担不同信息工作。 | 一份 README 同时介绍项目、给出启动步骤和限制；可以逐段辨认，不强迫整文件只有一种职责。 |
| 开发任务 | 理解问题、查找实现、设计方案、修改、测试、诊断、发布、恢复任务或审查结果。 | 同一架构说明可能用于设计，也可能用于解释故障；“给 Agent 看”还不足以决定细节和读取时点。 |
| 帮助形成的能力 | 材料可以帮助定位、理解关系、约束选择、执行操作、证明结果或接续工作。 | 撤去接口说明后，Agent 可能仍能查源码，但重建调用语义更费时；这比仅看文件名更能说明价值。 |
| 对象层次 | 目标原则、整体系统、模块、接口、局部操作与语法细节，描述的尺度不同。 | 系统图适合看跨模块关系，参数表适合精确调用；层次高不自动拥有更高指令效力。 |
| 内容是否研究自身 | 有的文档描述业务系统，有的描述如何研究、维护或组织文档。这是对象与自我描述的关系。 | 一份分类研究可以讨论分类法本身；它并不因此成为“永恒信息”或必然归入导航。 |
| 认知功能的比较角度 | 可以观察它是否承担概念知识、事件回忆、操作方法、当前工作状态、检索线索或主体设定。 | 这些功能有助于比较失效和恢复方式；它们是外部信息用途，不证明模型内部存在对应文件结构。 |

对同一材料问“保存什么”和“使开发者能够做什么”，可能得到不同答案。实验日志保存观察，但用途可能是查证、复盘或选择方案。两种描述可以互补，不必选其中一个消灭另一个。

## 谁生产、使用、维护和决定

| 观察角度 | 含义和可能区别 | 例子与判断用途 |
|---|---|---|
| 消费者 | Agent、人类开发者、最终用户、审查者或确定性程序；一份内容可服务多个消费者。 | 接口结构定义（API Schema）可以被生成器解析，也被 Agent 读取；对外许可证在分发任务中也可能是开发输入。 |
| 工作角色 | 同一主体可以进行研究、实现、测试、架构判断、审查或个人辅助。 | 不同 Agent 实例也可能承担同一种工作；按产品或模型名划分读者，未必比按任务有用。 |
| 作者 | 人、模型或共同创作，以及具体来源身份。作者说明谁产生过内容。 | AI 起草后经人修改，仍应能辨认来源；这不能单独说明每条事实经过了什么核实。 |
| 生产机制 | 手工编辑、模型生成、源码提取、确定性生成、工具导出或混合加工。 | 人运行脚本生成 API 文档，作者操作来自人，内容生成却可重建；“人工／AI”和“可生成／不可生成”不是同一轴。 |
| 维护责任 | 谁在对象变化后负责保持内容可用，谁能够推进更新。 | 开发 Agent 可以更新当前架构，人负责决定目标是否改变；阅读很少的人也可能承担关键维护责任。 |
| 审查责任 | 谁核对事实、谁决定采纳、谁审阅表达、谁检查最终行为。 | 测试检查一部分运行结果，用户决定是否满足需求；一位审查者不必承担全部核验。 |
| 修改与决定范围 | 直接修改、提出建议、决定采用、撤回或替代，是不同权能。 | 已授权的实现修复可以包括同步说明；变更产品目标可能需要人的选择。不能仅因文档属于某一类就新增审批。 |
| 来源所有权 | 项目自产、个人材料、第三方原件、供应商标准或共同维护。 | 本项目可能无权改第三方标准，却仍负责准确引用及解释其适用范围；不维护原文不等于不核实使用条件。 |

“人写给 Agent”“Agent 写给自己”“Agent 写给人”“人写给人”是几种生产消费关系。自写自读可能重复传播错误，但外部测试、用户纠正和新证据也可能打断传播。作者身份适合帮助追溯，不适合直接变成固定信任等级。

## 在什么范围成立，放在哪里

| 观察角度 | 含义和可能区别 | 例子与判断用途 |
|---|---|---|
| 适用范围 | 本机、用户、项目、子树、模块、接口、环境、版本或当前任务。 | 某个模块的禁止依赖约定即使在根入口被读到，也未必约束别的模块。 |
| 存放位置 | 根目录、模块旁、集中 docs、个人目录、宿主存储、外部服务或对话记录。 | 用户目录里可以保存只针对某个仓库的要求；位置不等于语义范围。 |
| 搜索范围 | 查找从哪里开始，是否包含祖先、子树、多个工作区或外部来源。 | 一个加载器只查当前目录，另一个沿祖先链查找；同样的目录布局可能产生不同输入。 |
| 可访问范围 | 工具当前能读哪些路径、服务或资源，受哪些实际条件影响。 | 已知道资料路径但没有相应工具访问能力，仍不能承诺需要时一定取得。 |
| 可见与共享边界 | 公开、团队共享、项目内部、个人、本机或特定角色可见。 | 私人偏好与团队约定可能同样长期有效，却有不同共享对象；不能按“长期”推定共享。 |
| 可携带性 | 内容离开这个项目、会话或主体后，是否仍有意义。 | 个人语言偏好可能跨项目，某项目的构建命令通常不会；可携带性与保存年限不同。 |
| 抽象与覆盖关系 | 更高层的解释、全局规则、局部例外和具体任务要求如何关联。 | 具体范围可能构成例外，也可能仍受全局约束；需要实际规则和授权，不能只用“局部总优先”推导。 |

范围本身也会变化。一个试验性约定可能后来扩成项目标准，一个全项目规则可能因反例缩小到某些模块。范围变化应进入当前表达，而不是只在历史里留一句说明。

## 一句话应该被当作什么

| 观察角度 | 含义和可能区别 | 例子与判断用途 |
|---|---|---|
| 陈述性质 | 来源原文、观测、事实主张、推断、假设、约定、意图或历史记载。 | “测试在环境甲通过”是观察；“所有环境都可靠”是外推。二者需要不同依据。 |
| 使用方式 | 当作当前要求、参考材料、候选解释、操作指引或被研究对象。 | 论文中引用的恶意指令仍是研究对象；读到命令句不意味着应执行它。 |
| 约束强度 | 必须满足的条件、默认选择、建议、经验或可选做法。 | 风格建议允许因任务调整，兼容性要求可能不能自行放弃；语气强弱不等于实际授权层级。 |
| 承诺程度 | 已决定、方向性意图、条件承诺、探索中、暂缓或明确不做。 | 路线图可能表达优先方向而非交付日期保证；计划项目不是已经实现的能力。 |
| 行动授权 | 文本是否包含本次允许做什么的决定，以及范围是否仍有效。 | 某计划可能已经获执行授权，也可能只是备选；不能统一称所有计划都不授权或都授权。 |
| 采纳状态 | 草拟、提案、接受、拒绝、弃用或被替代。 | 接受一个设计，说明选择已定，不说明代码已经符合设计。 |
| 实施状态 | 未开始、实施中、部分实现、已实现、已验证或回退。 | 架构稿写“已迁移”而代码仍是旧实现，需要核对实际进展；最近编辑日期不能裁决。 |
| 证据状态 | 已定位来源、核对原文、观察到实现、实际运行、重复验证。 | 有源码路径不等于执行过该分支；文件哈希一致不证明论证正确。 |
| 置信判断 | 对内容的把握及其理由，可以是文字判断，无须人为编百分数。 | 对原始记录有较高把握，对跨任务外推仍不确定；两者可同时存在。 |
| 有效性的依据 | 当前任务与采纳决定、实现与运行、事件原件、实验结果、外部标准或实际布局。 | 约定冲突要问哪项选择仍有效；版本数字冲突要回到获取事实；不存在统一的“文档／代码永远优先”。 |
| 语义偏离 | 项目含义与常见含义一致、重载、全新、存在歧义或暂不清楚。 | “会话”可能指连接也可能指持续任务。需要定义和关系说明，不等于提前放入全部词典。 |

把这些问题压成一个“可信／不可信”，会丢失行动差别：可信的历史未必是当前要求，未采纳的方案可以有正确事实，已经实施的代码也可以违反有效需求。

## 时间、有效期和变化

| 观察角度 | 含义和可能区别 | 例子与判断用途 |
|---|---|---|
| 时间指向 | 描述过去发生、当前情况、未来意图或跨阶段要求。 | 一份计划随着执行成为状态记录，完成后又有历史用途；时间指向不必决定搬文件。 |
| 有效条件 | 对哪些版本、环境、任务或前提成立，何时开始或不再成立。 | 迁移命令只适用于某个数据库版本；发布日期不是它唯一的有效条件。 |
| 产生与编辑时间 | 原内容何时产生，文件何时被修改。 | 修一个错字会改变修改时间，但不证明整篇事实已重新核验。 |
| 最近核验 | 最近在什么条件下检查过什么内容。 | 某操作指南上月在环境甲演练成功，不代表昨天升级的环境乙也成功。 |
| 复核安排 | 计划何时、因何事再检查。 | 随工具升级复查与每季度复查是不同方式；计划复查日期不等于当前失效日期。 |
| 变化频率 | 对象可能极少、缓慢、频繁、任务级或会话级变化。 | 高频依赖清单适合生成；长期稳定的定义仍可能因新证据修订。 |
| 更新触发 | 实现、依赖、政策、需求、任务状态、用户纠正、上游新版本或反例发生变化。 | 变更了公共接口，应看说明与调用示例；不必同步改与它无关的项目介绍。 |
| 生命周期 | 构想、草拟、采纳、实施、使用、失效、替代、结束等经历。 | 采纳、实施和归档可以独立变化，未必要排成一条统一成熟度阶梯。 |
| 保存期限 | 单次使用、会话、任务、项目或长期保存；是否仍有复用需要。 | 临时输出可以很快结束，重要原始观察可以长期保留；保存与默认读取分别选择。 |
| 退出结果 | 删除、归档、不再默认提供、被替代、关闭任务或缩小适用范围。 | 任务已完成不等于所有结果应删；归档也不自动取消当中仍有效的要求。 |

日历可以提醒复核，却不能代替适用性判断。一条有明确版本条件的旧记录，有时比一篇昨天写却没有条件的总结更容易正确使用。

## 怎样修改、生成和协调

| 观察角度 | 含义和可能区别 | 例子与判断用途 |
|---|---|---|
| 修改语义 | 原位改写、追加、更正后保留原件、显式替代、合并压缩、清账或完整重建。 | 当前架构随实现改写；一次原始观测不改成新运行结果；新决定可以替代旧决定。 |
| 维护机制 | 人工编辑、Agent 更新、Skill 辅助、确定性生成、与代码同步或按需修正。 | 生成目录树不需要逐项人工改，但生成时机和输入仍可能过期。 |
| 维护时点 | 对象改变时、使用前、发现错误时、任务收束、发布或周期检查。 | 完成任务时可集中提炼；影响当前行动的错误没必要等到任务结束再修。 |
| 负责来源 | 哪个位置负责某项当前含义，怎样确定应该改哪里。 | 改接口 Schema 后生成说明；理解设计理由的正文可能另有负责位置。 |
| 派生关系 | 原件、正文、镜像、摘要、索引、指针、适配文件、生成视图各承担什么。 | 客户端入口可以只做适配，也可以包含独立说明；不能仅看名字就当作副本。 |
| 可重建程度 | 能从代码、日志、外部来源或生成器恢复哪些信息，恢复过程会丢什么。 | 文件树容易重建，为什么放弃某方案未必可从最终代码推回。 |
| 同步依赖 | 哪些内容变化需要带动哪些其他表示更新。 | API 字段变化影响生成参考与示例，但不必影响每一份概览；依赖应是具体关系。 |
| 并发与合并 | 多个主体更新同一项、不同文件，或顺序依赖、覆盖、追加和合并冲突。 | 独立记录减少共享正文冲突，却仍可能同时修改索引或使用同一名称；分文件不等于没有并发问题。 |
| 保留依据的粒度 | 保存全部过程、关键观察、选择理由、短摘要或只有定位线索。 | 恢复任务需要状态，查证需要原条件；只存“当天做了什么”未必足够继续工作。 |

关系本身有含义：引用、支持、反驳、派生、取代、被否选项、前置依赖、实现对应和受影响对象，不能全部压成“相关链接”。关系可以在自然语言中说明，只有需要程序处理时才考虑结构化字段。

## 什么时候需要，怎样发现和取得

| 观察角度 | 含义和可能区别 | 例子与判断用途 |
|---|---|---|
| 首次需要时点 | 信息第一次影响理解、选择、实施、核验或恢复的位置。 | 不改公共接口的要求会影响设计；某测试命令可能执行验证时才需要。 |
| 阶段相关性 | 同一信息在任务不同阶段可能有不同价值。 | 架构关系在设计时重要，也可能在诊断时重要；不能将其静态标成只属于一个阶段。 |
| 被需要概率 | 在明确的一类任务分布下，多大比例可能需要某材料。 | 有真实任务记录时可以估计默认提供的价值；没有分布时只能给情景，不能编精确概率。 |
| 使用频率 | 每次调用、每次会话、每个任务或少数事件中使用几次。 | 文件只读取一次，之后仍可能反复作为模型输入；读取次数与消费次数不同。 |
| 发起者 | 系统、用户、Agent、入口条件或检查结果发起取用。 | 工具失败后返回修复指南，与 Agent 主动搜索的控制过程不同，但可以取得同一正文。 |
| 主动提供策略 | 默认提供、条件命中时提供、先给描述再展开，或不主动提供。 | 不主动提供的资料仍可保证随时查到；不能据此判断它低价值。 |
| 获取保证 | 承诺在所需时点默认提供、承诺需要时可发现取得、无持续保证或尚未说明。 | “可以搜索”只是能力；搜索对象完整、有足够线索和可访问才支持实际取得承诺。 |
| 触发条件 | 会话开始、进入子域、任务匹配、将进行操作、出现术语、失败、显式查询或任务收束。 | 不同事件帮助表达供给安排；不必每个触发都增加一种文档类型。 |
| 发现路径 | 名称、目录、直接链接、全文搜索、语义搜索、注册表、原生导入或明确点名。 | 已知唯一目标时可以直接读；无法判断该读什么时，问题式入口或简介可能更有用。 |
| 线索充分性 | 是否能判断资料是什么、何时使用、位置、版本及不适用条件。 | 一条裸路径可以定位，却不一定帮助选择；标题、描述或前置条件可以补足。 |
| 前置知识 | 理解某项内容前，需要哪些概念、范围、关系或先决步骤。 | 精确接口表若使用项目特有术语，仍需能取得相应定义；链接存在不保证顺序已满足。 |
| 缺失可检测性 | 缺了会报错、产生明显疑问，还是可能流利地形成错误解释。 | 非标准命令缺失常产生失败，术语误读可能不产生信号；两者适合不同提示和供给方式。 |

获取关系可以同时成立。一份当前说明既有入口链接，也能被搜索；特定任务又可能由用户直接提供。重要的是实际任务能否取得必要信息，而不是给文件强制选择一种唯一渠道。

## 实际提供了什么，保留了多久

| 观察角度 | 含义和可能区别 | 例子与判断用途 |
|---|---|---|
| 供给状态 | 作者希望被读、加载器支持、已发现、程序已读取、工具已返回、进入输入、被复述、用于行动。 | 每一项需要不同观察；程序读完整文件后仍可能只返回前缀。 |
| 选择粒度 | 整文件、章节、行段、条目、接口片段或多个文件组合。 | 工具支持片段时，维护单位不必跟着每次投递拆成多个文件。 |
| 表示深度 | 名称与指针、概览、条件明确的摘要、全文、正文与原始依据。 | 指针承担发现，摘要支持部分判断；需要例外条件时必须展开到足够深度。 |
| 上下文位置 | 前部、中部、尾部、稳定前缀或动态结果位置。 | 位置可以影响程序裁剪、缓存或模型处理，需要区分哪一层发生作用。 |
| 逻辑顺序 | 定义、问题、证据、规则、例子等内容的依赖与排列。 | 先明确“会话”的含义，再解释恢复流程，是语义依赖；不只是追求位置显著。 |
| 驻留方式 | 单次可见、阶段保留、反复携带、摘要化、移出后按需取回。 | 运行系统可能重组输入；文件自身的“请保持常驻”并不实现这些动作。 |
| 读取与缓存状态 | 曾读过、当前缓存可复用、当前输入仍包含、当前版本已刷新。 | 读取登记可以存在而正文已退出输入；缓存命中减少计算，不证明内容相关或新鲜。 |
| 恢复条件 | 能否重新取得原件、关键理由、当前状态和必要环境事实。 | 交接摘要说补丁已完成，接续者仍需知道测试未运行，并核对现在的分支。 |
| 相关性与干扰 | 必需、补充、无关、相似但错误、互相矛盾、必要重复或互补证据。 | 多一条信息可能补足前提，也可能误导；不能一律按新增 token 当同质噪声。 |

“足够”应针对具体判断。概览可以足以选择下一份资料，却不足以实施接口迁移；一句短理由可以足以理解当前边界，却不足以重新评估整套方案。

## 执行、核验和失败怎样区分

| 观察角度 | 含义和可能区别 | 例子与判断用途 |
|---|---|---|
| 可机械判定性 | 可由格式化、类型、静态规则、测试或运行条件判断，还是依赖语义解释与人的选择。 | 工具能稳定检查格式，未必能判断业务取舍；同一要求可以由多种方式共同检查。 |
| 实际执行点 | 模型遵循文本、编辑器、脚本、持续集成检查（CI）、运行时或人工审查。 | 有检查配置不证明任务实际运行了它；执行地点与说明放在哪里不同。 |
| 核验方法 | 查源、对照实现、运行命令、功能测试、场景演练、链接或字段检查、人类判断。 | 链接可达不证明所指原文支持结论；通过功能测试不自动覆盖全部需求。 |
| 核验覆盖 | 检查了哪些输入、路径、版本、条件和行为，哪些尚未检查。 | 一次演练可以证明该条件下的规程可行，不能宣布所有环境通用。 |
| 内容失效 | 事实过期、规范条件改变、错引、漏报新事项、摘要丢限定或错误解释被反复复用。 | 一份说明没有新增接口属于漏报；已有正确说明没有被取得属于漏读。 |
| 使用失败 | 未发现、选错材料、裁剪丢失、身份误解、误读，或信息已到位仍实施错误。 | 向失败任务明确提供缺失信息，有时能帮助区分获取问题与实现能力问题。 |
| 传播范围 | 影响一项局部操作、多个任务、多个主体或下游派生内容。 | 默认入口中的错误可能反复传播；并不意味着少读的迁移说明后果一定小。 |
| 失败后果 | 无用查找、返工、重复决策、违反需求、破坏兼容、交付错误或难以恢复的变更。 | 低频且后果大的材料可能比高频低影响材料更值得检查。 |
| 发现与修复成本 | 多久能发现、能否定位负责源、撤回旧表述、修产物或重新取得证据。 | 只在历史里说某规则作废，却没改当前入口，修正尚未进入下一次使用。 |
| 可审查性 | 能否说明依据、条件、所做变更与未决问题；人理解这些需要多少工作。 | 字段很多仍可能难以判断；一个短段落也可能清楚交代事实和取舍。 |

诊断的目的在于选择修复动作。测试失败可能来自环境未启动、命令错、说明过期或实现缺陷；不先区分原因就新增永久提示，容易使规则只增不减。

## 名称、形式和组织方式

| 观察角度 | 含义和可能区别 | 例子与判断用途 |
|---|---|---|
| 名称的程序作用 | 客户端或工具明确识别的名字、路径或元数据字段。 | 特殊入口重命名可能使自动发现失效；这与人或模型喜不喜欢名字是两回事。 |
| 名称的协作作用 | 项目约定用某个名称表达某种责任。 | TRADEOFFS 可以表示当前取舍准则，也可以表示某次历史权衡；正文应能说明用途。 |
| 名称的检索作用 | 与任务词是否接近、是否可区分、是否多义、是否需要解释。 | CONTEXT 可以指概念说明，也可以指运行输入或工作状态；准确副标题比一律禁用更能解决局部歧义。 |
| 名称常见度的依据 | 样本仓库出现率、文件词根次数、产品契约、训练分布或实际任务识别结果。 | 只扫描根目录 Markdown 得到的零命中，不能证明整个领域没有这种内容。 |
| 表达方式 | 叙述、定义、示例、规则、表格、图、代码或结构化字段。 | 示例展示实例，定义说明边界，关系图解释组成；它们可组合，没有已证明的统一优先级。 |
| 载体和语法 | Markdown、CSV、JSON、YAML、XML、数据库、网页、PDF、电子表格或图像等。 | 先看消费者原生支持和工作负载：连续论证、字段筛选、嵌套配置、关系查询、公式图表不同。 |
| 结构契约 | 固定字段、类型、空值、身份、嵌套关系、顺序及消费者如何解析。 | CSV 表头与空值口径、JSON 的对象结构、YAML 的解析规则会影响实际含义；语法有效不等于事实准确。 |
| 打包与组合 | 一文件一职责、同页分段、主次职责、共享原件多种视图或运行时组合。 | 同时需要的前提可相邻；独立更新、引用或交付可以支持拆分。 |
| 导航结构 | 直接链接、中心索引、局部入口、目录树、搜索、稳定标识查询或反向关系。 | 一个独有来源可由多个位置链接；不必复制到多个同名目录才能被找到。 |
| 独立性与关联程度 | 内容是否经常一起读、一起改，是否需要单独引用或交付。 | 架构的关键短理由可留在同页；完整决策历史可独立，二者保持联系。 |

格式比较需要保持语义和选中内容相同。若一种方案先筛字段、另一种读全表，差别主要来自选择策略；若一个文档被加载器按标题裁剪，形式又会影响传输。比较结果应说明改变了哪一部分。

## 成本与评价结果

| 观察角度 | 含义和可能区别 | 例子与判断用途 |
|---|---|---|
| 原始体量 | 文件的字节、字符、行数或特定分词器下的 token 数。 | 同为一千字符，中英文可能有不同字节数；这些单位不能随意换算。 |
| 选择后体量 | 筛选的记录、列、章节或片段，以及工具包装后的返回量。 | 从全表筛到相关行再只选两列，两个步骤可分别计量。 |
| 实际输入 | 最后进入模型调用的指令、正文、工具结果和其他输入。 | 工具输出存在截断或摘要时，文件原体量不等于模型看到的体量。 |
| 累计消费 | 多次调用中的重复携带、缓存读写、输入与输出、重新读取和重建。 | 静态正文缩短，不必然降低完整任务费用；缓存行为也不能直接等同内容已被正确使用。 |
| 交互与时间 | 搜索回合、工具往返、首次响应、总耗时、串行依赖和恢复延迟。 | 多一个入口跳转可能有代价，也可能避免读取许多无关文件。 |
| 维护投入 | 创建、更新、复核、派生同步、填写字段、归类争论、清理和工具维护。 | 一个复杂登记系统可能比资料本身更难维护；少几个文件也不保证更省事。 |
| 人的投入 | 反复补充项目前提、纠正误解、决定取舍与审查结果的成本。 | Agent 省下几次读取却需要人多次纠正，未必改善整体协作。 |
| 功能与要求满足 | 是否完成实际目标，功能是否正确，哪些必要要求遵守或违反。 | 代码通过现有测试仍可能漏新需求；少输出或早结束不能单独当作成功。 |
| 取得与理解效果 | 找到必要材料的比例、错误命中、定位时间、证据引用、误解、重读和重复论证。 | 一条准确路由可能减少查找，但仍要检查它是否漏掉关键例外。 |
| 维护与纠错效果 | 是否改对当前内容、保留必要依据、撤掉旧规则、避免错误继续传播。 | 违规由工具发现还是人工审查发现，可以帮助比较检查分工；这不是约束满足率本身。 |

总成本可以用于方案选择，但前提是说明单位和权重。多数初步研究更适合分别报告质量、资源、人的投入和后续维护，而不是立刻生成一个看似精确的排名。

## 研究结论与分类本身也需要观察

一项结果的适用范围取决于样本、任务、模型、运行系统、版本、对照和评价方式。要分清原文报告、本地静态阅读、本地确定性测量、实际 Agent 运行和重复验证。原始分母、缺失数据、快照完整性、统计口径及无差异结果，都可能改变结论。

分类方案则可以看覆盖、简约、可理解、可重复判定、是否支持实际选择，以及能否容纳新的对象。同一份文件允许多职责时，唯一归类不一定是目标；两位读者能一致归类，也不证明这种分类改善了开发。一个新原型可以从单例或推理提出，但是否适用于更多任务，需要进一步检验。

选择哪些维度，应跟随问题。研究读取时，重点看需要时点、发现路径、表示和实际供给；研究维护时，看有效条件、更新触发、负责来源和修改语义；研究长期连续性时，看工作状态、可重建性和恢复结果。若一种维度在当前研究中没有作用，可以暂不使用；以后出现新问题，再回来取用即可。

## 一个贯穿这些维度的例子

假设 Agent 要把本地存储换为数据库。首先区分当前实现、未来方案、必须维持的旧接口和当初选择本地文件的理由。兼容条件在方案形成前需要，具体迁移步骤在执行时需要；某份旧记录只适用于当时的单用户环境，要结合今天的并发要求解释。

当前架构可以保留概览并指向相关接口，完整历史可以由问题触发。代码与 Schema 是部分事实的负责源，必要理由由文字表达。实施后更新当前说明，保留尚未验证的迁移状态；恢复任务时再核对实际分支与测试条件。若多个执行者共同修改，还要处理各自看到的版本与合并顺序。

这里没有要求给每项信息填写几十个字段。观察维度帮助说明何时需要什么、能依据什么做判断、变化后怎样继续有效；文档与目录的具体形状可以由实际工作决定。
