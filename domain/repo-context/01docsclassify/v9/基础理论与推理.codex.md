# Agent 开发中的文档：基础理论与推理

> Codex（GPT-6），2026-10-12。以 Agent 承担主要开发工作、人设定目标并审查重要取舍为讨论情境。本文给出可继续研究的解释、条件与反例，不规定一种通用文件体系。

## 开发为什么需要文档

开发者要把目标转成项目变化：理解已有系统，辨认问题，形成方案，执行修改，检查结果，并让后续工作能够继续。文档的价值来自它为这些判断和动作提供的信息。这个信息可能难以从代码恢复，也可能可以恢复，但每次重新查找、组织和解释的代价较高。

例如，源码可以说明一个接口目前允许空值，却未必说明本次改动是否允许取消空值；测试可以证明某些输入的输出符合预期，却未必包含用户刚提出的新要求；一条旧决定可以说明当时为何不用数据库，却不能单独决定今天是否仍应如此。实现事实、有效要求、历史理由分别回答不同问题。

Agent 作为主要开发者，会同时生产和消费这些内容。它不能只得到零散命令：选择方案需要目标、范围、关系和理由。它也不需要重新读一部通用编程教材；已经掌握的常识、能可靠查询的事实和项目独有的条件，可以采用不同的取得方式。

人的角色仍包括目标、价值判断、优先级和不可替代的偏好。Agent 可以读码、运行测试、比较证据并完成技术判断；人的审查重点是实际差异、重要选择和未解决问题。把所有核实都交给人，会增加反复沟通；把人的采纳等同于事实正确，又会掩盖后续变化。

一个有用的研究起点是：**这项内容改变哪一次理解、选择、操作、核验或恢复？没有它时，能否从别处取得同样的信息，代价和失败方式是什么？** 这个问题既允许短文档，也允许长解释、生成资料和现场查询。

## 信息、文档和实际输入是不同单位

**信息项**是一段可以单独讨论含义、依据、适用条件或变化的内容。它可能是一条要求、一个关系、一组步骤，或必须一起理解的说明。切得越细不一定越好：去掉限定条件的孤立短句，反而更容易被误用。

**文档**是保存和维护内容的一种组织单位，例如文件、章节、接口定义或记录集合。**投递内容**则是一次实际送入模型输入的内容，可以只取一个文件的部分，也可以组合多个来源。文件放在磁盘上、程序读取了文件、模型收到返回内容、模型正确使用了内容，是不同事件。

**Context（上下文）**在这里指当次模型调用可见的输入；**Memory（记忆）**指跨步骤保存、更新并能影响后来行为的状态及其管理机制；**Harness（运行系统）**指组织模型调用、工具、状态和控制过程的软件。文档可能同时参与这三者，但目录名不会自动赋予它加载、记忆或执行能力。

固定模型参数时，输入会影响生成；然而整个 Agent 系统还有工具、环境、执行策略和外部状态等可变条件。编译配置能够直接改变构建，测试能够产生新观察，历史文件可以被后续读取。因此“文档未进入这次输入”和“它对整个系统没有作用”不能互换。

一次典型使用可以分解为：保存、发现、选择、读取、裁剪或转换、进入输入、解释和使用、行动、结果。真实过程会反复往返：发现缺口再查，查到新证据再改方案，完成操作后再核对。研究某个失败时，先区分缺在哪个环节，通常比直接增加文档或增加规则更有用。

## 需要时点来自判断的依赖

信息应在第一次依赖它的判断前可用。这里的“可用”可以是已经提供，也可以是在需要时能够可靠取得。它不要求探索开始前知道全部事实：读码、试验和方案比较本来就在发现新信息，关键是不要把尚未确认的条件当作已满足。

项目特定词义可能影响最初理解；兼容性要求可能改变设计空间；运行命令可能到验证时才需要；历史理由可能只有重访旧选择时才有用。但这些都随任务改变。一个只读诊断也可能需要设计约束，才能理解看似异常的重试；一个专门重新评估旧决定的任务，起点就应该包含相关历史。

“理解前、设计前、实施前、验证前、接续时”是有用的观察位置，不是每个任务必须经过的固定流水线。只改一句指定文案可能不需要设计；实现中出现反例可能要求返回方案讨论。

延迟读取可能减少不相关内容，也可能因为任务已收窄而提高选择精度。提前读取则可以避免遗漏难以察觉的前提，减少来回查询与方案返工。决定两者的条件包括：信息被需要的范围、缺失是否会产生信号、取得路径是否可靠、重新选择的代价，以及一段内容是否会影响后续读法。

缺失可检测性尤其值得单独看。Agent 不知道一个命令，可能会主动搜索；但如果项目把通用词用于特殊含义，Agent 可能在不困惑的情况下沿用通常解释。后一种情况可以通过简短定义、反例或入口提示降低误解，不必由此推出“所有术语全文都要默认加载”。

## 有限资源、注意力与上下文长度

窗口容量、程序传输预算、处理时间、费用和语义干扰是不同限制。某次内容消失可能是工具裁剪，也可能是上下文重组；某个任务变慢可能是多次读取，也可能是文档要求执行更多检查。用“上下文太多”概括这些现象，会失去可操作的解释。

注意力计算描述输入之间如何参与模型处理。单个归一化注意力分布的总权重固定，并不证明整个模型的任务能力会随着每个新增 token 按比例下降。新增内容可以补足定义、提供例子，也可以无关或误导。相关性、相似干扰、矛盾、位置和任务难度需要分别观察。

自回归模型按已有输入和生成内容继续预测。因果注意力限制一个位置直接使用后来的内容；KV 缓存保存注意力计算中的键和值，以便后续复用。这可以解释顺序和历史依赖，却不能推出“后来的解释无法纠错”。后续生成可以依据新证据改变结论，运行系统也可以重新组织下一次输入。缓存仍存在、内容仍可见、内容仍被相信，是三件事。

因此值得研究的是有条件的效应：错误但相近的说明是否比没有说明更具干扰；前置定义是否减少误读；同样的结论用例子、精确定义或叙述表达，在哪类任务上效果不同。它们可以成为实验问题，不需要预设“示例永远优于定义”或统一长度阈值。

重复也有不同用途。重复一个已经明确的无关背景，可能增加负担；在任务切换后重申一条关键约束，可能帮助重新定位；多个来源提供相同证据，未必是多个独立支持。评价重复要看新增的使用价值及维护责任。

## 读取策略的成本怎样比较

一个最简算例是：某文档长为 T，在某类任务中被需要的概率为 p。若总是完整读一次，正文载荷为 T；若只有需要时读一次，期望正文载荷为 pT。在 T 大于零、p 小于一时，后者较小。

这个算例没有包括入口、搜索、摘要、工具往返、反复读取、漏读修复和缓存。在相同计量单位下，若按需方案的额外发现与恢复代价为 H，那么只有 `pT + H < T`，才能在这项简化成本上占优。H 必须包括实际新增的路由说明与失败恢复，不能只计算成功检索的那一次正文。

实际任务还涉及多次调用。同一段文本反复随输入提交、通过缓存读取，或在新会话中重新取得，计费与延迟可能不同。字节数、token 数、费用、执行时间和质量损失不能未经定义权重就相加成一个总分。

可以分别记录：完成质量与必要约束、信息取得的完整性、读取回合、累计输入输出和缓存、人的补充与审查、后续维护。这些结果可能彼此权衡。一个失败后提前退出的低成本运行，不能视作效率提升；一份更长的入口若避免了大量错误路径，也可能值得。

另一种组织思路，是同时比较经常消费的成本与维护成本。高频且必须紧跟实现的接口材料，需要控制重复消费并保持准确；高频但较稳定的项目定位，适合较小的默认说明；低频但失效代价大的迁移步骤，需要可靠发现与版本条件；很少使用的历史，适合按问题查阅。这种分组帮助看取舍，但缓存、任务分布和更新方式变化后，材料的位置也会改变。

## 外部保存、压缩与恢复

把计划、事实或经验写入文件，可以降低对当前可见上下文的依赖。这是**认知卸载**在本题中的具体含义：让外部材料承担部分保存、组织或查询工作。它的收益要连同恢复过程一起看。

原文、提要和指针承担不同责任。指针告诉使用者哪里有内容；提要保存足以支持某些判断的核心信息；原文保留更多条件与细节。如果当次判断需要的是一个例外条件，删掉例外的摘要即使很短，也没有保住所需信息。好的压缩应围绕使用问题，保留会改变选择的条件。

“可以重新查到”不意味着恢复没有成本。恢复可能需要找到正确版本、重新解释分散代码、重做一次实验或重走排除方案。反过来，一个完整文件树可以随时生成，未必值得长期手工维护。需要比较的是可恢复程度、取得可靠性和复用跨度，而非简单区分“存”与“不存”。

持续任务尤其需要保存目标、已完成动作、尚未核实的结果、阻塞与下一步。恢复时再对照现实状态：旧会话中的通过结果，未必对应当前分支；已写补丁，未必已经运行测试。交接内容的质量取决于它能支持接续到哪一步，而非是否使用 HANDOFF 这个名字。

完整对话也可以成为可检索材料。是否需要另外提炼，取决于宿主保存能力、搜索可用性、恢复代价和必要条件是否容易丢失。不能将“当前难访问”说成“没有信息”，也不能期待未来搜索替我们重新发明从未写清的独特理由。

## 当前效力、证据与历史

一段文字至少可能表达当前事实、当前要求、拟议方案、历史选择、原始观察或分析结论。这些身份决定使用动作：执行要求、查证事实、比较方案、理解历史、复核观察。文章已被接受、进入版本库或由人审阅，并不自动使所有事实正确，也不证明方案已经实现。

有效性还取决于范围、版本、时间和前提。一项多年未变的规则可能仍有效，也可能只是无人维护；一份每天加载的文件可能已经过期；一条很少读取的限制可能在某次迁移中非常关键。保存时长、读取频率、当前效力应分别判断。

当前说明和历史理由可以共同支持行动。例如从本地文件迁到数据库后，当前说明要表达实际存储路径、事务边界和迁移状态；旧决定保留原约束、备选和改变原因。理解当前事务边界所需的短理由可以留在当前正文，完整历史不必每次一并读取。

原始事件与对事件的解释也要区分。过去发生的事不会因为现在改变选择而改变，但记录可能写错、遗漏或错引。冻结一次实验的原始结果，不意味着禁止追加更正；活动中的设计记录可以随事实更新，完成后的历史可以保留当时状态并指向后来决定。

如果实际实现与文档冲突，应先判断冲突句子在做什么。实现 A、要求 B，可能是实现未完成；说明声称 A、当前实现已为 B，可能是说明过期；旧决定写 A、新需求指向 B，需要重访前提。统一的“代码永远优先”或“文档永远优先”都不能完成这个判断。

## 文档生产、派生与维护

Agent 既写实现又写说明，使文档维护成为开发过程的一部分。一次修改改变了接口或条件，后来的可见内容也应能够反映变化。只在新日志里补一句而不修正仍在使用的旧正文，可能使下一次继续读到错误说法。

一个有效做法是明确哪份内容负责某项当前含义，其他表示怎样派生。摘要、索引、图和对外介绍可以重复同一事实，只要维护关系清楚。重点是减少多个彼此独立维护、却声称同样当前含义的版本；“单一负责来源”并不保证源本身真实。

提炼过程会引入新的判断。一次成功不必然成为通用方法；“多数情况下有效”不能压缩成“总是采用”；一条尚未确认的推测不能因为移入长期文档就变成事实。提炼时需要保住适用条件、原始依据和结论身份。

更新可由对象变化、任务推进、用户纠正、上游版本、实际失败或新证据触发。任务收束是一个便于集中处理的时点；需要立即纠正的内容也可以在中途更新。周期复核适合补充难被事件触发发现的过期问题，不存在统一适用于所有内容的天数。

删除、归档和替代都可能合理。临时状态完成后若没有恢复价值，可以结束；有复用价值的结论可以进入负责正文；独有观察或重要理由可以保留。不能因为“研究曾经产生过”就永久保存所有中间稿，也不能因为“现在不常读”就抹去不能重建的必要依据。

## 自主执行、人类判断与工具检查

主要开发者需要足够的自主空间完成已经授权的工作。文档可以表达已有的目标和边界，帮助它决定什么时候查证、什么时候继续、什么时候需要人的偏好。授权取决于实际任务和协作关系，不由 PLAN、ADR 或某个文件名自动决定。

机器可稳定检查的要求，适合由格式化工具、类型系统、测试或运行时机制承担。文字仍可能需要说明这些工具在哪里、何时使用、检查覆盖什么、失败意味着什么。生成文件应修改其源定义，再重新生成，就是一种会改变实施对象的必要说明。

人类审查主要需要看清做了什么、依据是什么、有什么重要差异、哪些问题还没有解决。这与让人阅读每一份被 Agent 消费的材料不同。作者、执行者、维护者、核实者和采纳者可以是不同主体，不能用“谁写的”代替“是否检查过”。

多个 Agent 协作时，除共享材料，还会出现各自可见上下文不同、状态交接、并发修改和过期视图问题。只有这些关系实际影响任务时，才需要专门的责任划分或合并机制。单个开发 Agent 不应仅因将来可能并发，就背上完整多主体制度。

## 认知理论可以提供哪些研究问题

一些人类认知概念提供了值得比较的角度，但由类比得到的软件设计仍需自己的依据。

**工作记忆与认知负荷**关注当前处理有限信息时的负担。对 Agent，可将问题转成可观察的输入、任务与行为：增加无关说明是否造成遗漏，拆分是否增加恢复成本，步骤指引是否减少反复推理。人类的容量或时长不能直接成为模型的行数、token 或天数阈值。

**编码特异性**强调提取与保存时的线索关系。在文档中，对应的问题是标题、关键词、问题式入口、稳定标识和关联说明怎样帮助找回内容。例如一条“更新数据格式时查看兼容性要求”的入口，可能比只列一个抽象文件名更容易匹配工作。这个想法不要求预先建立中央索引，也不能证明所有检索都依赖同一种线索。

**图式与语义框架**强调已有解释结构如何影响新信息的理解。项目中的“会话”若指跨多次调用的持久对象，而某库里指短连接，应说明两者关系。定义、反例与具体对象关系可以减少歧义；具体哪一种表达最有用，要看任务和模型。

**情景、语义、程序和个人记忆**可以分别启发对经历、一般知识、操作方法和主体信息的组织。例如原始事件记录与当前总结具有不同更新方式，步骤说明与结构解释有不同使用需求。这些区别本身有价值，但不能据此声称一个认知类别天然对应一个文件。

**巩固、遗忘与重构**可以启发对临时内容转为长期材料的研究：保留哪些经验、怎样合并、何时撤回、压缩丢失什么。实际保留策略应看来源可重建性与后续用途，而非套用固定的巩固窗口。

**负面结果与选择偏差**提醒研究者关注被放弃的方案、无差异结果和失败条件。只保存最后成功方案，可能使未来重复已经失败的探索；完整保存所有失败，又可能淹没关键条件。可以优先保留改变后来选择的失败原因与重新考虑条件。

这些角度可以产生新实验，也可以在没有额外解释力时放下。未来研究无需先接受一套认知映射，才有资格提出新的文档模型。

## 名称、结构和表达为什么会影响使用

文件名有时是程序接口，有时是项目约定，有时只是检索线索。若加载器识别特定名称，重命名会改变供给机制；若是普通说明，名称的含义、区分度和与任务用词的接近程度更重要。仓库样本中出现得多，不等于已知训练语料中的频率，更不等于模型一定理解正确。

内容结构也有多层作用。标题可以帮助人和模型定位，也可能被程序用来选择章节；表格可以紧凑表达固定属性，也可能形成超长行；例子可以明确边界，也可能让读者过度推广那个实例。应分别比较“传输了什么”与“传到后怎样被使用”。

文件拆分改变的是共同读取、独立更新、查询和引用的成本。全部文件每次都拼接输入时，拆成多个文件未必少任何正文；按任务筛选时，拆分可能减少无关信息，但增加路由和漏读风险。同一推理必须依赖的前提适合相邻，更新责任显著不同的内容可能值得分开。

可寻址性包括能定位到材料、判断它是什么、识别适用条件并取得正确版本。路径、目录、直接链接、搜索、注册表和关系查询都可以参与。文档中写“按需读取”只是供给意图；需要时是否真的能找到，仍是一个具体问题。

## 加载机制怎样改变文档的实际作用

下面三个案例来自 2026-09-26 的固定版本静态研究。它们说明机制差异，不代表产品的当前承诺。当时对每个项目的一个代表文件与上游固定提交做了统一换行后的内容比对；没有运行三个完整 Agent，也没有证明相关方案提高了任务成功率。

### 祖先目录与累计预算

在 Codex 提交 `75e0e0aad97a86138b8b1ec87d9b544b4a35ecbf` 中，项目指令沿项目根到当前工作目录发现。每一层按 `AGENTS.override.md`、`AGENTS.md` 和配置的后备名称择取一个文件，再组合内容。项目文件共享 `project_doc_max_bytes`，默认 32 KiB；读取后根据剩余额度保留前缀，并扣减预算。用户与线程指令走其他字段。

这使文件拆分的收益取决于选中集合。如果两份各 20 KiB 的文件仍沿同一祖先链全部被选中，拆分不会让它们各自获得 32 KiB。若根文件用尽预算，后面的局部说明可能没有空间。按作用域拆分可以让不同任务少选无关分支，但文件数量本身不证明省输入。

该实现还保存已加载快照，并依据环境选择和信任等状态决定重建；状态变化可形成替换或移除片段。磁盘文件修改、发现缓存刷新和新内容进入模型输入，不能当作同一动作。具体宿主的热更新行为还要继续追踪。

依据：[发现与选择](https://github.com/openai/codex/blob/75e0e0aad97a86138b8b1ec87d9b544b4a35ecbf/codex-rs/core/src/agents_md.rs#L189)、[读取与累计预算](https://github.com/openai/codex/blob/75e0e0aad97a86138b8b1ec87d9b544b4a35ecbf/codex-rs/core/src/agents_md.rs#L58)、[默认预算](https://github.com/openai/codex/blob/75e0e0aad97a86138b8b1ec87d9b544b4a35ecbf/codex-rs/config/src/config_toml.rs#L74)、[加载管理](https://github.com/openai/codex/blob/75e0e0aad97a86138b8b1ec87d9b544b4a35ecbf/codex-rs/core/src/agents_md_manager.rs#L79)。

### 读取路径可以触发新上下文

在 Gemini CLI 提交 `bedef96ef42905bd84a86dbec021c706168e7e2f` 中，初始化会查找多种来源的项目说明并处理导入。专用 `read_file` 读取文件后，还会按访问路径在可信边界内发现此前未加载的项目指令，去重后附到工具结果。所检查的 shell 工具实现中没有发现同一调用。

所以，用 shell 打印一个文件与用专用读工具取得它，可能不只返回包装不同，还会改变本次获得的附加指令。在这条动态发现路径上，较深目录的说明需要相关访问触发发现；没有走到该路径，不能据此认定目录内容已被提供。初始化导入、显式读取等仍可能通过其他路径提供同一材料。

该读工具默认选取最多 2,000 行；显式给出结束行时，所查函数不再用这个默认行数限制选区，但单行仍会被截到 2,000 字符。随后公共工具执行路径再按单个字符串或数组中的每个文本部分应用 64 KiB 限制；它不是所有多文件结果合计 64 KiB。文件大小另有门槛。这说明行数、长行、工具结果预算和最终请求预算分别影响内容是否完整。

依据：[读文件后的发现调用](https://github.com/google-gemini/gemini-cli/blob/bedef96ef42905bd84a86dbec021c706168e7e2f/packages/core/src/tools/read-file.ts#L194)、[路径发现](https://github.com/google-gemini/gemini-cli/blob/bedef96ef42905bd84a86dbec021c706168e7e2f/packages/core/src/tools/jit-context.ts#L18)、[选行与长行处理](https://github.com/google-gemini/gemini-cli/blob/bedef96ef42905bd84a86dbec021c706168e7e2f/packages/core/src/utils/fileUtils.ts#L557)、[公共结果裁剪](https://github.com/google-gemini/gemini-cli/blob/bedef96ef42905bd84a86dbec021c706168e7e2f/packages/core/src/scheduler/tool-executor.ts#L340)。

### 标题、表格和批量读取会参与选择

在 Tianshu-harness 提交 `79c10d30ba4fff8aaccfed30410d75050cecb451` 中，项目指令按章节选择。前言和顶层标题部分有专门的高优先级处理；进入普通章节分类器的部分，先检查表格行比例，达到 40% 即归参考级，随后才是其他规则词判断。选择器按优先级取节，再恢复原顺序。因此同样的规则写成表格或散文，可能在到达模型前就有不同的保留结果。

这一版本的 standard 项目指令预算为 8,000 字符，子代理覆盖为 4,000；诊断中的 6,000 是生成建议的条件。三个数字的角色不同，不能当作模型性能阈值。项目指令的转义后长度、分节规则和最终截断共同影响输出。

多文件读工具最多处理传入的前五个文件，并均分总体的长度及首尾配额。一次批量调用可能减少往返，却不保证每个文件更完整。启用重复读取引用时，未变内容可能先返回引用；在已经返回引用后再次请求，又可以回到正文。这把“过去读过”与“现在需要恢复正文”分成了不同状态。

依据：[分节与分类](https://github.com/huiliyi37/Tianshu-harness/blob/79c10d30ba4fff8aaccfed30410d75050cecb451/src/prompt/project-instructions.ts#L20)、[渲染预算](https://github.com/huiliyi37/Tianshu-harness/blob/79c10d30ba4fff8aaccfed30410d75050cecb451/src/prompt/block-policy.ts#L12)、[诊断条件](https://github.com/huiliyi37/Tianshu-harness/blob/79c10d30ba4fff8aaccfed30410d75050cecb451/src/context/payload-diagnostic.ts#L45)、[多文件分配](https://github.com/huiliyi37/Tianshu-harness/blob/79c10d30ba4fff8aaccfed30410d75050cecb451/src/tools/read-file.ts#L1049)。

### 技能的渐进展开发生在哪一层

Skill 在这里指带有发现描述、触发或使用条件、操作正文及相关资源的技能包。渐进展开可能指减少模型默认看到的内容，也可能指延后读盘、扩展可访问资源或结束后续重复注入；这些机制不能互相推定。

同样的固定版本中，Gemini 的加载器已经读取正文以解析技能，但默认提示先列名称、描述和位置，激活时才返回正文与资源树，并扩大相应可读工作区。Codex 有按来源区分的加载方式和条件式 `skills.list/read`，部分读取可以分页；续页可使用快照，未必反映文件即时变化。其隐式调用检测分析 shell 中的读取或脚本路径，不能由函数名推定为对用户任务做语义匹配。Tianshu 的技能目录有描述预算，候选可以因预算而不出现；已激活正文可以继续注入，完成标记再结束这一路径。

这些例子共同说明：程序持有全文不等于模型已看到；描述在目录中不等于一定被选择；激活过也不等于后续始终可见。文档设计可以提出“按需展开”的要求，实际发现、选择、读取与保留仍要由运行系统完成。

依据：[Gemini 技能加载](https://github.com/google-gemini/gemini-cli/blob/bedef96ef42905bd84a86dbec021c706168e7e2f/packages/core/src/skills/skillLoader.ts#L164)、[Gemini 激活](https://github.com/google-gemini/gemini-cli/blob/bedef96ef42905bd84a86dbec021c706168e7e2f/packages/core/src/tools/activate-skill.ts#L130)、[Codex 技能读取](https://github.com/openai/codex/blob/75e0e0aad97a86138b8b1ec87d9b544b4a35ecbf/codex-rs/ext/skills/src/tools/read.rs#L34)、[Codex 路径检测](https://github.com/openai/codex/blob/75e0e0aad97a86138b8b1ec87d9b544b4a35ecbf/codex-rs/skills/src/invocation.rs#L12)、[Tianshu 技能目录](https://github.com/huiliyi37/Tianshu-harness/blob/79c10d30ba4fff8aaccfed30410d75050cecb451/src/skills/skill-loader.ts#L241)。

## 已有实证如何约束这些推理

以下内容保留自 2026-09-26 对指定版本原文的阅读。结果均为论文或报告作者所报，没有在本项目复现。它们覆盖不同任务，不能合并成一种目录结构的总有效性证明。

### 项目指令、任务正确性与效率

[Evaluating AGENTS.md](https://arxiv.org/abs/2602.11988v2) 的 v2，2026-06-23，比较无项目文件、初始化生成文件和开发者提交文件。SWE-bench Lite 为 300 任务、11 仓库；CTXbench 为 138 任务、12 仓库，开发者文件只用于后者。使用 Claude Code、Codex、Qwen Code 与论文指定模型，每个条件一次，主要结果是补丁通过测试的比例。

§3.2、§4.1–4.2 和 Table 2–3 中，无文件与生成文件的比较在两个基准上报告 `p=.87/.37`；CTXbench 的无文件与开发者文件为 `p=.21`，开发者与生成文件为 `p=.038`。生成文件的平均推理成本分别增加 20% 和 23%。统计未显著不证明两者等效；这些 Python 任务和文件条件也没有衡量全部非功能要求。可借鉴的是把内容来源、真实任务结果与新增工作量分别看。

[On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents](https://arxiv.org/abs/2601.20404v2) 的 v2，2026-03-30，对十个仓库的 124 个 PR 作配对比较。任务限制为不超过一百行改动、五个文件，固定变更前快照，用 gpt-5.2-codex 比较有无单根 AGENTS。

Table 1 报告运行时间中位数从 98.57 秒降到 70.34 秒，输出 token 中位数从 2,925 降到 2,440；作者定义的总 token 中位数则由 223,707 增到 226,582。论文只抽查五十项任务排除明显空输出或不完整结果，没有全面评估功能正确性。因此它提供的是特定条件下的效率观察，不能与前一研究的测试通过率作简单对立，也不能推出所有 token 或费用都减少。

两项研究共同提出一个判断要求：更遵循说明、执行更多操作、更快结束和更正确地完成需求，是不同结果。只看其中一项会误判文档作用。

### 输入位置、长度和选择质量

[Lost in the Middle](https://arxiv.org/abs/2307.03172v3) 的 v3，2023-11-20，使用 2,655 个 NaturalQuestions-Open 问题，将含答案文档放在不同位置并改变干扰文档数量，另测合成键值检索。所用模型包括 GPT-3.5-Turbo 0613、Claude 1.3、MPT 与 LongChat。多文档问答出现中部较弱的曲线；重复查询可以明显改善键值检索，却未同样消除问答中的趋势。关键位置见 §2、Figure 5、§3 与 §4.2。

[Context Rot](https://www.trychroma.com/research/context-rot) 是 Chroma 于 2025-07-14 发布的技术报告。它比较十八个模型，在扩展的检索任务中使用八种长度、十一个位置；另取 306 个 LongMemEval_s 问题，比较约三百 token 的相关片段与约 113k token 的完整历史，并用 GPT-4.1 评判。相关片段条件表现更好，但该报告的检索设置下没有明显位置差异。

两者不应被压成统一的位置规律。模型、任务和干扰不同，结果也可能不同；后者的相关片段由已知标注和人工调整得到，尚未算入实际检索器漏选的代价。它们支持控制长度、位置和选择质量来做比较，不给出“窗口超过一半就失效”或某个通用文件行数上限。

### 缺失信息值得检索，检索也可以有条件

[RepoCoder](https://arxiv.org/abs/2303.12570v3) 的 v3，2023-10-20，研究仓库级代码补全。RepoEval 来自十四个 Python 仓库，行与 API 补全各 1,600 样本，函数补全 373 样本。GPT-3.5 的行补全精确匹配从单文件条件的 40.56%，提高到一次检索 55.31%、两次检索 56.81%；函数单测通过率为 23.32%、38.34%、42.63%。见 §3–5 与 Table 1–3。

这说明在缺少跨文件信息的补全任务中，取回相关代码可能有实质收益。它没有直接比较项目规范文档，也不是开放多步开发任务；使用真值帮助检索的上界条件不能作为实际部署方案。

[Repoformer](https://arxiv.org/abs/2403.10059v2) 的 v2，2024-06-04，训练模型判断是否检索。在 Appendix E.3、Table 8 的十亿参数模型、稠密检索 API 补全条件中，相对总是检索的基线，贪心选择的速度提高 71%，但 ES（Edit Similarity，编辑相似度，衡量生成代码与参考代码的文本接近程度）从 71.69 降到 70.82；阈值选择的速度提高 33%，ES 为 72.39。这不是功能测试通过率。同页正文对“超过 70%”的归属与表格不一致，这里按表中的条件保存。

这提供了比较“总检索”和“有条件检索”的例子：收益依赖选择器、阈值、模型和任务。不能据此认定通用 Agent 已经可靠知道自己缺什么，也不能因选择有误差就认定一律全读更好。该论文对 RepoEval 的仓库数使用三十二仓口径，与 RepoCoder 不同，不能直接合并两项研究的分母。

### 保留理由怎样影响后续维护

[Why Does CLAUDE.md Keep Growing?](https://arxiv.org/abs/2608.11095v1)，2026-08-11，同时观察 1,867 个仓库的指令演化，并用受控任务研究维护者如何删改规则。仓库观察中，重写和迁移使部分删除记录无法直接辨认；这类历史观察不能独自证明规则必然无限增长。

受控部分使用 Haiku 4.5 担任维护者与执行者，inverse IFEval 中每个环境有两至三条约束，184 个环境、三个随机种子、十五轮；更长的五十一轮只用一个种子。维护理由只给维护者读取，未直接扩充执行者输入。在有十六条额外干扰的 WildIFEval 六十四个环境中，三轮后的逐条约束满足率从 50.4% 到 62.0%，提高 11.6 个百分点；无干扰时没有一致收益。

§4 与附录显示，差异依赖模糊失败、通过反馈删失、隐藏约束标识、不要求简短、至少十轮等条件；完整披露验证规则后差异消失。因而有价值的问题是：保留理由能否帮助未来维护者正确修改，以及这些理由是否需要随执行输入一起增长。不能从这项实验推出所有规则都要写长注释或建立永久记录。

## 本地测量说明了什么

### 查询、表示和版本身份

2026-09-26 的一次标准库测量读取一份包含 134 条记录、十八个仓库标识的账本。其中 133 条为标记 verified 的文件记录，一条为 absent 占位，不能称为 134 份已核验文件。

在统一 UTF-8、LF、有表头的 CSV 序列化下，全账本为 10,579 字节；筛到 22 条项目入口记录后为 1,750 字节；再只保留标识与路径两列为 423 字节。筛行改变选择对象，选列改变每个对象传输的属性，这是两种不同操作。另一次 PowerShell 的三行小样本，统一序列化六列与两列分别为 509 与 99 字节。

同样的二十二条两字段数据，用 CSV、Markdown 表格、紧凑 JSON 数组和 JSONL 表示，分别为 423、575、813、811 字节。这个样本没有多行或 Markdown 特殊字段，因此只支持这份数据的表示长度比较。它不测模型理解、token 或总任务费用。

标准 CSV 解析还对一个含逗号、双引号和换行的构造记录完成往返；按逗号与物理行裸拆不能恢复记录。另一构造例中，一千个 ASCII 码点占一千 UTF-8 字节，一千个“中”占三千字节。单位和解析边界应先于格式比较。

对 133 条文件记录检查时，文件均存在且字节数相符，然而来源账本与抓取事实仍在 EverOS、MemOS、MemoryBear、mem0、memU、qwen-code 六个项目上记录了不同提交。文件存在、体量相符、内容相符和版本身份一致，各自回答不同问题。原始 JSON 保存了输入及文件指纹，没有凭某个字段擅自修正来源。

完整观察见 [2026-09-26 原始数据](data/local-observations-2026-09-26.json)。观测使用 Python 3.13.11，项目 Git 基线为 `2d99421b71a88ae2a9dff0b9492078a81c788e21`。可复用的 [测量工具](tools/probe_repository.py)使用项目现有账本与来源文件，不调用模型；它提供查询投影、格式往返和来源核对。重新测量时保存新结果，先比较输入指纹，再解释差异。

从本项目根目录复跑的例子如下。需要现有的 `00docslist/index.csv`、仓库来源账本及相应本地文件；输出前缀使用尚未存在的名字。脚本中的往返检查使用 Python 的断言，因此运行时不启用 `-O` 优化选项。

```powershell
python domain/repo-context/01docsclassify/v9/tools/probe_repository.py --root . --output domain/repo-context/01docsclassify/v9/data/local-observations-new
```

### 静态计数和预设路线的边界

2026-10-05 另有一组 `cl100k_base` 静态 token 计数：指定的仓内启动材料为 778 token，指定的按需材料为 9,856，合计 10,634。它说明这批文件在该分词器下的体量；启动集合是预先列出的，并非从实际 Agent 请求轨迹中提取。

同一组材料中，“入口→约定→表达规则”与“入口→表达规则”两条预设路线分别计为 4,983 和 2,006 token，差值来自中间那份 2,977-token 材料。这个构造说明多跳路由可能有成本，却不能证明真实 Agent 必须走第一条路线，尤其入口已提供直接线索时。

同期的名称统计按目录枚举，十八个目录中包含一个工具目录；只扫描 Markdown，每目录有数量上限，名称又按分隔符拆词。由此得到的是该快照与扫描规则下的词根频次，不是行业文件分布，更不是模型训练先验。统计“零命中”前，应确认后缀、复数、路径和截断是否改变了检索范围。

一个更有一般意义的测量教训来自残缺快照：索引列出许多文档，而本地下载不完整，链接检查会把未下载误判为原仓库死链。那次报告的 916 条死链、86.6% 已被撤回；它既不能证明索引维护失败，也不能用后来的“未统计”结果当作零死链。独立核对样本完整性，是理解这类比例的必要前提。

这组原始计数保存在 [2026-10-05 原始数据](data/local-observations-2026-10-05.json)。其中有统计口径和正文数值不一致的字段，不能作为未经核对的性能锚点；这里保留的是实际条件及其能说明的问题。

## 怎样继续研究而不重复堆积材料

先把一般口号改成能够区分解释的问题。例如“入口应当更短”可以展开为：对哪些任务，缩短后仍能取得必要前提？节省的是正文、工具回合，还是无关操作？出错是未找到材料、裁剪丢失，还是材料已到位但实现失败？

查机制时，从入口沿消费者路径看发现、选择、读取、转换、输入和保留。工具参数没有某种能力，不代表整个工具面做不到：没有列投影参数的读文件工具，可以由 shell 调标准解析器补足。反过来，代码里有一个函数，也不证明默认配置实际执行了它。

查效果时，固定任务、仓库状态、模型、运行系统、工具和材料内容，只改变要比较的条件。无额外项目说明、全文默认提供、短入口加按需取得，可以分别帮助分离新增信息与取得方式的作用。路由文字属于方案成本，搜索失败和提前退出也要记录。

一组有区分力的任务可以包括：指定错词修复作为简单对照；必须找到非标准测试命令的修复；跨解析器与序列化器共享字段的改动；重新评估因旧条件被否决的缓存方案；根据新实现修正当前说明而保留真实旧观察。每项先有明确预期和可核对结果，再运行 Agent；这些是实验设计，尚不是已完成的数据集。

命名实验需要保持加载机制相同。把被程序特殊识别的 AGENTS 改成随机名字，会同时改变发现行为；不能由此声称模型偏爱某个词。文件拆分比较也应保持信息内容和可达性相当，否则测到的可能只是某一组少了一半资料。

维护实验可以分别比较只有当前规则、规则加按需理由、规则与完整理由都默认提供；维护者删改是否正确和执行者完成任务是否可靠，应分别评分。记录无差异和失败，不只挑有利案例。同一仓库多个随机尝试也不等于多个独立仓库样本。

必要的研究记录可以很短：问题、对象与版本、实际条件、动作与结果、支持范围、能改变解释的反例。通用背景未来可以再查，独特观察和不可重建的选择理由需要在当时说明。新证据能改变问题时继续研究；现有材料只能留下一个待检验问题时，明确它即可，不用再积累更多同义转述。
