# 文档分类研究（第二轮）：从维度坐标到文档模型
**本轮结论先行**：你的转向是正确的，且可以用一条第一性原理论证其必然性——**上下文注入的最小单位是文件，不是属性。** agent 从不“加载X1=2、X2=3的组合”，它加载的是一份份完整文件；因此治理规则的天然挂载点只能是文件类型，而不能是轴值的笛卡尔积。维度思维隐含“治理可按轴拆解再组合”的假设，这个假设在运行时层面就不成立。下面按你给的研究顺序展开。

## 一、为什么放弃维度坐标系（转向的合法性论证）
除了注入粒度这条原理，还有一个实证证据链——回看这四轮讨论，每一根轴的死亡方式都相同：
| 死去的轴 | 死因 | 遗产被谁收编 |
|---|---|---|
| 受众（agent/developer/reader） | 读与维护分离；reader 降级 | 被“载入方式 + 审查”瓜分 |
| 辖域（根/子树/个人） | 本质是 harness 加载机制 | 被“归属 + 存放位置”瓜分 |
| 时间（事前/中/后/元） | plans 证明时态会随阶段流动 | 被模型的“阶段语境”收编 |
| 嬗变（不变/只增/更新/即焚） | 是结果不是原因 | 被模型的“生命周期”属性收编 |
规律：**每根轴都死于同一死因——它的规则被某个文档聚集整体收编了。** 这不是分类失败，这是证据：规则的真实挂载点从一开始就是“文档聚集”（即模型），轴只是它的不完整投影。你的直觉（“不纠结 x1×x2×x3 矩阵，直接建立文档类型模型”）不是妥协，是修正。
这也回答了“维度 vs 角度”的措辞问题：维度暗示单值、正交、组合；你实际需要的是**角度——一个可以有多个取值、甚至只有描述性取值的观察方向**。角度不参与组合运算，只用于给模型做画像。

## 二、验收标准的修订（对位回应你的四条质疑）
原四判据是理论标准，工程化替换如下，且判定对象从“轴”改为“模型”：
| 你的质疑 | 原判据 | 修订后（工程标准） |
|---|---|---|
| 正交性概念上说不清、会牺牲可读性 | 正交性 | **判定不犹豫**：任意文档三个问题内归入唯一模型；判定时不需要哲学讨论 |
| 规则可推导会被其他维度包含 | 规则可推导性 | **模型即治理包**：载入、审查、生命周期、存放位置整套打包在模型上；换模型=整套换。不存在“同模型不同治理”的分裂 |

## 三、角度生死簿（研究顺序第 2 条：保留的与舍弃的）
### 3.1 彻底舍弃的角度（4 个）
1. **受众**——最终形态：读=agent 为主（已被载入方式覆盖）；developer=审查者（已被审查角度覆盖）；reader=二等公民（入口模型附带处理）。
2. **辖域**——你问的“user 下建 skills 能否被读取”：取决于目录归属哪个工具（`~/.claude/skills/` 只被 Claude 系读取，跨工具需各自目录或经 AGENTS.md 指向）。这正说明辖域是 harness 实现细节，归后续《how-agent-read-file》章节，不进分类法。
3. **层级（公理/架构/模块/语法）**——早已降级为规范文档的内部小节结构。
4. **状态（草稿/受控）**——git 分支与目录位置天然表达，不需要重复建设。
### 3.2 保留为模型属性的角度（5 个）——不作为独立分类轴
**角度 1｜归属**：仓内 / 随身（跨仓有效）。这是你命名的 assistant 的判定核心。
**角度 2｜载入方式**：你的四档压缩为三档，压缩论证：
- **默认载入 → 常驻**（AGENTS.md、随身档）
- **条件载入 + 可选载入 → 检索**：你自己也说可选“不知道是否需要单列”——不需要，因为“都能主动读”是基线能力，真正有区分度的是仓库的**承诺**：检索档承诺“可达”（在导航中挂载、在指令中有指针）。你观察到的“实施阶段才读 CONVENTIONS”是个真实现象，表述为：**检索档文件在其触发窗口内临时升为常驻**。
- **仅供参考 → 拆解后删除**：sources 的特征其实不是“不载入”（agent 完全可能去查 papers），而是“不承诺维护”。所以它拆成两个属性：载入=沉睡，审查=零。你把两件事捏在一起了，拆开就不需要第四档。
- **沉睡**：能读到，但仓库不保证其相关性（sources、被取代的档案）。
**角度 3｜生命周期**：不变 / 只增 / 持续更新 / 用完删或归档。你已自行判死其分类资格，保留为模型属性。你补的“过程性文档：要么用完就删，要么整理后放进记录”——这正是过程模型的定义，见第四节。
**角度 4｜时间指向**：正面回答你的两个问题——
- “元跟时间的关系？解耦了吗？”——没有，你抓得准。INDEX 会随文档增删而变，它描述的“现状”就是文档体系自身的现状。之前的“元”是过度设计，并入“现在·状态”，INDEX 归现状类。
- “plans 三个时态都属于？”——对，而且这不是缺陷，是 plans 的本质：构想时指向未来、实施中描述当前、完成后转化为记录。**这恰恰证明时间不是文档的固有属性，而是文档当前所处阶段的属性**——所以它进不了分类轴，只能作为模型的阶段说明。plans 的正确归宿是“过程”模型。
**角度 5｜审查强度**：见第五节，这是你本轮最有价值的洞察，单独展开。

## 四、七个文档模型（核心交付物）
### 4.1 命名原则与总表
命名原则：日常词、双字为主、能自解释治理含义、互相不混淆。你的两个试命名，“assistant”保留为别名（“助手”描述功能，但 AGENTS 也是助手，有歧义）；“default”废弃（它描述的是载入方式而非文档性质，且无法扩展）。
| 模型 | 一句话本质 | 判定问题 | 代表文件 |
|---|---|---|---|
| **规则**（rules） | 告诉 agent 现在该怎么干 | 这是在下命令吗？ | AGENTS、CONVENTIONS、AGENTS.local、skills、lint 配置 |
| **随身档**（carry-on，原 assistant） | 与仓库解耦、跟随人机组合走 | 挪出仓库还有意义吗？ | MEMORY、USER、SOUL、用户级 skills |
| **现状**（state） | 仓库当前事实的陈述 | 这是可从历史重建的现状描述吗？ | ARCHITECTURE、GLOSSARY、LIMITATIONS、INDEX |
| **记录**（records） | 已发生且不可撤销的追加条目 | 这事已经定了且不可撤销吗？ | ADR、CHANGELOG、对话归档 |
| **过程**（working） | 生命周期短促的工作文档，双出口 | 它是手段而非目的吗？ | plans、EXPERIMENTS、scratch、dialogue |
| **参考**（reference） | 外来材料，仓库不拥有其内容 | 这内容的作者是仓库外的人吗？ | sources、papers、vendored 文档 |
| **入口**（entry） | 写给陌生人、且被 harness 默认读 | 它是外部世界碰这个仓库的第一站吗？ | README、SECURITY、CONTRIBUTING |
“随身档”的命名理由：像随身行李，过安检（换仓库）也带着；它服务于“这个 agent + 这个用户”的组合体，而不是服务于任何项目。
### 4.2 各模型治理包（骨架级，详细定义与对比按你的研究顺序留给后续）
**规则**：常驻~检索 · 持续更新 · 高审查。三种介质并存——markdown 文档（agent 自觉执行）、配置文件（工具强制执行，如 .editorconfig、lint 规则）、skills（触发式规则包）。**能配置化的优先配置化**：config 由工具强制执行，错了会被工具当场拒绝，这是“失败会喊”的最高形态。CONVENTIONS 内部仍分原则段（低频维护）与规则段（随版本维护）。
**随身档**：常驻（会话装载）· 持续累积 · 按写者分审查档。关键内部区分：USER/SOUL 人写，中等审查即可；**MEMORY 由 agent 自写，是全系统唯一“agent 写→agent 读”的闭环，审查档位最高**。MEMORY 有两种实践：放个人目录（豁免审查但必须隔离），或想入库共享——那就必须先蒸馏成受审形态（教训升格为 CONVENTIONS 条款或 ADR），**MEMORY 本体不直接入库**。
**现状**：检索 · 持续更新 · 中审查。四个子职能：结构（ARCHITECTURE）、词汇（GLOSSARY）、边界（LIMITATIONS）、导航（INDEX——只指向不载知识，但描述的仍是文档体系现状）。逃过工具替代检查的原因：模块边界的“为什么”无法从目录结构推导。
**记录**：沉睡~检索 · 只增 · 入库时一次审查（你说“最多在添加的时候让 AI 做语句规范化”——对，这是记录类唯一需要的审查）。之后结构性免维护：历史不会错，只会被取代，被取代时标注即可。**被否决的决策同样是记录**。
**过程**：临时载入 · 用完删或归档 · 审查随阶段变化。这是你 plans 直觉的形式化：**实施期的 plans 是 agent 的行动蓝图，临时常驻、需要重审查（人审计划本身）；完成后归档转记录、免审；废弃则直接删或留一条 rejected 记录。同一文件的审查强度随生命周期阶段流动**——这是“治理挂在模型+阶段上”的又一证据。双出口：删 / 蒸馏成记录。
**参考**：沉睡 · 不变 · 零审查。这是你本轮新增的、此前所有轮次都遗漏的类型——vibe coding 场景下往仓库塞参考资料是高频操作，它必须有正式位置。判定特征是**内容所有权**：作者在仓库外，本仓库无权也无义务修改。
**入口**：隐式常驻（harness 默认读，不由作者意图决定）· 持续更新 · 段落分治。事实段（安装命令、版本要求）按规则级审查；叙事段自由。
### 4.3 常驻包：化解你直觉与模型划分的张力
你把 AGENTS.md 和 ARCHITECTURE 放进同一个 "default"——直觉上它们一伙，但按模型一个是规则、一个是现状。两者都对，区分两个概念：
- **常驻包**（运行时概念）：AGENTS.md + 它直接指向的文件，构成一个载入单元，包内文件审查强度统一对齐到常驻级。
- **模型**（治理概念）：决定每份文件**内容性质与更新依据**——AGENTS 改坏了污染 agent 的行为（它是要被遵守的），ARCHITECTURE 改坏了污染 agent 对事实的理解（它是在描述现实的），两者的更新触发器不同。
进包资格：每会话都需要 + 行数预算内。你的直觉捕捉到的是“包”，模型刻画的是“性质”，正交使用，互不打架。

## 五、可达律与审查分层（你点名要深入发掘的部分）
先确认你的方法转变：**维护 → 审查**，正确。vibe coding 下文档由 agent 撰写，developer 的角色收敛为审查者——人是系统中唯一的核实来源，全部制度都在安排这种核实的分配。
你的核心洞察“越容易参考的文件，越要重点审查”，形式化为**可达律**：
> 审查强度 ∝ 载入可达性（常驻 > 检索 > 沉睡），而非文件重要性。
因果链：可达性高 → 每会话注入 → 错误每次进入上下文 → agent 不核实直接执行 → 错误复利。反直觉的推论：ROADMAP “重要”但低审查（低可达、事前、错误代价低）；MEMORY “琐碎”但最高审查（高可达 + 自写闭环）。
完整分层清单：
| 档位 | 对象 | 时机 |
|---|---|---|
| **L0 常驻审查** | AGENTS.md 及常驻包成员；MEMORY（agent 自写）；README 事实段（harness 默认读） | 每次变更 diff 必过目 |
| **L1 检索审查** | CONVENTIONS、GLOSSARY、ARCHITECTURE、INDEX（叠加自动链接检查） | 变更时顺手检查 |
| **L2 入库审查** | ADR 新条目、CHANGELOG 条目、蒸馏产物 | 进档时一次，此后免审 |
| **L3 零审查** | sources、papers、被取代档案 | 永不 |
| **阶段附加** | 过程模型（plans 等） | 实施期按 L0，归档后按 L3 |
你提到的“plans（INDEX 的表头）”如果指 plans 文档头部所引的工作区说明：它属于过程模型的 L0 窗口期对象，实施期与 plans 同审。
