# 文档模型：职责、组合与演化

> Codex（GPT-6），2026-10-12。V10 收束稿，待用户审阅。本文给出研究中的模型及其辨别依据；具体仓库如何选择文件、目录和工作流程，属于并列的组织方法研究。

## 从同一份文件里的不同需要开始

设想一个原先只供个人使用的项目，准备支持多人同时修改数据。Agent 查到一份说明：系统现在把数据存在本地文件；最初这样做是因为不需要并发；已有用户导出的文件必须继续能够导入；下一步考虑迁入数据库。这四句话完全可以出现在同一页，却不能用同一种方式理解。

第一句描述现状，要用实现核对。第二句解释过去的选择，要结合当时条件阅读。第三句表达有效要求，新方案应满足它。第四句还是待比较的方向，不能当成已经完成的迁移。以后数据库上线，现状要改，旧决定所记录的过去仍然成立，兼容要求可能继续有效，而原来的方案变成了一次已实施的选择。

这个例子说明，研究文档类型至少有两个不同任务：辨认内容承担什么信息职责，以及解释实际文档为何把某些职责组合在一起。只给整页贴一个“架构”或“历史”的标签，会丢掉前一个任务；把四句话各拆成一个文件，又把概念区别误当成了组织方案。

本文所说的**文档模型**，是对一类可重复的信息使用任务，以及围绕它形成的内容组织、使用关系和演化方式的概括。它可以描述较单纯的材料，例如术语表，也可以描述稳定的组合，例如协作入口、交接说明或 Skill。这里的“模型”不是 AI 模型，也不是要求所有项目照填的模板。

[基础理论](基础理论.codex.md)解释了信息如何参与理解、行动与后续恢复。本文沿这些使用需要展开文档全景：既解释常见材料为什么不同，也解释它们为什么经常重叠。

## 什么差异值得形成一个模型

文档名称首先帮助寻找对象，却不能独自决定对象是什么。本地样本中，Raven 的 `AGENTS.md` 自称只保存硬约束，Tianshu-harness 的同名文件则以架构地图和能力索引开头。两者都可以是开始协作的入口，正文承担的职责却不同。这一反例足以说明：`AGENTS` 是一种入口名称，不能因此被定义成一种纯粹的内容类别。原文与本轮核对见[研究依据与复核](研究依据与复核.codex.md)。

我们先从内容层辨认区别。当前事实、要求、操作方法、工作状态、理由、观察与定位线索，分别补足不同的信息需要。把“必须兼容旧格式”误读成“过去曾兼容旧格式”，即使文件路径和字句大体相似，也会改变行动。这种区别具有模型意义。

然后看使用关系。同样是一组目标、进展和待办，在正在执行的 Agent 手里是工作状态，交给接续者时还要回答“哪些是已知事实、哪些动作已经发生、哪些条件需要重查”。交接说明因此值得独立讨论。它未必新增一种基本内容职责，却形成了可重复的使用任务。Skill 同理：它可以使用已有的规则与步骤，但发现、激活和资源访问使它具有不同于普通规程的使用关系。

最后看变化如何影响这项任务。一个接口名称改了，当前说明应反映新名称；一份记录过去故障的报告仍应说明当时用的名称。差别不在谁更重要，而在两份文字分别声称描述哪个对象、哪个时点。演化方式帮助解释模型之间的关系，不能机械地把所有“会更新”和“不更新”的材料分成两个永久类别。

据此，本文采用以下辨别依据：**一个差异如果引入了值得单独理解的使用任务，并改变完成这项任务所需的内容或关系，就值得展开成模型；如果只是同一任务的名字、路径、格式或局部状态改变，通常仍是同一模型的实例变化。** 这是一种解释性建模取向，不声称存在唯一正确的模型数量。

实际辨别可以用“合并后失去什么”来检查。把术语定义与用词要求都称为“规范”，会失去“这个词是什么意思”和“以后应采用哪个词”的区别；需要保留。把两个内容、读者任务和更新方式相同的 `BRIEF` 与 `THISIS` 分成两种模型，通常只会重复命名；不必因此新设类别。把 Skill 完全等同于步骤清单，又会漏掉使该清单被发现和调用的关系；这种组合值得研究。

这也使模型有了可以修正的条件。若两个分别展开的模型在困难实例中始终没有值得保留的差别，可以合并解释。若已有模型必须含糊地称某项材料为“特殊情况”，而这个差别反复改变使用任务，就应补充或修正模型。可组合不等于没有边界：仍须说出组合了什么，以及各部分为什么会被一起使用。

下文按相近的阅读问题组织模型。标题帮助阅读，不构成一棵互斥分类树。来源身份、适用范围、采纳状态和表示格式贯穿这些模型；它们不会仅因有自己的名称，就成为与所有内容职责平行的基本类型。

## 建立对项目和对象的认识

### 项目定位与目标

定位说明让进入项目的人或 Agent 知道：这个项目要解决什么问题，服务谁，哪些取舍有意义。愿景、价值原则、目标用户、产品范围和当前阶段目标，都可能参与这种说明，但承担的承诺不同。“长期支持离线工作”可能是方向，“本次支持离线创建笔记”则是任务要求。

定位的重要性在于，系统现状不能唯一推出项目意图。一个实现了复杂权限的系统可能正在简化，一个暂时只有单用户能力的产品可能准备转向协作。只读代码可以知道已经实现什么，却不能据此认定应继续往哪个方向发展。

`README`、`VISION`、`MISSION`、`PRINCIPLES`、`BRIEF`、`THISIS` 都可能承载定位。读者需要理解的核心是目标与范围，名称只是寻找它的入口。方向改变会使定位变化；一次普通实现修改未必改变定位。稳定目标与短期任务可以同页，但应让读者看出两者的关系。

### 系统解释与领域概念

系统解释帮助读者理解组成部分怎样共同产生行为。它可以沿组件、数据流、状态转换、边界和依赖来组织。文件树只说明物理位置；即使每个目录都有名字，读者仍可能不知道数据先到哪里、谁负责校验、失败后由谁恢复。架构说明增加的就是这些关系。

`ARCHITECTURE`、`DESIGN`、`OVERVIEW`、模块说明和结构图，都是常见载体。标题不足以判断它描写现状还是目标方案。同一张图放进设计提案时表达拟议关系，放进当前系统说明时声称关系已经存在；采纳状态和实施状态需要分别理解。

领域概念说明与架构说明相邻，却看向另一组对象。架构可能解释 API 服务怎样调用存储，领域模型则解释用户、工作区、笔记、修订和共享权限之间的关系。技术组件可以改变，业务对象关系未必一起改变；领域词义变化，也可能迫使多个组件重新解释同一个字段。

术语表进一步解决词义的定位问题。项目把“会话”用于跨多次调用的持续任务，某个库却把它用于连接，两个用法必须能够区分。**定义说明某词指什么；概念关系说明对象怎样联系；用词约定说明本项目以后采用什么表达。** 它们经常合写在 `GLOSSARY`、`CONTEXT` 或 `DOMAIN-MODEL` 中，但不是同一件事。

这组模型的变化来自对象变化或认识修正。一个结构解释也可能在代码没有变化时被纠正，因为原解释遗漏了真实依赖。其事实依据与解释依据都重要：代码能确认某些关系，设计理由则帮助解释为什么这些关系值得注意。

### 能力、限制与技术环境

能力说明界定系统在什么条件下能做什么。限制说明暴露能力边界，但边界可能来自不同原因：尚未实现、现存缺陷、外部依赖、设计选择，或当前明确不做。`LIMITATIONS` 里的“暂不支持多人编辑”，不能自动解释为永久禁止，也不能自动变成已经承诺的待办。

技术环境说明描述运行这些能力所需的条件，例如平台、工具链、服务、依赖版本和启动方式。`TECH_STACK`、`ENVIRONMENT`、依赖清单与部署说明可能参与其中。机器配置能回答依赖的具体值，文字还可以解释环境之间的差别、非标准操作和已知冲突。

这类内容看起来都在描述“现在”，实际对应多个时间尺度。项目选择的语言可能多年不变，某次验证所使用的运行环境却属于那次观察。把环境要求与一次运行记录放在一起可以很方便，但后者不会自动证明要求在其他环境也得到满足。

## 规定应当成立的行为与选择

### 需求与契约

需求表达希望系统实现的结果，契约明确有关参与方可以依赖的行为。产品需求说明用户问题和目标，接口契约说明调用条件与响应，数据契约说明对象结构、约束、兼容和迁移语义。它们共享对未来或当前行为的要求，却在使用对象和检查方式上有足够差别，值得分别理解。

例如，“允许多人编辑一份笔记”是产品需求；“同一修订号的冲突更新必须被识别”是接口行为；“修订号递增且旧导出仍可解析”涉及数据契约。知道数据库表里有一个 `revision` 字段，并不能独自推出这些行为是否已经成立。

`PRD`、业务规则、`SPEC`、API 参考以及 OpenAPI、GraphQL Schema、Proto、类型定义等，可以承载部分要求。结构化定义通常擅长表达字段与类型，行为条件和例外可能仍由说明及测试表达。这里并没有一条“文字是真相”或“机器定义是真相”的统一排序；应辨认每个来源实际承诺和检查了什么。

需求获采纳不等于已经实现，测试通过也不说明所有需求都被覆盖。契约变化会影响使用它的调用者和实现者；当前实现与契约不一致时，冲突本身是需要解释的对象。若将契约仅归为“当前事实”，就无法描述尚待实现的有效要求；若将它仅归为“未来计划”，又无法解释已经在使用中的行为承诺。

### 约定与判断准则

约定表达当前共同采用的做法。判断准则则解释多个可行方案之间重视什么，例如优先保持兼容、优先避免重复维护，或优先保留研究推理。`CONVENTIONS`、`STYLE`、`GUIDELINES`、编码规范和部分 `TRADEOFFS` 常承担这些职责。

要求、默认做法与建议具有不同的使用方式。一条格式规则可以由工具准确执行，一条关于证据强度的准则需要语义判断；二者都可能被叫作“风格”，但不能据此把它们当作同一种检查。规则文本还可能包含理由与例外，因为读者需要知道它在什么情况下适用。

约定的效力来自当前协作关系和采纳决定，事实正确性则要由相关依据支持。“我们采用方案甲”可以是有效决定，配套的“甲在所有任务上都更快”仍可能是错误事实主张。把两者写在同一页，不会让后者自动得到证明。

一份约定在范围改变、工具承担了原来的工作、实际反例出现或项目重新作出选择时，可能需要修订。它的变化与历史记录有联系：当前规则说明现在采用什么，旧记录解释为什么曾经那样做。两者的认识任务不同，即使最后保存在同一份文件里，也不宜混读。

### 完成条件与验证说明

验证材料围绕“怎样知道工作做到了”组织。这里至少有三种内容：应达到的结果、取得证据的方法、已经取得的证据。`TESTING` 可以同时包含验收要求、测试命令和结果入口，不能仅因它们都与测试有关就认为可以互相替代。

多人编辑的要求需要在方案形成时就被理解；启动测试服务的命令在执行验证时使用；某次并发测试的输出描述那次运行。方法正确不证明测试已执行，测试通过不证明要求本身选得充分，要求写得完整也不保证实现符合它。

因此，验证说明是一个有明确使用任务的复合模型：把要求、操作与观察组织成可判断的关系。测试策略、验收案例、实验方法、性能报告都可能参与。它们值得分别展开到什么深度，取决于所回答的认识问题；本研究不从这个区分直接推出应建几个文件。

## 支持行动与持续工作

### 操作规程与 Skill

操作规程表达在一定前提下怎样完成一类工作。安装、调试、迁移、发布、故障处理和资料转换都可以形成规程。它把动作之间的依赖外部化：先取得哪些条件，按什么关系执行，怎样辨认结果。脚本可以承担机械动作，规程说明动作的意义与适用前提。

解释文档与规程的差别在于阅读目的。架构说明可以让人理解为什么存在迁移阶段，迁移规程则需要足够的信息让执行者完成这次迁移。一个清楚的步骤序列也不能取代所有解释：同样的失败提示，在数据未备份和数据已备份的情况下可能意味着不同后续动作。

Skill 是围绕发现和调用组织起来的能力材料。它可以组合描述、触发条件、规程、规则引用、脚本和其他资源。正文中的步骤未必比普通操作指南多，增加的关键关系是：它怎样被找到，什么任务会使用它，运行系统提供哪些资源，以及一次调用怎样结束。

这就是 Skill 值得独立讨论而不必成为新的基本内容职责的原因。把规程改名为 `SKILL.md`，本身不保证形成这种使用关系。若名称变化触发了消费者已有的识别和使用机制，运行关系会随之改变；相应机制不存在时，名字不能代替它们。本地归档 Skill 同时包含触发描述、规则引用、步骤和检查，固定版本的加载源码又显示“程序已经读到正文”和“模型已经看到正文”并不相同，相关依据见[研究依据与复核](研究依据与复核.codex.md)。

规程会因工具、对象或已知操作经验改变；Skill 除此之外还受发现与调用接口的变化影响。某客户端新增自动激活能力，不会使规程中的业务步骤自动更准确。内容的有效性与运行关系的有效性需要分别解释。

模板则参与产物的生成。它可以预置问题顺序、必需结构、字段和示例，与规程中的“怎样做”、规则中的“应满足什么”、检查中的“怎样确认”各有分工。一份实验模板可以提醒填写环境和输入，却不能保证填入的事实准确，也不能确保当前实验需要的信息已经穷尽。模板可以是 Skill 的资源，也可以独立使用；它是可复用的产物结构，不能仅按其 Markdown 或 JSON 格式理解。

### 路线、问题与任务状态

路线表达值得推进的方向和优先关系，问题记录保存有待理解或解决的现象，任务状态描述当前工作走到了哪里。`ROADMAP`、`PROBLEMS`、`BACKLOG`、`TASK`、`PLAN`、`WIP` 和任务板可能承担这些职责。它们共同面向未完成工作，但“计划”并不是一个足以解释全部差异的标签。

问题可以先于解法存在。一个间歇性数据丢失问题，最初只有现象、发生条件和已有观察；直接把它写成“换数据库”就同时加入了原因判断与解决方向。路线又可能选择暂缓它，或者先完成能够帮助调查的日志能力。任务状态则在实际推进中记录查过什么、排除了什么、哪一步尚未完成。

任务状态之所以值得单独研究，是因为它表达执行过程中的位置。一个实施方案可以长期不变，当前测试是否已运行却可能随下一次工具调用改变。缺少这种状态，接续者容易重做已完成的探索，或把计划中的动作当成已经发生。

同一计划可以从设想进入执行，再在结束后成为历史。其正文仍可能有复用价值，身份却已变化：过去的下一步不再是现在的待办。这个变化首先需要在理解上被辨认，不意味着必须按时态迁移文件。是否创建任务页、保留多少过程以及结束后怎样整理，是组织方法问题。

### 交接与恢复

交接是把工作状态转成接续者可使用的表示。它保存目标、已经发生的动作、结果、未完验证、阻塞与下一步，还要补足原执行者习以为常、接续者却不知道的前提。因此它与工作状态有大量相同内容，却有自己的完整性问题。

“迁移补丁已完成”不足以说明可以发布。如果测试尚未运行、只改了一部分调用者或另一分支仍在使用旧数据格式，接续者需要知道这些条件。交接的任务不是把前一段工作写得像一个完成总结，而是使下一步能够从真实位置继续。

日历式日志告诉读者发生过哪些动作，未必直接支持恢复；摘要能减少重读，却可能丢失关键限定；完整对话保留更多细节，又需要能够定位和解释。它们可以共同服务交接，但不是同一种表示。

交接也解释了“曾经正确”和“现在可用”的差别。前一执行者确认过的分支、服务和测试条件，可能在交接期间改变。恢复既包括取回材料，也包括使材料与现实重新对应。这个使用任务足以让交接作为复合模型独立展开，无须假定每个项目都需要一份名为 `HANDOFF` 的文件。

## 保留思考、观察与可复用认识

### 提案与研究

提案使一个尚未决定的选择成为可讨论的对象。它需要表达问题、前提、候选方案和重要取舍；研究还可能需要重建事实、提出解释、比较反例并设计检验。`RFC`（Request for Comments，征求意见稿）、`PROPOSALS`、设计草图、研究稿、实验计划和部分 `SPEC`、`TRADEOFFS` 都可以承载这些活动。

未采纳是状态，却不能充分定义这类模型。提案的独立价值是组织选择：让参与者看见问题被怎样理解、有哪些可以改变决定的条件。把数据库方案的一页接口结构单独取出来，它可能与最终接口文档完全相同；提案整体还包含被否的文件锁方案、并发假设、迁移成本和等待确认的问题。这些关系不会由“草稿”两个字自动表达。

研究又不必以采纳一个方案为终点。它可能厘清一个概念、解释一次反常现象，或证明原先的问题需要改写。原始观察、解释与建议在这里相互联系，但不能互相冒充。一项推测被写进长期保存的研究稿，并不会因此成为已证实事实。

提案从讨论进入采纳，可以继续保留比较过程；其中某些内容以后成为当前要求或当前说明。变动的是具体陈述的身份与用途，不是整份文件必然沿着“草稿—真相—历史”的单一阶梯上升。这一点使研究模型能够容纳失败、撤回和问题重构。

### 决定、当前理由与历史理由

决定记录保留一次选择为什么在当时成立：面对什么问题，有哪些约束和重要备选，采用了什么，承担了什么后果。架构决策记录 ADR（Architecture Decision Record）、`DECISIONS`、已定 RFC 和部分复盘都可能承担这项任务。[Nygard 的 ADR 提议](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)以背景、决定、状态和后果组织小记录，也允许把后来失效的决定标为被替代。

当前理由与完整历史在这里有重要分工。多人协作的系统说明中，“写入必须在同一事务中完成，否则修订号与内容可能不一致”直接帮助理解现在的结构。若把所有理由都放到远处的历史中，当前结构可能只剩一组难以理解的规定。完整历史则保存当时为什么选择事务、考虑过哪些其他办法、哪些条件以后可以重访。

两者并不重复同一项工作。短理由支持当前理解，完整取舍支持重新评估。一个只有标题的决定索引可以帮助发现记录，却不能替代任何一者；一个现行原则也不需要每次都附上从最初讨论到最后选择的全部历史。

记录的更新方式要由其陈述对象解释。过去确实作过的选择不会因今天换方案而消失；对这项选择实施进度的描述却会改变；原记录还可能存在错记。deepseek-harness 的 Notes 同时要求更新活动记录中的实施事实、保留原有决定的身份，并在归档后冻结。这一实例说明，所谓“记录”内部就可能同时存在需要更新和需要保留的内容。

因此，把决定记录定义成永远不改的文本，会遗漏更正、实施状态与替代关系；把它当作随时重写的当前说明，又会失去当时的依据。模型需要解释这几种变化，具体采用追加、更正说明、版本记录还是其他组织方法，留给实际方案研究。

### 事件、实验与复盘

事件记录保存发生过什么。提交记录、会议纪要、故障时间线、实验原始结果和会话导出具有不同精度和消费者，但都把观察绑定到一定条件下。它们的价值在于可以重新回到当时的事实，而不是只能接受后来的一句话结论。

实验比事件记录多出一个组织关系：问题或假设、输入与设置、观察、分析和结论需要相互对应。一个延迟数字离开负载、模型、配置和计量方法，几乎无法参加比较。性能报告将这些内容组合起来，读者的任务是判断一个结论究竟得到哪些观察支持。

复盘则从事件出发追问原因、判断与改进。时间线与原因解释可能由同一作者写在一篇文章中，认识地位却不同。后来发现一个此前未知的依赖，可能推翻复盘中的原因判断，而不改变已发生的故障时间。区分观察与解释，正是复盘能够被纠错的前提。

负面结果也有独立信息价值。只保留“最后采用数据库”，无法恢复文件锁方案在哪种并发条件下失败；完整保存所有尝试，又不保证未来能找出改变选择的那一条。文档模型需要辨认原始过程、关键结果与后来提炼的关系，而不能把实验仅等同于废弃方案或把结果仅等同于成功。

### 经验与跨任务记忆

经验材料把过去的事实、方法和纠正，组织成以后可能复用的认识。它与原始记录的差别在于，提炼本身加入了判断：哪些条件是关键的，什么可以推广，哪些只是一次偶然成功。`MEMORY`、`LESSONS`、项目笔记和宿主记忆库，都可能承载这样的内容。

“某次测试因服务未启动而失败”是一项观察；“运行这一组测试前需要启动服务”可能是可复用的操作知识；“所有测试失败都先重启服务”则是过度推广。由事件到经验并不是删掉细节后把句子写得更肯定，而是辨认哪些关系有理由在下一次继续成立。

经验可能与当前事实、规程、约定和决定理由重叠。它们的差别不在文件位置，而在阅读者的需要：工作状态支持接着做，经验支持后来复用，当前说明解释现在的对象，历史理由支持重访过去的选择。一份 `MEMORY.md` 可以包含几种内容，分析时仍需辨认它们。

保存只是记忆过程的一部分。经验要影响后续任务，还需要能够被找到、取得、解释，并在失效时修正。跨任务保存不等于跨项目适用，长期有效也不等于每次都要读。主体、任务、环境和取回方式，共同决定这类材料怎样参加工作。

## 帮助发现、进入和交付材料

### 导航、库存、目录树与大纲

这些材料都可能带来“找到东西”的效果，但表达的是不同关系。导航把问题或工作连到材料，例如“修改数据格式时查看兼容约定”；目录树展示文件系统的层级；库存或注册表保存对象的身份与可查询属性；大纲安排一项论证或产物的展开顺序。

差别可以用一个问题看出来：目录里有 `docs/storage/`，并不等于读者知道多人写入的限制在哪一篇；库存中的文件大小也不解释模块为什么不能互相依赖。带有用途说明的目录图可以兼任导航，带有数据流和边界解释的导航又可以兼任架构说明。组合不会消灭这些区别。

大纲也可能承担计划责任。已经写成的文章大纲概括现有结构，准备写作的大纲则表达预期顺序，某些标题对应的内容尚不存在。用“导航元数据永远稳定”概括它们，会忽略目标、内容与路径都可能变化。

`INDEX`、`TREE`、`registry`、`outline`、`MANIFEST`、资源目录和 `llms.txt` 都可以成为寻找材料的线索。是否需要中心索引、怎样生成目录、采用全文搜索还是字段查询，是组织与工具选择。01 所需说明的是，它们分别提供了什么信息，为什么不能仅凭名字认为可以互相替代。

### 项目介绍与协作入口

README 常常承担“第一次接触时形成足够理解并开始使用”的整体任务。它可能组合定位、能力、上手步骤、限制与进一步导航。这个任务解释了为什么 README 值得作为复合模型讨论：读者通常既不知道项目的完整结构，也不知道下一步应去哪里，相关内容共同支持一次进入过程。

协作入口则面向准备参与工作的人或 Agent，可能加入当前约定、工作方式、非标准操作和进一步读取线索。`AGENTS.md`、`CLAUDE.md`、`GEMINI.md` 以及各类规则文件的程序识别方式并不相同；正文中的独立内容、共享内容和客户端适配也可能不同。

这里有两个同时成立的事实：入口是一种有辨认价值的使用关系；入口里的每段内容仍需按自己的职责理解。它可以包含系统解释，也可以主要是指令，不能从“协作入口”推出“只能写硬约束”。相反，普通文件包含了同样的指令，也不能仅凭正文就认定某个客户端会自动读取它。

人和 Agent 不构成两套完全隔离的文档类型。Agent 可以使用面向用户的入门说明，人也可能审阅一份给 Agent 的规则。真正改变阅读需要的是当时要完成的工作、已经知道的内容和可用工具。作者是谁、谁决定采纳、谁执行、谁维护，也应按这些关系分别理解。

### 外部来源与派生表示

外部来源是一种来源身份，不能单独告诉读者正文承担什么职责。一份第三方 API 说明可以是操作参考，一篇论文可以提供观察与解释，一份外部设计提案仍可能处于未定状态。本项目自产的实验也可以成为证据，因此“外部来源”与“证据”不能互换。

来源模型值得讨论的是版本、归属、可重建性以及原件与本地解释的关系。固定快照表达当时依据的是哪个对象，可刷新的检出目录表达当前可访问的副本；二者可能有相同内容，却对未来复核有不同意义。引用一份来源也不等于采纳其中所有要求。

摘要、镜像、翻译、客户端适配和生成参考，则体现派生关系。概要选择保留什么，翻译改变语言，适配改变消费者接口，生成参考按照输入规则重建表示。它们可能需要不同的检查：摘要是否丢失关键例外，翻译是否改变词义，生成视图是否对应当前输入。

派生关系不必把内容变成新的基本类型，却能形成独立使用模型。发布摘要让用户判断是否升级，原始变更清单保留更细的事件，两者围绕同一变化服务不同任务。明确这种关系，也才能解释为什么某处信息改变会使另一处过时。

### 用户、工作角色与对外交付

主体设定保存某个参与者特有的背景、偏好、目标或职责。个人语言偏好、项目所有者的优先级、代码审查者的工作分工、子 Agent 可使用的工具，都可能进入这类材料。`USER`、`PERSONA`、`SOUL`、本地配置和 Agent 定义文件只是部分载体。

偏好与工作角色有必要分别理解。“用中文回答”是一种表达偏好，“负责设计审查并返回问题清单”规定了工作任务，某个工具字段则可能被程序解析。实际 Agent 定义经常将几者组合。本地 MemOS 的审查者文件就是结构化字段与角色正文共同存在的例子；这能说明组合形态，不能单凭文件存在证明工具配置已经被执行。

主体信息的适用范围也不由存放位置决定。用户目录里可能保存某一项目专用的环境事实，仓库里的用户画像也可能只是产品设计对象，而不是当前操作者。需要理解的是文字描述谁、对谁有效、在什么任务中参与判断。

对外交付又是另一种关系。教程、发布说明、支持指南、`CONTRIBUTING`、`SECURITY`、许可证、归属和引用说明，围绕上手、协作、迁移、分发或认可贡献等任务组织内容。它们可以成为 Agent 的输入，也可以是 Agent 负责生产的结果。不能因为主要读者是外部用户，就把其中的有效要求排除出开发活动。

[Diátaxis](https://diataxis.fr/)用教程、操作指南、参考和解释区分读者需要。这一划分有助于解释为什么同一主题会有不同呈现：建立能力需要学习路径，完成已知任务需要步骤，精确查询需要可定位的细节，理解原因需要关系与论证。它与本文的职责和使用关系可以相互参照，却不会自动回答加载时点、采纳状态或维护方式。

## 同一内容怎样经历不同用途

回到多人协作的例子。最初的研究提出“本地文件为什么发生冲突”，保存观察与候选解释；数据库提案把接口、备选和迁移条件组织成可讨论的选择；方案采纳后，既有兼容要求继续约束实施，已定方案成为实施依据，但迁移还没有发生；任务状态随后记录实际改动和测试进展。实现完成时，系统说明可以描述新的结构，原始观察继续支持此前的诊断，决定记录仍保存当时的取舍。

这不是一份文档从低到高的成熟度阶梯。几种用途可以同时存在：提案中的接口契约已经生效，另一部分方案仍在试验；活动决定中的实施路径需要更新，当时排除的备选仍作为历史保留；当前架构中包含短理由，完整历史另有自己的读取任务。

由原始结果提炼经验，又是另一种变化。原始结果与经验结论可以同时保留，前者不会因为后者产生就变成低价值材料。反过来，某个临时进度失去接续用途后，也不必为了维持模型完整而永久保存。概念上的区别帮助解释发生了什么，不能直接裁决每一份实际材料的保存方案。

这使观察维度找到了位置。内容身份解释一句话应怎样使用；范围与版本解释它在哪里成立；使用关系解释谁因什么任务需要它；演化方式解释什么变化会使它不再准确；表示与取得方式解释当次实际能看到什么。它们按问题参与分析，不是一份要求每篇文档填写的登记表。

Markdown、CSV、JSON、YAML、XML、网页、PDF、图像和数据库也处在表示这一层。连续论证、字段查询、嵌套契约、关系图和公式排版需要不同表达；改变格式不自动改变职责。同一库存从 Markdown 表格导出 CSV，可能只是方便查询；若增加机器消费者，实际解析契约才进一步改变了使用关系。关于选择、表示和成本的区别，见[基础理论](基础理论.codex.md)。

## 这份全景完成了什么

本文把两种容易混在一起的研究对象连起来了：能够逐段辨认的信息职责，以及围绕完整使用任务形成的文档模型。前者解释事实、要求、状态、方法、理由、观察和线索为什么不同；后者解释入口、提案、验证说明、交接、Skill 和派生交付物为什么有自己的整体用途。获取与演化关系贯穿其间，使同一内容可以在不同任务和时期被正确理解。

这份全景的充分性建立在主要问题能够被解释、已知困难实例没有被强行抹平上，不建立在文件名列表永远不会增长上。以后出现一个新名字，首先看它是否带来新的使用任务或重要关系；如果只是现有模型的另一个载体，就没有必要重建分类。若一个新实例暴露了现有解释无法保留的实质差别，应修正模型本身。

具体仓库是否需要某份文档、怎样安排路径、拆成几份、默认读多少以及怎样维护，仍需要任务和环境条件。本文为这些问题提供了可用的认识对象；这些组织选择由并列研究继续处理。本轮案例、证据与尚待效果检验的问题集中保存在[研究依据与复核](研究依据与复核.codex.md)。
