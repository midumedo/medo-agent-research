# 机器可读工程文档治理与代码库上下文拓扑重构

**从文档堆砌到分层心智模型：注意力稀释、语义冗余与确定性闭环的实证校准**

**报告日期：2026年9月22日**

## 摘要

本报告对"仓库根目录堆砌规则文档"引发的三类故障做实证校准，并给出可落地的治理路径。校准结果是三类故障证据强度差别很大：注意力衰减有跨模型、跨架构、跨微调状态的重复实验，答案文档位于上下文中段时准确率降幅有时超过 30%，且召回数量的边际收益明显递减；规则打架的根源可在加载机制的官方表述中直接定位——所有层级文件被拼接进同一上下文而非按作用域覆盖，矛盾规则可能被任意选择一条；文档腐烂率则需下调口径，可核验的测量是仓库级 23.0% 与元素级 1.27%，"高达 80%"未找到学术出处。

治理路径分五层。工业格局上，AGENTS.md 已由 Linux 基金会旗下 Agentic AI Foundation 托管、被超过 6 万个项目采用，单变量对照实验显示其使平均运行时间下降 20.27%、输出 Token 下降 20.08%。加载机制上，渐进式披露用约 100 Token 的元数据换掉全量注入，分层目录使单次任务加载量从 200 行以上降到 106 至 140 行。格式选型上，准确率与 Token 效率指向不同答案——YAML 检索准确率领先（62.1%），Markdown Token 效率领先（比 JSON 少 34% 至 38%），从测试生成的行为索引可把搜索结果压缩约 30 倍且不会腐烂。决策留痕上，ADR 对 Agent 的影响分为被忽略、仅建议、被强制三级，只有第三级产生硬保证，而瓶颈已从"写下来"转移到"能被检索到"（检索层 precision@3 仅 0.33）。闭环上，没有验证的循环工程只是自动化，确定性代码检查是唯一可重复的硬停止。

边界同样明确：自动生成的上下文文件比不提供更差，人工编写的仅提升 4% 准确率而推理成本上升超过 20%；ContextBench 显示前沿模型的块级 F1 普遍低于 0.45，更复杂的检索脚手架并不稳定优于简单基线。指令冲突的频率与影响、索引文件的存活时长、腐烂的完整口径三处仍是证据缺口。

## 1. 三类故障的实证校准：哪些数字站得住

仓库根目录堆积十余份规则文档所引发的三类故障，在方向判断上都能找到实证支撑，但三类故障的证据强度差别很大。注意力衰减有跨模型、跨架构、跨微调状态的重复实验；规则打架的根源可以在加载机制的官方表述中直接定位；而"高达 80% 的文档腐烂率"这一说法在可检索的学术文献与工业报告中找不到对应测量，需要替换为已有口径。把这三件事分开处理，是后续所有治理设计的前提。

### 1.1 注意力衰减不是玄学：U 型曲线与召回边际递减

Lost in the Middle 是被反复复现的实证现象，而非工程直觉的修辞。原始实验的设计十分简洁：在多文档问答任务中给模型提供 10 至 30 篇文档，其中只有一篇包含答案，通过改变这篇答案文档在输入中的位置观察准确率变化，结果呈现清晰的 U 型曲线——答案文档在开头时准确率最高，在结尾时也不错，在中间时显著下降，降幅有时超过 30%[feishu.cn](https://docs.feishu.cn/article/wiki/K2QPw1Nnni8KqJk7COWcWZXlnid)。更值得警惕的是，这不是某一个模型的特例，几乎所有被测模型都表现出同一模式，包括专门为处理长上下文设计的模型[feishu.cn](https://docs.feishu.cn/article/wiki/K2QPw1Nnni8KqJk7COWcWZXlnid)。

围绕成因的对照实验进一步排除了几种流行的解释路径。

**表1：Lost in the Middle 现象的对照实验观测**

| 实验条件 | 观测到的位置敏感性 |
|---|---|
| 多文档问答，文档数为 10、20、30，对应约 2K、4K、6K Token | 相关文档位于开头或结尾时效果更好，位于中间时性能下降 |
| 键值对查询，上下文长度为 4K、8K、16K | 表现较好的模型在各位置均接近 100% 准确率，表现较差的模型在目标键位于中间时结果变差 |
| 在多文档问答中加入 Encoder-Decoder 架构模型 | 同样出现中间位置性能下降 |
| 把查询置于文档之前而非之后 | 同样出现中间位置性能下降 |
| 指令微调前的基座模型与微调后模型对比 | 微调之前已存在该现象 |
| 同一模型家族的 7B、13B、70B 三档规模对比 | 13B 与 70B 的现象比 7B 更明显 |

这组对照的推论是收敛的：现象既不是解码器架构的产物，也不是查询与文档相对顺序的产物，更不是指令微调引入的偏差；而且模型规模扩大不但不缓解，反而让现象更明显。对文档治理而言，最后一条尤其致命——它意味着"换个更强的模型就能吃下十份规则文档"这条路没有实证支撑。

标称上下文长度与有效注意力长度之间的差距也被独立测量过。GPT-4 在 64K Token 以内能保持较高准确率且对针的位置不敏感，超过 64K 后性能开始明显下降，在 100K Token 的极限情况下若针被放在文本中间位置，准确率会显著降低。Claude 2.1 在首轮大海捞针测试中只有 27% 的准确率，Anthropic 后续分析把原因归到模型的行为倾向而非检索能力：由于插入的个人信息与草堆内容毫不相关，模型倾向于判定该信息来源不可靠而拒绝引用，调整提示词后表现大幅提升。这个插曲本身给出一项方法论提醒——长上下文测试的分数同时包含能力与行为倾向两种成分，不能直接当作能力读数。随着单针测试失效，评测演进到多针检索、多针推理、序列针检索与多模态大海捞针，2025 年的研究显示即便是表现最好的模型，在要求同时找到多个信息点并按正确顺序排列的序列针检索任务上准确率也只有 63.5% 左右。

对文档堆砌策略最直接的一击来自召回数量的边际收益实验。研究者通过控制检索系统召回的文档数量，比较 Top5、Top10、Top20、Top30、Top40、Top50 六种条件下模型的准确率，结果显示准确率相对召回数量的边际收益明显递减，多召回的文档对回答问题几乎没有帮助[feishu.cn](https://docs.feishu.cn/article/wiki/K2QPw1Nnni8KqJk7COWcWZXlnid)。把这一结论平移到仓库文档场景，"把可能相关的规则全都塞进去"在证据上是负收益策略：它不增加信号，只增加噪声，同时把真正需要被遵守的条款推向 U 型曲线的中段。

学术界对这一现象的机制解释与缓解手段也在推进。一项 2026 年的研究识别出控制模型整体上下文注意力的 contextual heads，指出分心源于这些注意力头未对相关上下文分配足够注意力，并提出通过 focus directions 增加对相关上下文的注意力激活来缓解，但该方法需要缓存 key/query 激活并在推理时修改注意力权重，与 FlashAttention2 一类的推理加速技术不兼容[openreview.net](https://openreview.net/forum?id=h7Tm6dSWWp)。另一条路径是纯数据驱动的 IN2 训练：用合成长上下文问答数据强调"长上下文中任意位置都可能承载信息"，训练得到的 FILM-7B 能在 32K 窗口中稳健完成前向、后向与双向检索，在 NarrativeQA 上把 F1 从 23.5 提到 26.9，同时在 MMLU 上保持 59.3 到 59.2 的相当水平[arXiv](https://arxiv.org/abs/2404.16811)。这两项工作说明现象可以在模型侧被削弱，但都要求介入训练或推理内核，仓库文档治理无法指望它们。工程侧能引用的证据是 Chroma 的技术报告结论：喂进去的内容越多，模型与 Agent 的表现越差[脸书 Facebook](https://www.facebook.com/groups/vibecodinglife/posts/2066531260602067/)。

从这些结果可以提炼出一个对文档设计有直接约束力的三难关系：上下文窗口大小、有效注意力长度与信息密度三者无法同时最大化。窗口扩张的计算与内存开销按 O(n²) 增长，而注意力会被稀释；信息密度过低会让噪声淹没信号，密度过高又会因过度压缩导致语法断裂与语义模糊，研究显示存在一个甜点区，约每 Token 承载 0.15 个实体时效果最佳。这三条边界共同构成了后文分层加载方案的物理依据：不是"少写文档"，而是"在任一时刻只让当前任务需要的文档进入窗口"。

### 1.2 规则打架的机制根源：拼接而非覆盖

草稿中把规则冲突描述为 Agent 的"认知抖动"，这个描述抓到了症状但没定位病灶。病灶在加载机制：Claude Code 一类的配置体系并不按作用域覆盖，而是把所有被发现的文件拼接进同一个上下文。官方文档的表述是"All discovered files are concatenated into context rather than overriding each other"，加载顺序从最广泛作用域到最具体作用域，目录树中越靠近工作目录的指令越晚读取，同级的 CLAUDE.local.md 在 CLAUDE.md 之后追加[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy)。

拼接语义带来的直接后果是：冲突不会被系统消解，只会被一并送给模型。官方文档对此没有回避，直言"if two rules contradict each other, Claude may pick one arbitrarily"——两条规则矛盾时模型可能任意选择一条[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy)。而且这些指令是以 user message 而非 system prompt 的形式交付，Anthropic 明确表示不保证严格遵循[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy)。官方给出的对照表述把边界划得很清楚：settings.json 中的规则由客户端强制执行，无论模型决定怎么做；CLAUDE.md 中的指令塑造模型行为，但不是硬性执行层[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy)。因此凡是必须成立的约束，正确去处是带严格优先级链（managed > local > project > user）的 settings.json 或生命周期钩子，而不是任何一份 Markdown[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy)。

层级结构本身在不同文档中有三级与五级两种描述，需要区分。三级描述是 user（`~/.claude/CLAUDE.md`）、project（仓库根 CLAUDE.md 或 `.claude/CLAUDE.md`）、directory（子目录 CLAUDE.md）[claudearchitectcertification.com](https://claudearchitectcertification.com/concepts/claude-md-hierarchy)；五级描述在此之上加入 enterprise 与 local，形成 Enterprise（`/etc/claude-code/CLAUDE.md`）→ User → Project → Local（`./CLAUDE.local.md`）→ Subdirectory 的序列[hackernoon.com](https://hackernoon.com/the-complete-guide-to-ai-agent-memory-files-claudemd-agentsmd-and-beyond)，另一份资料给出 global → organization → project → local → subdirectory 的同构划分[morphllm.com](https://www.morphllm.com/claude-md-examples)。企业策略最先加载，随后是个人偏好、项目级、子目录级[hackernoon.com](https://hackernoon.com/the-complete-guide-to-ai-agent-memory-files-claudemd-agentsmd-and-beyond)。值得注意的是，社区曾提出 Defaults ← User ← Local Project 的合并逻辑，但那是 issue 中的提案而非官方语义[GitHub](https://github.com/anthropics/claude-code/issues/4442)。

拼接语义还产生一个容易被忽略的时序问题：上下文压缩之后，各层级文件的恢复行为不一致。`/compact` 之后项目根目录的 CLAUDE.md 会从磁盘重新读取并自动恢复，而子目录 CLAUDE.md 与带 `paths:` frontmatter 的 `.claude/rules/` 文件不会自动恢复[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy)。这意味着一个长会话在压缩前后的有效规则集合可能不同——冲突是否出现、哪条规则被采纳，会随会话长度漂移。诊断手段是存在的：`/memory` 列出已加载的指令文件路径与顺序[Medium](https://medium.com/@bijit211987/the-complete-guide-to-claude-md-memory-rules-loading-and-cross-tool-compression-97cc12ed037b)，`/context` 报告当前会话实际加载的内容[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy)。

`@` 路径导入语法在这一机制下需要重新理解。语法本身是 `@` 加路径（并不存在 `@import` 关键字），每一行 `@<path>` 在加载时被立即内联进 CLAUDE.md，`@import` 支持递归引用，最深 5 层[hackernoon.com](https://hackernoon.com/the-complete-guide-to-ai-agent-memory-files-claudemd-agentsmd-and-beyond)。立即内联意味着拆分文件改善了人类的可维护性，却不减少最终进入上下文的体积[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy)。这是后文分层方案里必须处理的一处内在张力：把详情拆到子文件只有在"子文件按需加载"时才省 Token，靠 `@` 导入拉进来的部分一分不省。

针对冲突的治理手段目前有两类。第一类是仲裁规则的形式化：多 Agent 场景下的冲突解决被整理为六层有序仲裁——authority（权威性）、scope（作用域）、validity（有效性）、specificity（具体性）、arbitration（仲裁）、recency（时效性）[allainews.net](https://allainews.net/how-to-handle-conflicting-instructions-between-ai-agents/)。第二类是工具化的静态检测：开源工具 ai-context-kit 的 lint 能力会显式报告 conflict（例如"始终使用分号"与"从不使用分号"这类直接对立）、duplicate-content（跨文件重复）、token-budget（超过 2000 Token 警告、超过 5000 Token 报错）、directory-listing（超过 10 行的目录树）与 vague-instruction（"遵循最佳实践"一类模糊指令），并给出 0 至 100 的评分[GitHub](https://github.com/ofershap/ai-context-kit)。

需要指出的是，指令冲突目前缺少公开的量化研究。可查到的相关工作集中在代码层面而非规则层面：AgenticFlict 是一个大规模 AI 编码合并冲突数据集，用于研究冲突的普遍性与特征[arXiv](https://arxiv.org/html/2604.03551v1)；反模式目录中记录的 Assumption Propagation 描述的是早期误解级联放大到后续全部工作[agentpatterns.ai](https://agentpatterns.ai/patterns/anti-patterns/)。规则文档之间的语义冲突频率、冲突对任务成功率的边际影响，尚未见到对照测量。因此本章对"规则打架"的判断建立在加载机制的官方语义之上，属于机制推导而非统计结论。

工业界为这套碎片化付出的同步成本已经公开化。Shopify CEO Tobi Lütke 曾考虑在公司内部禁用 Claude Code，直到它支持读取 AGENTS.md 与 `.agents/skills`；当团队同时使用 Codex、Cursor 与 Claude Code 时，同一仓库会出现多个配置入口，使用 Codex 的开发者读 AGENTS.md、使用 Claude Code 的开发者读 CLAUDE.md，两份文件存在差异时不同 Agent 获得的项目规则也不同。他把这种额外负担称为"复杂性税"[36氪](https://36kr.com/p/3989811919076098)。

### 1.3 文档腐烂率的可核验口径：23.0% 而非 80%

草稿引用的"高达 80% 的文档腐烂率"在本次调研覆盖的学术文献与工业报告中找不到对应测量。这一节给出可核验的替代口径，并说明 80% 这个数字最可能的来源混淆。

目前针对 AI 配置文件腐烂最直接的学术研究是 2026 年 6 月的《Context Rot in AI-Assisted Software Development》[arXiv](https://arxiv.org/html/2606.09090v1)。该研究把"Context Rot"定义为 AI 配置文件与代码库、工具、架构或约定之间的渐进式分歧，方法上把原本用于 README 一致性检查的 DOCER 工具不加修改地直接应用于 AI 配置文件[arXiv](https://arxiv.org/html/2606.09090v1)。数据规模是：以 Galster 等人收集的 9,470 个配置文件（来自 4,463 个 GitHub 仓库）为基础，筛选出记录了首次提交 SHA 的 8,213 个文件（来自 4,420 个仓库），再以随机种子 42 采样 356 个仓库（95% 置信水平、5% 误差范围），保留每个仓库内的全部配置文件，最终分析 612 个文件[arXiv](https://arxiv.org/html/2606.09090v1)。这些文件在数据集中的占比为 AGENTS.md 42.7%、CLAUDE.md 30.3%、copilot-instructions.md 13.7%[arXiv](https://arxiv.org/html/2606.09090v1)。

**表2：三类故障的原始主张与可核验数据对照**

| 故障类型 | 草稿中的主张 | 可核验的测量结果 | 口径与限定条件 |
|---|---|---|---|
| 注意力衰减 | 10 份以上独立规则文档使信噪比断崖式下跌 | 答案文档位于上下文中段时准确率下降，降幅有时超过 30%[feishu.cn](https://docs.feishu.cn/article/wiki/K2QPw1Nnni8KqJk7COWcWZXlnid) | 多文档问答任务，10 至 30 篇文档、约 2K 至 6K Token；未直接测量"规则文档份数"这一自变量 |
| 规则打架 | CONVENTIONS.md 与 AGENTS.md 对立导致认知抖动 | 官方文档承认矛盾规则可能被任意选择一条遵循[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy) | 机制层面的官方表述，非统计测量；缺少冲突频率与影响的对照研究 |
| 文档腐烂 | 高达 80% 的腐烂率，精确到路径的 INDEX.md 撑不过一周 | 356 个仓库采样中 23.0% 存在过时代码元素引用（95% CI 18.8–27.2%）[arXiv](https://arxiv.org/html/2606.09090v1) | 仅测量代码元素引用这一类腐烂；单文件级过时率为 1.04% 至 1.42%[arXiv](https://arxiv.org/html/2606.09090v1) |

腐烂的两级口径需要分开读。仓库级：356 个仓库中 23.0% 存在过时的代码元素引用，95% 置信区间为 18.8% 至 27.2%[arXiv](https://arxiv.org/html/2606.09090v1)。元素级：从 612 个配置文件中提取出 29,454 个候选代码元素，其中 18,048 个经验证在首次提交时确实存在，230 个（1.27%）已失效[arXiv](https://arxiv.org/html/2606.09090v1)。按文件类型划分的元素级过时率为 CLAUDE.md 1.42%（77/5,423）、AGENTS.md 1.04%（70/6,762）、Copilot instructions 1.42%（77/5,436）、GEMINI.md 0.75%（1/133）[arXiv](https://arxiv.org/html/2606.09090v1)。两个口径差了一个数量级，原因是单个仓库内绝大多数引用仍然有效，但只要有一处失效就把整个仓库计入 23.0%。引用该数据时若不注明口径，很容易把 1.27% 说成 23.0%，或反过来。

该研究还给出了检测工具自身的精度上限：在 50 个被标记为过时的元素中，人工验证确认 64%（32 个）为真实过时，36%（12 个假阳性加 6 个模糊案例）为误报[arXiv](https://arxiv.org/html/2606.09090v1)。过时的具体形态包括函数不存在、方法被删除、文件路径失效、脚本被移除与依赖项丢失[arXiv](https://arxiv.org/html/2606.09090v1)。

更早的传统文档研究给出了同一量级的参照。Tan 等人 2023 年发表于 Empirical Software Engineering 的研究——也正是 DOCER 工具的原始论文——在 top-1000 GitHub 数据集上发现 19.2% 的文档至少包含一个过时的代码元素引用，28.9% 的项目至少有一份过时文档[theodd0ne.com](https://theodd0ne.com/blog/article/the-organisational-memory-leak-why-lessons-disappear-between-teams/)。23.0%（AI 配置文件、仓库级）与 19.2%（传统文档、文档级）在数值上接近但口径不同，不宜直接相减比较；两者共同支持的是"约五分之一的范围存在过时引用"这一量级判断。同一来源还引用 DORA 2025 报告，指出文档质量与组织绩效之间存在明确关联，应把文档视为支撑其他能力的技术工作而非边缘任务[theodd0ne.com](https://theodd0ne.com/blog/article/the-organisational-memory-leak-why-lessons-disappear-between-teams/)。

关于 80% 这个数字，本次调研能找到的最接近的高位数据来自 MAST 2025 研究：流行的多 Agent 框架失败率在 41% 至 86.7% 之间，其中 41.77% 的失败可归因于规范（specification）问题[Medium](https://medium.com/@adnanmasood/agentic-ai-design-patterns-a-practical-field-guide-to-what-works-in-production-45c476c65a37)。86.7% 是框架任务失败率的上界，41.77% 是失败原因的归因占比，两者都不是文档腐烂率。较合理的判断是，草稿中的 80% 可能来自对这类高位失败率的转引，或来自某个团队内部的非公开观察。在正式文本中，建议改用 23.0% 与 19.2% 两个可核验数字，并把"精确到文件路径的索引撑不过一周"改写为定性判断——本次调研没有找到对索引文件时效性的量化测量。

腐烂治理在工业侧已出现自动化路径。OpenAI 的 Harness Engineering 实践中，自动化 Agent 会扫描仓库中过时或缺失的文档并直接开出清理 PR，把文档腐烂当作机械问题而非人为纪律问题处理[swequiz.com](https://www.swequiz.com/articles/openai-harness-engineering)。学术侧的研究议程则把腐烂拆成可递进的五段：引用腐烂（可从传统文档研究直接迁移）→ 行为指令一致性 → MCP 工具描述漂移 → 架构声明漂移 → 依赖版本过期，并给出确定性检测配合语言模型修复（检查 git 历史后建议更新引用）的方向[arXiv](https://arxiv.org/html/2606.09090v1)。这五段中只有第一段有测量结果，后四段仍是待办。另有 practitioner 记录的 Silent Config Rot 案例：一次自查发现自动化配置已经静默失效六天[领英](https://www.linkedin.com/posts/nhan-dinh-8474ab42_i-ran-a-diagnostic-on-my-ai-coding-setup-activity-7488256586117767168-vmvH)。教程可执行性研究 Docable（FSE 2020）也把文档腐烂列为软件教程的既有问题之一[chrisparnin.me](https://www.chrisparnin.me/pdf/docable_FSE_20.pdf)。

## 2. 仓库上下文文档的工业格局：碎片化与正在发生的收敛

### 2.1 七套并存的上下文文件约定

当前主流编码 Agent 各自维护独立的上下文文件约定，同一个仓库要服务多个工具就需要同时维护多份内容高度重叠的文件。这种碎片化不是审美问题，它直接制造语义冗余与规则漂移：内容重叠意味着一处修改要同步多处，同步失败就意味着不同 Agent 拿到不同的项目规则。

**表3：主流 AI 编码工具与其读取的上下文文件**

| 工具 | 读取的上下文文件 | 作用域与冲突处理机制 |
|---|---|---|
| Claude Code | CLAUDE.md、CLAUDE.local.md | 三级层级，拼接而非覆盖，矛盾规则可能被任意选择[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy) |
| OpenAI Codex | AGENTS.md、AGENTS.override.md[arXiv](https://arxiv.org/html/2606.09090v1) | 分层指令发现，纳入仓库级 AGENTS.md |
| Cursor | .cursor/rules/*.mdc（现代格式）、.cursorrules（已弃用）[GitHub](https://github.com/ofershap/ai-context-kit) | YAML frontmatter 定义激活模式，也读取 AGENTS.md[hackernoon.com](https://hackernoon.com/the-complete-guide-to-ai-agent-memory-files-claudemd-agentsmd-and-beyond) |
| GitHub Copilot | .github/copilot-instructions.md 与 instructions/*.md[arXiv](https://arxiv.org/html/2606.09090v1) | 同时识别 CLAUDE.md 与 AGENTS.md[arXiv](https://arxiv.org/html/2606.09090v1) |
| Windsurf | .windsurfrules[GitHub](https://github.com/ofershap/ai-context-kit) | 双结构规则文件 |
| Gemini CLI | GEMINI.md[arXiv](https://arxiv.org/html/2606.09090v1) | 仓库级单文件 |
| Cline | .clinerules[GitHub](https://github.com/ofershap/ai-context-kit) | 仓库级单文件 |

这些文件的功能是同一件事：为模型提供跨会话持续存在的项目专属知识，内容涵盖约定、贡献指南、架构、构建命令与测试实践[arXiv](https://arxiv.org/html/2606.09090v1)。差别只在命名与加载语义。研究用的数据集显示这些文件并非只放指针的空壳，而是包含被 AI 工具直接消费的详细描述[arXiv](https://arxiv.org/html/2606.09090v1)。

碎片化的实际成本在大型仓库中被放大。开发者给出的临时办法是建立软链接，或在 CLAUDE.md 中写入 `@AGENTS.md`；小型项目采用这些方案比较容易，到了大型 monorepo，配置文件会沿目录树递归生效，维护成本迅速上升[36氪](https://36kr.com/p/3989811919076098)。一份实践指南把最终的收敛方案写得很具体：项目根放 AGENTS.md 承载共享指令（构建命令、代码标准、测试要求），CLAUDE.md 通过 `@imports` 承载 Claude 专属行为并保持在 100 行以内，CLAUDE.local.md 放个人偏好，其余工具文件全部用软链接指向 AGENTS.md，作者对这套方案的评价是"优雅吗？不。能防止指令漂移吗？能"。

### 2.2 AGENTS.md 的收敛进程与实测收益

AGENTS.md 已从工具私有约定变成有治理主体的开放格式。它由 AI 软件开发生态中的多方协作推动，参与方包括 OpenAI Codex、Amp、Google 的 Jules、Cursor 与 Factory，目前由 Linux 基金会旗下的 Agentic AI Foundation 托管[agents.md](https://agents.md/)。采用规模上，官方站点给出的数字是超过 6 万个开源项目[agents.md](https://agents.md/)，一项 2026 年的学术研究在引言中独立引用了"超过 6 万个仓库采用"这一量级[arXiv](https://arxiv.org/html/2601.20404v2)。

它的设计定位是"给 Agent 看的 README"：README 面向人类，承载快速上手、项目描述与贡献指南；AGENTS.md 补充 Agent 需要的额外上下文——构建步骤、测试与约定——这些内容放进 README 会显得杂乱，或对人类贡献者并不相关[agents.md](https://agents.md/)。格式本身刻意保持宽松，官方 FAQ 中不设置必填字段，也直接回答了"指令冲突怎么办"这一问题[agents.md](https://agents.md/)。对 monorepo 的支持方式是嵌套：子目录可以放置自己的 AGENTS.md，Agent 遵循就近原则[agents.md](https://agents.md/)，离被编辑文件最近的 AGENTS.md 优先级最高，而显式的用户提示覆盖一切[hackernoon.com](https://hackernoon.com/the-complete-guide-to-ai-agent-memory-files-claudemd-agentsmd-and-beyond)。写作风格上的建议是命令优先——给出精确的调用命令，而不是写人类文档[blakecrosley.com](https://blakecrosley.com/blog/agents-md-patterns)。

收敛是否真的带来收益，目前有一项对照实验可以引用。该研究在 10 个仓库的 124 个 PR 上测试 OpenAI Codex，实验的唯一变量是 AGENTS.md 文件是否存在（其余文件不变），两种条件下 Agent 收到相同的任务输入[arXiv](https://arxiv.org/html/2601.20404v2)。任务输入的构造方式是：用本地 LLM（gpt-oss-120b，通过 Ollama 运行）读取 PR diff 与合并前的仓库文件树，生成一份结构化的、形如 GitHub issue 的任务描述（含问题陈述、期望行为、约束与验收标准），以此统一 Agent 的输入格式并降低方差[arXiv](https://arxiv.org/html/2601.20404v2)。AGENTS.md 文件的分类同样由该模型按既定标准执行，随后人工验证过滤结果，筛选后保留 26 个仓库[arXiv](https://arxiv.org/html/2601.20404v2)。

**表4：AGENTS.md 存在与否两种条件下的实测对比（OpenAI Codex，10 个仓库 124 个 PR）**

| 指标 | 无 AGENTS.md | 有 AGENTS.md | 变化幅度 |
|---|---|---|---|
| 平均运行时间 | 162.94 秒 | 129.91 秒 | 下降 20.27%[arXiv](https://arxiv.org/html/2601.20404v2) |
| 中位运行时间 | 98.57 秒 | 70.34 秒 | 下降 28.64%[arXiv](https://arxiv.org/html/2601.20404v2) |
| 平均输出 Token | 5744.81 | 4591.46 | 下降 20.08%[arXiv](https://arxiv.org/html/2601.20404v2) |
| 总 Token | 687,632 | 619,321 | 下降 9.93%[arXiv](https://arxiv.org/html/2601.20404v2) |

四项指标同向下降，且中位数降幅（28.64%）大于均值降幅（20.27%），说明收益在分布上偏向原本耗时较短的任务，长尾任务的改善被均值拉平。总 Token 降幅（9.93%）明显小于输出 Token 降幅（20.08%），这个差值本身值得注意：AGENTS.md 自己也要占用输入 Token，它抵消了一部分节省。净收益为正，但不是"加了文件就省 Token"这么简单的叙事。

该研究的作者也说明了这项工作的定位：此前已有研究考察过 copilot-instructions.md 与 CLAUDE.md 一类的配置文件，但在保持任务、仓库与 Agent 架构不变的前提下，单独隔离"引入一份 AGENTS.md"这一动作对效率的影响，此前没有先例[arXiv](https://arxiv.org/html/2601.20404v2)。换句话说，这是首个单变量对照，样本量（10 个仓库 124 个 PR）与单一 Agent（OpenAI Codex）构成明确的外推边界。

标准收敛在 2026 年 3 月跨过了最有代表性的一道门槛：Anthropic 接受 AGENTS.md，Claude Code 新增原生支持[36氪](https://36kr.com/p/3989811919076098)。接入方式的细节决定了兼容的深度——读取项目子目录文件时会按目录层级补充对应的 AGENTS.md，同级目录若存在 CLAUDE.md 则遵循原有 CLAUDE.md 规则；相关设置位于 `/config` 的 Project instructions 中，用户可以选择仅使用 CLAUDE.md、在没有 CLAUDE.md 时回退到 AGENTS.md，或同时加载两类文件[36氪](https://36kr.com/p/3989811919076098)。默认模式下只有项目路径上没有 CLAUDE.md 时才会回退读取 AGENTS.md[36氪](https://36kr.com/p/3989811919076098)。而且兼容不等于统一：`.agents/skills` 与 `.claude/skills` 仍是两套独立目录，团队依然要决定哪些规则属于跨工具的共同内容、哪些只服务于 Claude Code[36氪](https://36kr.com/p/3989811919076098)。

Anthropic 此前坚持私有约定的理由也值得记录，因为它划出了标准化的天然边界：不同模型家族有不同的行为特点，system prompt 会显著影响模型表现，Claude 模型对 skills、system prompt 与 CLAUDE.md 的组织方式有特定偏好，Claude Code 也会针对不同模型调整 system prompt[36氪](https://36kr.com/p/3989811919076098)。这套模型专属设计优化了单一工具的体验，代价是跨工具协作的维护成本[36氪](https://36kr.com/p/3989811919076098)。可以据此推断：AGENTS.md 收敛的是工具无关的公共部分，模型专属的调优内容仍会留在私有文件里，碎片化会被压缩但不会消失。

## 3. 分层加载：把全量注入换成按需披露

### 3.1 渐进式披露的机制与四种实现模式

渐进式披露是从交互设计借来的原则，在 Agent 语境下的含义是：不一次性呈现全部可用信息，而是按当前阶段的需要分层展开。落到实现上，最清晰的量化来自技能机制——会话启动时只有每个技能的名称与描述进入上下文，每条约占 100 Token，这个量刚好够模型判断某个技能是否与当前任务相关，命中之后才加载完整内容[claude.com](https://claude.com/blog/skills-explained)。用约 100 Token 换掉一次全量注入，这就是分层加载的收益结构。

它对抗的失效模式有明确命名。上下文腐烂（context rot）指注意力稀释、矛盾累积与信噪比下降三者共同作用，使输出质量非线性退化，表现为倒 U 型失效模式：上下文增加在初期提升质量，越过某个阈值之后开始主动损害质量[mindstudio.ai](https://www.mindstudio.ai/blog/progressive-disclosure-ai-agents-context-management)。同一来源明确否定了"换更大窗口"这条退路——更大的上下文窗口不解决问题，它只提高阈值，不消除退化[mindstudio.ai](https://www.mindstudio.ai/blog/progressive-disclosure-ai-agents-context-management)。

四种可落地的实现模式已被归纳出来：索引优先加载（先读索引再决定读什么）、侦察兵模式（用一个前置的轻量 Agent 预筛选材料）、阶段化上下文加载（按任务阶段切换注入内容）、以及技能文件不嵌入参考材料（技能文件只写流程定义，引用列出但不内联，Agent 走到相关步骤时才去取）[mindstudio.ai](https://www.mindstudio.ai/blog/progressive-disclosure-ai-agents-context-management)。第四条是前三条得以成立的前提：如果参考材料被直接写进流程文件，分层就退化成了分文件，体积一分没少。

触发机制本身需要三个组件才能闭环：条件检测、获取机制、加载确认与作用域限定[mindstudio.ai](https://www.mindstudio.ai/blog/progressive-disclosure-ai-agents-context-management)。缺少最后一项时，加载进来的材料会残留在后续所有步骤的上下文里，分层加载又变回累积注入。

同一原则在多 Agent 架构下表现为上下文隔离而非单会话内的分阶段：编排器 Agent 不需要代码生成子 Agent 才用得到的 API 文档，审查 Agent 不需要综合 Agent 处理过的完整研究语料，每个 Agent 应获得与其角色相称的上下文[mindstudio.ai](https://www.mindstudio.ai/blog/progressive-disclosure-ai-agents-context-management)。Claude Code 的官方建议把这条落到了操作层面——当需要上下文隔离，或上下文窗口即将满时使用子代理，子代理可以读几十个文件、跑大量检索，而这些中间过程留在它自己的窗口里[claude.com](https://code.claude.com/docs/en/features-overview)。

### 3.2 分层目录结构的 Token 账本

分层加载在仓库文档上的具体形态是三层结构，每层有明确的行数预算与加载时机。第一层是根目录文件，只放索引与全局规则，控制在 50 行以内；官方文档对单份 CLAUDE.md 的建议上限是 200 行[turbodocx.com](https://www.turbodocx.com/blog/how-to-write-claude-md-best-practices)，但根目录文件每次都会加载，所以越短越好，真正的详情下沉到子目录[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f)。第二层是子目录文件，承载技术栈说明、目录结构映射、常用命令与本项目特有约定；其决定性特性是子目录 CLAUDE.md 不会在启动时加载，只有当 Agent 读取该目录下的文件时才按需加载[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f)。第三层是 `.claude/rules/` 下按 glob 自动匹配的规则文件，通过 frontmatter 中的 `globs` 字段绑定文件类型，连文件都不用打开就能生效[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f)。

收益可以用加载量直接算。以一个 monorepo 为例，根目录文件 42 行，后端子目录文件 97 行，前端子目录文件 64 行：Agent 改后端时只加载根 42 行加后端 97 行约 140 行，改前端时只加载根 42 行加前端 64 行约 106 行；而此前的单一大文件方案每次加载 200 行以上，且还不够详细[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f)。除了 Token，探索成本也下降了：Agent 的探索阶段从读 30 个文件变成读 1 至 2 个文件，理解反而更准确[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f)。

**表5：三种上下文组织方案的代价对比**

| 做法 | Token 消耗 | 准确性 | 维护成本 |
|---|---|---|---|
| 让 Agent 每次自己探索 | 高 | 低（靠猜） | 零[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f) |
| 单一大 CLAUDE.md | 中（全量加载） | 中 | 低[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f) |
| 分层按需加载 | 低（只加载相关的） | 高（人写的精确描述） | 中（需同步维护）[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f) |

这张表的价值在于它承认了分层方案的代价：维护成本从零或低上升到中。这个代价的具体形态就是同步——方案再好，文档过时了比没有更糟，因为 Agent 会按照错误的架构理解写代码[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f)。应对方式是把同步要求写进规则本身，在每一层都设置提醒：根目录的全局不变量第一条写明"修改任何子项目的代码时，若涉及架构、约定、目录结构变更，必须同步更新该子目录的 CLAUDE.md"，每个子目录文件底部再列一份本目录的同步触发条件[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f)。同一来源还建议写入一条全局行为准则——引入新依赖或技术组件时先查官方文档确认最新稳定版本，不要凭记忆猜测 API，理由是模型训练数据有滞后性，它记忆中的 API 可能是 v2 而最新稳定版已经是 v4[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f)。

三条原则可以概括这套方案：顶层极简（根目录只放索引与全局规则，50 行以内）、详情下沉（每个子项目维护自己的上下文文件并按需加载）、代码改了文档也改（把同步规则写进不变量，让 Agent 自觉维护）[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f)。提出者自己的评价是，这不是革命性创新，本质就是给 AI 写 onboarding doc，只不过用了分层加载来控制 Token 开销[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f)。

需要补一条前文已经指出的张力：`@` 路径导入是加载时立即内联，不减少最终上下文体积[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy)。所以"把详情拆到子文件"与"用 `@` 把子文件拉进主文件"是两件相反的事，前者省 Token，后者不省。真正省 Token 的是按需加载机制——子目录文件、带 `globs` 的规则文件、命中后才展开的技能[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy)。

## 4. 格式选型：Markdown 不是所有场景的最优解

### 4.1 准确率与 Token 效率的实测分野

格式选择存在准确率与 Token 成本的明确权衡，两者并不指向同一个答案。一项针对嵌套数据的对照实验给出了准确率侧的测量：研究者用 YAML、Markdown、JSON、XML 四种格式表示同一份嵌套数据（以 Terraform 状态一类的层级结构为样本），每种格式提 1,000 个问题，考察模型检索特定嵌套值的能力，问题形如"resource.aws_subnet.api-12.tags.Environment 的值是什么"，数据量按模型校准到约 40% 至 60% 的准确率区间以便区分格式差异，回答用子串匹配判分[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/)。

**表6：三个模型在四种格式上的嵌套数据检索准确率**

| 格式 | GPT-5 Nano | Gemini 2.5 Flash Lite |
|---|---|---|
| YAML | 62.1%（95% CI 59.1%–65.1%）[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/) | 51.9%[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/) |
| Markdown | 54.3%[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/) | 48.2%[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/) |
| JSON | 50.3%[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/) | 43.1%[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/) |
| XML | 44.4%[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/) | 33.8%[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/) |

两个模型上的排序完全一致：YAML 领先，Markdown 次之，JSON 再次，XML 垫底。第三个被测模型 Llama 3.2 3B Instruct 对格式不敏感，四种格式表现接近[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/)，说明格式敏感性本身与模型能力有关，不是所有模型都会因选错格式而受损。XML 落后被归到三条原因：重复的 `<tag></tag>` 模式可能干扰内容识别、Token 低效意味着更多注意力扩散的机会、以及 XML 在现代训练语料中的占比可能较低[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/)。

Token 效率侧的排序恰好相反，Markdown 全面领先。跨模型的具体差值是：GPT-5 Nano 上 Markdown 比 JSON 少 34% Token、比 YAML 少 10%；Llama 3.2 3B Instruct 上同样是比 JSON 少 34%、比 YAML 少 10%；Gemini 2.5 Flash Lite 上比 JSON 少 38%、比 YAML 少 12%[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/)。XML 方向上，它比 Markdown 多用 80% Token[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/)。另一组独立测量给出的绝对数字与此吻合：同一份内容的 Token 数为 JSON 13,869、TOML 12,503、YAML 12,333、Markdown 11,612，即 Markdown 比 JSON 省约 15%[OpenAI](https://community.openai.com/t/markdown-is-15-more-token-efficient-than-json/841742)。YAML 通常比 JSON 更省 Token，但比 Markdown 略重[推特 X](https://x.com/dpaluy/status/1887385427687965102)。

**表7：同一内容在四种格式下的 Token 数**

| 格式 | Token 数 | 相对 JSON 的变化 |
|---|---|---|
| JSON | 13,869[OpenAI](https://community.openai.com/t/markdown-is-15-more-token-efficient-than-json/841742) | 基准 |
| TOML | 12,503[OpenAI](https://community.openai.com/t/markdown-is-15-more-token-efficient-than-json/841742) | 减少 1,366 |
| YAML | 12,333[OpenAI](https://community.openai.com/t/markdown-is-15-more-token-efficient-than-json/841742) | 减少 1,536 |
| Markdown | 11,612[OpenAI](https://community.openai.com/t/markdown-is-15-more-token-efficient-than-json/841742) | 减少 2,257 |

两组数据合起来给出的判定条件是：按数据形态选格式，而不是按习惯选。准确率优先且数据是深层嵌套结构时，YAML 的 62.1% 对 Markdown 的 54.3% 是 7.8 个百分点的差距[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/)；Token 成本优先且数据可以扁平表达时，Markdown 省下的 34% 至 38% 直接转化为上下文预算[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/)。XML 在这两项测量中同时落后，唯一被承认的优势是标签提供的强边界隔离——同等信息量下它的 Token 消耗是 CSV 的 2 至 3 倍，追加新项还必须插在根标签之前，不如 CSV 或 Markdown 直接在末尾追加干净。

面向网页内容的对比给出了另一组参照：Markdown 比 HTML 少用约 68% 的 Token，并在 RAG 管道一类重视 Token 效率的机器理解基准上表现良好[agentmail.to](https://www.agentmail.to/blog/html-vs-markdown-for-ai-agents)。

学术侧对这一选型问题有专门研究。《Structured Context Engineering for File-Native Agentic Systems》比较了四种 schema 表示格式在文件原生 Agent 系统中的表现，其中 YAML 对应层级结构与 grep 友好的特性、Markdown 对应文档风格与自然语言表达、JSON 对应机器可读性[arXiv](https://arxiv.org/pdf/2602.05447)。这说明格式选型已经进入正式研究议程，而不只是社区经验之争。

### 4.2 生成式索引替代手工维护的静态索引

静态索引的腐烂是结构性的：INDEX.md 里写的每一条文件路径都是一次会过期的断言，代码重构后它就变成错误信息，而错误的索引比没有索引更危险，因为它以强先验的形式把 Agent 引向已经不存在的位置。替代思路是让索引从代码自身生成，从而不会与代码脱节。

行为索引（behaviour index）是这一思路的具体实现：一份名为 BEHAVIOR.md 的 Markdown 文档，列出应用中所有已定义的行为，内容不是手写的，而是从测试生成的，每行格式为 `{path}:{line} {describe} > {test name}`[itnext.io](https://itnext.io/using-a-behaviour-index-to-help-ai-coding-agents-explore-your-code-f02ecbf6f2ef)。它的使用方式是在 Agent 指令中要求先查行为索引来定位实现某个行为的代码——当 Agent 搜索某个概念时，索引返回相关测试，给出这个概念在该应用中的高层含义与预期行为，Agent 再据此读相关测试或做更有针对性的搜索[itnext.io](https://itnext.io/using-a-behaviour-index-to-help-ai-coding-agents-explore-your-code-f02ecbf6f2ef)。三项工程属性使它区别于手写索引：无需手动维护、语言无关、零第三方依赖[itnext.io](https://itnext.io/using-a-behaviour-index-to-help-ai-coding-agents-explore-your-code-f02ecbf6f2ef)。

压缩效果有实测数字。搜索 "subagent" 一词时，匹配代码行的结果约 56,000 Token，匹配文件路径的结果约 4,000 Token，行为索引的结果约 1,800 Token，相对代码行搜索减少约 30 倍[itnext.io](https://itnext.io/using-a-behaviour-index-to-help-ai-coding-agents-explore-your-code-f02ecbf6f2ef)。跨 40 个搜索词的实验中，代码行搜索的结果平均比文件路径搜索与行为索引大 20 至 30 倍[itnext.io](https://itnext.io/using-a-behaviour-index-to-help-ai-coding-agents-explore-your-code-f02ecbf6f2ef)。

这条路径的适用边界同样明确。行为索引的质量上限由测试决定——如果测试名称解释不好某个概念，索引也解释不好，作者把这反过来当作诊断测试质量的信号[itnext.io](https://itnext.io/using-a-behaviour-index-to-help-ai-coding-agents-explore-your-code-f02ecbf6f2ef)。而且它只覆盖"有测试的行为"，架构决策、约束与取舍这类不在测试里的信息仍需人工维护的记录文件。作者本人也承认，存在更成熟的从代码生成文档的工具，也存在更成熟的代码库索引系统[itnext.io](https://itnext.io/using-a-behaviour-index-to-help-ai-coding-agents-explore-your-code-f02ecbf6f2ef)。

同一方向上还有两种探索。一是持久化的本地代码索引，动机是开发者反复观察到 Agent 每次重启后都丢失上下文[Reddit](https://www.reddit.com/r/LLMDevs/comments/1v04h4z/i_built_a_persistent_local_code_index_for_ai/)。二是更激进的提问：代码本身能否直接作为面向 AI 编码 Agent 的知识表示，而不只是被挖掘成外部知识对象的文本[arXiv](https://arxiv.org/html/2608.16295)。

与生成式索引相关的一项反直觉发现来自检索方式的对比：在编码 Agent 基准测试中，grep 有时优于向量检索，理由是嵌入在需要精确的地方引入了模糊性，而索引在需要新鲜的地方引入了陈旧性[领英](https://www.linkedin.com/posts/ritvik-rastogi-003085153_ive-spent-a-lot-of-time-building-rag-pipelines-activity-7462345677625479168-USu6)。陈旧性正是本节讨论的腐烂问题的另一种形态——向量索引一旦建立，就成了一份需要与代码同步的派生文档。

## 5. 决策留痕：ADR 从归档文档变成执行护栏

### 5.1 三级执行阶梯与被忽略的决策

架构决策记录（ADR）的官方定义是一份捕获单个重要架构决策及其上下文与后果的短文档，标准由 adr.github.io 与 GitHub 上的 architecture-decision-record 组织维护[GitHub](https://github.com/architecture-decision-record/architecture-decision-record)。被广泛使用的极简格式由 Michael Nygard 推广，包含标题、上下文（forces）、以主动语态书写的决策、后果，以及 proposed/accepted/deprecated/superseded 状态字段[mnemehq.com](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/)。

在 Agent 参与的代码库里，这套东西的作用发生了性质变化。一句概括是：没人检查的 ADR 是一条评论，机器检查的 ADR 是一条约束；差别不在文档写得多好，而在于是否有一个确定性检查会读取该决策，并能阻止破坏它的变更[mnemehq.com](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/)。据此可以把 Agent 与 ADR 的关系分成三级阶梯，价值恰好在级与级之间的跃迁上。

**表8：Agent 与 ADR 交互的三级阶梯**

| 层级 | 状态描述 | 约束力 | 失效方式 |
|---|---|---|---|
| 第一级 | 被忽略：ADR 根本不在 Agent 的上下文里，它存在于仓库中，但生成该变更的提示从未包含它 | 零影响 | 大仓库中只有少量文件能进窗口时，这是常见状态[mnemehq.com](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/) |
| 第二级 | 在上下文内但仅为建议：ADR 被检索并放进提示，Agent 被告知要遵循 | 概率性 | 合规取决于模型是否正确权衡该指令与其他内容，且随上下文增长而退化[mnemehq.com](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/) |
| 第三级 | 被强制执行：确定性检查读取决策并能阻止违规变更 | 硬保证 | 检查覆盖不全时出现漏网，但不会因上下文变长而退化[mnemehq.com](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/) |

第二级是大多数"规则文件"与记忆方案所处的位置[mnemehq.com](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/)。它相对第一级是真实改善，但本质是概率性的，这也解释了为什么往仓库里加更多规则文档不能解决合规问题——加文档只把系统从第一级推向第二级，而第二级的失效方式恰恰是随上下文增长而退化，与第 1 章的注意力衰减是同一件事。

爬到第三级需要三个要素：检索出相关 ADR、对提议的编辑执行确定性检查、拒绝时指明具体的 ADR 编号让 Agent 依规则重试而不是猜测[mnemehq.com](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/)。执行时机有两级可选：在 CI 中运行属于 diff 级的批处理审查，好处是能拦住一切进入主分支的违规，代价是反馈滞后——Agent 已经产出了整个变更，一次违规意味着一整轮返工；在编辑时运行则在 Agent 尝试写入的瞬间就检查，Mneme 的 Claude Code 集成通过 PreToolUse 钩子在 Edit 与 MultiEdit 之前拦截[mnemehq.com](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/)。两者的关系是编辑时检查让 Agent 在工作过程中保持诚实，CI 作为兜底保证无论代码如何产生，违反 ADR 的变更都到不了主分支[mnemehq.com](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/)。

一个具体设想可以说明第三级的形态：仓库中 ADR-014 规定所有后台工作必须使用既有的 worker 服务，Agent 被要求增加发邮件功能时提议引入 Redis 与 BullMQ 在新队列上跑任务——这在抽象层面完全合理，也很可能是它训练数据中的常见模式；有了编辑时检查，这次写入会被拦下并被告知违反 ADR-014[mnemehq.com](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/)。

瓶颈的位置有基准数据支撑。Mneme 的冻结执行基准显示 7 项违规全部被正确捕获，但检索层的 precision@3 仅为 0.33[mnemehq.com](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/)。这两个数字放在一起说明：执行环节已经可靠，而"能不能把对的那条 ADR 找出来"仍是薄弱环节。这与第 7 章 ContextBench 的结论方向一致——检索精度而非执行强度，是当前的短板。

围绕第三级已经出现工具生态。ADR Guard 是一个 GitHub Action，当被监控的代码路径发生变更而没有新增或更新 ADR 时让 PR 失败，豁免必须显式书写，用带理由的 `ADR-Exempt:` 行[GitHub](https://github.com/architecture-decision-record/architecture-decision-record)。ArchGate 给每个决策两种表达：一份供人与 AI Agent 阅读的文档，加一份可选的、供机器执行的规则文件[archgate.dev](https://cli.archgate.dev/concepts/adrs/)。适应度函数（fitness functions）是用代码编写的客观自动化检查，用来验证决策是否被持续维持，官方表述是"决策记录记录决策，适应度函数保证决策"，它让决策变得可测试、可保证，可以配合任何 CI 系统与 pre-commit 钩子运行[GitHub](https://github.com/architecture-decision-record/architecture-decision-record)。另有 AgDR（Agent Decision Records）这一专为 AI 编码 Agent 设计的决策记录标准，把传统 ADR 扩展到 Agent 时代[GitHub](https://github.com/me2resh/agent-decision-record)；以及 kgai，一个面向 AI 编码 Agent 的仅追加决策日志，作为 MADR 的机器可读伴侣[GitHub](https://github.com/architecture-decision-record/architecture-decision-record)。LLM Agent 自身也可以参与这套流程：起草初始 ADR、持续对照代码验证其假设、连接相关决策[领英](https://www.linkedin.com/pulse/agentic-ai-living-architecture-enhancing-adrs-llms-decision-khan-5gpgc)。

### 5.2 Agent-first ADR 的写法约束与目录命名

在 Agent 写大部分代码的仓库里，决策记录需要满足三条写法约束，它们都来自预算与解读方式，而不是文风偏好[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。

第一条是必须能被加载。人类团队通常在入职时读一次 ADR，之后在争论重提时再读，它的社会功能是阻止同一场讨论反复发生；在 Agent-first 工作流中，ADR 应当为每一个触及它所辖领域的任务被刻意加载，它不只是关于系统的文档，而是提示的组成部分[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。第二条是必须足够短。一份 4,000 字的决策记录会与 Agent 真正需要读的代码争夺上下文，无情的简洁在这里不是风格偏好而是预算约束[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。第三条是在字面解读下无歧义。人类会做插值，读到"我们暂时不做 X"能理解其中的限定；Agent 可能把这句话压平为一条永久禁令，也可能直接忽略，而你可能要等代码已经存在之后才发现它采用了哪种解读[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。

缺少决策日志时，Agent 的失败模式有五种可辨识的形态：自信地选中那个被否决过的方案、按文件逐个漂移、静默反转既有取舍、默认采用最流行的模式、重做已经废弃的实验[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。第一种最值得展开——你评估过强约定的重型框架与极简框架并选择了重型的那个，只读代码的 Agent 看到的是它认为多余的仪式感，于是把它删掉[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。

配套的结构要求有四项。机器可读的 front matter：tags、domain、scope、created 日期，用于支持选择性检索[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。索引文件：Agent 先读索引（标题加一行摘要），再决定加载哪一份记录[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。检查列表以数据形式存在而不是埋在流水线配置里，一行一个检查，含 group、id、severity、command 四列[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。以工作形式书写的后果，加上可测量的重开条件（revisit triggers）[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。拒绝原因被单列为实际的护栏，配合状态字段与不可变性[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。

过时记录比缺失记录更危险：Agent 可能字面执行一条过时的决策，产出"自信的错误代码"[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。这与第 1 章的腐烂问题在后果上合流——腐烂的文档不只是无用，它会主动生产错误。同一来源还把指令文件列为攻击面，建议扫描不可见字符，并把新引入的指令标记出来交人工审查[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)；凭据收敛方面，建议把个人环境文件移出工作树、决定密钥存放位置、定义哪些路径不可触及、明确扫描规则[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。需要标注的是，该来源自己声明其中关于 Agent 行为的论断是来自这项工作的观察，而非基准测试结果[websiteinit.com](https://websiteinit.com/blog/architecture-decision-records-for-ai-agent-codebases/)。

目录命名上，官方规范给出的建议是用 "decisions" 而非 "ADRs"，理由是团队理解更快、也更愿意往里写[GitHub](https://github.com/architecture-decision-record/architecture-decision-record)。文件名约定为小写加连字符、用现在时祈使动词短语，示例是 choose-database.md、format-timestamps.md[GitHub](https://github.com/architecture-decision-record/architecture-decision-record)；另一套约定是四位数字顺序编号，形如 `adr-NNNN-[title-slug].md`，保存在 `/docs/adr/` 目录下[mcpservers.org](https://mcpservers.org/agent-skills/github/create-architectural-decision-record)。不可变性原则要求不修改已有信息，通过追加新信息或创建新 ADR 覆盖旧 ADR[GitHub](https://github.com/architecture-decision-record/architecture-decision-record)。生命周期被划分为 Initiating → Researching → Evaluating → Implementing → Maintaining → Sunsetting 六个阶段[GitHub](https://github.com/architecture-decision-record/architecture-decision-record)。官方仓库同时提供多套模板，包括 Michael Nygard 的极简版、MADR 项目的含选项与利弊版、以及 Jeff Tyree 与 Art Akerman 的更复杂版本[GitHub](https://github.com/architecture-decision-record/architecture-decision-record)。

## 6. 确定性闭环：把建议变成门控

### 6.1 两层停止条件与验证的位置

循环工程（loop engineering）指的是设计一个能自己发现工作、分发工作、检查结果并决定下一步的系统。Claude Code 的负责人 Boris Cherny 把自己的工作直白地概括为写循环，Addy Osmani 也写过同方向的长篇论述；杠杆从"敲提示词"上移了一层，变成"设计那个敲提示词的系统"[sonarsource.com](https://www.sonarsource.com/blog/loop-engineering-without-verification-is-just-automation/)。这套系统的机械部分已经被充分记录：调度与触发、用于并行运行的 git worktree、存放项目知识的技能、MCP 连接器、让 Agent 恢复而非重来的状态文件、拆分工作的子代理[sonarsource.com](https://www.sonarsource.com/blog/loop-engineering-without-verification-is-just-automation/)。

而决定这一切是否有意义的只有一个节点：谁有权宣布循环结束。答错了，循环的其他优点会反过来对付你——更多自动化意味着更多未经审查的产出，并行子代理意味着代码合并速度快过任何人的阅读速度，更大的上下文窗口与更长的调度意味着 Agent 在任何东西检查它之前跑得更远[sonarsource.com](https://www.sonarsource.com/blog/loop-engineering-without-verification-is-just-automation/)。

答案被组织为两层停止条件。第一层是 LLM 验证器子代理，它对意图与语义提供概率性批评，把评分者的上下文与生产者的上下文分开，从而消除最明显的相关性偏差；它足够灵活，能判断没有任何自动化测试可以编码的问题（"这真的解决了用户的问题吗"），带来规则系统不具备的意图感知[sonarsource.com](https://www.sonarsource.com/blog/loop-engineering-without-verification-is-just-automation/)。但它不应充当最终门控——LLM 审查仍是概率性判断，而安全、正确性这类问题需要更硬的保证[sonarsource.com](https://www.sonarsource.com/blog/loop-engineering-without-verification-is-just-automation/)。第二层是确定性代码验证层，作为最终的硬停止，在循环速度上强制执行可复现的安全、质量与可维护性门控，正是它把一个开放式的循环变成有边界、成本可控的循环[sonarsource.com](https://www.sonarsource.com/blog/loop-engineering-without-verification-is-just-automation/)。

只靠测试通过作为停止条件是不够的，因为测试通过对代码是否安全、是否可维护、甚至是否可理解保持沉默[sonarsource.com](https://www.sonarsource.com/blog/loop-engineering-without-verification-is-just-automation/)。Sonar 的 AC/DC 框架把两层组织成四段：Context Augmentation 负责引导，Agentic Analysis（Verify）对生成的代码运行完整的 CI 级确定性分析，恢复常规 CI 扫描所用的依赖与类型上下文以保证发现精确且有规则支撑，Remediation Agent 与 AI CodeFix 负责闭合 Verify 层暴露出的问题[sonarsource.com](https://www.sonarsource.com/blog/loop-engineering-without-verification-is-just-automation/)。时机上，PostToolUse 钩子在每次文件编辑后触发分析，把 Verify 步骤嵌入循环内部而不是放在循环之后[sonarsource.com](https://www.sonarsource.com/blog/loop-engineering-without-verification-is-just-automation/)。安全边界被要求在循环内执行，包括 SAST、依赖审计与超过 450 种模式的密钥扫描[sonarsource.com](https://www.sonarsource.com/blog/loop-engineering-without-verification-is-just-automation/)。

这套设计有一个前提条件：确定性检查器必须存在。如果无法用代码定义"正确"是什么意思，就无法构建自我改进的循环[sonarsource.com](https://www.sonarsource.com/blog/loop-engineering-without-verification-is-just-automation/)。独立验证的价值也已被单独指出——它可以暴露自检查系统存在的盲区[领英](https://www.linkedin.com/posts/jeremyprasetyo_stop-prompting-ai-start-designing-the-system-activity-7505218656168194051-JJ4S)。IBM 对循环工程的定义是设计迭代引导 AI Agent 完成用户定义目标的 agentic 工作流[IBM](https://www.ibm.com/think/topics/loop-engineering)，另一份资料把它描述为发现工作、分发、检查结果、反馈的自纠正循环，目标是消除开发者干预[saulius.io](https://saulius.io/blog/loop-engineering-systems-that-drive-agents)。

### 6.2 WSCI 四策略与四类上下文失败

上下文工程与提示词工程的分工是清楚的：提示词工程关注一组静态指令，用一套规则有效引导 Agent；上下文工程关注如何管理一组动态信息（包含初始提示），确保 Agent 随时间推移始终拥有它需要的东西，核心诉求是让这个过程可重复、可靠[github.io](https://microsoft.github.io/ai-agents-for-beginners/12-context-engineering/)。上下文窗口大小有限，所以构建者需要建立系统与流程来管理信息的加入、移除与浓缩[github.io](https://microsoft.github.io/ai-agents-for-beginners/12-context-engineering/)。

被管理的上下文分五类：指令（提示、系统消息、少样本示例、工具描述）、知识（RAG 检索内容）、工具（工具定义与 MCP）、对话历史、用户偏好[github.io](https://microsoft.github.io/ai-agents-for-beginners/12-context-engineering/)。

四种操作与四类失败模式一一对应，这套划分由 LangChain 提出并被微软的开源课程采用[github.io](https://microsoft.github.io/ai-agents-for-beginners/12-context-engineering/)。

**表9：WSCI 四策略与其对应的上下文失败模式**

| 策略 | 对应失败模式 | 实现手段 |
|---|---|---|
| Write（写入） | Poisoning 污染 | 上下文验证与隔离，信息经验证后才写入长期记忆[newline.co](https://ai-school.newline.co/learn/context-engineering) |
| Select（选择） | Distraction 分心 | 用 RAG 按任务动态检索最相关的工具与文档，工具选择限制在少于 30 个[newline.co](https://ai-school.newline.co/learn/context-engineering) |
| Compress（压缩） | Overload 过载 | 定期把累积信息压缩为摘要，移除冗余历史[github.io](https://microsoft.github.io/ai-agents-for-beginners/12-context-engineering/) |
| Isolate（隔离） | Clash 冲突 | 用上下文剪枝移除过时或冲突信息，或用 scratchpad 分离处理[github.io](https://microsoft.github.io/ai-agents-for-beginners/12-context-engineering/) |

这套词表为前文所有治理手段提供了统一的归位方式。分层加载（第 3 章）是 Select 与 Isolate 的组合：按需加载是选择，子代理隔离是隔离。生成式索引（第 4 章）是 Select 的实现载体，同时因为它不会腐烂，也在削弱 Poisoning 的来源。ADR 的三级阶梯（第 5 章）跨越 Write 与 Isolate：把决策以机器可读形式写入是 Write，用确定性检查拒绝违规变更是把冲突挡在上下文之外。确定性闭环（第 6 章）则是唯一不依赖模型判断的一类手段，它不属于 WSCI 中的任何一项，而是这四项之外的验证层。

隔离在实现上还有两种具体形态值得记录。一是沙箱环境：当 Agent 需要运行代码或处理文档中的大量信息时，处理结果会占用大量 Token，与其全部存在上下文窗口里，不如让 Agent 使用一个能运行代码的沙箱环境，只读回结果与相关信息[github.io](https://microsoft.github.io/ai-agents-for-beginners/12-context-engineering/)。二是运行时状态对象[github.io](https://microsoft.github.io/ai-agents-for-beginners/12-context-engineering/)。在记忆与 RAG 场景下，建议存储检索文档 id、记忆 id、分数、被选中的 id 与脱敏状态，而不是完整的检索文本；安全与隐私场景下优先使用哈希、id 与 token 桶[github.io](https://microsoft.github.io/ai-agents-for-beginners/12-context-engineering/)。

监控方式也随之改变：不记录原始提示，而是记录选择数量、压缩前后的 Token 数、被隔离的子任务 id、检索到的文档 id 这类元数据[github.io](https://microsoft.github.io/ai-agents-for-beginners/12-context-engineering/)。这一条对文档治理有直接含义——要判断上下文预算是否被浪费，需要的是可计量的注入清单，而不是提示词全文。

## 7. 评测现状与治理方案的有效边界

### 7.1 仓库级上下文检索仍然很难

ContextBench 是目前直接测量"编码 Agent 能否检索到并使用正确上下文"的基准。它由 66 个仓库的 1,136 个真实 issue 解决任务构成，覆盖 8 种编程语言，包含 522,115 行人工验证的黄金上下文，覆盖 4,548 个文件与 23,116 个代码块[arXiv](https://arxiv.org/html/2602.05892v3)。它的定位是过程性评估——不只看最终提交的聚合上下文，还用附录中的指标分析 Agent 在执行过程中如何一步步检索上下文[arXiv](https://arxiv.org/html/2602.05892v3)。

**表10：ContextBench 的基准构成与黄金上下文规模**

| 维度 | 数值 |
|---|---|
| 仓库数 | 66 个[arXiv](https://arxiv.org/html/2602.05892v3) |
| issue 解决任务数 | 1,136 个[arXiv](https://arxiv.org/html/2602.05892v3) |
| 覆盖编程语言数 | 8 种[arXiv](https://arxiv.org/html/2602.05892v3) |
| 人工验证的黄金上下文行数 | 522,115 行[arXiv](https://arxiv.org/html/2602.05892v3) |
| 黄金上下文覆盖的文件数 | 4,548 个[arXiv](https://arxiv.org/html/2602.05892v3) |
| 黄金上下文覆盖的代码块数 | 23,116 个[arXiv](https://arxiv.org/html/2602.05892v3) |
| 黄金上下文一致性（82 个任务的 Jaccard 相似度均值） | 0.9518[arXiv](https://arxiv.org/html/2602.05892v3) |

最后一行是这套基准可用性的前提：82 个任务上的 Jaccard 相似度均值为 0.9518，说明黄金上下文高度一致[arXiv](https://arxiv.org/html/2602.05892v3)。

模型侧的结果是负面的。四个前沿模型（GPT-5、Claude Sonnet 4.5、Gemini 2.5 Pro、Devstral 2）在使用标准编码 Agent 脚手架（mini-SWE-agent）解决 issue 时，块级 F1 分数普遍低于 0.45，行级 F1 更低[arXiv](https://arxiv.org/html/2602.05892v3)。具体到 GPT-5：文件级召回 0.709、精确率 0.634、F1 0.645，块级 F1 只有 0.375，行级 F1 只有 0.312；Claude Sonnet 4.5 的行级 F1 最高，为 0.344[arXiv](https://arxiv.org/html/2602.05892v3)。粒度越细，分数越低——文件级能找到大致位置，行级定位不准，这意味着"Agent 读了正确的文件"与"Agent 用到了正确的那几行"是两件差别很大的事。

三项结构性发现比单个分数更重要。其一，更复杂的检索脚手架并不稳定优于简单基线，研究者把这称为编码 Agent 领域的 Bitter Lesson，并指出这暗示存在过度工程[arXiv](https://arxiv.org/html/2602.05892v3)。其二，所有模型都倾向于让召回优先于精确率，即宁可多拿也不放过，代价是引入大量噪声[arXiv](https://arxiv.org/html/2602.05892v3)。其三，检索到的上下文与最终被使用的上下文之间存在显著差距，所有 Agent 都存在上下文使用衰减，其中 Gemini 2.5 Pro 与 Devstral 2 的衰减最严重，Drop 达到 0.431[arXiv](https://arxiv.org/html/2602.05892v3)。在各模型的检索动态差异中，Claude Sonnet 4.5 表现出独特行为，取得了最高的效率[arXiv](https://arxiv.org/html/2602.05892v3)。

围绕仓库级上下文还有一批评测在成形。Agent Retrieval Bench 评估仓库检索器能否在真实工作流信号与现实上下文约束下，找到编码 Agent 下一步需要的上下文[github.io](https://agent-retrieval-bench.github.io/)。CoreStory 的评测得出的结论是，架构上下文注入是 AI 编码 Agent 在复杂软件维护任务上表现的一阶驱动因素[corestory.ai](https://corestory.ai/post/deep-dive-how-corestory-improves-benchmark-performance-for-coding-agents)。更通用的编码基准包括 SWE-bench（2,294 个任务实例，爬取自 12 个流行 Python 仓库的 PR 与 issue）[swebench.com](https://www.swebench.com/original.html)、经人工审查的 SWE-bench Verified[epoch.ai](https://epoch.ai/benchmarks/swe-bench-verified)、面向上下文学习的 SWE Context Bench[github.io](https://deepsoftwareanalytics.github.io/Awesome-Issue-Resolution/)、评估增量代码维护能力的 FEA-Bench[aclanthology.org](https://aclanthology.org/2025.acl-long.839.pdf)，以及 SWE-bench Live 与 ProjectEval[GitHub](https://github.com/YerbaPage/Awesome-Repo-Level-Code-Generation)。长上下文能力侧有 RULER 基准，测试检索、多键值查找与模式匹配在递增上下文长度下的表现[elvex.com](https://www.elvex.com/blog/context-length-comparison-ai-models-2026)。

### 7.2 尚未解决的问题与本报告的证据边界

治理方案的有效边界，最直接的证据来自一项由 ai-context-kit 工具引用的 ETH Zurich 2026 年 2 月研究[GitHub](https://github.com/ofershap/ai-context-kit)。四项发现值得逐条记录：自动生成的上下文文件比不提供更差；人工编写的上下文文件仅提升 4% 的准确率；推理成本因浪费的 Token 上升超过 20%；某些模型因过度服从不必要的指令而性能下降[GitHub](https://github.com/ofershap/ai-context-kit)。

这四条合起来否定了两种流行的偷懒做法。"让 AI 自己生成一份 AGENTS.md"在测量上是负收益[GitHub](https://github.com/ofershap/ai-context-kit)。"把所有想到的规则都写上"会让成本上升而收益微薄，甚至因过度服从而变差[GitHub](https://github.com/ofershap/ai-context-kit)。4% 的准确率提升是人工精心编写的上限读数，它支持"值得做"，但不支持"做了就解决"。

同一工具把治理动作做成了可执行的检查项，其规则集本身构成一份问题清单：token-budget（超过 2000 Token 警告、超过 5000 Token 报错）、empty-rule、duplicate-content（跨文件重复）、conflict（如"始终使用分号"与"从不使用分号"的对立）、directory-listing（超过 10 行的目录树）、vague-instruction（"遵循最佳实践"一类模糊指令），并给出 0 至 100 的评分[GitHub](https://github.com/ofershap/ai-context-kit)。它支持的文件格式覆盖 `.cursor/rules/*.mdc`、`.cursorrules`、CLAUDE.md、AGENTS.md、copilot-instructions.md、`.windsurfrules`、`.clinerules`[GitHub](https://github.com/ofershap/ai-context-kit)。功能上，loadRules() 自动检测项目中的所有上下文文件，measure() 计算每条规则的 Token 成本与占比并做预算检查，lint() 报告冲突、重复、膨胀、模糊指令与无用的目录树，select() 按任务相关性选择规则并遵守 Token 预算（alwaysApply 优先，其次按相关性），sync() 实现单一事实源——在 `.cursor/rules/` 写一次，同步到 CLAUDE.md、AGENTS.md 与其余文件[GitHub](https://github.com/ofershap/ai-context-kit)。

仍然缺少测量的环节有四处，需要明确标注为证据缺口。第一，指令冲突的频率与影响没有量化研究：第 1 章对规则打架的判断建立在加载机制的官方语义（拼接而非覆盖、矛盾规则可能被任意选择）之上[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy)，属于机制推导；可查到的相关数据集 AgenticFlict 面向的是代码合并冲突[arXiv](https://arxiv.org/html/2604.03551v1)，反模式目录记录的 Assumption Propagation 是定性描述[agentpatterns.ai](https://agentpatterns.ai/patterns/anti-patterns/)。第二，"精确到文件路径的索引撑不过一周"没有找到时效性测量；腐烂研究测的是引用失效率，而非索引文件的存活时长[arXiv](https://arxiv.org/html/2606.09090v1)。第三，文档腐烂的完整口径尚未建立，学术议程把引用腐烂、行为指令一致性、MCP 工具描述漂移、架构声明漂移、依赖版本过期列为五段递进路线，其中只有第一段有测量结果[arXiv](https://arxiv.org/html/2606.09090v1)。第四，多 Agent 系统的失败归因虽有高位数字（MAST 2025 报告框架失败率 41% 至 86.7%，其中 41.77% 归因于规范问题[Medium](https://medium.com/@adnanmasood/agentic-ai-design-patterns-a-practical-field-guide-to-what-works-in-production-45c476c65a37)），但该归因针对的是 Agent 间协作规范，不是仓库文档质量。

据此可以给本报告的结论分级。机制层结论（拼接式加载导致冲突不被消解、立即内联不省 Token、按需加载才省 Token）来自官方文档表述[claudecertificationguide.com](https://claudecertificationguide.com/learn/3-claude-code-config/3-1-claude-md-hierarchy)，可信度高。单变量对照结论（AGENTS.md 带来 20.27% 的运行时间下降）来自一项 10 仓库 124 PR 的实验[arXiv](https://arxiv.org/html/2601.20404v2)，样本与单一 Agent 构成外推边界。格式选型结论（YAML 准确率领先、Markdown Token 效率领先）来自三个模型的 1,000 题对照[improvingagents.com](https://www.improvingagents.com/blog/best-nested-data-format/)，被测模型均为中小规模，未覆盖前沿模型。腐烂率结论（仓库级 23.0%、元素级 1.27%）来自 356 仓库采样[arXiv](https://arxiv.org/html/2606.09090v1)，且检测工具自身的人工验证精确率为 64%[arXiv](https://arxiv.org/html/2606.09090v1)。实践层结论（分层结构的加载量、行为索引的 30 倍压缩、ADR 三级阶梯）来自从业者报告与单一工具的基准[腾讯网](https://mp.weixin.qq.com/s?__biz=MzAxNTEzMTUxNQ==&idx=1&mid=2247484053&sn=3a4246fab894f9e58c09db75c64b054f)、[itnext.io](https://itnext.io/using-a-behaviour-index-to-help-ai-coding-agents-explore-your-code-f02ecbf6f2ef)、[mnemehq.com](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/)，未经独立复现。

最后需要说明的是，本报告的全部结论建立在检索到的资料之上，其中从业者博客与厂商文档占有相当比重，学术来源集中在 Lost in the Middle[feishu.cn](https://docs.feishu.cn/article/wiki/K2QPw1Nnni8KqJk7COWcWZXlnid)、IN2 训练[arXiv](https://arxiv.org/abs/2404.16811)、contextual heads[openreview.net](https://openreview.net/forum?id=h7Tm6dSWWp)、Context Rot[arXiv](https://arxiv.org/html/2606.09090v1)、ContextBench[arXiv](https://arxiv.org/html/2602.05892v3)、AGENTS.md 效率对照[arXiv](https://arxiv.org/html/2601.20404v2)、结构化上下文工程[arXiv](https://arxiv.org/pdf/2602.05447)、Agent 友好文档[arXiv](https://arxiv.org/html/2608.20195v1)这几项。凡未见于这些来源的数字与判断，本报告一律未采用。
