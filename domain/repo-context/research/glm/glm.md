# AI 时代的 Repo 文档治理框架
**核心治理原则只有一条：按"读者"与"生命周期"分层，将面向机器的高频上下文压缩到根目录，将面向人的长尾知识下沉到 `docs/` 子目录，并为决策与历史类文档建立不可变的目录约定。** 这套治理的底层逻辑是：AI agent 的上下文窗口是一种稀缺预算——ETH Zurich 与 LogicStar 的实证研究显示，LLM 自动生成的上下文文件反而会降低 agent 任务成功率并增加 20%–23% 的成本，而人工维护的文件只有在聚焦于"agent 无法自行推断的细节"时才有净收益。因此，文档治理的本质不是"多写文档"，而是**把每条信息放在 agent 需要时才被加载的位置**。
## 一、推荐目录结构（结论先行）
```
repo/
├── AGENTS.md              # 机器读，根级，极简（<200行）
├── AGENTS.local.md        # 个人偏好，gitignore
├── README.md              # 人类读，项目门面
├── ARCHITECTURE.md        # 人类+机器读，架构总览
├── SECURITY.md / CHANGELOG.md / LICENSE / CONTRIBUTING.md / CODE_OF_CONDUCT.md
├── docs/
│   ├── INDEX.md           # 文档总索引（唯一入口）
│   ├── CONVENTIONS.md     # 代码/提交/命名约定
│   ├── TRADEOFFS.md       # 显式权衡记录
│   ├── GLOSSARY.md        # 领域术语表
│   ├── LIMITATIONS.md     # 已知限制与边界
│   ├── ROADMAP.md         # 路线图
│   ├── PROBLEMS.md        # 活跃问题清单
│   ├── DEPRECATED.md      # 已废弃机制（补充建议）
│   ├── adr/               # 架构决策记录（编号+不可变）
│   └── experiments/       # 实验记录（可丢弃）
└── .claude/CLAUDE.md      # 工具专用（symlink 到 AGENTS.md）
```
## 二、文档分类总表
| 文档 | 层级 | 主要读者 | 更新频率 | 上下文加载策略 |
|---|---|---|---|---|
| `AGENTS.md` | 根目录 | AI agent | 高频 | 每次请求自动加载 |
| `README.md` | 根目录 | 人类 | 中频 | 按需（agent 会读但不强制） |
| `ARCHITECTURE.md` | 根目录或 `docs/` | 人+AI | 中频 | 渐进披露 |
| `AGENTS.local.md` | 根目录（不提交） | AI agent | 极高频 | 每次请求加载 |
| `docs/adr/*` | `docs/adr/` | 人+AI | 追加式（append-only） | 按需 |
| `CHANGELOG.md` | 根目录 | 人类 | 每次发布 | 不加载 |
| `GLOSSARY.md` | `docs/` | 人+AI | 低频 | 按需（agent 遇到术语歧义时） |
下面按功能分组逐个拆解。

## 三、根目录层：机器的"操作系统接口"
### AGENTS.md —— agent 的 README，治理核心中的核心
这是整套体系里**唯一强制建议存在的 AI 原生文件**。OpenAI 于 2025 年 8 月发布，目前由 Linux 基金会旗下的 Agentic AI Foundation（AAIF）托管，已有超过 6 万个开源项目采用，Cursor、Copilot、Devin、Gemini CLI、Zed 等主流工具均直接读取。
**定位**：它位于系统提示词与代码库之间，是一个"配置层"，作用是告诉 agent 那些**无法从代码中推断的事实**——包管理器选择、非标准构建命令、不可触碰的目录、测试必须运行等。
**关键治理约束**：
- **指令预算**：前沿思维型模型大约能稳定遵循 150–200 条指令，每条指令每次请求都会被加载，因此文件必须极简。Anthropic 给出的目标线是 **200 行以内**。
- **只写不可推断的内容**：ETH Zurich 的研究明确指出，"repository overviews"（仓库概览）虽然被模型厂商广泛推荐，但实测对任务成功率无贡献、纯烧 token。应写的是：非标准工具链（如用 pixi 而非 pip）、"don't touch" 目录、必须运行的测试命令。
- **不写文件路径**：文件路径是高漂移信息，一旦重命名就会"污染上下文"——agent 会自信地去错误的位置找代码。应描述**能力**而非**结构**，比如"认证逻辑大致在 auth 相关模块"而非精确路径。
- **禁止 LLM 自动生成**：自动生成的 AGENTS.md 在实证中降低了 0.5%–2% 的成功率，同时增加 2.45–3.92 步的操作开销。
- **monorepo 嵌套**：Codex 的机制是从根到叶拼接（concatenation），越靠近被编辑文件的 AGENTS.md 优先级越高；累计上限默认 32 KiB，超过后叶级指令会被静默丢弃。OpenAI 官方仓库自身就有 88 个 AGENTS.md。
- **工具兼容**：Claude Code 不读 AGENTS.md，读的是 CLAUDE.md——官方推荐 `ln -s AGENTS.md CLAUDE.md` 做符号链接；Next.js 仓库即采用此法。
**最小模板**（基于 AI Hero 与 GitHub 对 2500+ 仓库的分析收敛出的六段结构）：
```markdown
# AGENTS.md
## 项目一句话定位
这是一个用于 __ 的 __。
## 命令
- 安装依赖: `pnpm install`
- 运行测试: `pnpm test`
- 类型检查: `pnpm typecheck`
## 不可触碰
- `vendor/` 目录永不修改
- 永不提交 .env 或任何密钥
## 约定
详细规范见 docs/CONVENTIONS.md（按需加载）
## 测试规则
- 任何代码改动必须附带测试更新
```
### AGENTS.local.md —— 个人偏好层
这是 AGENTS.md 体系里预留的**个人作用域**文件：提交风格偏好、个人编码习惯等，**加入 `.gitignore`，不入库**。治理要点：团队成员各自维护，永不合并，避免个人偏好污染项目级指令。
### CLAUDE.md —— 工具方言桥
Claude Code 的专用上下文文件。如果你只用 Claude Code，直接维护 CLAUDE.md；如果多工具并存，用符号链接统一到 AGENTS.md，或在 CLAUDE.md 顶部写 `@AGENTS.md` 引入并在下方追加 Claude 专属指令。

## 四、根目录层：人类的入口
### README.md —— 人类优先，但对 agent 友好
README 的受众是**人类开发者**：项目简介、安装、快速上手、使用方式。AI 时代的额外要求是：
- **结构化标题**：agent 依靠 markdown 层级进行语义切分，扁平或混乱的标题会降低检索精度。
- **不承载 agent 指令**：把"如何构建""如何测试"留在 README（人类视角），把"agent 必须运行什么"留在 AGENTS.md——两者职责不同，AGENTS.md 的设计初衷就是"保持 README 简洁"。
- **不重复**：README 里已有的内容，AGENTS.md 不应复述，否则双重加载纯烧预算。
### ARCHITECTURE.md —— 架构总览
写**系统级架构**：核心模块、依赖方向、数据流、部署拓扑。读者是人类新成员和需要宏观理解的 agent。治理要点：放在根目录（高频访问）或 `docs/`（保持根目录干净），**按模块拆分**优于单文件巨石；随着系统演进同步更新，是"中频高漂移"文档，需要与代码评审流程绑定。
---
## 五、`docs/` 上下文层：Agent 的渐进披露资源
这一层的核心机制是**渐进披露（progressive disclosure）**：根 AGENTS.md 只放一句 `For TypeScript conventions, see docs/CONVENTIONS.md`，agent 写 TS 时才去加载对应文件，其他任务不浪费 token。
### CONVENTIONS.md / STYLE.md —— 编码约定
涵盖命名、提交格式、错误处理模式、导入排序等。**关键洞察**：一条真实的代码片段胜过三段描述；最有价值的是**反直觉的约定**——例如"API 客户端永不抛异常，全部返回 Result 类型"，没有这条信息 agent 会给每个调用都套上 try/catch。STYLE 可以并入 CONVENTIONS，避免文件碎片化。
### TRADEOFFS.md —— 显式权衡
记录"为什么不做某事"：为什么不用 Redis 而用内存缓存、为什么选 SSR 而非 CSR。这是 ADR 的轻量版，聚焦**未成形为正式决策的权衡**。对 agent 的价值：防止它"好心"地把你的权衡推翻。
### GLOSSARY.md / CONTEXT.md —— 领域术语
领域概念（organization vs group vs workspace）比文件路径**更稳定**，是适合写入文档的安全内容。这是 agent 消除语义歧义的关键资源，建议根 AGENTS.md 里放一句 `Domain terms: see docs/GLOSSARY.md`。
### LIMITATIONS.md —— 已知限制
记录系统已知的能力边界、不支持的场景、遗留的 hack。与 PROBLEMS.md 的区别：LIMITATIONS 是**长期事实**，PROBLEMS 是**待修复项**。
---
## 六、`docs/` 治理层：决策、演进与历史
### ADR/ —— 架构决策记录（不可变）
治理最成熟的文档类型。**每条决策一个文件，编号递增，一经合入不再修改**——如果要推翻旧决策，写一条新 ADR 引用并取代旧编号。Martin Fowler 的经典建议是放在代码库内、与代码同版本，社区常用路径是 `docs/adr/` 或根目录 `adr/`，推荐格式是 MADR（Markdown ADR）。每条 ADR 的标准字段：Status / Context / Decision / Consequences。
### DECISIONS.md —— 轻量决策日志
ADR 的日记本版本：未上升到架构级别的决策流水。可以与 ADR 并存，也可以作为 ADR 的草稿区——足够重要时升级为正式 ADR。
### ROADMAP.md / PROBLEMS.md —— 演进与问题
ROADMAP 记录规划中的功能与优先级；PROBLEMS 记录当前已知未修复的 bug、技术债。两者都是**活文档**，需要定期清理已过时条目。
### EXPERIMENTS.md —— 实验记录
研究性质的尝试、spike 结论、未上线验证。**可丢弃文档**，建议放 `docs/experiments/` 并明确其"阅后即焚"属性，避免与正式文档混同。
### dialogue/ —— 对话日志
你列表中较独特的一项，推测用于存放人机协作对话、agent 会话记录。治理建议：**默认不入库**（体积大、噪音多），若确需保留作为决策溯源，放入 `docs/dialogue/` 并建立索引，只保留与决策相关的关键片段。
---
## 七、`docs/` 记忆层：Agent 的私有上下文
### MEMORY.md —— 机器记忆
agent 跨会话记忆的持久化存储：项目历史教训、已尝试失败的方案、"这个 repo 的特殊性"。与 AGENTS.md 的区别：AGENTS.md 是**指令**（做什么），MEMORY 是**事实**（发生过什么）。治理要点：定期蒸馏，将高频使用的事实提升到 GLOSSARY 或 CONVENTIONS，将过期内容清除。
### USER.md —— 用户画像
记录仓库所有者/维护者的偏好：喜欢的注释密度、偏好的 API 设计风格。属于**个人作用域**，与 AGENTS.local.md 类似，建议 gitignore。
---
## 八、传统层：不变的经典
### CHANGELOG.md
遵循 Keep a Changelog 格式，面向**版本消费者**，每次发布追加，永不重写历史。agent 场景下价值有限（很少加载），维持人类阅读体验优先。
### SECURITY.md
安全策略、漏洞上报流程、支持版本矩阵。GitHub 界面会直接展示，必须放根目录。对 agent 的价值：明确"安全红线"，防止 agent 生成引入漏洞的代码。
### 其他建议补充的
- **CONTRIBUTING.md**：人类贡献者指南，PR 流程、代码风格（人类视角）。
- **CODE_OF_CONDUCT.md / SUPPORT.md / LICENSE**：开源治理标配，agent 基本不读，人类必读。
---
## 九、你列表中建议裁剪或合并的文件
| 文件 | 评估 | 建议 |
|---|---|---|
| `THISIS` | 与 README 定位重叠（推测是"THIS IS xxx"式项目简介） | 并入 README 首段 |
| `BREIF` | 即 BRIEF，与 README/AGENTS.md 重叠 | 并入 AGENTS.md 的"项目一句话定位" |
| `TREE` | 仓库结构树，高漂移，过期即误导 | 不建独立文件；如必要放 ARCHITECTURE.md，且只描述模块能力不写精确路径 |
| `INDEX` | 有价值，但应作为 `docs/` 的唯一索引 | 保留为 `docs/INDEX.md`，维护成本高，需定期校验链接有效性 |
| `registry` / `outline` | 语义模糊，推测为资源清单/大纲 | 如非团队既有约定，建议并入 INDEX 或 ARCHITECTURE |
| `EXPERIMENTS` | 有价值但需隔离 | 移入 `docs/experiments/` |
## 十、治理原则总结（写在前面的方法论回顾）
1. **指令预算**：AGENTS.md 保持 200 行以内，只写不可推断的事实，其余全部下沉。
2. **渐进披露**：通过根级索引文件 + 子目录深度引用，让 agent 按需加载。
3. **过期即删除**：对 agent 而言，过期文档不是"有点烦"，而是"主动污染上下文"——文件路径漂移、命令变更会让 agent 自信地做错事。建立"文档与代码同 PR 更新"的强制约定。
4. **单一事实源**：同一条信息只出现在一个地方，其他位置用链接引用，避免多处维护导致漂移。
5. **人类 vs 机器分治**：README/CONTRIBUTING/CHANGELOG 面向人类，AGENTS.md 及 `docs/` 深层资源面向机器，**不要在一个文件里同时服务两类读者**——这是 AGENTS.md 设计的初衷。
6. **决策不可变**：ADR 只追加不修改，历史通过"取代"关系而非"覆盖"来演进。
7. **多工具兼容**：AGENTS.md 为主，CLAUDE.md 符号链接，`.cursor/rules/`、`.github/copilot-instructions.md` 等按需作为工具方言桥。
## 落地建议
**最小可行集**：先只做 `AGENTS.md`（≤200 行，只写命令/边界/约定索引）+ `README.md` + `docs/adr/`，其余按需生长。AI Hero 提供了一个实用的重构提示词，可以直接丢给 coding agent 来压缩膨胀的 AGENTS.md：找出矛盾 → 提取根级必需项 → 其余分组下沉到 `docs/` → 标记可删除项。这套体系的核心不是"文档越多越好"，而是**每一行都有存在的成本，每一行都必须在正确的位置被正确的读者在正确的时机读到**。

# Repo 文档的四维坐标系：一套可推导治理规则的分类系统
**设计目标**：不是给现有文件“贴标签”，而是构建一个**生成性分类系统**——任何文档（包括未来出现的）都能被定位，且坐标本身就决定了它的位置、预算、更新流程和审查规则。类比化学周期表：元素的位置预测其化学性质，文档的坐标预测其治理属性。
---
## 一、“优质分类”的四个判据
在设计前先明确验收标准，这也是排除劣质方案的依据：
| 判据 | 含义 | 排除的反例 |
|---|---|---|
| **1. 正交性** | 轴与轴独立变化，改变一个轴值不需要联动另一个 | ❌ 按“目录位置”分类（root/docs/）——位置是治理的**输出**而非本质属性，循环论证 |
| **2. 规则可推导性** | 每个轴值至少绑定一条独立的治理规则，否则轴无存在意义 | ❌ 按“文件大小”分类——大小是衍生属性，推不出规则 |
| **3. 完备性** | 能安置任意未来文档，不留“无法归类”的孤儿 | ❌ 平铺式功能列表（“这是架构文档、这是约定文档”）——只是枚举，无法预测 |
| **4. 最少轴数** | 4 轴已覆盖全域，不为边缘案例加第 5 轴 | ❌ 加“更新频率”轴——与时向/嬗变高度耦合，非正交 |
---
## 二、四轴定义
### 轴 1｜受体轴（Reader）——谁是第一读者
| 值 | 代号 | 判定方法 |
|---|---|---|
| 机器优先 | **M** | 该文档存在的首要理由是 AI agent 会读它 |
| 双读者 | **D** | 人类与 agent 都是高价值读者，缺一不可 |
| 人类优先 | **H** | agent 几乎不读，读了也无行动价值 |
### 轴 2｜时向轴（Temporal Orientation）——知识指向哪个时间
| 值 | 代号 | 语义 |
|---|---|---|
| 过去·纪事 | **P** | 记录已发生的事：决策、变更、实验 |
| 现在·状态 | **N** | 描述当前是什么：架构、约定、术语 |
| 未来·意图 | **F** | 表达期望：路线图、问题清单 |
| 元·导航 | **X** | 关于文档系统本身，时不变：索引 |
### 轴 3｜嬗变轴（Mutation）——文档如何随时间变化
| 值 | 代号 | 语义 |
|---|---|---|
| 纪年式 | **I** | 追加式（append-only），只增不改 |
| 活文档 | **L** | 持续编辑，反映最新现状 |
| 阅后即焚 | **E** | 有保质期，定期清理 |
**正交性证明**（为何时向与嬗变是两根轴而非一根）：P 类通常为 I（ADR、CHANGELOG），但 P 也可以是 E（EXPERIMENTS、dialogue/）或 L（MEMORY、TRADEOFFS）——三种组合在现实中都存在，故两轴独立。
### 轴 4｜辖域轴（Scope）——生效范围
| 值 | 代号 | 语义 |
|---|---|---|
| 仓库根 | **R** | 全仓库生效，占据根目录稀缺位置 |
| 子树 | **S** | monorepo 中包/模块级，就近生效 |
| 个人 | **P** | 单人作用域，不入库 |
---
## 三、主矩阵：12 格“周期表”
受体 × 时向构成二维主视图，嬗变/辖域作为格内标注：
```
              │  M 机器优先           │  D 双读者                 │  H 人类优先
──────────────┼───────────────────────┼───────────────────────────┼──────────────────────
 F 未来·意图   │ (预留格：agent 任务    │ PROBLEMS                  │ ROADMAP
              │  队列/记忆待办)        │   [L · docs/]             │   [L · docs/]
──────────────┼───────────────────────┼───────────────────────────┼──────────────────────
 N 现在·状态   │ AGENTS.md             │ ARCHITECTURE              │ README
              │   [L · R · 预算≤200行] │   [L · R或docs/]          │   [L · R]
              │ AGENTS.local          │ CONVENTIONS (吸收STYLE)    │ SECURITY
              │   [L · P · gitignore] │   [L · docs/ 可按S拆分]    │   [L · R]
              │ USER                  │ GLOSSARY (统一CONTEXT)     │ (THISIS/BREIF/TREE
              │   [L · P]             │ LIMITATIONS [L · docs/]   │  归入左侧/ARCH)
──────────────┼───────────────────────┼───────────────────────────┼──────────────────────
 P 过去·纪事   │ MEMORY                │ ADR/ DECISIONS [I · docs] │ CHANGELOG
              │   [L · agent私有]      │ EXPERIMENTS [E · docs]    │   [I · R]
              │ dialogue/             │ TRADEOFFS  [L · docs]     │
```

## 五、规则引擎：从坐标推导治理
这是该分类系统的核心价值——**治理规则不是记忆的清单，而是坐标的函数**。
### 5.1 加载策略 = f(受体 × 辖域)
| 坐标组合 | 加载策略 | 依据 |
|---|---|---|
| M × R | **常驻**——每请求注入，硬预算（≤200行） | 上下文窗口稀缺性 |
| M × 非R | **按需**——由 agent 的记忆系统或索引触发 | 避免预算浪费 |
| D × 任意 | **按需**——根 AGENTS.md 留一行索引，任务相关时拉取 | 渐进披露 |
| H × 任意 | **不加载**——零预算，纯人类可读性优化 | agent 无行动价值 |
### 5.2 更新工作流 = f(时向 × 嬗变)
| 坐标组合 | 工作流规则 |
|---|---|
| P × I | Code review 中**禁止修改已合入内容**；推翻旧决策 = 新增条目并引用旧条目（ADR 的 superseded 模式） |
| P × E | 显式标注保质期；定期清理任务；默认不入库（dialogue/ 入库 = 反模式） |
| P × L | **蒸馏机制**：高频被引用的历史事实升格为 N 类文档（MEMORY → GLOSSARY/CONVENTIONS），低频的清除 |
| N × L | 与代码**同 PR 强制更新**；过期即删——对 agent 而言过期文档是主动污染源 |
| F × L | 周期对账；已实现的条目**归档到 P 类**（ROADMAP 完成项 → CHANGELOG 记录） |
| X × L | 链接有效性 CI 检查；全仓库唯一入口 |
### 5.3 审查规则 = f(受体)
| 受体 | 审查重点 |
|---|---|
| M | ① 行数/token 计量 ② 漂移审计（路径、命令是否过期）③ **禁止 LLM 批量生成**（实证降低成功率）|
| D | 双轨结构：结构化标题（机器语义切分锚点）+ 可读叙事（人类）；与 GLOSSARY 术语互链 |
| H | 可读性优先，无需为机器优化，无预算约束 |
### 5.4 位置规则 = f(辖域 × 嬗变)
| 组合 | 规则 |
|---|---|
| R | 根目录文件总数硬上限（建议 ≤ 8）；每个根级文件须证明“常驻或门面”资格 |
| S | 就近原则，子树优先级高于根（Codex 拼接机制） |
| P | .gitignore，永不合并，避免个人偏好污染项目级指令 |
| E × R | **禁区**：易逝文档禁止放根目录 |

## 八、这套系统买到的东西
1. **从清单到函数**：治理规则从“要背的一堆注意事项”变成“坐标的推导结果”——新人不需要理解 25 个文件的历史沿革，只需要理解 4 根轴。
2. **冗余的自动检测**：同格合并原则让 THISIS/BREIF/registry/outline 这类“感觉重复但又说不清为什么”的文件有了机械化的裁决标准。
3. **未来的容纳能力**：任何新文档（包括 agent 自主生成的文档）都有确定的归属判定流程，系统不会随时间腐化为无法归类的文件垃圾场。
4. **反模式的先验识别**：禁区坐标让“什么不该做”在文件创建之前就能被判断，而不是在上下文被污染之后才被发现。
**一句话总结**：这份分类的本质是把上一轮所有零散的治理结论（预算、渐进披露、过期即删、追加不可变、个人不入库）**收编为四个正交维度的投影**——文档是什么不重要，它在坐标系里的位置决定它如何被治理。

## 二、你方案的三个真洞察（我的系统必须吸收的）
### 2.1 “永恒”时态：我漏掉的一整个知识类
我的 N（现状）轴混合了两种真值锚定方式完全不同的知识：
- **现状**：真值锚定在“现在”这个移动时点，必须随版本持续重写（ARCHITECTURE、“我们用 pnpm"）
- **公理**：真值不锚定任何时点，跨版本恒定（“简单性优于性能”、“错误处理不抛异常”）
检验方法：新文档引用它时是否需要标注来源。引用“根据 ADR-007"的是事后知识；被当作先验前提直接陈述的（无需出处）是永恒知识。我的系统把 CONVENTIONS 里的两类条款塞进同一个治理桶（N·L·docs/），导致公理条款被按“高变文档”的频率无谓审查——**你的“永恒”格精确修复了这个治理税**。
进一步：永恒其实是“事后”的**语义升格**（正典化，canonization）。一条决策从“历史上某次的选择”升格为“本项目的先验前提”，标志是引用方式的改变。这是一个我完全没有刻画的状态转换。
### 2.2 层级轴：嬗变率的机制解释
这是我系统最深的一个结构性弱点。我的嬗变轴（I/L/E）登记的是**现象层属性**——你观察并记录“这个文档怎么变”。你的层级轴登记的是**机制层变量**——公理层天然低变，语法层天然高变，嬗变是层级的函数。
这带来一个登记经济性的实质差异：新文档入库时，判断“它是什么层级”（语义判断）比预测“它会怎么变”（行为预测）**更容易且不易错**。类比门捷列夫周期表：原子量是现象，质子数是机制——你的方案提供了质子数。
但要诚实标注推导的不完备性：CHANGELOG（高变但无层级，它是记录不是规范）、MEMORY（高变，主体类）——层级→嬗变的推导只对**规范类文档**成立。这决定了层级在融合系统中是**条件轴**（规则类激活，参考类空转）。
### 2.3 状态轴与知识相变链：你的系统最深刻的贡献
把你的四个时态值连起来看，它们构成一条**知识成浆管线**：
```
TRADEOFFS        dialogue/           ADR/              CONVENTIONS 原则段
(事前：选项空间) → (事中：推演过程) → (事后：结论快照) → (永恒：正典化公理)
 草稿·可编辑       草稿·默认焚毁       受控·append-only    受控·恒定
```
在我的系统里，这是**四个独立登记的文档类型**，各自有坐标，相互之间没有转换语义。在你的系统里，这是**同一知识在四个成熟度阶段的相态**。我的系统对“成为 ADR 之前的讨论过程”完全失明——dialogue/ 被我机械地登记为 M·P·E 就完了，但它实际上是 ADR 的**前驱相态**，它的治理规则（何时归档、如何转换、转换时保留什么）是相变问题，不是静态登记问题。
“草稿→受控”的单向闸门同理：ADR 草稿期可编辑可丢弃，定稿瞬间全部治理规则反转（可变→不可变、无审查→强制审查）。我的系统只登记了终态（I），**没有捕捉闸门本身**。

## 三、你方案的四个盲区（需逐一证明）
### 3.1 二元契约对象丢失 D（双读者）
“写给人看的共识 vs 写给工具读的配置”这个二分，对 ADR/ARCHITECTURE 是失真的。它们的存在理由恰恰是**同时**服务两类读者，且由此推导出独特的双轨规则：结构化标题（机器语义切分锚点）+ 可读叙事（人类）。二元框架强迫二选一后，这条双轨审查规则就无处安放。
### 3.2 层级轴非全域（完备性破坏）
对以下文档做层级判定：
| 文档 | 公理/架构/模块/语法？ |
|---|---|
| MEMORY | 无值（agent 私有记忆，不指涉任何抽象层级） |
| INDEX | 无值（纯导航） |
| dialogue/ | 无值（过程记录） |
| USER | 无值（主体画像） |
你的四条轴里，时态与状态全域适用，**层级与实体各有一片无值域**。这不是致命伤（可以声明为条件轴），但在未声明时会造成“无法归类”的孤儿——恰好违反你自己上一轮验收过的完备性判据。
### 3.3 嬗变模式缺失（治理规则发散的证明）
对比 CHANGELOG 与 ROADMAP 在你系统中的坐标：
| | CHANGELOG | ROADMAP |
|---|---|---|
| 你的坐标 | 事后·受控 | 事前·受控 |
| 实际变化方式 | append-only，禁止改写 | 持续重写，完成项删除 |
两者在你全部四轴上几乎同格，但治理规则**完全相反**：一个是审计史（改写历史 = 犯罪），一个是活计划（不清理完成项 = 腐化）。状态轴的“受控”承载不了这个区分——必须独立的嬗变轴。
### 3.4 空间辖域缺失
monorepo 的嵌套 AGENTS.md 机制（根到叶拼接、叶级优先、32 KiB 累计上限、超限静默丢弃）是**空间作用域**问题。你的层级轴（公理→语法）是纵向抽象谱系，回答不了“这个文件放哪、作用半径多大、和上层文件如何竞争预算”。个人作用域（AGENTS.local 的 gitignore 永不合并）同样无层级解。注意：层级与辖域**部分相关**（公理→根、模块→子树），但 AGENTS.local（操作级内容+个人辖域）证明相关性不构成可推导性。

| 6 | ADR 定稿 | 契约对象二选一 | D 双读者 → 双轨结构审查 | **我胜**——受体三分必要性 |
三比三。这个对称性不是外交辞令，而是投影差异的必然结果：**你赢在时间维（生命周期），我赢在空间维（形态与作用域）**。

## 五、融合系统：双层五轴 + 状态转换门
融合的裁决标准采用**信息熵原则**：一根轴必须携带无法从其他轴推导的信息，否则降级为派生属性。逐轴检验后：
### 5.1 全域轴（四条，任何文档必有值）
| 轴 | 取值 | 来源 |
|---|---|---|
| **受体** | M / **D** / H | 我的（保留三分） |
| **时态** | 事前 / 事中 / 事后 / **永恒** / **元** | 你的（吸收“永恒”）+ 我的（保留"X"，安置 INDEX） |
| **状态** | 草稿 / 受控 | 你的（独立为轴，捕捉发布闸门） |
| **辖域** | 根 / 子树 / 个人 | 我的（空间作用域，承载 monorepo 拼接与 gitignore 规则） |
### 5.2 条件轴（一条，规范类文档激活）
**层级**：公理 / 架构 / 模块 / 语法——你的贡献。激活条件：实体=规则类。参考类文档（MEMORY、INDEX、dialogue）此轴显式标注“—”而非强行赋值。
### 5.3 派生属性（降级，不占轴位）
- **嬗变**：默认由“时态×层级”推导（事后×架构→append-only；现状×语法→高变重写），**异常时显式登记**（CHANGELOG 高变无层级 = 登记异常）。机制层推导 + 现象层兜底。
- **维护强度**：你的四档收编为治理输出函数，与其他函数并列：
| 档位 | 触发坐标 |
|---|---|
| 全量（每 PR 强制同步） | 语法层·受控（AGENTS.md 命令段、CONVENTIONS 现状条款） |
| 重点（架构变更时同步） | 架构层·受控（ARCHITECTURE、ADR 新增） |
| 大概（周期对账） | 事前·受控（ROADMAP、PROBLEMS） |
| 无需（一次性） | 事后·I（ADR 合入后）、永恒（正典化后） |
### 5.4 状态转换门（融合系统的动态骨架，你的管线的形式化）
```
草稿 ──发布闸门──→ 受控        （触发：强制审查、冻结修改权）
事前 ──决策事件──→ 事后        （触发：选项文档归档为决策记录）
事中 ──结算─────→ 事后        （触发：dialogue 蒸馏入 ADR）
事后 ──正典化───→ 永恒        （触发：引用方式改变，出处标注消失）
事前 ──实现─────→ 事后        （触发：ROADMAP 完成项 → CHANGELOG）
```
由此区分两类文档（这是对比分析中涌现的新概念）：
- **管线型**：时态会迁移（TRADEOFFS→ADR→CONVENTIONS，治理重点是转换时机与内容保全）
- **驻留型**：时态恒定（GLOSSARY、INDEX，治理重点是就地保鲜与过期清除）
我的原系统把所有文档都当驻留型治理——这是对管线型的系统性误判，你的方案纠正了它。

## 六、哲学层收尾：两套系统在方法论上的真实分歧
| 维度 | 你的系统 | 我的系统 |
|---|---|---|
| 时间参照系 | **决策事件**（事前/事后相对于一次决策） | 墙钟时间（过去/现在/未来） |
| 核心隐喻 | **相变**——知识在成熟度阶段间迁移 | **登记**——文档在属性空间中定位 |
| 治理规则形态 | 枚举式（查表：四档维护强度） | 推导式（坐标→规则的函数投影） |
| 优势 | 生命周期连续性、草稿态治理、知识供应链表达 | 完备性、正交性证明、空间/预算机制、新文档机械判定 |
| 代价 | 孤儿文档、规则需人工枚举新增 | 对过程失明、对公理误税、登记成本（行为预测难于语义判断） |
最深的一条分歧：你的系统回答“**这段知识处于什么成熟度**"，我的系统回答“**这个文件需要什么治理**"。前者以知识为中心（同一知识跨文件迁移），后者以文件为中心（一个文件一组坐标）。AI agent 时代的特殊压力恰好横跨两者——agent 的上下文预算是**文件中心**的（按文件加载计量），而 agent 的持续学习是**知识中心**的（MEMORY 里的教训应升格为 GLOSSARY/CONVENTIONS）。这就是为什么融合系统必须同时保留两半：**状态转换门为知识的相变服务，规则引擎为文件的治理服务，两者通过坐标登记表对接**。
一句话总结：你的方案贡献了“时间之箭”（知识如何成熟），我的方案贡献了“空间之网”（文件如何共处）；完整的治理体系 = 相变管线 × 形态坐标系，缺任何一半，另一半的规则都会在特定文档上系统性失效。

如何融合两套系统？

# 融合方案：「三层 · 五轴 · 七闸门」文档治理操作系统
**融合的第一原则**：不是把两套系统的轴取并集（那会得到九根轴、大量冗余的怪物），而是**让每个系统驻留在它结构上最强的层**。我此前的系统本质是静态的——登记（这个文件是什么）+ 派生（因此如何治理）；你的系统本质是动态的——知识在成熟度阶段间的迁移（草稿→受控、事前→事后、事后→永恒）。融合 = 把两者组装成一个分层的操作系统：**静态层管形态，动态层管生命周期，中间由派生规则对接**。
---
## 一、融合方法论（五步，可复用）
任何两套分类系统融合都应走这五步，这是本次融合的显式过程：
| 步骤 | 操作 | 本次的应用 |
|---|---|---|
| **S1 熵检验** | 每根候选轴问：它携带能否从其他轴推导的信息？不能推导才配当轴 | 实体轴被淘汰，嬗变轴被降级（见下节审计表） |
| **S2 同构合并** | 识别语义相同的轴，合并取超集 | 我的时向(P/N/F/X) ≈ 你的时态(事前/事中/事后)，合并为五值时态轴：你的“永恒”补我的盲区，我的“元”补你的盲区 |
| **S3 正交修复** | 解开部分重叠的轴 | 你的“层级”与我的“辖域”重叠（公理→根，模块→子树），但 AGENTS.local（语法级内容+个人辖域）证明二者独立，保留双轴 |
| **S4 全域/条件分流** | 有大片无值域的轴降为条件轴 | 层级对 MEMORY/INDEX/dialogue 无值 → 声明为条件轴（规范类激活） |
| **S5 派生降级 + 动态升格** | 现象属性降为函数；过程语义升为独立层 | 嬗变降为 `f(时态,状态)`；你的四时态管线升格为动态层的闸门系统 |
---
## 二、熵检验审计：每根轴的最终裁决
这是融合最关键的一张表——**所有轴（含双方的）逐一审判**：
| 候选轴（来源） | 熵检验结果 | 裁决 |
|---|---|---|
| 受体 M/D/H（我） | 独立。决定加载策略与审查规则；D 类（ADR/ARCHITECTURE）的双轨规则无法从你的“人/工具”二元推出 | ✅ 全域轴 |
| 时态（你+我） | 独立。事前/事中/事后/永恒决定转换语义；“永恒”修复了我对公理的治理误税 | ✅ 全域轴，五值（含“元”） |
| 状态 草稿/受控（你） | 独立。捕捉发布闸门的变更纪律；与辖域“个人”解耦后（存储问题归辖域）信息量独立 | ✅ 全域轴 |
| 辖域 根/子树/个人（我） | 独立。空间半径+共享范围，monorepo 拼接机制与 gitignore 规则的唯一载体 | ✅ 全域轴 |
| 层级 公理/架构/模块/语法（你） | 半独立。仅规范类有值；但它是嬗变率的**机制解释**（公理天然低变），语义判断比行为预测更不易错 | ⚠️ 条件轴（规范类激活，参考类标"—"） |
| 实体 主体/机制/规则/导航（你） | **不独立**。四个值几乎完全落在其他轴组合上（见下） | ❌ 溶解为派生标签 |
| 嬗变 I/L/E（我） | 可由 `时态×状态` 推导 | ⬇️ 降级为派生属性 |
| 维护四档（你） | 本质是治理输出 | ⬇️ 降级为派生属性 |
**实体轴溶解证明**（这是融合中涌现的最深结果）：
```
主体 ≈ 受体M × 辖域个人      （MEMORY/USER/AGENTS.local 全落此格）
机制 ≈ 事中 × 草稿            （dialogue/、MEMORY-as-process）
规则 ≈ 永恒 × 规范类          （CONVENTIONS 公理段）
导航 ≈ 元                     （INDEX、嵌套 AGENTS.md）
```
实体轴的每个值都是「时态×受体×辖域」的投影，**残余熵为零**——但它作为自动生成的派生标签仍有检索价值（登记时由系统标注，无需人工填写）。

### L2 派生层（规则）：坐标的函数
**嬗变推导表**（你的层级提供机制，我的现象登记被收编为函数）：
| 时态 × 状态 | 派生嬗变 | 实例 |

| 事后 × 草稿 | L（可变记忆） | MEMORY |

| 事中 × 草稿 | E（可焚毁） | dialogue/ |
| 事前 × 草稿 | E（可丢弃） | EXPERIMENTS |
| 事前 × 受控 | L（活计划） | ROADMAP |
| 永恒 × 受控 | 恒定（仅 G6 可变更） | CONVENTIONS 公理段 |
| 元 × 受控 | L（链接同步） | INDEX |
**其余派生函数**（承前轮，坐标不变则规则不变）：
- 加载策略 = f(受体， 辖域)：M·根→常驻+≤200行；M·个人→本机常驻；D→按需索引；H→不注入
- 维护强度 = f(状态， 层级， 时态)：受控·语法→**全量**（每PR）；受控·架构→**重点**；受控·事前→**大概**；事后·I 与永恒→**无需**；草稿·任意→**无需**（升级时才审）
- 位置 = f(辖域， 状态)：个人→gitignore；E 类→禁入根目录；根文件总数硬上限
- 审查 = f(受体)：M→行数+漂移审计+禁 LLM 生成；D→双轨结构；H→可读性
- **同格合并 = (受体， 时态， 层级) 三元组相同 → 并入既有文件**（THISIS/BREIF/TREE→README；registry/outline→INDEX；STYLE→CONVENTIONS 的机械化裁决在此系统下自动成立）
### L3 动态层（过程）：七闸门
每道闸门 = 触发条件 + 守卫检查 + 落地动作。这是你的“知识成浆管线”的形式化：
| 闸门 | 转换 | 触发 | 守卫 | 动作 |
|---|---|---|---|---|
| **G0 立项** | ∅→草稿 | 需要新文档 | 同格检验、熵检验、（M·根）预算审计 | 登记坐标、INDEX 挂载 |
| **G1 发布** | 草稿→受控 | 维护者决定发布 | 评审、INDEX 登记、行数预算 | 变更纪律生效（冻结或同步义务） |
| **G2 决策** | 事前→事后 | 决策作出 | 新 ADR 必须引用其前驱 | 选项文档归档，结论入 I 类记录 |
| **G3 结算** | 事中→事后 | 会话/推演结束 | 蒸馏完整性检查 | 有效结论入 ADR/MEMORY，原始过程焚毁 |
| **G4 正典化** | 事后→永恒 | **引用方式改变**（“根据 ADR-0042”→直接陈述为前提） | 人工确认 | 公理迁入 CONVENTIONS 公理段 |
| **G5 归档** | →焚毁/归档 | E 类到期、条目完成 | — | 删除，或转为事后记录（ROADMAP 完成项→CHANGELOG） |
| **G6 去正典化** | 永恒→事后 | 公理被现实违反 | **必须写取代性 ADR** | 公理段删除，决策史恢复 |
由此区分的两类文档获得精确形式化：**管线型**（时态会迁移，治理重心是过闸时机与内容保全）与**驻留型**（时态恒定，治理重心是就地保鲜）。我的原系统把所有文档当驻留型，你的方案纠正了它；你的方案没有闸门守卫（比如公理被随手改），这套补上了。

## 六、反模式（融合坐标下的自动检测）
融合系统的一个涌现能力：**禁区从“记忆的清单”变成“派生表的违例”**——组合本身逻辑矛盾即报警：
| 违例坐标 | 检测机制 |
|---|---|
| M·根·多文件 | 预算竞争：多个文件争常驻注入 → symlink 统一 |
| E 类 × 根目录 | 位置函数违例：易逝文档禁占门面 |
| 事中 × I（append-only） | **派生表违例**：现状+不可变 = 必然过期，组合非法 |
| 事后·草稿 被当权威引用 | 绕过 G1：未发布的内容进入 agent 上下文 = 污染源 |
| 永恒 被随手修改 | 绕过 G6：决策史断裂 |

## 〇、两把新裁决工具
### 工具 A｜工具替代性检验
> 一份内容的死亡条件：**agent 用确定性只读工具（ls / grep / cat / git log）能以零漂移风险现场推导出它。**
原理：文档的本质价值是**人类意图的注入**。凡是机器能自己算出来的，写进文档就凭空创造了一个漂移面——静态快照必然过期，而现场查询永远新鲜。检验可推广到三类工具：
| 替代工具类型 | 被处决的内容 |
|---|---|
| 查询工具（ls/tree/grep/git log） | TREE、目录清单、“改了哪些文件” |
| 执行工具 | 格式规范 |
| 外部系统 | PROBLEMS、手写 API 文档 |
### 工具 B｜知识单源多投影原理
> 一份知识只允许一个**事实源**，但可以按受体有多个**投影面**。
推论：拆分文档的合法方向是**按受体/按主题**，非法方向是**按详略**——“简要版/详细版”双文件（THISIS/BREIF 模式）必然漂移，因为两个文件承载同一知识却没有同步机制。

## 一、GROUP 1：AGENTS, README, THISIS, BREIF

| README | H·事中·受控·根 | 人类投影面，合法 |

## 二、GROUP 2：TRADEOFFS, ARCHITECTURE, DECISIONS, CHANGELOG
**辨析**：你按“架构调整”聚合，但 CHANGELOG 是混入者（它面向版本消费者，记 What，H 受体为主），其余四个构成一条完整的**事件溯源管线**。用数据库隐喻精确化：

```
TRADEOFFS ────→ ADR/ ────────→ ARCHITECTURE ────→ CONVENTIONS 公理段
```

这个隐喻直接推出三条治理规则：
1. **ADR 是事件日志**：不可变、追加式；**rejected 决策也是事件**——被否决的选项与被采纳的同等重要。

## 四、GROUP 4：ARCHITECTURE, INDEX, TREE vs agent 现场查目录
你的疑问是本轮最锋利的一刀，值得完整回答。先修正 INDEX 的定义。
### TREE：死刑
TREE 的信息 100% 可被 `ls -R` / `tree` 现场获取，且是静态快照必漂移。这是“可推导信息文档化”的最纯反模式。**裁决：删除。**
### INDEX：存活，但重新定义为“语义路由表”
直接回答你的两个困惑：
**“INDEX 总不能指向具体文件吧？"** ——恰恰相反：INDEX **应该**指向具体文件，但只指向**文档文件**，绝不指向**代码文件**。区分在于两个集合的稳定性：`docs/` 下是几十个低频稳定文件，AGENTS.md 里的代码路径是成千上万的高漂移物。前者做索引锚点成本可控（配合 CI 链接检查），后者是已证实的上下文污染源。
**“和 agent 现场查目录比有什么价值？"** ——因为 agent 工具查到的是**物理层**（文件名、层级），而导航的真问题是**语义层**（什么知识在哪）。INDEX 是物理查询之前的**第一跳**：
```
任务意图："认证相关的约定是什么？"
物理层方案：grep -ri auth .        → 500 个命中，大量噪音
语义层方案：查 INDEX → "认证约定 → docs/CONVENTIONS.md#auth"
```
INDEX 的准确定义：**键为任务/话题/意图，值为文档+锚点的路由表**。类比 DNS——agent 工具是 IP 直连，INDEX 把“认证约定”这个域名解析到具体位置。同义词/别名映射（“auth / 认证 / 鉴权 → 同一条目”）也是它的职责，这是 grep 永远做不到的。
### ARCHITECTURE：存活，且不可替代
工具替代性检验在此的裁决与 TREE 相反：依赖方向、模块边界意图、数据流拓扑**无法从文件系统推导**——目录树告诉你代码在哪，不告诉你为什么这么切、谁不许依赖谁。这些是设计事实而非文件事实，必须人类注入。
**本组总结**：物理层导航（文件在哪）→ 工具现场查；语义层导航（知识在哪）→ INDEX；意图层知识（为什么这样设计）→ ARCHITECTURE。三层各司其职，TREE 伪跨三层，死。

## 五、GROUP 5：STYLE, CONVENTIONS, LIMITATIONS, AGENTS, CONTEXT, GLOSSARY
**辨析**：你按“规范”聚合，但坐标上这是三类东西，且混入了一个混入者（AGENTS）：
**a) 应然类（规范）——STYLE 与 CONVENTIONS 的生死分界**
工具替代性检验的第二次执行：**能被 formatter/linter 执行的规范，文档化即反模式**。Prettier/Black/gofmt 时代，缩进、命名、引号风格属于 `.editorconfig` 和 lint 配置的领土——写进 STYLE.md 就创造了漂移面，且没有任何强制力。**裁决：STYLE 死亡，遗骸（格式条款）迁入工具配置文件。**

**b) 词典型——CONTEXT 与 GLOSSARY 同格合并**
两者坐标完全相同（D·事中·受控·docs/），且 CONTEXT 在 AI 时代是个语义重载的词（上下文有专门含义），命名劣势。**裁决：GLOSSARY 吸收 CONTEXT，消歧义、单一文件。**
**c) 边界类——LIMITATIONS 其实不属于本簇**
它是**实然的否定面**（系统不能做什么），不是应然规范。真正的邻居是 PROBLEMS，两者区分：LIMITATIONS 是**长期事实**（设计取舍导致的能力边界，“我们不支持 Windows"），PROBLEMS 是**待修项**（“登录在 Safari 下崩溃”）。一个描述形状，一个描述伤口。
**混入者 AGENTS 的澄清**：它不与本簇竞争，是**入口与本体的关系**——AGENTS.md 放约定速查（最高频的三五条）+ 指向 CONVENTIONS 的链接，本体在 docs/。这是渐进披露在本簇的落地。

## 六、GROUP 6：ROADMAP, PROBLEMS（未来的管理）
事前时态文档的治理难题：天然高漂移 + 承诺固化风险（写下来的计划变成心理包袱）。管理原则三条：
**原则 1｜期权而非资产**：未来条目的信息价值随时间单调衰减（六个月没人碰的 roadmap 条目信息量趋近于零）。所以事前文档要**设到期日**：每条带“最后确认日期”，超过一个周期未确认 → 自动降级 Dropped 或强制重新确认。
**原则 2｜承诺分级**：条目分 Committed（有版本锚定的承诺）与 Exploring（随时可弃的意向），状态机 Proposed → Accepted → In Progress → Shipped / Dropped。防承诺固化的机制就是显式允许 Dropped。
**原则 3｜两个出口都要接管线**（这是本组与 GROUP 2/7 的连接）：
```
Shipped → CHANGELOG 对应版本条目（事前→事后的 G5 归档）
Dropped → 轻则标注一句原因；重则升格为 rejected ADR
          （"我们曾计划做 X，因 Y 放弃"——这是重要的架构知识！
            agent 未来提议类似方案时，这条记录能阻止它重蹈覆辙）
```
**PROBLEMS 的特别裁决——与 issue tracker 的竞争**：工具替代性检验的第三次执行（外部系统型）。GitHub Issues 能做而 PROBLEMS.md 做不到的：分配、状态流转、通知、跨引用。PROBLEMS.md 的**唯一存活条件**：① 仓库不在 GitHub 生态；② agent 缺少 issue 读取工具、需要免 API 调用的快速待办通道。两个条件都不满足时，**裁决：PROBLEMS 迁出仓库，迁移至 issue tracker**——这可能是整套体系里唯一“建议删除而非合并”的活跃文档。

## 七、GROUP 7：DECISIONS, EXPERIMENTS, NOTES/, ADR/（文档-证据分离）
你括号里的直觉（“记录型的可以放后面的研究——文档-证据分离模式”）方向完全正确，展开为完整模式：
**分离的三层结构**：
```
结论层  docs/adr/0042.md          [D·事后·受控·I]     永生，含证据摘要+指针
证据层  docs/evidence/0042/       [草稿·E·gitignore   速朽，原始数据
        ├── bench-output.txt       或 git-lfs]
        └── dialogue-digest.md
过程层  dialogue/ / NOTES/ / scratch/  [M·事中·草稿·个人·E]  默认焚毁
```
**分离的三个必然理由**：
1. **信噪比**：agent 读 ADR 需要结论+关键理由，不需要 300 行 benchmark 原始输出。证据是人类的深挖材料，不是机器的常载内容——把证据塞进 ADR 正文等于给每次上下文注入强加垃圾。
2. **体积**：实验日志、性能输出动辄 MB 级，入主分支会膨胀仓库；lfs/ignore 是自然的隔离层。
3. **生命周期错配**：结论近乎永生（I 嬗变），证据随时间贬值（E 嬗变）——**两种嬗变模式的实体禁止同库**，这是嬗变派生表的结构性推论。
**ADR 正文的写法**：Decision + Consequences + **证据摘要（三五行）+ 指针**（`完整数据见 docs/evidence/0042/`，链接断掉不报警——因为证据层本来就允许消失）。
**簇内其他成员的归位**：
- **EXPERIMENTS** = 事前·草稿·E，本质是“用实验填充 TRADEOFFS 选项空间的证据生产活动”，其产出直接落入 evidence 层。
- **NOTES/** 与 **dialogue/** 同属过程层，统一为 `scratch/` 概念，gitignore，阅后即焚。
- **DECISIONS** 已在 GROUP 2 裁决并入 ADR。
这个模式其实就是 **G3 结算闸门的物理实现**：蒸馏出的结论进 I 类，原始过程焚毁——文档-证据分离不是新机制，是既有闸门的存储布局。

# 受体轴的死刑：从“属性分类”到“关系模型”
**总判决先行**：你的两个批评击中的是同一个病根——**旧分类法把“关系”压缩成了“属性”**。文档没有“读者”这个属性，就像公司没有“客户”这个属性一样荒谬：它有的是一组**客户关系**。README 的问题不是“它到底是 H 还是 D”，而是这个问题本身问错了——正确的问法是“agent、developer、reader 各自与它是什么关系”。同理，“谁维护”从来不是“谁读”的派生属性，而是一条**独立的有向关系**。本轮把五轴中的受体轴拆掉，重建为**关系模型**，并顺着你给的线索继续深挖——旧系统里被压缩掉的关系，不止这两条。

## 一、两个批评各自击碎了什么
**批评 1（读者非单选）** 击碎的是枚举轴的合法性基础。反例不用找别处：README 在多数 agent harness 里被默认读取——它事实上是“人类门面 + 机器隐式注入源”的复合体。旧系统的 D（双读者）值其实就是这个问题的遮羞布：它是“画像里有两行都高”的强行单值编码，是分类压缩的产物而非真实类别。
**批评 2（读 ≠ 写）** 击碎的是一个更隐蔽的假设：旧模型里“AGENTS.md 是 M 类”隐含着机器文档的完整叙事——但真实情况是**消费它的是 agent，维护它的是 developer，且维护强度极高**。你的例子揭示的公式是：
> **维护义务的强度 ∝ 消费侧的暴露量 × 消费侧的失败成本，与维护者自己读不读无关。**
developer 几乎从不“阅读” AGENTS.md（他们写的，内容在脑子里），却必须重度维护它——因为读的频率属于读者画像，维护的强度属于**消费侧风险**。这两个量在 AGENTS.md 上完全脱钩，证明它们是两条独立关系。

## 二、重建：文档 = 关系束
新模型的最小单元不再是“文档 + 坐标”，而是**关系**。每个文档锚定两组关系。
### 2.1 先精化 role（回应“当然，可能不止”）
三个 role 都不单调，但拆分它们的**不变量**是同一个——语境占有量：
| Role | 语境占有 | 权限 | 关键变体 |
|---|---|---|---|
| **agent** | 零团队语境（无历史、无口头文化）+ 全代码权限 | 读写工具 | ① 注入型（只能收预载）② 工具型（能 ls/grep 现查）③ 记忆型（跨会话） |
| **developer** | 高语境 + 写权限 | 全部 | 核心（天天在）/ 新入（一次性密集读）/ 偶发贡献者（外围半永久） |
| **reader** | 零语境 + 零权限 | 只读 | 评估者（决定要不要用）/ API 消费者 |
role 不是身份而是**语境占有量的聚类**，且是轨迹上的状态（reader → 新developer → 核心developer 是同一个人的三个阶段）。这个不变量后面会统一全场。
### 2.2 阅读画像：role × 文档 → 一条阅读关系
每条阅读关系是四元组：**触发方式 × 频率 × 认知姿态 × 补偿的语境缺口**。
| 文档 | agent 的关系 | developer 的关系 | reader 的关系 |
|---|---|---|---|
| AGENTS.md | 预载 · 每会话 · **轻信执行** · 补“无项目记忆” | 参考 · 罕见（自己写的）· 怀疑 | 无关系 |
| README | **harness 默认读** · 常见 · 轻信（!）· 补同上 | 入职读一次 · 叙事式 | 评估 · 一次 · 扫读 |
| CONVENTIONS | 任务触发检索 · 按需 · 半信（有 lint 兜底） | 偶发查证 · 怀疑 | 无关系 |
| ADR | 极少（事故时检索） | **事故触发** · 重构式阅读（“为什么是这样？”） | 无关系 |
| MEMORY | 预载 · 每会话 · **最高度轻信**（自己的经验） | 仅蒸馏时 · 筛选 | 无关系 |
| CHANGELOG | 无关系 | 升级时 · 怀疑 | 版本消费者 · 扫读 |
注意两个此前完全不可见的结构：
- **认知姿态不对称**：agent 是**轻信读者**（读到就执行，不质疑），人类是**怀疑读者**（拿文档与现实比对）。同一句过期内容，对人是“困惑”，对 agent 是“自信地做错事”。失败成本不对称由此产生。
- **MEMORY 的姿态比 AGENTS.md 更危险**：agent 对外部文档是轻信，对自己的记忆是**当作经验信任**——错误教训还会因重复被强化。这是正反馈，不是静态错误。
### 2.3 维护画像：与阅读画像完全独立的一组关系
| 文档 | 写权限 | 维护责任 | 失败成本（按消费侧算） | 变更率 |
|---|---|---|---|---|
| AGENTS.md | developer | developer | agent 中毒 · 每会话放大 | 低 |
| MEMORY | **agent** | 周期蒸馏者 | agent 复合中毒 · 反馈强化 | 高且无界 |
| README | developer | developer | agent 隐性中毒 + reader 困惑 | 中 |
| ADR | developer（过 G1 后冻结） | **无**（见 3.4） | ≈ 0 | 合入后为 0 |
由此得到维护的完整分解——**旧系统的“维护强度四档”只是这个分解的输出**：
```
维护频率 ← 变更率
维护纪律等级 ← 暴露量 × 失败成本
维护总负担 ≈ 频率 × 纪律
```
代入检验：AGENTS.md 是**低频 × 极高纪律**（每会话暴露 × 中毒成本，所以同 PR 强制 + 漂移审计）；CHANGELOG 是**高频 × 低纪律**（怀疑读者兜底）；**MEMORY 是高频 × 高纪律——全系统最贵的文档**。这直接推出一条资源分配结论：MEMORY 的蒸馏（G3）不是锦上添花，是**成本控制**——不蒸馏，维护负担无界增长。
### 2.4 信任有向图：新模型涌现的最深结构
把所有“写→读”关系画成有向图，按安全性排序：
| 边 | 例子 | 安全性 | 治理要求 |
|---|---|---|---|
| agent 写 → 人读 | PR 描述、变更摘要 | **最安全**：人类怀疑是天然过滤器 | 应鼓励，无需闸门 |
| 人写 → 人读 | ADR、CONVENTIONS | 安全：怀疑读者互兜底 | 常规评审 |
| 人写 → agent 读 | AGENTS.md | 方向安全但消费侧轻信：**单点错误被无条件执行** | 纪律要求**最高**——G1 对 M 面内容的审查标准必须高于 H 面 |
| **agent 写 → agent 读** | MEMORY、dialogue/ | **危险**：无过滤器的闭环，正反馈无阻尼 | 必须隔离（个人辖域）+ 阻尼（周期蒸馏） |
这张表给出此前所有裁决的统一解释：**MEMORY 必须 gitignore，不是隐私问题，是控制论问题**——它是系统里唯一的 agent→agent 反馈环，不加阻尼就会振荡发散。而所有闸门（G1 发布、G4 正典化、G6 去正典化）在这张图上获得共同本质：**让内容变更经过一次人类怀疑**。整条文档管线里，人类的怀疑是唯一的纠错资源，闸门就是它的制度化。

## 三、继续深挖：关系模型照出的其他旧症结
按你“还有其他的，深入分析”的要求，以下是同一把刀继续剖出的五条。
### 3.1 隐式注入面：README 是系统里最危险的反例
既然 harness 默认读 README，那么 README 的事实性内容（安装命令、版本要求）**事实上是 M 面**——却按 H 标准维护。这是旧系统完全不可见的隐患：**注入面不由你的意图决定，由 harness 的行为决定**。治理回应：① 审计哪些文件被主流 harness 默认读取，这些文件的事实性段落必须达到 AGENTS.md 级准确率；② 事实性内容尽量单源于 AGENTS.md，README 用指针。
### 3.2 文件 ≠ 治理单元：治理的真正粒度是段落
一份文件内部，各段落的画像可以完全不同：README 顶部（评估者·稳定）/ quickstart（agent+新developer·高漂移·须 M 级准确）/ 哲学段（稳定）；ARCHITECTURE 的图（高漂移的物化视图）与原则段（稳定）。**治理附着于画像同质的段落，文件只是序列化容器。**这反过来修正上一轮的同格合并规则：合并只能在段落级合法——THISIS 并入 README 顶部合法，但把 quickstart 和哲学段搅在一起就制造了混合画像的肿瘤。
### 3.3 给轻信读者的内容必须自证
认知姿态不对称推出一条全新设计原则：**面向 agent 的内容，优先选“失败会大声喊”的形式**。一条命令（过期了会报错，agent 能自纠）优于一条断言（“我们用 tabs”——过期了静默中毒）。所以 AGENTS.md 的黄金内容是可执行命令和“失败可见”的边界，最差内容是无验证手段的风格断言。这条规则旧模型推不出来，因为它需要“轻信 vs 怀疑”这个姿态维度。
### 3.4 I 类文档的失败成本 ≈ 0：日志不会“过期”
“过期”这个概念只对**现状断言**成立。ADR 合入后是历史记录——历史不会错，只会被取代。所以 I 类（append-only）的维护成本只剩链接腐与“被取代状态未标注”，后者正是 G6 存在的理由。这解释了为什么登记表里 ADR 的维护档是“无需”：不是偷懒，是**该类文档的结构性免疫**。
### 3.5 阅读的生命周期模式：接力棒型文档
onboarding 文档的阅读画像很奇特：**每个读者只密集读一次，然后永不再读**。它的维护是“为下一个读者保鲜”——像接力棒，只在交接瞬间检验质量，腐化在两次交接之间无人察觉。治理回应是不同的审计触发器：接力棒型文档的漂移检查绑定“新人入职事件”而非 PR。CHANGELOG 是每发布触发，ADR 是事故触发，AGENTS.md 是每 PR 触发——**审计频率跟着阅读触发器走，而不是一刀切**。
### 3.6 语境缺口统一场论：上一轮的刀在这里获得证明
把 2.1 的不变量（语境占有量）推到底，得到文档存在的充要条件：
> **一份内容值得成为文档，当且仅当：存在一个真正缺乏该语境的读者，且没有工具能消除这个缺口。**
这把上一轮的“工具替代性检验”从经验规则升格为模型推论：TREE 死于 agent 不缺目录信息（`ls` 就是它的语境）；STYLE 死于 linter **消除了读者需要知道的缺口本身**（强制执行让“知道约定”变得不必要）；ARCHITECTURE 活于依赖意图是任何工具都查不出的语境缺口。同一个原理，两侧得证。

## 四、新模型推导出的规则集（旧模型推不出的）
1. **自证原则**：M 面内容优先可执行/失败可见的形式，静默断言降级到检索层。
2. **反馈环阻尼**：agent 写 → agent 读的内容必须个人辖域隔离 + 周期蒸馏；升格共享必须过人类怀疑（G1）。
3. **隐式注入面审计**：维护一个“harness 默认读取清单”，清单内文件的事实段落按 M 级标准治理。
4. **段落级治理**：画像同质的段落是治理单元；合并与拆分在段落级裁决。
5. **维护分解公式**：频率←变更率，纪律←暴露×失败成本；MEMORY 类“高频×高纪律”文档必须靠蒸馏压暴露、靠隔离压成本。
6. **最弱 harness 地板声明**：预载下限由你支持的最低能力 harness 决定（有无 read 工具），这条声明本身应写进治理文档——它决定了 AGENTS.md 该装多少。
7. **审计触发器跟随阅读触发器**：每 PR / 每发布 / 每事故 / 每入职，四种节奏各配其类。

## 六、收束
旧分类法问“这个文档**是**什么”，新模型问“谁与它**是什么关系**”——前者把多元关系压扁成单值属性，于是 README 卡在 H/D 之间，AGENTS.md 的维护义务无处安放。展开成关系束之后：**读与写分离成两组独立画像，写→读的信任方向决定治理形态，认知姿态（轻信/怀疑）决定准确率标准，语境缺口决定存在资格**。而全部闸门在这个模型里露出共同本质——系统里只有一种纠错资源，人类的怀疑；文档治理的一切制度，都是在规划这种稀缺资源该浇灌在哪条内容流上。
一句话：**文档没有读者，只有关系；治理的对象从来不是文件，是关系网上的信任流。**

## 〇、先接住开头的方法论主张
“列举 → 分类 → 定义”这个顺序为什么是对的，可以给出机制层面的理由：**定义是格子的地址，格子没立起来之前，地址无处可写**。这轮对话本身就是证据——前几轮给各文档下的定义反复返工，不是定义写错了，而是定义所投影的坐标系一直在被拆改（受众轴拆成了关系、辖域被吸收、状态降成了位置）。定义只能最后写，因为它要继承分类法推导出的全部治理规则。
列举先行还有一个额外好处（见受众节）：**分类法不是设计出来的，是从被占据的角落里“发现”的**。
唯一要补的风险：语料会变——agent 能力演进会带来今天不存在的文档类型。所以列举之后加一步**生成性检验**：拿一个尚不存在的文档（比如“未来 agent 自写的任务笔记”）问它落在哪个格子。列举保证接地，生成检验保证外推。

## 一、受众：你的三个问题各有一个答案
### 1.1 角色锚点（回应“需要定义好两个 role”）
锚点由**关系不变量**定义，不由职位或物种定义：
- **agent**：零语境（对项目无记忆、对关系无历史），一切语境靠注入获得；对注入内容**默认信任**；拥有工具全集。
- **developer**：高语境（项目历史在脑内、团队文化在口头）；**默认怀疑**（拿文档对现实核对）；拥有写权限。
命名选 developer 不选 human：**锚点该由不变量命名，而非物种命名**——“human”会把已降级的 reader 也包进来。至于边界案例（长驻 agent 积累了语境算不算 developer）：锚点是为了挂规则，不是为了给存在者建档，轨迹态（评估者→新人→核心）不改变锚点用途。
reader 降级的判据可以显式化，供你复用：**一个角色成为轴上一等公民，当且仅当它的关系绑定了别的角色推不出的结构规则**。reader 的关系只绑定“可读性”这类修饰性规则，所以降级为 skill/投影是对的。留一个尾巴：harness 默认读 README——这不是 reader 关系，是 **agent 关系**（隐式注入面），所以 README 事实段的准确率要求不随 reader 降级而消失。
### 1.2 “2×n 正交太繁琐”——不会发生，因为其中两维会塌缩
把读、写、角色、强度全展开，理论空间确实爆炸。但语料只占据少数角落，且：
- **写侧塌缩**：developer 写是默认值，agent 写是稀有例外（只有 MEMORY 和对话原始层）。降为一个比特：人写 / agent 写。
- **维护纪律塌缩**：它不是独立维度，是**读关系的函数**——纪律 ≈ 暴露量（多常被注入给轻信消费者）× 错误代价（错了多疼）。AGENTS 是“低频改动 × 极高纪律”，CHANGELOG 是“高频改动 × 低纪律”：角色没变、纪律变了，因为暴露和代价变了。你的例子里 developer “不读却重度维护” AGENTS，正是这个公式的体现——维护强度挂靠消费侧，不挂靠维护者自己的阅读。
所以真正要展开的只有**读关系**（两个锚点各一条画像）加一个**写比特**。爆炸从未发生。
### 1.3 agent 二分（你的新想法）：成立，但要精确化一步
**分出来的不是两个 agent，是同一个 agent 的两种注意力模式**：
- **工作模式**：注意力的对象是项目（第三人称）——AGENTS、CONVENTIONS、ADR 归此。
- **记忆模式**：注意力的对象是自我与用户（第一/第二人称）——MEMORY、USER、SOUL 归此。
检验法：**退出仓库后内容是否仍有意义**。MEMORY/USER/SOUL 出仓仍活；AGENTS 出仓即死。注意 AGENTS.local 出仓也死（它是项目工作指令）——所以按注意力它归工作模式，尽管它归个人存储。这说明“注意力对象”与“存储位置”是两回事，别混。
这个二分为什么值钱——两种模式的**语境性质**不同：
- 工作语境**可再生**：每会话重读指令即恢复。失败模式是**腐烂**（过期）。药方：保鲜纪律（随 PR 同步）。
- 记忆语境**累积**：MEMORY 只增不减。失败模式是**膨胀与复利式错误**（错误教训被复读强化）。药方：蒸馏与阻尼（周期蒸馏＋个人隔离）。
需要精确化的一步：**读侧二分（工作/记忆）必须再乘上写比特（人写/agent 写）才挂规则**。USER 和 SOUL 是记忆簇里的人写文件——记忆模式的 agent 读它们，但它们不构成 agent 写→agent 读的回路，只需隔离、不需阻尼；MEMORY 是 agent 写的，回路成立，阻尼必须。你的二分是必要的，但单独不充分。
### 1.4 落点：文档类型 = 关系空间被占据的角落
这是受众节的收束，也是“列举先行”的兑现——枚举语料后，反复出现的关系束只有七种：
| 原型 | 定位（轴组合，白话） | 错了会怎样 | 药方 | 代表 |
|---|---|---|---|---|
| **指令** | 人写 · agent 常驻或可达 · 事中 | 轻信执行，每会话放大 | 随 PR 同步；优先可自证的形式 | AGENTS、CONVENTIONS |
| **记录** | 人写 · developer 事故时读 · 事后 | 合入后≈零（历史只会被取代，不会错） | 免维护，只标注“被谁取代” | ADR、CHANGELOG |
| **记忆** | agent 写 · agent 常驻 · 事后累积 | 错误复利强化 | 隔离＋周期蒸馏＋日期戳 | MEMORY、对话原始层 |
| **门面** | 人写 · 评估者读一次＋harness 默认读 | 事实段被 agent 隐式注入 | 事实单源于指令层 | README |
| **导航** | 人写 · agent 按需拉取 · 元 | 断链即孤岛 | 链接 CI＋孤岛检查 | INDEX |
| **视图** | 人写 · 双方按需 · 事中 | 过期即误导 | 周期对账（视图 vs 记录层比对） | ARCHITECTURE、GLOSSARY |
| **谋划** | 人写 · 双方按需 · 事前 | 承诺固化、过期误导 | 到期日＋双出口（成→记录，弃→rejected 记录） | ROADMAP、TRADEOFFS |
注意这张表演示了轴的正交性：指令与视图受众关系几乎相同，被**触发承诺**区分开；视图与谋划受众关系几乎相同，被**时态**区分开。七行覆盖你全部列举项，无孤儿——这就是完备性检验通过的样子。

## 二、触发方式：你发现的交叉，病根在“按能力分类”
“都会能主动触发”——对，因为 agent 的**能力面**是全连通的（什么都读得到），全连通的东西区分不了任何东西。修正：**按承诺分级，不按行为分级**。承诺是仓库侧的设计意图，与 harness 无关：
- **常驻**：承诺在每个相关语境中在场（AGENTS 预载、MEMORY 会话装载）。
- **可达**：不承诺在场，承诺“相关时找得到”——由路由保证（INDEX 条目、AGENTS 里的指针）。
- **自由**：不作承诺（归档、证据层、被取代的记录）。
每份文档必须声明其一；“需要可达却没挂路由”＝孤岛，可被 CI 检测。工具替代问题也住在这里：`ls` 一秒能现场推导的信息，不值得为它做任何一级承诺——TREE 的死因。
对你推迟决定的 endorsing：**承诺分级（轴，放不变的部分）与执行机制（章，放随 harness 变的部分：嵌套拼接、字节预算、read 工具行为）分开**。轴回答“你保证了什么”，章回答“保证怎么被兑现”。穿插感由此消解一半。

## 四、“认知姿态？”——这里搅在一起的是两个概念，拆开
**姿态是角色的常量，不是文档的变量**。agent 信任注入物、developer 怀疑一切，每份文档都一样——所以它从来不是轴。真正随文档变化的是**背书**：错了会不会被当场抓住。可执行命令过期会大声报错（agent 能自纠）；lint 兜底的约定半信即可；散文断言无背书，错了静默中毒。由此得到设计规则：给 agent 的内容优先选“失败会喊”的形式。这是原则，归设计章节。
**草稿/受控：同意降级，且可以比你走的更远——它不是注解，是位置**。草稿＝住在 scratch/、或分支上、或未提交；受控＝合并进主干受控目录。发布闸门就是那次合并评审。git 的分支与合并本来就是为此发明的状态机，再造一根轴是重复建设。
**`by{ai}` 后缀的评估：它标错了变量**。要紧的不是“谁写的”而是“过没过人的审”——人审过的 AI 草稿无害，没审的人写草稿同样危险；且作者标记会随 AI 辅助普及而失效（当九成内容都有 AI 参与，标记不再携带信息）。真正该用的：agent 自维护的 MEMORY 用**日期戳**（记忆的失败模式是过期与复利，日期让新旧可判）；协作草稿用位置/分支。至于“写进 AGENTS.md 作为注意点”——只值一行边界指令（“scratch/ 与 evidence/ 不作为事实依据”），完整约定放治理文档，别占常驻预算。

**补偿（“这是个啥”）**：我原来的措辞失败了，白话重说——每个读者都带着某个“不知道”进仓库（agent 不知道项目是什么，新人不知道为什么长这样，评估者不知道值不值得用）。**文档的生存权 = 存在一个真实的“不知道”＋没有更便宜的填法**。TREE 死于 `ls` 填得更便宜。这是立项时问的问题，不是分类值——你放“暂不纳入”是对的，它住在闸门里，不住在轴上。

## 六、代号：全盘接受
全文已弃用。原因说透，当作可迁移的教训：**记号是压缩，压缩只有在“使用密度高到图例成本被摊平”时才划算**（数学论文的密度）。我们的使用是表格注释级密度，且图例本身在轮次间漂移——单字母是撞义 token（machine？module？maintain？），漂移的图例比没有图例更糟。对 AI 读者尤其如此：完整词自带分布语义，代号是歧义 token。还有一层自指：一个宣讲“内容应当自证”的框架，自己却要求读者先背图例——违反了它自己的第一原则。

## 七、元问题：研究互相穿插怎么办
病根先说清：**研究对象（文档体系）是网状的，写作是线性的。任何网状物的线性化都有接缝**——穿插不是你研究做错了，是线性媒介的税。解法不是避免接缝，是给接缝立规矩。把写作当代码重构：
1. **内联优先，第二次交叉时抽取**：某话题第一次被别处引用，原地留指针加一句话；第二次被另一处引用，抽成卫星章。脊柱不塞实现细节。
2. **三种制品**：**脊柱**（分类法本体，交付物）、**卫星**（how-agent-read-file、compare——机制与两两辨析）、**台账**（开放问题与术语裁决——你 draft 里的"？？"项就是台账条目）。
3. **依赖单向**：卫星可以引用脊柱的概念，脊柱只通过稳定指针引用卫星、不依赖其内部。脊柱稳定，卫星随便 churn。
你其实已经在这么做了——“放在后面的章节讨论”就是抽取动作，只是没命名为规则。命名之后，它从每次的临时补救变成政策。
最后一层自指：**这个研究过程本身就在跑我们设计的管线**——对话历史是过程层（蒸馏后可焚），你正在写的 draft 是蒸馏动作，最终文档是受控件。穿插的烦躁感，正是“在过程层干活时试图同时起草受控层”的体感成本；解法也就是我们给仓库开的同一个方子：草稿归草稿区，蒸馏进脊柱，机制流放卫星。

## 第一部分 角色锚点
锚点由**关系不变量**定义，不由物种或职位定义。判断一个存在者属于哪个锚点，只看它满足哪组不变量。
### 1.1 agent
| 不变量 | 内容 |
|---|---|
| 零语境进入 | 每次会话对项目无记忆、对团队无历史、对文化无感知，一切语境靠注入获得 |
| 默认信任 | 对注入内容读到即执行，不与现实核对——是**轻信读者** |
| 工具全集 | 拥有查询工具（列目录、搜字符串、读文件），能现场推导部分语境 |
| 无怀疑能力 | 唯一的纠错机会是“错误自己大声喊出来”（命令报错、构建失败） |
agent 内部按**注意力对象**分两种模式：
- **工作模式**：注意力指向项目本身（第三人称）。消费 AGENTS、CONVENTIONS、ARCHITECTURE。
- **记忆模式**：注意力指向自身与用户（第一、第二人称）。消费 MEMORY、USER、SOUL。
检验法：**出仓存续检验**——内容脱离仓库后是否仍有意义。记忆类出仓仍活，工作类出仓即死。注意 AGENTS.local 出仓即死，故其注意力属工作模式，尽管其存储属个人——**注意力对象与存储位置是两回事**。
### 1.2 developer
| 不变量 | 内容 |
|---|---|
| 高语境 | 项目历史在脑内、团队文化在口头、决策背景在记忆 |
| 默认怀疑 | 拿文档与现实比对——是**怀疑读者**，天然过滤器 |
| 写权限 | 文档体系中**唯一的纠错资源**——一切治理制度本质是在规划这种怀疑该浇灌在哪条内容流上 |
developer 有轨迹变体（核心／新入职／偶发贡献者），阅读强度差异巨大，但不变量相同——**轨迹态不改变锚点**。
其特殊性质是**维护者身份**，且维护纪律不挂靠维护者自己的阅读：
> **维护纪律 ≈ 消费侧暴露量 × 消费侧错误代价**
AGENTS 对 developer 是“几乎不读（自己写的）却必须重度维护”，因为它的消费侧是每会话暴露、错误被无条件执行的轻信读者。此公式是全部原型治理规则的生成器。
### 1.3 reader（降级，非锚点）
**降级判据**：一个角色够格成为锚点，当且仅当它的关系绑定了其他角色推不出的结构规则。reader 只绑定“可读性”这类修饰性规则，故降级为门面原型上的一个消费投影，用技能/模板方式维护，不进入分类轴。
**遗留尾巴**：harness 默认读取 README——这不是 reader 关系，是 **agent 关系**（隐式注入面）。README 事实段的准确率义务不随 reader 降级而消失，详见门面原型。
### 1.4 信任边四象限（写→读）
| 写→读 | 安全性 | 治理含义 |
|---|---|---|
| 人写 → agent 读 | 方向安全，但消费侧轻信：单点错误被无条件执行并每会话放大 | **纪律要求最高**，发布须过人审 |
| agent 写 → agent 读 | 唯一无过滤器的闭环：错误因复读而复利强化，正反馈无阻尼 | 必须隔离 + 周期蒸馏（阻尼） |
| 人写 → 人读 | 安全：怀疑读者互为兜底 | 常规评审即可 |
| agent 写 → 人读 | 最安全：人本身就是过滤器 | 应鼓励，免闸门 |

## 第二部分 三轴
### 轴一：受众关系
**这不是一个单值属性，是一束独立关系。** 每份文档对每个锚点各有一条阅读关系（触发 × 频率 × 强度），彼此不互斥、不摊薄、不归一。AGENTS 对 agent 是“每会话 · 轻信”，对 developer 是“几乎不读 · 重度维护”——两条关系描述同一份文件，互不折算。
外加一个**写比特**：人写（默认）／ agent 写（例外，仅记忆簇）。写比特决定文档落入信任四象限的哪一格，从而决定其治理形态。
### 轴二：触发承诺
按**承诺**分级，不按行为分级——agent 能力面全连通（什么都读得到），行为无区分力；承诺是仓库侧的设计意图，不随 harness 变化。
| 取值 | 仓库承诺什么 | 违例形态 | 检测 |
|---|---|---|---|
| 常驻 | 在每个相关语境中在场（预载或会话装载） | 该在场而缺失 | 预算审计 |
| 可达 | 相关时找得到——由路由保证（导航条目、指令内指针） | **孤岛**：需要可达却没挂路由 | CI 可检测 |
| 自由 | 不作任何承诺（归档、证据、被取代的记录） | 无违例可能 | 无需检测 |
每份文档必须声明其一。执行机制（嵌套拼接、字节预算、读取工具行为）外置至卫星章《how-agent-read-file》。
**附带死刑法则**：凡 agent 用确定性工具一秒能现场推导的信息（如目录树），不值得为它做任何一级承诺。
### 轴三：时态，即真理锚定
时态轴的最终解释：**每个取值 = 该文档的真理锚定在哪个位置**。锚定物漂移而文档未跟，就是腐烂。这统一解释了全部失败模式。
| 取值 | 真理锚定于 | 腐烂机理 | 关联闸门 |
|---|---|---|---|
| 事前 | 尚不存在的未来 | 未来变成别的样子 | 决策、实现出口 |
| 事中 | 移动的"现在" | 现状变了快照没跟 | 随 PR 同步 |
| 事后 | 事件发生时刻（永恒固定） | **不腐烂**，只能被取代 | 结算、取代 |
| 永恒 | 不锚定任何时点的公理 | 仅当公理被现实推翻 | 正典化、去正典化 |
| 元 | 文档系统自身 | 结构失效、断链 | 链接审计 |

## 第三部分 七个原型
统一模板：定义 → 坐标 → 真理锚定 → 语境缺口（存在的理由）→ 失败模式 → 治理 → 判别式 → 近邻边界 → 代表。
### 3.1 指令
**定义**：由人颁发、以约束 agent 当下行为为目的的祈使性语境。真理源于**人的现行意志**。
**坐标**：人写 · agent 常驻或可达 · 事中（含永恒变体：公理段）。
**语境缺口**：agent 零语境进入，需要无法从代码推导的操作事实——用什么包管理器、别碰什么目录、必须跑什么测试。工具查得出“是什么”，查不出“你要我怎么办”。
**失败模式**：静默中毒——过期指令被轻信执行，agent 自信地做错，每会话放大。
**治理**：全系统最高纪律。随 PR 强制同步；优先**自证形式**（可执行命令 > 有 lint 兜底的断言 > 无验证手段的散文断言——失败会喊的形式优于沉默的形式）；常驻者受行数预算约束；禁止 agent 批量生成指令文件（实证：降低任务成功率、推高成本）。
**判别式**：这段内容是否在告诉 agent **现在该怎么干活**？是则指令。
**近邻边界**：与视图的区别在**真理来源**——指令效忠于人的意志（与旧 ADR 矛盾时，现行意志赢），视图效忠于历史重放（与 ADR 矛盾时，是视图有 bug）。指令有两个注意力变体：工作指令（AGENTS）、交互指令（USER、SOUL、AGENTS.local 的个人部分——交互指令出仓仍活，属记忆注意力，但写侧是人，不构成 agent 闭环，故只需隔离不需阻尼）。指令内部按时态分节：规则段（事中，每 PR 维护）与公理段（永恒，低频维护）。
**代表**：AGENTS、CONVENTIONS、AGENTS.local、USER、SOUL。
### 3.2 记录
**定义**：对已发生且不可撤销事件的追加式条目。真理锚定在**事件发生时刻**。
**坐标**：人写 · developer 事故时读 · 事后。
**语境缺口**：developer 的高语境有缺口——“为什么当时这么定”不在新人脑内、已从老人记忆蒸发。事故与重构时需要考古。
**失败模式**：≈ 零。历史不会错，只会被取代——“过期”这个概念只对现状断言成立。残余风险仅剩链接腐与“被取代状态未标注”。
**治理**：结构性免维护。唯一义务：被取代时显式标注。写法为结论 + 关键理由 + 证据指针（证据层允许断链，不报警）。**被否决的决策同样是事件**——rejected 记录与 accepted 同等重要。
**判别式**：内容是否描述一个已经发生且不可撤销的决策？是则记录。
**近邻边界**：与记忆的区别在写比特与嬗变——记录是人写的档案（不可变、共享、免维护），记忆是 agent 写的经验（可变、个人、需蒸馏）。与谋划是镜像：同一事件在发生前后分属两型。
**代表**：ADR（含 rejected）、CHANGELOG（语义层；其“改了哪些文件”段落被 git log 处决，只留为什么与影响面）。
### 3.3 记忆
**定义**：agent 自写自读、跨会话装载的累积语境。真理源于**经验**，可修订。
**坐标**：agent 写 · agent 常驻（会话装载）· 事后累积。
**语境缺口**：agent 每会话零语境重启，需要一个跨会话的自延续层。
**失败模式**：双重——**膨胀**（只增不减，预算无界增长）与**复利式错误**（agent 对自己的记忆不是轻信而是当作经验信任，错误教训因复读而强化，这是正反馈不是静态错误）。
**治理**：这是全系统最贵的文档（高频 × 高纪律），治理三板斧全部来自控制论而非编辑学：**隔离**（个人辖域、不入库——因为它是唯一的 agent 写→agent 读闭环，无阻尼则振荡发散）；**蒸馏**（周期执行，高频教训升格为指令或视图，升格必须过人审——让人类怀疑进入这条流）；**日期戳**（每条记忆的失效可判定）。
**判别式**：出仓存续为真 **且** 写者为 agent？双真则记忆。
**近邻边界**：对话原始层（dialogue、scratch）是记忆的过程态，阅后即焚；USER、SOUL 同属记忆注意力簇但为人写，只需隔离不需阻尼。
**代表**：MEMORY、对话原始层。
### 3.4 门面
**定义**：面向零语境一次性读者的项目入口叙事，兼作 harness 的隐式注入面。真理是**借来的**——事实段单源于指令层。
**坐标**：人写 · reader 读一次 + agent 默认读 · 事中。
**语境缺口**：评估者需要在三十秒内判断“这是什么、值不值得用、怎么装”。
**失败模式**：**隐性中毒**——quickstart 的安装命令过期，agent 通过 harness 默认读取隐式注入、照跑不误。门面的危险不在它在清单上，在于你**没把它当指令维护**。
**治理**：段落级二分——叙事段自由（讲给人听的故事）；**事实段按指令级准确率治理**，且单源于指令层（AGENTS 持有事实，门面持有指针）。维护一份“harness 默认读取清单”，清单内文件的事实段一律按此标准。注入面由 harness 行为决定，不由作者意图决定。
**判别式**：是否为不了解项目的人写的一次性入口？是则门面。
**近邻边界**：平台变体（SECURITY、CONTRIBUTING、LICENSE）治理权在社区平台，登记坐标、遵守社区格式即可。
**代表**：README 及平台簇。
### 3.5 导航
**定义**：不携带知识、只携带指向的语义路由表——键为意图或话题，值为文档与锚点。真理锚定于**位置**。
**坐标**：人写 · agent 按需拉取 · 元。
**语境缺口**：agent 的工具查询是物理层（文件名、字符串），而检索的真问题是语义层——"grep auth"命中五百处噪音，"查路由表：认证约定 → 文档+锚点”命中一处。同义词归并（auth／鉴权／认证 → 同一条目）是工具永远做不到的。
**失败模式**：断链即孤岛化——路由指向不存在的内容；或可达承诺的文档没挂路由，成为事实孤岛。
**治理**：链接有效性 CI；孤岛检测（对账“声明可达的文档集合”与“实际挂路由的集合”）；**只索引文档、不索引代码**——文档目录是几十个低频稳定文件，代码路径是高漂移物，混编即制造上下文污染。
**判别式**：内容是否只是指向其他内容？是则导航。
**近邻边界**：物理层导航（文件在哪）归 agent 工具现场查；语义层（知识在哪）归导航；TREE 试图用静态快照跨两层，死。
**代表**：INDEX、嵌套 AGENTS 的路由段。
### 3.6 视图
**定义**：可从记录层重放重建的现状快照，为省去历史重读而物化。真理锚定在**移动的“现在”**。
**坐标**：人写 · 双方按需 · 事中。
**语境缺口**：纯性能优化——agent 不该重读一百条记录来推断当前架构。视图的理论定义保证它可重建，物化只是缓存。
**失败模式**：过期即误导——视图与记录层重建结果矛盾，即漂移警报。
**治理**：周期对账（视图 vs 记录层比对，可做成 CI）；意图层知识（依赖方向、模块边界的“为什么”）不可被任何工具推导，**这是视图的死因豁免**——TREE 死于 ls 替代，ARCHITECTURE 活于意图不可推导。
**判别式**：是否是原则上可从历史重建的现状描述？是则视图。
**近邻边界**：与指令的区别在真理来源（历史重放 vs 人的意志）与触发承诺（视图不承诺在场）。词汇视图（GLOSSARY，术语从使用史蒸馏）、否定面视图（LIMITATIONS，“我们不支持什么”——从设计取舍推导的现状负空间）皆属此型。
**代表**：ARCHITECTURE、GLOSSARY、LIMITATIONS。
### 3.7 谋划
**定义**：承载未决意图与选项空间的活文档，带显式承诺等级。真理锚定在**尚不存在的未来**。
**坐标**：人写 · 双方按需 · 事前。
**语境缺口**：agent 与 developer 都需要“接下来往哪走、哪些方案在桌面上”的语境，以避免提出已被放弃的方向。
**失败模式**：期权性衰减——信息价值随时间单调递减，六个月无人确认的条目信息量趋零；承诺固化——写下的计划变成心理包袱，没人敢删。
**治理**：**到期日**（每条带最后确认日期，超期未确认即强制降级或重新确认）；**承诺分级**（Committed 有版本锚定／Exploring 随时可弃，显式允许 Dropped 是防固化的机制）；**双出口**——Shipped 转入记录（CHANGELOG 对应版本条目），Dropped 轻则标注一句原因、重则升格为 rejected 记录（“曾计划做 X，因 Y 放弃”是能阻止 agent 重蹈覆辙的重要架构知识）。
**判别式**：是否描述尚未发生、且可能永远不发生的事？是则谋划。
**近邻边界**：EXPERIMENTS 是谋划的子型——用实验填充选项空间的证据生产活动，产出落入证据层（自由承诺，允许消失）；PROBLEMS 若仓库在 issue 平台生态内且 agent 有 issue 读取工具，则被外部系统替代，迁移出库。
**代表**：ROADMAP、TRADEOFFS、EXPERIMENTS。

## 第四部分 判别流程与全量归位
### 4.1 判别决策树
```
新文档提案
 ├─ 出仓后仍有意义？
 │   ├─ 是 → 写者为谁？
 │   │       ├─ agent → 【记忆】（隔离 + 蒸馏）
 │   │       └─ 人   → 【指令 · 交互变体】（个人存储）
 │   └─ 否 ↓
 ├─ 内容只是指向？ ──────────── 是 → 【导航】
 ├─ 描述已发生且不可撤销的事？ ── 是 → 【记录】
 ├─ 描述尚未发生/可能不发生？ ── 是 → 【谋划】
 └─ 描述现状 →
       ├─ 面向陌生人的一次性入口 ─── 【门面】
       ├─ 祈使语气（效忠人的意志）── 【指令 · 工作变体】
       └─ 陈述语气（可从历史重建）─ 【视图】
```

## 第五部分 外置与遗留
**卫星章**（按“第二次交叉时抽取”节奏析出）：《how-agent-read-file》——嵌套拼接、字节预算、读取工具行为、harness 默认读取清单；《compare》——原型两两辨析的展开版。
**台账**（开放问题）：① 记忆模式与工作模式的命名待定稿；② PROBLEMS 迁移 issue 的触发条件量化（平台生态？工具集？）；③ harness 默认读取清单的维护责任归属；④ 视图对账 CI 的具体实现（视图 vs 记录层重建比对）。
---
**收束**：七原型共用一个属——文档是关系束加真理锚定；种差只在锚定物：指令效忠人的意志，视图效忠历史的重放，记录效忠事件时刻，记忆效忠经验，谋划效忠尚未到来的未来，门面效忠借来的事实源，导航效忠位置。**腐烂的定义由此统一：锚定物漂移了，而文档没有跟上；治理的定义也由此统一：按锚定物的漂移速率配维护，按消费侧的错误代价配纪律。** 分类法到此闭合。
