# Agent 项目文档体系：边界、重复与本质的第一性原理拆解
所有文档看起来重复、混淆、维护不起的根源，本质上是没搞清楚三个底层属性：
1. **时态**：它是「决策前的选项」「决策后的结论」「当下的现状」还是「永恒的公理」？
2. **层级**：它是「宪法级原则」「架构级决策」「模块级设计」还是「操作级规范」？
3. **契约对象**：它是写给人看的共识，还是写给工具读的配置？

下面针对你提出的 5 组疑问逐个击穿，最后给出通用的拆分/合并判断法则。

---

## 1. CONVENTIONS.md vs STYLE.md：规范的两种粒度
### 本质定义
- **STYLE.md**：**代码语法级风格规范**，只关心“代码长什么样”。
  内容：缩进、换行、命名大小写、import 顺序、lint 规则、格式化配置说明。
  契约对象：主要写给 linter / formatter 工具读，其次是人。
- **CONVENTIONS.md**：**项目级协作约定**，关心“在这个项目里怎么干活”。
  内容远不止代码：
  - 目录命名约定、文件后缀规范、`.local` 文件规则
  - Prompt 片段怎么组织、Skill 怎么写、ADR 编号规则
  - Git 提交格式、分支命名、版本号规则
  - 文档写作规范、术语使用约定
  契约对象：写给所有参与项目的人，是团队的“内部交通规则”。

### 核心边界
**STYLE ⊂ CONVENTIONS**。代码风格只是项目约定的一个子集。

### 混淆根源
很多项目只做代码规范，于是直接把 STYLE 改名叫 CONVENTIONS，导致两者看起来是一回事。

### 架构师建议
- **小团队 / 个人项目：直接合并**。在 CONVENTIONS.md 里开一个「代码风格」小节即可，不必单独维护 STYLE.md。
- **大团队 / 多语言仓库：必须拆分**。STYLE.md 可以直接被 lint 配置引用、甚至自动生成；CONVENTIONS.md 是纯人文档，讲协作规则。
- 反模式：两个文件各写一遍代码规范，内容不同步，文档直接腐化。

---

## 2. INDEX.md vs ARCHITECTURE.md：导航和设计是两回事
你觉得“一直维护精确 INDEX 不现实”——**这不是 INDEX 的问题，是你把 INDEX 做错了**。

### 本质定义
- **INDEX.md**：**文档的目录页 / 导航台**，唯一职责是「可发现性」。
  它不承载任何设计内容，只做一件事：**把所有内部文档按类别列出来，加一句话标签，加链接**。
  正确的 INDEX 长这样：
  ```
  # 内部文档索引
  ## 公理层
  - THESIS.md 项目核心立论与边界
  - CONTEXT.md 领域术语表
  ## 架构层
  - ARCHITECTURE.md 系统架构与数据流
  - DECISIONS.md 架构决策记录
  ## 子系统
  - AGENTS.md 内置Agent角色定义
  - MEMORY.md 记忆子系统设计
  ```
  维护成本极低：新增文档时加一行链接即可，不需要“精确描述每个文件的细节”。

- **ARCHITECTURE.md**：**系统设计说明书**，讲模块划分、组件依赖、数据流、调用链路、目录职责。
  它是有内容、有逻辑、有图的设计文档，本身就是被 INDEX 索引的对象。

### 核心边界
- INDEX：**是什么、在哪里**（地图索引）
- ARCHITECTURE：**为什么、怎么工作**（建筑图纸）

### 为什么你会觉得重复且难维护
典型误区：**把 INDEX 写成了简化版 ARCHITECTURE**，每个条目都写一大段说明，等于把设计内容抄了两遍。

### 架构师建议
- 文档 ≤ 5 个：**删掉 INDEX.md**，直接靠目录结构发现。
- 文档 5~15 个：极简 INDEX，只做链接列表，不写内容。
- 文档 > 15 个：INDEX 价值指数级上升，是新人上手的第一入口。
- 铁律：**INDEX 永远不描述设计细节**，描述设计是 ARCHITECTURE 的事。

---

## 3. THESIS.md vs AGENTS.md：宪法和岗位职责
### 本质定义
- **THESIS.md**：**整个项目的宪法 / 公理集**。
  它回答：我们认为 Agent 应该是什么样？我们反对什么？什么在边界外？
  例子：
  - 所有 Agent 不得拥有无限循环能力，必须有最大步数约束
  - 记忆必须独立于 LLM 上下文，不能全部塞进 System Prompt
  - 本项目不做多智能体协作，只做单 Agent 增强
  它不针对任何具体 Agent，是所有 Agent 都必须遵守的底层原则。

- **AGENTS.md**：**岗位说明书合集**。
  它回答：系统里有哪几个 Agent？每个叫什么？职责是什么？有什么能力？边界在哪？
  例子：
  - Planner Agent：负责拆解任务，不执行具体工具调用
  - Coder Agent：负责写代码，不做产品决策
  它是 THESIS 在角色层面的具体落地。

### 核心边界
- THESIS：**约束所有 Agent 的设计原则**（Why）
- AGENTS：**每个 Agent 的具体职责定义**（What）

### 混淆根源
很多人在写 AGENTS 时，忍不住把设计原则也写进去，就和 THESIS 重复了。

### 架构师建议
- 只有 1 个 Agent 的简单项目：AGENTS 可以合并进 ARCHITECTURE.md，不用单独文件。
- 多 Agent 系统：严格拆分。THESIS 写原则，AGENTS 写角色，角色必须符合原则。
- 检查标准：如果你删掉 AGENTS，THESIS 依然完整成立；反过来不成立。

---

## 4. ADR / TRADEOFFS / DECISIONS / EXPERIMENTS：四者的时态与分工
这是最容易混的一组，核心区分维度是**时态**和**用途**。

### 四象限拆解
| 文档 | 时态 | 性质 | 核心内容 | 回答的问题 |
|---|---|---|---|---|
| **TRADEOFFS** | 决策前 | 选项池 | 多个备选方案的利弊枚举 | 「我们有哪些选择？各有什么好坏？」 |
| **EXPERIMENTS** | 决策前 | 证据库 | 原型实验数据、踩坑记录、实测结果 | 「实际上试过吗？数据怎么样？」 |
| **ADR** | 决策后 | 完整决策档案 | 背景→备选方案→决策理由→影响→风险 | 「当时为什么选了这个？」 |
| **DECISIONS** | 决策后 | 结论清单 | 只列最终决策结果，不列过程 | 「最后定了什么？」 |

### 逐个回答你的疑问
#### ① ADR 到底是什么？
ADR（Architecture Decision Record）**不是一个结论，而是一份完整的“决策判决书”**。
标准 ADR 包含：
1. 背景（为什么要决策）
2. 考虑过的备选方案
3. 决策结果
4. 决策理由
5. 带来的影响、后果、风险
6. 后续跟进项

它的核心价值不是“记录选了什么”，而是**“记录为什么这么选”**——这是防止后人反复踩坑的核心。

#### ② 为啥 TRADEOFFS 不是 DECISIONS？根目录只保存最终决策不行吗？
不行，原因很简单：
- **TRADEOFFS 是菜单，DECISIONS 是点餐结果**。菜单不是订单，不能互相替代。
- 只存最终结论，后人看到一定会问：“为什么不选 B？B 明明更好”，然后把已经否决过的方案再拿出来争论一遍，浪费所有人的时间。
- 架构圈有句老话：**不记录理由的决策，三个月后就会变成“历史遗留问题”**。

但你的直觉是对的：**绝大多数项目不需要同时维护 TRADEOFFS 和 ADR**。
- 小项目：把利弊直接写进 ADR 的「备选方案」章节，**删掉独立的 TRADEOFFS.md**。
- 大团队 / 复杂基座：才需要独立 TRADEOFFS 作为公共选项池，供多个 ADR 引用。

#### ③ EXPERIMENTS 不就是记录型的吗？
是，但它是**「证据记录」，不是「决策记录」**。
- 实验数据是客观事实（跑了什么、结果如何、为什么失败）
- 决策是主观判断（基于证据，我们选了什么）

分开的原因：
1. 实验数据通常很长，有大量日志、指标、图表，塞进决策文档会让决策本身难以阅读；
2. 一个实验可以支撑多个决策，独立存档可以复用；
3. 实验可能失败、作废，但决策一旦做出就是正式记录。

**最佳实践**：ADR 里写「参见 EXPERIMENTS-003 号实验」，用引用关联，不复制内容。

#### ④ 那 DECISIONS.md 还有必要吗？
绝大多数项目**没有必要**。
- ADR 本身就是结构化的决策记录，再单独维护一个 DECISIONS 结论清单属于重复。
- 只有一种情况需要：高层管理者只看结论不看过程，单独出一份极简决策列表给他们。

### 架构师建议（90% 的项目适用）
- **删除** TRADEOFFS.md、DECISIONS.md
- 保留：`docs/adr/` 文件夹，每条决策一个 ADR 文件，里面自带备选方案利弊
- 保留：EXPERIMENTS.md（或 `docs/experiments/`），独立存放实验记录
- ADR 中通过编号引用实验，不复制数据

---

## 5. MEMORY.md / USER.md / AGENTS.local.md：机制、模型、草稿箱
### 本质定义与边界
#### ① MEMORY.md：记忆机制的设计文档
- 它讲的是**系统怎么处理记忆**：短期记忆窗口多大、长期记忆怎么分层、压缩策略是什么、遗忘规则、检索方式。
- ⚠️ 铁律：**MEMORY.md 是机制文档，不是内容仓库**。绝对不要把具体的记忆条目、用户历史写进去。
- 类比：相当于数据库的《表结构设计文档》，不是数据库本身。

#### ② USER.md：用户主体的模型定义
- 它讲的是**Agent 眼中的“用户”是什么**：用户有哪些属性、什么权限等级、偏好怎么存储、会话状态有哪些字段。
- ⚠️ 铁律：**USER.md 是模型定义，不是真实用户数据**。不要把具体张三李四的信息写进去。
- 类比：相当于《用户实体设计文档》，不是用户数据表。

#### ③ AGENTS.local.md：本地草稿缓冲区
- 它的核心属性不是“Agent 定义”，而是**`.local`**：本机临时、不提交 Git、个人实验用。
- 用途：你本地调试一个新 Agent 角色、测试一套 prompt、写了个实验性 skill，还不稳定，不想提交污染主仓库，就写在这里。
- ⚠️ 铁律：**稳定后的正式 Agent 必须从 .local 迁移到 AGENTS.md**。.local 永远是草稿箱，不是正式配置。

### 常见混淆坑
1. 把运行时的真实记忆数据写进 MEMORY.md
2. 把真实用户信息写进 USER.md
3. 正式 Agent 长期停留在 .local.md 里，导致其他人看不到
4. 把 MEMORY 和 USER 混为一谈：记忆是系统，用户是主体，用户产生记忆，但记忆系统不专属某个用户

### 架构师建议
- MEMORY 和 USER 必须分开：一个是存储系统设计，一个是主体模型设计，正交关系。
- .local 后缀规则推广到所有文档：任何草稿都用 `*.local.md`，统一加入 .gitignore。
- 定期清理：每个版本发布前清理一次 .local 文件，该转正的转正，该删的删。

---

## 补充：你没提到但极其重要的底层文档
### CONTEXT.md / GLOSSARY.md（术语表）
这是所有文档的共同基础，也是最容易被忽略的文档。
- 作用：统一定义项目里所有核心名词，消除歧义。
- 例子：什么叫 Session？什么叫 Turn？什么叫 Skill？什么叫 Harness？
- 价值：所有其他文档都引用这里的定义，避免同一个词在不同文档里意思不一样。
- 对应你之前聊的 `grill-with-docs`，它实时维护的就是这个文件。

### LIMITATIONS.md（局限性声明）
对外+内部都有用。明确写死“本项目不做什么”，防止使用者产生不切实际的预期，也防止内部架构跑偏。

---

## 最终：文档拆分/合并的架构师判断法则
不用死记硬背，记住三条原则：
1. **同时修改原则**：如果两份文档永远需要同时改，就该合并。
2. **分别查阅原则**：如果两份文档经常被不同的人、在不同场景下分别查阅，就该拆分。
3. **最小维护原则**：小项目优先合并，大团队才拆分；不要为了“看起来专业”拆一堆没人维护的死文档。

### 最简推荐配置（个人 / 小团队 Agent 项目）
**根目录（对外）**
- README.md
- CHANGELOG.md
- SECURITY.md

**docs/design/（内部设计）**
- THESIS.md（公理+边界）
- CONTEXT.md（术语表）
- ARCHITECTURE.md（架构+模块）
- DECISIONS.md（单文件 ADR 合集）
- AGENTS.md（角色定义）
- MEMORY.md（记忆设计）
- CONVENTIONS.md（规范+风格）
- INDEX.md（极简导航）

**草稿（.gitignore）**
- *.local.md

# Agent 文档体系：五个核心困惑的底层拆解
所有文档混淆的根源，本质上是没有用「四维正交属性」去定位每一份文档：
1. **时态**：事前（选项/实验）、事中（过程）、事后（结果/快照）、永恒（原则）
2. **层级**：公理层、架构层、模块层、语法层
3. **状态**：正式受控（提交Git）、草稿实验（不提交）
4. **实体**：主体（Agent/User）、机制（Memory）、规则（Conventions）、导航（Index）

下面逐个击穿你的疑问，全部回到第一性原理。

---

## 1. TRADEOFFS、ARCHITECTURE、ADR 的关系：不是吸纳，是「原料→档案→快照」的三级流水线
### 一句话结论
**ARCHITECTURE 里只有「决策的结果」，没有「决策」本身；TRADEOFFS 是决策前的原料，ADR 是决策的完整档案，ARCHITECTURE 只是最终落地的静态快照**。三者是流水线关系，不是包含关系。

### 本质拆解（时态维度）
| 文档 | 时态 | 本质 | 类比建筑行业 |
|---|---|---|---|
| TRADEOFFS | 决策前 | 可选方案的利弊枚举，是「选项池」 | 竞标方案合集 |
| ADR | 决策后 | 完整的决策过程记录：背景→备选→理由→风险 | 竣工验收报告+设计变更档案 |
| ARCHITECTURE | 当下 | 系统最终长成的样子，只描述现状 | 最终施工图纸 |

### 你混淆的根源
你误以为「ARCHITECTURE 里有决策」——其实没有。
ARCHITECTURE 只告诉你“系统分了这几个模块，数据流是这么走的”，但它永远不会告诉你：
- 为什么分成这几个模块，而不是另外一种拆法
- 当初放弃了哪两种架构方案
- 选这个方案付出了什么代价

这些信息，只存在于 ADR 里；而 ADR 里用到的备选方案利弊，来自 TRADEOFFS。

### 清晰边界
- **ARCHITECTURE 绝对不写“为什么”**，只写“是什么”。一旦开始写理由，就越界到 ADR 了。
- **ADR 是“决策的坟墓”**：一个决策一旦写入 ADR，就正式归档，除非发起新的 ADR 推翻它，否则不能改。
- **TRADEOFFS 是“选项的仓库”**：一个方案可以这次没选，下次决策还能再拿出来讨论。

### 最佳实践（90% 的项目）
- 删掉独立的 `TRADEOFFS.md`，把利弊直接写进对应 ADR 的「备选方案」章节。
- ARCHITECTURE 只画模块图、数据流、目录职责，所有“为什么这么设计”全部指向对应 ADR 编号。
- 只有当团队很大、决策很多、大量方案被反复讨论时，才需要独立的 TRADEOFFS 作为公共选项库。

---

## 2. INDEX.md：它解决的不是「设计问题」，是「可发现性问题」
### 一句话结论
**INDEX 不是架构摘要，它是「文档的目录页」。ARCHITECTURE 讲系统的结构，INDEX 讲文档的结构。它存在的意义，就是帮人和模型快速找到正确的文档，而不是在一堆 md 里乱撞。**

### 本质拆解（实体维度）
- ARCHITECTURE：描述**代码系统**的结构
- INDEX.md：描述**文档集合**的结构

你觉得“维护精确 INDEX 不现实”“模型可以自己查项目结构”——这个想法有两个致命漏洞：

#### ① 模型自己查文件结构，会读到大量“噪音文档”
一个项目跑久了，根目录会出现：
- 正式设计文档：ARCHITECTURE、ADR
- 草稿：*.local.md
- 废弃文档：old-arch.md、v1-plan.md
- 临时文档：debug.md、test-notes.md
- 自动生成的文档：api-docs、coverage

模型没有能力判断“哪些是权威的、最新的、正式的设计文档”。而 INDEX.md 就是人工维护的**权威文档白名单**：明确告诉模型和新人“你只需要看这些，别的都是草稿/废弃/噪音，不用管”。

#### ② 团队管理的本质是「契约」，不是「技术」
如果没有 INDEX，每个人都可以随便新建 md，文档会指数级膨胀，最后没人知道哪份是对的。
INDEX 不是技术产物，是管理产物：它明确了“本项目哪些文档是受控的、需要评审的、修改需要走流程的”。它是文档体系的“宪法目录”。

### 为什么你会觉得和 ARCHITECTURE 重复
典型误区：把 INDEX 写成了“简化版架构说明”，每个条目都写一大段模块介绍。
**正确的 INDEX 根本不写任何设计内容**，它就是一个纯链接列表，维护成本极低：
```markdown
# 内部文档索引
## 公理层
- THESIS.md 核心立论与边界
- CONTEXT.md 统一术语表
## 架构层
- ARCHITECTURE.md 系统架构与数据流
- docs/adr/ 架构决策记录
## 子系统
- AGENTS.md 内置Agent角色
- MEMORY.md 记忆子系统设计
```

### 最佳实践
- 文档 ≤ 5 份：删掉 INDEX，靠目录结构就能发现。
- 文档 5~15 份：极简 INDEX，只列标题+链接，不写内容。
- 文档 > 15 份：INDEX 价值指数级上升，是新人上手和模型检索的第一入口。
- 铁律：**INDEX 永远不描述设计细节**，描述设计是 ARCHITECTURE 的事。

## 3. LIMITATIONS.md vs THESIS.md：主动选择 vs 客观约束
### 一句话结论
**THESIS 是我们主动选择的「设计立场」，可以改；LIMITATIONS 是系统客观存在的「边界约束」，改不了（或者改的代价极大）。** 一个是战略，一个是短板。

### 本质拆解（层级维度）
| 文档 | 属性 | 核心 | 例子 |
|---|---|---|---|
| THESIS | 主动立场 | 我们**选择**要什么、不要什么 | 我们不做多智能体并行，坚持单智能体深度优先 |
| LIMITATIONS | 客观约束 | 系统**目前**做不到什么、有什么缺陷 | 当前架构超过32轮对话后，推理质量显著下降 |

### 清晰边界
1. **可变性不同**
   - THESIS 里的“不做”是**战略选择**：下个版本想改，只要调整立场就能改。
   - LIMITATIONS 里的“不能”是**技术现实**：想改就要重构核心模块，付出巨大代价。

2. **受众不同**
   - THESIS 是**内部文档**：写给开发者看，统一设计思想。
   - LIMITATIONS 是**对外文档**：写给用户看，降低预期，减少无效的 issue 和提问。

3. 范围不同
   - THESIS 覆盖整个项目的设计哲学，包括做什么、不做什么、怎么做。
   - LIMITATIONS 只讲“局限和缺陷”，不讲设计理念。

### 为什么会混淆
因为 THESIS 里通常会有一节“非目标（Non-Goals）”，写我们不做什么，看起来和 LIMITATIONS 很像。
区别在于：
- Non-Goals：我们**不想**做（战略选择）
- Limitations：我们**不能**做（客观限制）

比如：
- “不支持多租户” → 如果是不想做，写进 THESIS；如果是技术上做不到，写进 LIMITATIONS。

## 4. CONTEXT/GLOSSARY vs STYLE：语义层 vs 语法层
### 一句话结论
**完全是两个维度的东西：CONTEXT 管「词是什么意思」（语义统一），STYLE 管「代码怎么写」（格式统一）。一个解决沟通歧义，一个解决代码美观。**

### 本质拆解（层级维度）
| 文档 | 层级 | 作用对象 | 解决的问题 | 例子 |
|---|---|---|---|---|
| CONTEXT / GLOSSARY | 语义层（最高） | 所有人+所有文档+模型 | 大家说的是不是同一个东西 | 本项目中「Agent」特指：拥有独立回合循环、可调用工具的智能体实体，不包括纯提示词角色 |
| STYLE | 语法层（最低） | 代码+编辑器 | 代码长什么样统一 | Agent 相关类名用大驼峰，文件名全小写加连字符 |

### 混淆的根源
很多项目的 `CONVENTIONS.md` 里既写术语定义，又写代码风格，导致大家觉得它们是一回事。
实际上 CONVENTIONS 是一个大杂烩，里面包含了：
- 语义约定（来自 CONTEXT）
- 代码风格（来自 STYLE）
- 流程规范（Git 提交、分支、版本号）

### 更深一层：CONTEXT 是给模型读的第一优先级文档
你之前聊的 `grill-with-docs` 为什么核心维护的是 `CONTEXT.md`？
因为模型最容易出的问题不是代码写得不对齐，而是**术语理解偏差**——你说的“会话”和模型理解的“会话”不是一个东西，后面所有推理都会跑偏。
CONTEXT 就是人和模型之间的“语义契约”，优先级比所有设计文档都高。而 STYLE 只是代码格式，模型根本不在乎。

### 最佳实践
- 小项目：术语表可以放在 CONVENTIONS.md 的第一节，不用单独文件。
- 中大型项目：必须独立 `CONTEXT.md`，作为所有文档的语义基础。
- STYLE 永远不要独立成文件，直接写进 CONVENTIONS，或者直接用 `.editorconfig`、`.eslintrc` 配置文件替代——配置文件比 md 文档靠谱一万倍。

## 5. MEMORY、USER、AGENTS.local.md：主体、机制、草稿箱的本质区别
这三个最乱，因为它们分属三个完全不同的维度，根本不是同一类东西。

### ① MEMORY.md：为什么是机制文档，不是决策记录？
#### 一句话结论
**“要不要做独立记忆层”是决策，写在 ADR 里；“记忆层具体怎么工作”是机制，写在 MEMORY.md 里。** MEMORY.md 是「子系统设计说明书」，不是决策记录。

#### 本质拆解
MEMORY 描述的是**记忆子系统的运行规则**，就像操作系统的内存管理设计文档。它回答：
- 短期记忆窗口多大
- 长期记忆分几层
- 记忆压缩的触发条件和算法
- 遗忘策略是什么
- 检索的优先级逻辑

它和 Agent 的关系：**Agent 是主体，记忆是主体使用的基础设施**。
就像人和大脑的关系：人用大脑思考，但大脑不是人的一部分，是独立的器官系统。Agent 可以调用记忆系统，但记忆系统可以被多个 Agent 共享，所以必须单独设计、单独文档。

> 误区纠正：机制文档不在 agents 里面。Agent 是主体，机制是工具；主体用工具，但工具不属于主体。

### ② USER.md：它是「类型定义」，不是「数据」
#### 一句话结论
**USER.md 是「用户实体的模型定义」，定义的是“用户这个概念在系统里是什么样的”，不是真实的用户数据。** 它和 AGENTS.md 是同一类：都是主体定义。

#### 本质拆解
USER.md 回答：
- 用户有哪些属性字段
- 用户的权限等级划分
- 用户会话状态机
- 用户偏好的存储结构

类比数据库：
- USER.md = user 表的表结构设计文档
- 真实用户数据 = user 表里的行数据

> 铁律：永远不要把具体用户的信息写进 USER.md，它是类型定义，不是数据仓库。

### ③ AGENTS.local.md：它的核心是「.local」，不是「AGENTS」
#### 一句话结论
你理解的完全正确：**它就是个人本地草稿，不方便也不应该上传团队。** 它的本质是「实验沙箱」，核心属性是「非正式、不提交、有生命周期」。

#### 本质拆解
`.local` 后缀的意义：
1. **降低实验门槛**：你想试一个新 Agent 角色、一套新 prompt，不用修改正式文档、不用走评审流程，本地写了就能跑，不影响团队。
2. **明确生命周期**：
   - 实验成功 → 迁移到正式 `AGENTS.md`，删除 .local 版本
   - 实验失败 → 直接删除，不留痕迹，不会污染仓库历史
3. **通用规则**：不止 AGENTS，任何文档都可以有 .local 版——`MEMORY.local.md`、`USER.local.md`、`ARCHITECTURE.local.md`，只要是草稿、实验、不提交的，统一加 .local 后缀，全部加入 `.gitignore`。

### 三者的终极边界（一张表说清）
| 文档 | 实体类型 | 状态 | 是否提交Git | 核心作用 |
|---|---|---|---|---|
| MEMORY.md | 机制（工具） | 正式受控 | ✅ | 记忆子系统的设计说明 |
| USER.md | 主体（用户） | 正式受控 | ✅ | 用户实体的模型定义 |
| AGENTS.local.md | 主体（Agent） | 草稿实验 | ❌ | 本地Agent角色的实验草稿 |

> 简单记：
> - 带 .local 的全是草稿，别提交；
> - 不带 .local 的正式文档里，Agent 和 User 是主体，Memory 是它们用的工具。

## 最后：文档拆分的「一刀判定法」
以后遇到任何文档不知道该不该拆、该不该合并，问自己四个问题：
1. **时态一样吗？** 事前选项和事后结果不能混。
2. **层级一样吗？** 公理原则和代码格式不能混。
3. **状态一样吗？** 正式受控和草稿实验不能混。
4. **实体一样吗？** 主体和机制不能混。

四个问题有一个答案是否定的，就应该拆分；四个都肯定，就可以合并。
