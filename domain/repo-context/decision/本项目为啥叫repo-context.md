# 为啥本项目叫repo-context
不绕弯子，直接给最终裁决：**选 `repo-context**`。

前面之所以在分析引用内容时迁就讨论了 `project`，是因为顺着那段引用里“想兼顾文档项目”的预设在打转，导致结论摇摆。但如果剥离所有妥协、在这两者之间做**绝对二选一**，`repo-context` 在真实技术场景中完胜。

理由只有三条，招招致命：

1. **真实边界判定：文档项目也是 Repo**
引言里所谓“repo 会排除纯文档项目”是个伪命题。现在需要引入 Agent、定义架构边界、防范上下文污染的严肃文档项目（比如基于 VitePress、Docusaurus、Mintlify 或 GitBook 的体系），**无一例外都是 Git Repo**。只有单篇随意写的 Word/Notion 才不是 Repo，而那种场景根本不需要这套规范。
2. **语义精度：消除歧义**
* `project-context` 会带来严重的“业务/管理学歧义”——很多人看到的第一反应是 Jira 工单背景、敏捷管理看板、PRD 商业诉求或项目排期。
* `repo-context` 则没有任何歧义——在开发者和 Agent 领域，它直接锚定“代码库/版本库层级的上下文拓扑”（Repo-level context），技术专业感拉满。


3. **受众认知：只对真正的工程用户说话**
会去搜索、学习和采纳你这套 `.md` 治理方案的人，100% 都是面对着一个具体的 Repository（仓库）在发愁的工程师。对这群人来说，`repo` 远比泛化平庸的 `project` 更亲切、更精确。

**定案：`repo-context`。**
