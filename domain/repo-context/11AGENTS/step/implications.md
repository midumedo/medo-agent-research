# 对「管理 vibe docs 的 skill」设计的原则性含义

> 配套[主稿](first-principles.md)第六节判据表。本文只落到**原理层**：skill 应当固化什么、检测什么、不替代什么。具体实现（脚本结构、交互形式、与哪些 harness 配合）由各 AI 结合项目自行设计——这是 11AGENTS 与 repo-context 两份 AGENTS.md 的明确立场。

## 一、skill 的第一性原理：不生产内容模板，生产「放置判据＋问责」

从主稿推导直接得到：`AGENTS.md` 的失效不在写得慢，在**放错**——把可推断的、易腐的、有正本的、可强制的内容放进常驻通道，同时把身份、语义、纪律这些唯一不可推断的内容挡在通道外。因此管理 skill 的核心资产不是一份推荐章节表，而是：

1. **判据表程序化**：对每个候选条目跑五问（时机/可推断/易变可核对/唯一性/归属），输出四分类（常驻/路由/外置/拒绝）。skill 的全部判断力收敛在这张表里。
2. **问责表**：每份 `AGENTS.md` 一个 owner＋一组更新触发条件。判据表决定内容能不能进，问责表决定进去以后谁负责它不死。没有问责表的 skill 只做完一半。

## 二、反模式检测：哪些能机械化，哪些不能

检测项按主稿失效结构列出，并诚实标注机械化程度：

| 反模式 | 判据 | 机械化程度 |
|---|---|---|
| 体裁先行 | 段落存在但内容为空、或内容与段落名无关（如研究仓的「构建命令」节） | 部分可机械化：空节、虚构命令可查；「无关」需模型判断 |
| 规则只增不减 | 行数单调上升且 git 历史无删除事件 | 可机械化（行数、删除事件频率） |
| 状态内联 | 常驻通道含可变状态且无指针语义（没有「详见 X」的正本指向） | 部分可机械化：可检测「状态词＋无链接」的共现；语义判定需模型 |
| 副本漂移 | 多份同名内容文件逐行相同而无同步机制 | 可机械化（字节比对） |
| 强规则错位 | 能被 lint/CI/hook 检查的规则写在指令文件里 | 可机械化（与已有检查器清单比对） |
| 问责缺失 | 某段内容无 owner、无更新触发 | 需人工/模型确认（这是约定，不是文件属性） |

原则：**能机械查的不麻烦模型，不能机械查的不伪装成机械结论**。第六条尤其危险——「无 owner」无法从文件内容证明，skill 应当把它输出为「待确认」而非「通过」。

## 四、skill 明确不做的事

1. 不代写 `AGENTS.md` 内容。内容属于项目判断，skill 给判据与问责框架；代写会把「体裁先行」重新引进来。
2. 不设行数硬门禁。行数是判据表的结果，不是目标；把它当门禁会诱导截断身份与纪律这类真正不可推断的内容。
3. 不宣称治理已生效。跑过判据表等于「放置已审查」，不等于「模型会遵守」。遵守是行为问题，留给实验（主稿第八节未决问题）。

## 五、落地顺序建议（原理性）

1. 先做问责表：给现有每份 `AGENTS.md` 定 owner 与触发条件——这是零判据也能做的部分，且直接消解最脆的一段。
2. 再上判据表程序化：对存量内容做一次四分类盘点，识别状态内联与副本漂移（这两类有现成机械信号）。
3. 最后补反模式的周期性检查：删除事件频率、行数趋势、空节检测。周期性动作需要在项目内显式约定，不默认自带。
