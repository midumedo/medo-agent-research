# 读 PDF 与读 HTML 的成本对比 · 本地确定性测量

> 启明 · 观测时间：2026-09-27 修订（文件名沿用同日 UTC 日） · 由 measure_read_cost.py 生成（HTML 侧标准库 `html.parser`，PDF 侧 PyMuPDF）。
> 输入基线 Git：`2732c8b` 之后工作区 · Python 3.13.11。

这是同一份文档两种格式表示下的**文件/字符/像素/结构观测**，不是 Agent 效果实验。没有调用任何模型，没有测量理解质量，也没有测量识别准确率。完整数据见同名 JSON。

## 结论：分界点在 1.37×–1.64× 渲染倍率

问「原生视觉把 PDF 丢过去」和「读 HTML」，谁更省——答案不是固定的，取决于 PDF 被渲染成多大：

| PDF 渲染倍率 | 视觉路径 tokens | 正文字高 | 相对读 HTML 文本 |
| --- | ---: | ---: | --- |
| 1×（595×842 px/页） | 29,392 | 8.2 px | **省 37%–53%** |
| 2×（1190×1684 px/页） | 117,568 | 16.4 px | 贵 47%–106% |
| 3×（1785×2526 px/页） | 264,528 | 24.6 px | 贵 230%–363% |

- **打平点**：`29,392 × z² = 54,971…79,065` → **z ≈ 1.37–1.64**，对应字高 11.2–13.4 px。
- 低于这个倍率，视觉路径更省；高于它，文本路径更省。
- **而这份文档的正文只有 8.2 pt**（页高 842 pt）——倍率越低字越小，越可能读不准。**能"省"的那个档位，恰好是字最小的档位。**

所以对中文小字正文文档：**读 HTML 文本更省**；但对字号大、或内容以图表/公式/版式为主的文档，结论会反转。

## 先解决前提：这条通道没有视觉

用户要问的是"原生视觉直接把 PDF 丢过去"。我实测了这条路在当前运行时是否存在：

把 PDF 第 6 页渲染成 1190×1684 PNG，用 `read_file` 读它——返回的是

```
Error: File is binary (.png format). read_file only reads text files.
```

**图片不会作为视觉附件进入上下文。** 所以本轮无法实测"视觉读 PDF 的识别效果"，脚本只渲染位图并测量其像素与字节，**不宣称模型看得准**。这是通道限制，不是对任何模型能力的判断——换一个支持图像输入的客户端，同一份 44 页图可以直接对比。

## 两条路的成本模型不同（这是「省」的根源）

| | 图像路径 | 文本路径 |
| --- | --- | --- |
| 计费变量 | **页面面积** | **字符数** |
| 与内容量的关系 | 无关：空页与满页同价 | 成正比 |
| 空白与版式 | 照付 | 不付 |
| 这份文档的实测 | 文字 bbox 只占页面面积 **20.0%** | 85,905–92,530 字符 |
| 传输体积 | 6.98 MB（44 页 @2× PNG 抽样估算） | 184 KB |

**80% 的页面面积是空白与版式**，图像路径要为它们付 token；文本路径不付。这是两条路的成本差异根本所在，与"谁更准"无关。

## 数字

token 为按字符构成的估算区间（CJK 1.0–1.5 tok/字、ASCII 0.25 tok/字），视觉为像素粗估；均**非实测分词**，只用于同一口径下的相对比较。

| 读取路径 | chars | UTF-8 bytes | tok 低 | tok 高 |
| --- | ---: | ---: | ---: | ---: |
| **文本·html.visible_text（去标签）** | 85,905 | 176,357 | 54,971 | 77,610 |
| **文本·html.markdown（含结构标记）** | 91,726 | 182,178 | 56,426 | 79,065 |
| 文本·html.raw（原样含标签 CSS） | 142,568 | 233,087 | 69,161 | 91,816 |
| 文本·pdf.text_extract（PyMuPDF） | 92,530 | 184,404 | 57,108 | 80,118 |
| 图像·pdf.visual 1× | — | — | 29,392 | — |
| 图像·pdf.visual 2× | — | — | 117,568 | — |
| 图像·pdf.visual 3× | — | — | 264,528 | — |

同一份内容，两条路的载体差了 38 倍（6.98 MB 图像 vs 184 KB 文本）。

## 待验证假设（本轮无法证伪的）

1. **字高多少 px 才能可靠识别中文**——本轮没有视觉通道，**未验证**。1× 的 8.2 px、2× 的 16.4 px 读得准不准，只能由有视觉通道的客户端实测。打平点落在 11.2–13.4 px，所以这个阈值直接决定结论朝向哪边。
2. **视觉计费公式 `tokens ≈ w×h/750`** 取自 Anthropic 图像文档的公开口径，**本轮未能联网核实**（`docs.claude.com` 在本机被解析到保留地址 198.18.0.64，抓取失败），可能随版本变化。OpenAI 用 512×512 tile 制，量级相近但绝对值不同。
3. **"原生视觉读 PDF"是否叠加文本层**——若实现是「每页图像 + 提取文本」都传，视觉路径的成本要再加上 57k–80k 文本 token，比上表更贵。本轮未核实，上表**只算像素项**。
4. **HTML 也可以走图像路径**（渲染成截图）。那时它同样按面积付费，唯一优势变成"单页连续、不必切成 44 张"；本表未列这一条。

## 与文本抽取路径的关系（上一轮测量仍然有效）

在"文本 vs 文本"这一层，同一内容下：

- HTML 结构化文本 91,726 字符 vs PDF 抽取 92,530 字符，**差 0.9%**——进上下文的文本量几乎相同。
- HTML 以 5,821 字符（+6.8%）的标记税带回 **140 个标题、34 张表（804 单元格）、271 处代码**；PDF 抽取把结构压平，且**不可恢复**：615 个字体引用中 610 个是 Type3 子集，粗体/等宽语义在打印时已丢（`bold_spans=2`、`mono_spans=0`），只剩字号。
- PDF 抽取另带 88 行页眉页脚（含 44 行源 `file://` URL）与 10.0% 的 ≤3 字符断行碎片——第 5 页表格「窗口内管理」被拆成 `① 窗` / `口内` / `管理`，HTML 侧是完整的 `<td>口内管理</td>`。

也就是说：**若确定走文本模态，HTML 是更省且更完整的那一份；只有在内容落在图表与版式里时，图像路径才有不可替代性**——而这份文档恰好有 34 张表，正是文本抽取最容易坏的地方。这个取舍不是"哪个格式好"，是"要不要为版式付 5–10 倍的 token"。

## 复跑

```bash
python domain/repo-context/05read-pdf-vs-html/measure_read_cost.py \
  --out domain/repo-context/05read-pdf-vs-html/results/replication-01
```

脚本不下载、不修改输入，只读 `sources/books/*/` 下成对同名文件；会抽样渲染 3 页位图（首/中/尾）以测图像体积。HTML 侧只用标准库 `html.parser`（与项目「零第三方运行时依赖」一致）；PDF 侧的标准库无法完成（需解压内容流并处理字体映射），PyMuPDF 为可选依赖——未安装时脚本仍产出全部 HTML 侧结果，PDF 侧标 `unavailable` 并提示安装命令，不静默降级。

复跑结果变化时先比 `inputs.sha256`；`generated`、`git_head` 与运行耗时随运行变化，其余确定性值仅在输入相同时可比。
