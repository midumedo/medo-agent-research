# 读 PDF 与读 HTML 的成本对比 · 本地确定性测量

> 启明 · 观测时间（UTC+8）：2026-09-27T07:14:56 · 由 measure_read_cost.py 生成。
> 输入基线 Git：`0d25bf49aa895948bc23ef3593d8a99ddb913180` · Python 3.13.11 · PyMuPDF + lxml。

这是同一份文档两种格式表示下的**文件/字符/结构观测**，不是 Agent 效果实验。没有调用任何模型，没有测量理解质量。完整输入指纹与逐项结果见同名 JSON。

## 结论

**HTML 更省——但不是因为文件小。**

1. **进上下文的文本量几乎相同**：HTML 结构化文本 91,726 字符 vs PDF 文本抽取 92,530 字符，差 0.9%。
2. **同等文本量下 HTML 多带结构**：HTML 以 5,821 字符（+6.8%）的标记税换回 140 个标题、34 张表（804 单元格）、271 处代码标记；PDF 文本抽取把这些压成扁平文本行，且 PDF 自身的字体信号已不可用于恢复。
3. **PDF 文本路径另带固定噪声**：88 行页眉页脚（2,631 字符，含 44 行源文件 `file://` URL），HTML 版本为零。
4. **若走视觉路径则成倍更贵**：44 页按 2× 渲染约 117,568 tok ≈ 文本路径的 2.06 倍（仅位图部分，未含文本层）。
5. **HTML 唯一的劣势在朴素读取**：原样读字节时 HTML 142,568 字符、比 PDF 文本抽取多 54%（39.7% 是标签与 CSS）；这一次 `DOM 解析` 即可消除，而 PDF 的结构损失不可逆。

token 为按字符构成的估算区间（CJK 1.0–1.5 tok/字、ASCII 0.25 tok/字），**非实测分词**，只用于同一估算器下的相对比较。

| 读取管线 | chars | UTF-8 bytes | tok 低 | tok 高 |
| --- | ---: | ---: | ---: | ---: |
| html.raw（原样） | 142,568 | 233,087 | 69,161 | 91,816 |
| html.no_style_script（去样式） | 136,366 | 226,818 | 67,586 | 90,225 |
| html.visible_text（去标签全文） | 85,905 | 176,357 | 54,971 | 77,610 |
| html.markdown（含结构标记） | 91,726 | 182,178 | 56,426 | 79,065 |
| pdf.text_extract（PyMuPDF 抽取） | 92,530 | 184,404 | 57,108 | 80,118 |
| pdf.visual 1×（595×842 px/页） | — | — | 29,392 | — |
| pdf.visual 2×（1190×1684 px/页） | — | — | 117,568 | — |

`html.markdown` 由本脚本 DOM 转换，转换后用 98% 可见文本覆盖率断言自检，本次实测覆盖率 1.0——「更省」不是靠丢内容换来的。

## 结构保真

| 结构 | HTML 显式标签 | PDF 文本抽取 | PDF 原生信号 |
| --- | ---: | ---: | --- |
| 标题 | 140（h1×2, h2×20, h3×75, h4×9, h5×34） | 无标记，靠换行 | 字号可分级（正文 8.2/7.2 pt，标题 13.4 pt） |
| 表格 | 34 张 / 233 行 / 804 单元格 | 压平为逐行文本 | 需按坐标重建 |
| 代码 | 271 个 `code` + 4 个 `pre`（8,430 字符） | 无标记 | 不可恢复 |
| 粗体 / 等宽 | 标签与 CSS 承载 | 不可恢复 | `bold_spans=2`、`mono_spans=0` |

字体信号失效的原因是可复查的：PDF 共 615 个字体引用，其中 610 个是 `Type3 (N 0 R)` 形式的子集化引用，字体族语义（粗体、等宽）在打印时已被丢弃，只剩字号与坐标。**字号可分级、粗体与等宽不可恢复。**

## 噪声税

| 噪声 | PDF 文本抽取 | HTML |
| --- | --- | --- |
| 页眉页脚 | 88 行 / 2,631 字符（44 行源 URL + 44 行「页码/总页数」） | 0 |
| 断行碎片（≤3 字符的行） | 263 / 2,628 行 = 10.0% | 表格有 804 个显式单元格，无此现象 |
| 标记开销 | 0 | 56,663 字符 = 原文 39.7%（标签 + 6,202 字符内联 CSS） |

PDF 的碎片有实例：第 5 页表格在抽取后变成逐格竖排——`① 窗` / `口内` / `管理`，即「窗口内管理」被拆成三行，行序也不再对应原表。HTML 侧同一处是 `<td>口内管理</td>`，结构完好。

两种格式各有各的税：HTML 的税是标记（可由解析器一次性剥离），PDF 的税是页眉页脚与版式断行（是内容流的一部分，剥离器无从区分）。

## 解释边界

**已观测**：同一内容下，HTML 能以略少的字符预算同时携带全部结构；PDF 文本路径在字符量相当的前提下丢结构并附带页眉页脚噪声；PDF 打印产物无粗体/等宽信号。

**尚未知**，需要模型在环才能回答：

- 文本量差 0.9% 在真实 tokenizer 与真实 harness 里是否仍是这个量级（本轮未装 tokenizer）。
- 结构损失对任务正确率的实际影响——本报告的 10% 碎片率只说明结构被破坏，不说明模型答错。
- 视觉路径的真实计费是否叠加文本层（取决于供应商实现，本轮未实测，表中只给位图部分）。
- 1× 渲染虽 token 最省（29,392），但 8.2 pt 中文正文在 595×842 px 下的可读性未验证——「省」可能以读不清为代价。这一点在 [README](../README.md)「待执行」里列为必查项。
