# 同名文档定义锁定

> 第一版 · 2026-10-14。按文件名建立当前统一定义，以第一性原理解释其职责；这是一轮形成体系的研究产物，可以继续修订。

## 本版约定

本稿为不同仓库中同名的文档选定一个共同定义。分组依据是 basename，即路径最后一段的文件名；本轮保留大小写、扩展名和语言后缀的实际写法。`NOTICE` 与 `NOTICE.md` 分开，`README.md` 与 `README.en.md` 分开列项。后者可以共享语义职责，但不因此改写样本的实际名字。

**每个文件名只有一个主定义。** “锁定”指本版一致采用这个定义与简称，不是宣称所有实例正文等价或研究终结。职责分解写在主定义内部：分清它承载了哪些工作、哪些关系必须保留、哪些只是具体范围或载体差异。这一版不把每种差异先拆成独立文档类型；若共同定义开始遮蔽重要条件，就在下一版重开边界。

[逐实例定义](definitions.md)保留每个路径的具体描述，本稿提供跨仓引用时的共同称呼。这里的共同定义是本项目的工作约定；实例表中的正文差异是样本观察；由信息任务推导的共同职责是研究判断。三者分开理解。

本次覆盖 [00 台账](../00docslist/index.csv)中至少在两个仓库出现的文件名：**12 组、83 条 verified 实例**。其余 50 条 verified 单例仍在逐实例定义中；没有正文的 claude-code absent 占位不进入本稿。

## 怎样从文件名走到定义

文件名只决定先把哪些材料放在一起比较。定义必须继续回答 [01 V11 的四问](../01docsclassify/v11/研究方法与证据.md)：保存或规定什么信息；谁在什么情境中据此回答什么问题；哪些内容关系使任务成立；什么变化要求更新、替代或重建。

本稿用“删掉什么就无法完成这项工作”识别最低成立内容。比如贡献指南即使不接收代码 PR，仍可说明允许的参与方式和接纳条件；只有安装命令而没有贡献关系，则不能靠文件名变成贡献指南。对差异再问：它改变了任务本身，还是只改变本仓的范围、具体政策、正文组织或入口形式？

以下“职责剖析”列出的工作不要求每份实例全部承载。“成立内容”给最低识别条件；实例表说明实际覆盖哪些职责。仓库政策的具体取值可以相反，例如接受或暂不接受 PR，共同定义必须保留让读者查明本仓取值的关系。

证据沿用固定本地 checkout 的正文位置与逐实例核读记录，并复核有区分力的反例。正文定义、来源自述、程序消费和行为效果各自成立：一个命名入口可以先有工作定义，而自动加载与效果仍待研究。Raven 的长篇 `CONTEXT.md` 仍是代表性章节核读，未完成全文与源码逐项核对。

## README.md：项目入口说明（project-entry）

**锁定定义**：面向初次或重新进入项目的读者，说明项目的身份、用途与范围，并提供适合其任务的开始路径或后续资料，使读者能建立基本认识并进入使用、开发、部署或研究工作。

- **信息与任务**：组织“这是什么、适合做什么、我从哪里开始”。读者可以是用户、开发者、部署者或研究者；“开始”不限定为下载安装。
- **成立内容**：可辨认的项目身份与用途，加上可采取的进入路径。路径可以是操作步骤、接口示例、资料导航或其组合；只有项目名称或宣传口号不足以完成入口任务。
- **必要关系**：项目定位必须与可进入的产品形态、环境和资料相连；多种开始方式须能辨认各自适用条件。
- **演化条件**：定位、能力边界、安装/部署方式、产品形态、关键接口或资料入口变化时更新；其中嵌入的指标与历史消息按各自来源和时点维护。

**职责剖析**：入口是共同职责；上手操作、部署教程、开发初始化、系统解释、API 参考、论文与指标说明是实例可能一起承载的职责。ZCode 主要把读者带入开发与运行，ReFind 把产品介绍与方法/API 说明放在一起，Cline 主要提供产品和安装导航。它们的读者与进入方式不同，仍能用一个入口定义解释；共同定义不能把长正文中的每段都说成“导航”，也不能要求所有 README 都是面向终端用户的营销页。

**邻居与反例**：独立安装手册围绕一个已选定环境展开操作；系统参考围绕精确查询展开；README 把读者带入这些任务。一个名为 README 的文件若仅是某次内部状态流水，既无项目定位也无进入关系，就不符合当前共同定义。目录级 README 是否以“所在组件”为项目对象，需在后续扩样时明确，不能从本轮仓根样本直接推广。

**重开条件与缺口**：若发现入口关系无法解释的同名材料，修订对象范围或记录同名异用；若定义宽到任何文本都能符合，收紧最低关系。本轮没有统一复核所有命令、外链、性能主张或实际读者行为，入口成立不代表入口有效。

## AGENTS.md：Agent 仓库工作说明（agent-work-guide）

**锁定定义**：为参与本仓库开发工作的 Agent 提供适用范围内的工程规则、项目事实、操作方法及进一步阅读入口，使其能取得理解、实施和验证改动所需的本地工作信息。

- **信息与任务**：回答“在这里工作，我需要先知道什么，能怎样改，如何定位和验证”。人类开发者也可以读取；文件名不决定是否已经被某个 harness 投递。
- **成立内容**：明确或可辨认的仓库/组件范围，以及与工作任务相连的规则、事实或操作信息，至少形成一种可执行或可查找的工作关系。不是每份都必须含规则、地图和命令三类全文。
- **必要关系**：要求须对应适用对象；命令须对应组件和环境；阅读路由须对应问题与资料。全局规则与子树说明共存时，需要保留范围与覆盖关系。
- **演化条件**：规则、组件边界、工具链、环境、验证方法或阅读路径改变时更新；多份入口共用正文时另维护同步关系。

**职责剖析**：工程约束决定“允许/要求怎样做”；项目地图帮助理解和定位；环境操作安排构建、启动和测试；验证要求说明交付依据。它们共同服务仓库工作，但各自会因不同对象变化而过期。Cline 的环境操作、Tianshu 的架构地图和 Raven 的硬约束分别突出不同职责；本版把这些差异保留在一个工作说明定义中，而不按仓库拆型。

## CLAUDE.md：Claude 仓库工作入口（claude-work-entry）

**锁定定义**：以 Claude 命名入口承接本仓库适用的 Agent 工作信息，通过直接正文、对其他规则的引用或 Claude 情境的补充说明，提供工程理解、工作规则和运行时协作所需的信息。

- **信息与任务**：回答“从这个 Claude 入口进入时，应取得哪些本仓信息与专属要求”。它可以只是取得资料的入口，也可以直接承载大部分工程说明。
- **成立内容**：指向可识别项目的适用工作信息，或能够取得这些信息的明确引用；若是专属补充，须能辨认它补充了什么工作条件。
- **必要关系**：区分共用规则、全文副本、引用目标和专属补充。正文复制要求维护一致性；指针要求目标可定位；补充要求共用与专属范围可区分。
- **演化条件**：共用规则、引用路径、Claude 专属工具/子代理边界或工程事实变化时更新。副本与指针的维护动作不同。

**职责剖析**：取得共用规则、承载完整工程上下文、补充运行时协作，是此入口可能承担的工作。全文、指针和补充是关系与载体差异，不各设一个主定义。入口定义也不授予独立权威：要由对应正文和运行机制判断哪份是正本、哪些只是同步副本、引用是否实际展开。

## CONTEXT.md：领域语义说明（domain-context）

**锁定定义**：针对仓库中的明确领域，解释对象、术语、状态及其关系，说明本地含义、适用边界和易混用处，使设计、实现与文档能够使用一致的领域语言。

- **信息与任务**：开发者、Agent 和设计讨论者在理解或修改某个领域时，查询“这个词指什么，哪些对象和状态必须区分，它们怎样关联”。
- **成立内容**：可辨认的领域范围，加上有区分力的本地语义或关系；仅罗列词语、没有解释区别，不足以承担这项工作。
- **必要关系**：词义须与对象、关系、生命周期和使用边界相连；若说明实现依据，应区分当前实现事实与规范性不变量。
- **演化条件**：领域对象、状态、字段、关系或命名含义变化时同步；实现位置改变时维护引用。

**职责剖析**：术语定义解决词义；关系说明解决多个词如何共同解释对象；不变量说明允许/禁止的关系；实现引用让读者追溯依据。Raven 范围大，ZCode 范围小，这一版按领域范围保留差异，不以篇幅、子域数量另造类型。

**邻居与反例**：CONTEXT-MAP 主要路由领域与资料；CONTEXT 本版共同定义主要解释领域语义。一个同名文件若只列当前任务进度或保存运行日志，就不满足此定义；“上下文”一词本身不能抹去这些差异。

**重开条件与缺口**：仅有两例，尚不能断言 CONTEXT 在其他项目都指领域语义。若后续遇到会话恢复材料、通用架构综述或动态任务快照，应重新分析同名的任务范围。Raven 是章节抽读且未逐项反查源码，ZCode 小文件已全文核读；此处锁定的是可迭代定义，未锁定每项领域事实的正确性。

## CONTRIBUTING.md：贡献参与与接纳说明（contribution-guide）

**职责剖析**：参与和接收政策决定可走哪些路；开发与验证说明怎样准备成果；提交和评审组织工作交接；维护者整合把成果纳入项目。DeepSeek 暂不收外部 PR，与其他仓接收 PR 的政策取值相反，但仍回答同一个参与问题。因而“如何提交代码 PR”不能充当共同定义。Tianshu 双仓收编和 EverOS 核心团队章节需要保留执行主体，不能写成每个贡献者都能直接合入主仓。

## SECURITY.md：项目安全政策（security-policy）

**锁定定义**：说明本项目安全问题的适用范围与处理路径，使报告者、使用者和开发者能够查明问题如何受理或处置；还可以在正文或引用资料中说明安全使用前提、防护与信任边界，为运行和开发提供被声明的安全条件。

- **信息与任务**：漏洞报告者查“向谁报、提供什么、哪些版本适用”；使用者和开发者查“有哪些风险、依赖哪些前提、哪些边界不可越过”。
- **成立内容**：项目/安全问题的适用对象，与可采取的处置或报告路径。九个样本都给漏洞报告入口；风险说明、支持表、响应时限和完整威胁模型各按实例存在与否判断。
- **必要关系**：报告入口须对应问题范围和接收责任；支持范围须对应响应承诺；安全建议或防护声明须对应风险来源、信任假设与局限。引用安全资料时保留入口和被转介内容的区别。
- **演化条件**：报告渠道、支持版本、响应政策、能力/权限、部署前提、数据风险或信任边界改变时更新；风险说明与报告联系方式不必同时变化。

**职责剖析**：漏洞报告与响应政策组织“发现问题以后怎么处理”；运行风险与安全边界说明帮助“运行或开发时怎样理解风险”。两者可以在同一文件共存，但一个报告链接不能替代威胁模型，一段防护说明也不能替代受理渠道。此版锁定一个项目安全政策定义，同时保留这两个内部职责，后续再研究它们是否适合独立文档。

## CODE_OF_CONDUCT.md：社区行为与执行准则（community-conduct）

**锁定定义**：规定项目社区参与空间中的期望与禁止行为，并说明其适用范围、违规报告和执行责任，使参与者与维护者能够理解互动边界并处置违反准则的行为。

- **信息与任务**：参与讨论、贡献或代表社区时查明“怎样互动，行为问题向谁报告，谁能作何种处置”。
- **成立内容**：参与行为标准与其适用范围；要形成完整执行准则，还须有可定位的报告/处置责任或引用入口。
- **必要关系**：行为标准须对应适用空间和执行主体；处置说明须对应触发行为、报告方式与责任。仅有价值口号无法据以判断或处理具体行为。
- **演化条件**：社区空间、行为标准、执行主体、联系方式或处分规则改变时更新；采用的模板版本也需明确。

**职责剖析**：交往标准、贡献诚信、报告/调查与违规处置可以共同组织社区责任。mem0 加入 AI 使用披露、验证责任和不伪造证据，扩展到技术贡献行为；这仍是参与责任，但其中工程检查细节与 CONTRIBUTING 相邻，应分别说明而非互相吞并。短版与 Contributor Covenant 不同版本的篇幅差异不决定类型。

## CHANGELOG.md：项目变更历史入口（change-history）

**锁定定义**：以版本、日期或发布状态组织项目变化的记录或索引，使读者能够定位某阶段改变了什么及其影响；包含未发布项时，须能区分它们与正式发布历史的关系。

- **信息与任务**：用户、维护者与 Agent 在升级、排查、发布核对或历史追查时查询“哪次变化影响了什么，属于哪个版本或时期”。
- **成立内容**：变化与版本/时间/发布状态的对应，或者取得该对应关系的明确索引。记录可以直接写在文件，也可以委托外部发布历史。
- **必要关系**：条目须与版本、时点或发布状态相连；同时出现未发布与已发布项时须能区分。影响或迁移提示须对应变化；外部索引须指向所委托的历史来源。未发布项不可冒充已发布事实。
- **演化条件**：新变化或发布发生时追加/整理，状态从未发布转为发布时调整；生成来源或发布平台变化时维护索引。历史事实可以纠错，不能当作当前行为规范直接执行。

**职责剖析**：变化摘要保存历史；分类/版本组织支持定位；影响和迁移提示帮助升级；外部发布链接承担索引。按日期、版本、自动生成或直接编辑属于组织/生产差异。Codex 把发布详情委托给 Releases，仍是变更历史入口，但不把本地文件说成完整历史正文。

## NOTICE：权利归属与许可范围声明（rights-notice）

**锁定定义**：随项目材料说明作品的权利归属、所涉第三方来源及适用许可范围，关联署名与许可证依据；存在整体许可之外的材料或依赖条件时说明其范围，使使用和再分发时能够按实际来源查明相应条款。

## 下一版怎样推进

当前按文件名得到的是便于一致引用的定义层，不是已经确定的最终文档体系。后续优先处理三类问题：定义是否足以区分新实例与邻居；同一个定义内部哪些职责需要共同组织、哪些可以独立使用和维护；不同文件名是否承载同一项职责。

若需要调整，先写出引发调整的实例与信息关系，再修改共同定义或职责边界。已有实例差异保留在逐实例稿中，避免为了维持“同名同定义”而把观察改成一致。下一版可以收紧、合并或分化定义；这一版不预设最终类型数量。
