# 主要 Vibe 文档：具体定义可读稿

> 状态：供审阅的工作稿，不是已定分类或文件创建规范。
>
> 本稿按具体候选名称逐项提出定义。没有假设这些文件已经存在，也不根据文件名推断它们在实际项目中承担什么工作。以下定义是本项目拟赋予这些名称的职责；实际正文若承担不同任务，应按正文调整定义或名称映射。

## 定义口径

每条定义说明：这个具体名称对应的文档要解决什么问题、读者需要从中得到什么、它与相邻名称有什么区别。大标题只是该任务可能需要回答的问题，不是强制模板。一个文件可以组合多项职责；组合不代表这些职责是同一种文档。

本文只展开主要候选名称。其余 `docslist.md` 候选的轻量归属关系仍见[文档定义 v1](文档定义v1.md)。旧分类、实际仓库中的写法以及尚未定型的 `doc-model` 都只是线索，不能代替这里的定义推导。

## 项目入口与 Agent 工作边界

### `README.md`

`README.md` 是项目或目录的首要介绍页：它让第一次到达这里的读者认出当前对象、判断它是否与自己的任务相关，并找到开始使用或继续阅读的入口。根目录 README 介绍项目整体；子目录 README 应明确它介绍的是哪个模块或资料范围。

README 可以组合简短安装步骤、能力说明和导航，但不应成为完整架构说明、全部开发规则或长操作手册的替身。如果一段内容需要独立维护、经常按任务查阅，README 应提供入口而不是复制其全部正文。

**大标题设想**

- 这是什么
- 面向谁与适用范围
- 能做什么
- 如何开始
- 进一步阅读

### `THISIS.md`

`THISIS.md` 是一份直接回答“这个项目/目录是什么”的身份说明。它应给出对象的名称、边界和核心目的，使读者能区分本项目与相邻项目或子系统。

它与 README 的差别不能仅靠文件名成立：如果两者的读者、维护责任和内容范围没有可说明的差异，THISIS 更适合作为 README 中的身份段或其别名，不必形成另一种文档。它不负责完整上手步骤或内部架构。

**大标题设想**

- 对象身份
- 目的与边界
- 与相邻对象的区别

### `BRIEF.md`（原清单另有拼写 `BREIF`）

`BRIEF.md` 是项目或模块的短摘要，供读者在有限注意力或有限上下文中快速建立基本认识，并被引导到更完整的资料。它保留“是什么、做什么、范围到哪里”这些识别信息，不承担 README 的完整入口职责，也不等于目录树或索引。

原清单中的 `BREIF` 暂按拼写变体处理，不单独定义一种文档。若某个 BRIEF 只是 README 的缩写副本，是否需要独立维护仍是待判断问题。

**大标题设想**

- 对象与目的
- 能力与范围
- 关键关系
- 继续阅读

### `AGENTS.md`

`AGENTS.md` 是适用于其所在仓库或目录范围的 Agent 工作说明。它让 Agent 判断当前任务受哪些项目要求约束、还需要读哪些资料、如何验证结果，以及什么条件下可以交付；它建立规则的适用范围和所需信息入口。

AGENTS.md 可以写项目事实、地图或常用命令，但这些内容只有在服务于 Agent 当前工作时才属于这份文件的职责。它不应被定义成完整架构百科、所有操作手册或一次性任务计划。此定义也不预设某个 harness 会自动发现或加载它；具体发现和优先级属于运行机制问题。

**大标题设想**

- 适用范围与优先关系
- 工作要求与禁止项
- 必需信息、工具与资料入口
- 验证和交付条件
- 冲突、例外与升级路径

### `CLAUDE.md`

`CLAUDE.md` 是面向 Claude Code 工作过程的项目说明入口。它应告诉 Claude Code 哪些项目规则适用、如何定位细节，以及本项目是否提供了 Claude 专用的补充约束。

它和 AGENTS.md 的关系必须写明：可以是专用补充、指向另一份正本的入口，也可以是单独维护的正文；不能只因两者面向 Agent 就把它们当作等价文件。若内容完全相同，重复副本会产生同步责任；若内容不同，应说明差异分别解决什么问题。此定义不主张 Claude Code 的具体加载行为。

**大标题设想**

- Claude Code 适用范围
- 正本与补充规则关系
- 工具使用和验证要求
- 进一步阅读

### `GEMINI.md`

`GEMINI.md` 是面向 Gemini CLI 或相关 Gemini Agent 工作过程的项目说明入口。它应界定适用范围、提供必要工作要求，并说明它与项目通用规则之间的关系。

它不是 AGENTS.md 的天然别名。若它只是适配入口，应指出适配内容和正本位置；若它保存完整规则，应说明自己的适用范围和维护关系。实际工具会不会读取它，不能由这个文件名本身证明。

**大标题设想**

- Gemini 工作范围
- 通用规则与专用补充
- 工作要求和资料入口
- 验证与交付

### `AGENTS.local.md`

`AGENTS.local.md` 是只对某个本地工作区或个人环境生效的 Agent 规则补充。它用于表达不应自动推广给整个团队的路径、机器条件或本地工作偏好，并说明它覆盖哪些任务和如何与共享规则并存。

它不是一般用户画像，也不是另一份共享 AGENTS.md。局部内容如果会影响团队共同工作，应迁入共享规则；涉及个人环境的信息则应限制在本地适用范围。文件本身也不能证明工具会读取它。

**大标题设想**

- 本地适用范围
- 环境与局部要求
- 与共享规则的关系
- 失效或清理条件

## 系统说明与开发约定

### `ARCHITECTURE.md`

`ARCHITECTURE.md` 描述项目在明确范围内由什么组成、各部分负责什么、关键交互和状态如何流动。它帮助读者定位一个行为发生在哪一层、组件为何相互依赖，以及系统边界在哪里。

架构说明的主要工作是解释结构。必须满足的接口或模块约束应标成契约；当初为何选择这种结构应由决策记录解释；操作步骤应放在规程中。ARCHITECTURE.md 可以链接这些文档，不必把它们全并入正文。

**大标题设想**

- 范围与系统边界
- 组件及职责
- 关键交互或数据流
- 外部依赖
- 结构不变量及其性质

### `CONVENTIONS.md`

`CONVENTIONS.md` 规定项目或目录中可跨多次工作复用的开发约定，使不同维护者和 Agent 在相似情境下做出一致选择。每条约定都应能回答：对谁生效、什么情况下生效、符合要求是什么样。

它不同于 AGENTS.md 的入口和适用路由，也不同于完成一次任务的操作规程。测试、兼容性、安全或限制内容不会因为“属于规范”就自动全部归入 CONVENTIONS.md；只有确实是稳定、反复适用的开发约定，才适合由它承载。

**大标题设想**

- 适用范围与原则
- 组织、命名和实现约定
- 变更、评审和提交约定
- 质量要求
- 例外与更新方式

### `STYLE.md`

`STYLE.md` 规定一种特定表达表面的呈现规则，例如代码风格、文档写作、翻译语气或品牌文案。它的独立价值在于存在明确的规则使用者、独立的维护节奏或可独立检查的产物。

如果这些规则只是 CONVENTIONS.md 的少数条目，拆成 STYLE.md 会增加入口和同步负担；如果代码格式已经完全由工具配置执行，STYLE.md 应说明人需要理解的语义选择，而不是抄写配置。风格规则也不能替代实际 linter 或格式化器。

**大标题设想**

- 适用对象与范围
- 表达和格式规则
- 示例或反例
- 与其他约定的关系

### `CONTEXT.md`

`CONTEXT.md` 的候选职责是提供 Agent 在理解项目问题时需要的、跨任务可复用的项目事实和关系，例如概念如何相连、哪些边界不能混淆、理解工作所需的背景入口。它回答“理解这里的工作时，哪些背景和关系不能丢”。

它不应只是一个含义不明的“上下文仓库”，也不等同于一次会话的临时上下文。如果内容仅是按词查找的定义，GLOSSARY.md 已足以承担该任务，两者应合并或明确差别；如果内容主要是当前进度，应该标出时效并按状态材料维护。原清单曾把 CONTEXT 与 GLOSSARY 视作同类，这是待检验线索，不是本稿预设的结论。

**大标题设想**

- 适用范围与背景
- 核心概念及关系
- 关键边界与不变量
- 当前事实的有效期
- 详细资料入口

### `GLOSSARY.md`

`GLOSSARY.md` 是一个可按词条查找的项目词典。每个条目给出项目采用的含义，并在必要时指出易混词、缩写或来源用法差异，使读者能快速确认一个词在本项目里具体指什么。

它不负责解释整个项目背景或当前任务状态。若 GLOSSARY.md 与 CONTEXT.md 都存放同一批词条而没有不同使用者或维护责任，应视为同一项词典职责，而不是两种文档类型。

**大标题设想**

- 术语与工作定义
- 易混词与禁用词
- 缩写和命名
- 适用范围或来源差异

## 导航与定位

### `INDEX.md`

`INDEX.md` 是人工可读的导航页，告诉读者有哪些相关资料、各自解决什么问题、下一步应该打开哪里。它重在建立“问题到资料入口”的对应关系，而不只是抄一份目录。

INDEX.md 不承担被索引文档的正文职责。如果条目和路径可以机械生成，INDEX.md 可以由其他资料生成，但生成来源和更新责任需要明确。目录树只展示层级时，应使用 TREE.md 的定义，不要把两种呈现假装成同一内容。

**大标题设想**

- 索引范围
- 按任务或主题分组的资料入口
- 每项用途
- 维护或生成信息

### `TREE.md`

`TREE.md` 展示项目或文档集合的层级结构，使读者看清目录、模块或层级之间的位置关系。它回答“树形结构是什么”，不自动回答“每个部分有什么语义职责”。

TREE.md 可以是生成快照；如果目录变化很快，应说明生成方式或更新时间。若读者需要按任务找到文档，单纯的树形列表不足以替代 INDEX.md。

**大标题设想**

- 树的范围
- 目录或模块层级
- 必要的节点说明
- 生成或更新时间

### `outline`

`outline` 是一份主题或文档的提纲，表达内容准备按什么顺序展开、哪些主题相互依赖。它帮助作者或读者掌握论述结构，不等同于项目目录树，也不等同于文档索引。

只有当这份提纲指向一个具体内容对象并持续维护时，它才有清楚的文档职责；临时写作提纲应保留为草稿，而不是提升成稳定项目地图。

**大标题设想**

- 提纲对象与范围
- 主题层级
- 展开顺序
- 未完成部分

### `registry`

`registry` 是一份对某类对象逐项登记的名册。每项应有可辨认的身份和被维护的字段，使读者或程序可以确认“登记了哪些对象、各自处于什么记录状态”。

它与 INDEX.md 的区别是条目本身：INDEX 提供资料入口，registry 维护对象记录。若只是链接列表，就不需要另造 registry；若程序依赖字段，字段含义和更新责任必须可辨认。

**大标题设想**

- 登记对象与范围
- 条目身份
- 维护字段
- 更新责任或生成方式

## 状态、决定与历史

### `MEMORY.md`

`MEMORY.md` 保存跨任务仍可能影响后续判断、且不应每次从头恢复的信息。每条内容都应能说明适用主体、来源或有效期；只因内容过去重要，并不足以证明它现在仍应保留。

它不等同于完整对话归档、项目变更历史或待办列表。若它记录用户偏好，应与项目事实区分；若它记录项目经验，应说明何时需要复核或失效。

**大标题设想**

- 适用对象与范围
- 可复用信息
- 来源或有效期
- 更新与淘汰条件

### `USER.md`

`USER.md` 描述 Agent 为了适当服务某个用户而需要保持的相对稳定信息，例如用户明确表达的偏好、目标、约束或协作方式。它回答“这个用户有哪些会影响交互的已知条件”。

它不是关于项目架构的事实库，也不应把一次性的任务状态写成永久用户特征。信息需保留来源或确认状态，避免把一次推断写成用户明确偏好。

**大标题设想**

- 适用用户
- 明确表达的偏好
- 持续目标或约束
- 来源、确认和更新状态

### `DECISIONS.md`

`DECISIONS.md` 是一份项目决策索引或汇总页，帮助读者找到已经作出的重要选择及其状态。若它采用单文件保存每项决定，仍应让每项背景、取舍和结果可以分别定位；若只列标题和链接，它是索引而不是决策正文。

它不等同于正在讨论的提案、普通计划或当前规则正本。已生效规则应在适用的规则文件中维护；DECISIONS.md 负责保留选择为何形成及其后续状态。

**大标题设想**

- 决策范围
- 决策条目或链接
- 当前状态
- 替代与复审关系

### `ADR/`

`ADR/` 是一组逐项保存的架构或技术决策记录。每份记录对应一个决定，使背景、备选方案、理由和后果不会被后来的决定覆盖；目录负责保留时间顺序和替代关系。

它与 DECISIONS.md 的核心任务相同，主要差异是单位和载体：DECISIONS.md 可以是汇总文件，ADR/ 是多份单项记录。ADR 不应被当作当前规则正本；若一个决定已被替代，历史理由仍可保留，但状态要清楚。

**大标题设想**

- 背景与待决问题
- 候选方案
- 决定与理由
- 后果
- 状态或替代关系

### `TRADOFFS.md`（原清单拼写）

`TRADOFFS.md` 记录几个可选方案之间的得失，帮助读者看清选择会改善什么、牺牲什么。它的核心产物是比较依据，不是替项目作出决定；如果文档最后确实选定一个方案，应明确指出决定本身及其记录位置。

它不应成为所有决定的另一个副本，也不应只留下孤立的优缺点列表而没有比较目标和适用条件。原清单拼写为 `TRADOFFS`，本稿保留这一候选名称，不擅自改成别名或新类型。

**大标题设想**

- 比较的问题与目标
- 候选方案
- 主要得失
- 适用条件
- 决定状态或关联记录

### `ROADMAP.md`

`ROADMAP.md` 描述项目未来一段时间希望达到的方向、优先顺序和阶段目标，帮助读者理解“接下来大致往哪里走”。它是计划性说明，不天然构成对日期、功能或交付的承诺。

它不同于待办队列和当前问题清单：roadmap 表达目标方向，待办表达近期动作，问题清单表达当前尚未解决的事项。若外部看板是实时状态来源，ROADMAP.md 应指出其摘要范围和更新关系。

**大标题设想**

- 规划范围与期限
- 方向和优先级
- 阶段目标
- 依赖与不确定性
- 更新方式

### `PROBLEMS.md`

`PROBLEMS.md` 登记仍未解决、且值得在项目层面持续跟踪的问题。每项至少要让读者辨认问题是什么、影响什么、当前是否仍成立；如果没有状态或边界，它容易退化成重复的愿望清单。

它不等同于设计上明确接受的能力限制，也不等同于未来计划。问题被解决、降级或转交后，应更新条目状态或入口，而不是继续把旧问题呈现为当前事实。

**大标题设想**

- 问题范围
- 问题及影响
- 当前状态
- 关联决定或计划
- 复核条件

### `EXPERIMENTS`（文件或目录）

`EXPERIMENTS` 保存为回答明确问题而安排或实施的检验。定义一项实验时，要能区分计划、实际执行和结果解释：计划不是观察，观察不是结论，结论也不能超出测量条件。

若一个文件只记录待做实验，它是实验计划；若记录已执行的条件和观察，它是实验记录；若记录解释和限制，它是结果分析。这些可以放在同一档案中，但当前状态必须清楚，不能把不同阶段混作一个已证实结论。

**大标题设想**

- 问题与待检验判断
- 条件与方法
- 实际观察
- 限制与反例
- 解释与后续

### `dialogue/`

`dialogue/` 保存讨论过程，使读者能追溯某个决定或定义是如何形成、修改或撤回的。它保留当时的理由、分歧和上下文，不负责把所有过程文本变成当前执行规则。

它与 DECISIONS.md / ADR/ 的区别在于：dialogue 保留完整推演过程，决策记录提取需要长期引用的结论和选择理由。讨论结束后可以链接决定，但不必逐字复制全部日志。

**大标题设想**

- 讨论背景
- 主要分歧与证据
- 收敛结果
- 未决问题
- 相关决定

## 规则与既往变化

### `SECURITY.md`

`SECURITY.md` 这个名字本身不能唯一确定职责。按本项目候选清单，至少有三种可能的具体文件：

- **漏洞披露页**：告诉外部报告者如何私下提交漏洞、提供哪些信息、项目如何响应。重点是安全报告关系，不是完整产品威胁模型。
- **产品或 Agent 安全说明**：说明使用时的权限、信任边界和风险，帮助使用者判断如何安全操作。它不是漏洞报告入口的替代品。
- **安全开发政策**：规定维护者在设计、实现、评审中持续遵守的安全要求。它属于开发规则，不能与产品风险说明或对外披露流程混成一个模糊定义。

若同一份 SECURITY.md 同时包含这些任务，应分别标出受众和入口；若任务的更新责任不同，则需要分开维护或明确各节的正本关系。

**大标题设想**

- 适用对象与范围
- 安全要求或风险边界
- 报告/响应入口（若承担披露任务）
- 维护责任与更新

### `LIMITATIONS.md`

`LIMITATIONS.md` 说明项目当前能力的边界：在哪些条件下不能完成什么、有哪些已知限制、读者不应据此期待什么。它回答“系统做不到什么，以及限制成立的条件”。

它不等于禁止行为清单。禁止某类操作是面向执行者的规则；能力边界是对系统现状或设计范围的说明。若某项限制是主动选择的非目标，应标明这是设计决定，而不是当前技术缺陷。

**大标题设想**

- 限制对象与条件
- 当前不能保证的能力
- 明确不支持的范围
- 已知影响与替代路径
- 复核条件

### `CHANGELOG.md`

`CHANGELOG.md` 按版本或发布批次总结已经发生、对用户或维护者有意义的变化，使读者能判断升级后哪些行为、能力或修复有所不同。它是经过整理的变化摘要，不是每次提交的完整流水。

它不代替当前使用说明，也不等同于未来的 RELEASE 操作规程、内部活动日志或实验记录。若旧版本条目可能影响当前判断，应同时提供当前规则或对应版本入口。

**大标题设想**

- 版本或发布范围
- 新增与变更
- 修复或移除
- 兼容影响
- 关联发布说明

## 当前开放项

上述条目是具体名称对应的候选定义，不意味着这些文件名应全部被采用。尤其 `CONTEXT.md` 与 `GLOSSARY.md`、`README.md` 与 `THISIS.md`/`BRIEF.md`、`DECISIONS.md` 与 `ADR/`，是否值得并存，要看它们能否回答不同问题、由不同条件触发或独立维护；若这些差异不存在，就应合并定义或只保留一个名称。
