# 本文讨论一些除了.md之外的东西
但是依旧是草稿级别，不作为绝对教条，很有可能有幻觉，错误。

# “大规模数据 + 需要条件过滤” 或许可以.csv 而不是.md
如果业务场景**真的只需要二维表格即可胜任**，并且首要诉求是**行级精准过滤**与**防范长度膨胀**，选择的核心逻辑可以进一步拆解：

---

### 一、 为什么依然坚决排除 `.xls` / `.xlsx`？

即使纯表格能解决问题，`.xls`/`.xlsx` 在代码仓库里依然存在不可逾越的工程缺陷：

1. **二进制黑盒，完全破坏 Git 协作**：
* `.xlsx` 实际上是一个被 zip 压缩打包的 XML 集合包，Git 只能将其视为二进制文件（Binary Blob）。
* **无法 Code Review**：在 GitHub/GitLab 提 PR 时，人类看不出这行到底改了什么，只能看到 `Binary file differs`。
* **分支合并（Merge Conflict）必定损坏**：如果两个分支同时增加了一行，Git 无法做文本级合并，强行 merge 会直接导致 Excel 文件损坏打不开。


2. **Agent 读写摩擦成本极高**：
* Agent 读写文本文件只需最基础的系统工具（`read_file`、`cat`、`grep`、`awk`）。
* 读写 Excel 必须依赖 Python 环境和第三方库（如 `openpyxl`、`pandas`），且涉及内存反序列化，执行链条过长且脆弱。



> **结论**：如果需要纯表格，在文本和 Git 的世界里，对应的替代品是 **`.csv` 或 `.tsv**`，而不是 `.xls`。

---

### 二、 那么 `.xml` 和 `.csv`（表格形态）到底能不能用？

**能用，而且在特定场景下比 `.md` 更好。** 但需要看具体侧重点是“机器检索性能”还是“语义推理深度”。

#### 1. `.csv` / `.tsv`：纯表格场景的降维打击方案

如果需要记录的真的只是**结构高度固定的纯表格数据**（如端点映射、状态码清单、组件路由表、纯字段字典）：

```csv
id,type,scope,target,summary
T01,tool,retrieval,src/retrieval/hnsw.py,Milvus HNSW 向量索引策略
R02,rule,database,src/db/,禁止手写裸 SQL 统一走 ORM
R03,rule,frontend,src/ui/,强制使用 Tailwind CSS

```

* **为什么适合条件过滤**：
* **极致的 Token 压缩比**：没有任何多余的标签、括号、对齐空格，信息密度达到纯文本上限。
* **低成本原生过滤**：Agent 不需要把几千行全塞进提示词，可以在终端直接用标准命令行工具做秒级过滤后，只把匹配行带入上下文：
```bash
# 只取出 scope 为 database 的行，直接过滤掉 99% 的干扰
awk -F',' '$3=="database"' registry.csv

```


* **对 Git 极其友好**：纯文本，逐行变更在 PR 中一览无余。



#### 2. `.xml`：大模型注意力机制的“原生硬边界”

在目前的主流 LLM（如 Claude、GPT-4）的系统提示词（System Prompts）与长上下文设计中，XML 标签的使用非常频繁：

```xml
<registry>
  <item id="T01" type="tool" scope="retrieval">
    <target>src/retrieval/hnsw.py</target>
    <summary>Milvus HNSW 向量索引策略</summary>
  </item>
  <item id="R02" type="rule" scope="database">
    <target>src/db/</target>
    <summary>禁止手写裸 SQL 统一走 ORM</summary>
  </item>
</registry>

```

* **为什么用 XML 做过滤有效**：
* **注意力边界清晰（Attention Anchoring）**：LLM 在预训练中见过海量的 XML/HTML 闭合结构。清晰的 `<tag>...</tag>` 能极大减少“幻觉提取”和跨字段信息串味。
* **支持 XPath 语法过滤**：配合命令行工具（如 `xmllint` 或 Python 单行脚本），可以通过标准 XPath 精准抽取节点：
```bash
xmllint --xpath "//item[@scope='database']" registry.xml

```




* **XML 的劣势**：
* **Token 膨胀**：每个字段都要有开闭双标签（`<summary>...</summary>`），同等信息量下，Token 消耗是 CSV 的 2~3 倍。
* **追加不如 CSV 纯粹**：追加新项必须插在根标签 `</registry>` 之前，不如 CSV 或 Markdown 直接在末尾追加干净。



---

### 三、 最终选型决策矩阵

在面对“大规模数据 + 需要条件过滤”时，各格式的真实选型边界：

| 需求特征 | 最佳格式 | 过滤机制 | 为什么选它？ |
| --- | --- | --- | --- |
| **纯粹扁平结构（无多行代码、无复杂富文本说明）** | **`.csv` / `.tsv**` | `grep` / `awk` 命令行预过滤 | Token 消耗最低，人类秒读，Git 完美 Diff，过滤最快 |
| **纯表格但单元格包含换行、复杂嵌套或需要强语义闭合** | **`.xml`** | `xmllint` / XPath 过滤 | 标签强边界隔离，避免换行符破坏表格结构 |
| **包含代码片段、示例、详细设计思考、非结构化规则** | **`.md` (分片架构)** | 文件名索引路由 + 按需单点读取 | 能优雅渲染富文本/代码块，对 LLM 和开发者综合体验最均衡 |

如果仓库里的子项**确实只有 4~5 个固定字段，没有任何复杂的长代码块或富文本**，直接使用 **`.csv`** 配合 `awk/grep` 过滤是比单体大 `.md` 更加高效利落的方案。

# 同名文件夹作为决策记录以及更详细的东西
我选择一个同名文件夹作为决策记录以及更详细的东西，是否可行。
比如
- arichitecture.md 讲本项目架构
- evidence/arichitecture/ 下面讲每个决策

当然，叫evidence/ 还是 record/ 需要思考，因为不止 arichitecture ，其他的markdown也可以这么做


这种“骨干总览文件（Summary File）+ 同名细化文件夹（Companion Directory）”**的设计，在现代 AI 驱动的代码仓库和系统架构中不仅**完全可行，而且是目前工业界解决长文本退化（Context Bloat）与架构记忆沉淀的**顶层最佳实践（Gold Standard）**。

它在传统软件工程中对应著名的 **ADR（Architecture Decision Records，架构决策记录）** 模式，而在 AI 时代，它更演变成了一种“渐进式上下文投喂机制”。

---

### 一、 核心价值：为什么这种结构对 Agent 极其友好？

1. **天然的“两级加载（Two-Tier Retrieval）”机制**：
* **Tier 1（极小上下文）**：Agent 默认只读 `architecture.md`。这保证它随时掌握全局地图、分层规范与设计准则，消耗极低 Token。
* **Tier 2（深潜证据链）**：当 Agent 准备对某个模块动手术，或者在评审代码需要理解“当初为什么不用方案 A 而是方案 B”时，才单点调入对应决策记录。


2. **彻底解决“只增不改（Append-Only）”的痛点**：
* 细化决策以独立小文件存放（如 `0003-milvus-over-pgvector.md`），Agent 做新决策时只需新建文件，永远不会因并发修改单体大文件而产生 Git 冲突或格式损坏。



---

### 二、 目录命名权衡：叫 `evidence/`、`records/` 还是其他？

命名的本质是在给 Agent（以及人类开发者）建立第一反应的**语义暗示（Semantic Prior）**。

| 备选命名 | 语义暗示 | 适合的场景与优缺点 |
| --- | --- | --- |
| **`records/`**<br>

<br>(如 `records/architecture/`) | **中立、客观、时序留痕**<br>

<br>“这里记录了过往发生的事情与决议” | **通用性最强（强烈推荐）**。<br>

<br>不仅能放架构决议（ADR），还能装性能基准记录（`benchmark/`）、技术选型对比、故障复盘。语义覆盖面极广。 |
| **`decisions/`**<br>

<br>(如 `decisions/architecture/`) | **行动、意图、权威裁定**<br>

<br>“这里规定了最终敲定的设计” | **架构场景首选**。<br>

<br>软件行业标准（如 ThoughtWorks 的 ADR 规范）。Agent 一看 `decisions/` 就知道这里包含的是不可违背的“硬性裁定”。 |
| **`evidence/`**<br>

<br>(如 `evidence/architecture/`) | **证明、证据链、支撑材料**<br>

<br>“这里是证明主文档观点的论据” | **语义稍显偏狭**。<br>

<br>在法律、科学实验或合规场景很准，但在普通工程中，它听起来像“测试日志/压测截图/跑分数据”，容易让 Agent 误以为里面存放的是辅助附件，而非“决策逻辑”。 |
| **`history/` / `archive/**` | **过去、过时、归档** | **不推荐**。<br>

<br>容易让 Agent 误以为这是“已废弃（deprecated）”的历史垃圾代码，从而在检索时直接忽略掉。 |

#### 命名建议方案

1. **如果你希望高度通用（涵盖架构、业务规则、API 演进）**：采用 **`records/`**。
* `records/architecture/`
* `records/api-design/`
* `records/benchmarks/`


2. **如果你记录的核心内容是“为什么做这个选择（Trade-offs）”**：直接采用行业标准的 **`decisions/`**（即 ADR 模式）。

---

### 三、 推荐落地的目录组织与链接规范

为了让 Agent 在读完总览文件后，能够精准定位到底层记录，建议在文件间建立**单向/双向索引挂载**：

#### 1. 目录结构示例

```text
docs/
├── architecture.md                     <-- 骨干总览（讲当下系统是怎么样的）
├── records/                            <-- 细化记录总目录
│   └── architecture/                   <-- 同名伴随目录
│       ├── 0001-use-event-driven-bus.md
│       ├── 0002-milvus-indexing-strategy.md
│       └── 0003-session-compression.md

```

#### 2. 主文件 `architecture.md` 中的挂载示范

不要把决策论证细节塞在主文档里，主文档只留一句话 + 相对路径超链接：

```markdown
# System Architecture

## 3. Storage & Retrieval Layer
- 向量存储选用 Milvus，采用 HNSW 索引以保证低延迟。
  > 详细选型论证与压测对比参见：[Decision 0002: Milvus Indexing Strategy](records/architecture/0002-milvus-indexing-strategy.md)
- 状态缓存采用 Redis Memory Store。
  > 决策记录：[Decision 0003: Session Compression](records/architecture/0003-session-compression.md)

```

#### 3. 伴随记录文件的标准格式（ADR 极简模板）

给 Agent 新建决策时一个标准的 Prompt 骨架，保持单一职责：

```markdown
# 0002: Milvus Indexing Strategy

- **Status**: Accepted
- **Date**: 2026-09-22
- **Author/Agent**: @developer

## Context (背景与问题)
检索并发量上升至 500 QPS，原有 FLAT 暴力检索出现严重延迟瓶颈。

## Decision (最终决策)
全量切换为 HNSW 索引，`M=16`, `efConstruction=200`。

## Consequences & Trade-offs (代价与影响)
- 优势：P99 延迟降低 80%。
- 代价：内存开销上涨约 1.2 倍。

```

---

### 四、 避坑指南

1. **主文档必须代表“当前生效状态（Current State of Truth）”**：
* 很多团队犯的错误是：做了新决定只写进 `records/`，结果 `architecture.md` 永远过时。
* **铁律**：每一次在 `records/` 追加了重大决策，必须同步用一句话更新 `architecture.md` 的当前描述。


2. **编号使用固定前缀（如 `0001-`）**：
* 方便文件排序，且 Agent 用 `ls` 或列目录工具时，能一眼看出决策的时序流。
