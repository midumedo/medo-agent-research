## 1. 这份研究的说服力集中在两个来源上，而它们都不是权威来源

**观察。** 主研究稿 21 个来源中，只有 3 个属于官方层级：`agents.md`（标准站）、`docs.devin.ai`、`docs.cline.bot`。剩下 18 个里，2 个是 arXiv 论文的二手转述，16 个是商业厂商指南、社区博客与内容聚合页。其中 augmentcode 一家承担了第 2.2、4.1、4.3、5.1 节的关键论断；digitalapplied 一家承担了第 6.1 节整张工具矩阵，以及第 4.1 节表 3 中四行里三行的限制数字（第四行 Codex 另有神马来源）。

**推断。** 这不是「21 个来源交叉验证」的证据结构，而是「3 个官方来源 + 2 个单点支柱 + 16 个同层级回响」。16 个博客之间高度可能互相转引，按 [CONVENTIONS](../../../../CONVENTIONS.md)「重复转引同一来源不算独立证据」，它们的合计数不能当作独立来源数。因此主研究稿里凡是只由 augmentcode 或 digitalapplied 支撑的数字，实际证据强度是**单一商业来源**，而不是「多家一致」。

具体受影响且优先级最高的四条：`100-200 行` 建议阈值、`缓存读取便宜 90%`、`8 个实验设置中 5 个成功率下降`、`Antigravity 12,000 字符`。

**待验证。** 四条逐一回原始出处核：行数阈值找 augmentcode 是否给了依据还是纯经验；90% 缓存差价应与各模型厂商官方定价页对照（这是可查的公开数字，不需要转述）；「5/8 设置」与「12,000 字符」分别找 Gloaguen 原文与 Antigravity 官方文档。

**反例／削弱。** 商业指南不是必然错。augmentcode 与 digitalapplied 都在这条赛道上有实际产品，其经验可能来自真实客户仓库。问题不在于可能错，而在于**无法核对**：它们没有给出测量方法、样本或日期，读者既不能验证也不能证伪。

## 2. 「ETH Zurich 的研究」在本轮资料里无法定位到任何论文

**观察。** 第 2.2 节的「非可推断细节」（Non-Inferable Details）判据、以及第 5.1 节四类失效模式中的三类，在主研究稿里都标为「ETH Zurich 的研究明确指出」，来源标记指向 augmentcode。本轮资料中没有出现该研究的标题、作者、年份或 arXiv 编号。

**推断。** 这条判据是全篇最有解释力的一条——「代理的先验来自训练数据，凡是通行做法的内容它本来就会做对」这个推理链条能把表 2 两列统一起来，也能解释第 4.2 节自动生成文件为何是负收益。但它的证据地位目前只是**一家商业指南转述的、无法定位的研究**。它可能是真实论文，也可能是 augmentcode 对自己经验的学术化包装，或是对另一项研究的错误归属。

**待验证。** 三条路径：① 在 arXiv 与 Google Scholar 检索 "non-inferable details" + AGENTS.md；② 直接读 augmentcode 原文看是否给了脚注；③ 检索 ETH Zurich 近两年关于 agentic coding / repository context 的产出。三者任一命中即可把它从「转述」升级为可引用来源。

**为什么这条重要。** 如果它成立，「非可推断细节」应该成为 `repo-context` 全阶段的判据，而不只是 AGENTS.md 的写法建议——它同样适用于 README、ARCHITECTURE、CONVENTIONS 的内容取舍：一份文档的价值 = 读者（人或代理）无法从其他途径获得的增量。这比 [初步研究计划](../../drafts/初步研究计划.md) 里的时态／层级／实体三维分类更靠近「为什么要有这份文档」这一层。

## 3. 指令文件是软约束，能被机器拦截的规则不该写进来

**观察。** 两处事实并置：其一，完整优先级链的第一级是「用户在聊天中的显式指令，覆盖一切」；其二，知识升级流程里有一条排除规则——能由 lint、CI 或 hooks 拦截的规则不要进 AGENTS.md。第 5.1 节的静默丢失还说明，即便没有用户推翻，长上下文中间位置的具体约束也会被忽略（保留架构决策、丢弃具体约束）。

**推断。** 这两条合起来给出一个明确的分层判据：**AGENTS.md 的可靠性上限由代理的注意力决定，而不是由文件的存在决定**。因此按「约束失败的代价」分层：

- 代价不可接受（安全、数据损坏、越界写入）→ 落到 CI、hooks、权限配置、沙箱，用机器强制。
- 代价可接受且可自动检查（格式、命名、导入顺序）→ 落到 lint／formatter。
- 无法机器检查、只能靠理解与判断（架构意图、反直觉决策、为什么这样做）→ 才落到 AGENTS.md。

按这个分层，主研究稿表 1 里的「代码风格与约定」段落是**可疑的**：命名规范、缩进、导入顺序全部可被 linter 拦截，按排除规则不该占指令文件的位置。它之所以还在各家推荐段落里，可能因为这些团队的 lint 覆盖不全，指令文件在补位——但那是工具缺口，不是指令文件的职责。

**反例／削弱。** 有两类风格约定确实无法被 lint 表达：跨文件的架构性约定（如「API 客户端不抛异常」）和意图性约定（如「这个模块故意不用异步」）。前者属架构决策而非风格，后者 lint 无法判断。所以正确的结论不是「删掉风格段落」，而是「风格段落里只留 lint 表达不了的那部分」。

**对本项目的意义。** 本项目 [AGENTS.md](../../../../AGENTS.md) 目前几乎全是第三类（按任务读取哪份文档、区分来源／观测／推断、破坏式重构的许可范围），没有可被机器拦截的内容——这与判据一致。但「普通审阅默认不改文件」这条是行为约束，无法机器检查，只能靠注意力，因此它属于长会话中最容易被丢弃的那一类。是否需要在子树 AGENTS.md 里重复它，是一个真实的取舍（重复提高遵循率，但违反第 4 条的反膨胀原则）。

## 4. 位置策略与截断策略指向同一批内容，这是本轮最实用的一条

**观察。** 三个独立事实：① 长上下文中代理可能忽略中间位置的指令，对策是关键规则放文件开头；② Codex 合并后超过 32 KiB 时**按加载顺序从末尾截断**；③ 合并是把全局层、根目录、各级子目录依次拼接。

**推断。** 把三条串起来：在 Codex 类工具上，最后加载的（最近、最具体的子目录文件）位于合并结果的末尾，因此**超限时最先被截掉的正是针对性最强的内容**；同时，即使没超限，靠后位置的内容也更容易被注意力衰减忽略。两种机制方向一致，都惩罚「放在后面」和「放在深层」。

这给出一条可执行的写法约束，比「控制在 100-200 行」更硬：**把最不可妥协的约束写在根文件的开头，而不是写在子目录文件里**。子目录文件适合放局部差异（这个目录的测试命令、这个模块的禁区），不适合放全局性硬约束——因为局部文件既在末尾、又离根远、还可能被 override 整个跳过。

**待验证。** ① 截断方向只由 digitalapplied 与神马两个非官方来源给出，必须回 Codex 官方文档或源码核实（本项目 `sources/repos/` 已有 codex checkout，可直接检索 `project_doc_max_bytes` 的实现）。② 「lost in the middle」在指令文件场景下的实际影响幅度未测——它是从长文档检索研究借来的机制名，是否同样适用于「每轮都重新注入的指令」并不确定：如果指令文件每轮都出现在上下文开头的固定位置，它可能根本不在「中间」。

**反例（这条可能整个不成立）。** 表 6 显示不同工具的注入时机差别很大：Cursor 是「应用于模型上下文开头」，Codex 是「每次运行构建一次」，Claude Code 是「会话启动加载」，Copilot／Gemini CLI／Cline 是「每条消息／每条提示」。**每轮都重新注入开头位置的文件，可能天然免疫 lost in the middle**，那么位置策略只对「会话启动加载一次、随上下文增长被推向中间」的工具（Claude Code）成立。这个区分本轮资料没有讨论，是我从表 6 反推的，属推断而非来源所述。

## 5. 与 round-01 在 Claude Code 上的记录冲突，可能是版本演进

**观察。** [research/kimi round-01](../../research/kimi/research/round-01-agents-md.md) 的兼容矩阵记：Claude Code 原生文件是 `CLAUDE.md`，**不读** AGENTS.md（可用 `@AGENTS.md` import 或 symlink 桥接）。本轮资料记：Claude Code 是 `CLAUDE.md` 系列优先，**无 CLAUDE.md 时读 AGENTS.md**，v2.1.277+ 支持，也可配置为同时读取两者。

**推断。** 两条记录方向相反，但都可能是对的——差别在时间点。若 v2.1.277 是分界版本，round-01 记录的是该版本之前的行为，本轮记录的是之后。这属于**标准演进**，不是资料错误。

**待验证。** 查 Claude Code v2.1.277 的发布日期与 changelog。这一步同时能校准 round-01 的时效：它标注为「2026 年中口径」，如果 v2.1.277 早于那个时间，则 round-01 当时就漏了；如果晚于，则 round-01 无误。

**为什么单独记一条。** 这是本轮唯一发现的与既有研究的实质分歧，而按 [domain/AGENTS.md](../../AGENTS.md) 与本项目的纠错要求，分歧要么解决要么显式保留，不能静默选一边。主研究稿采用的是本轮资料的版本，但**没有**因此否定 round-01；两张矩阵并列保留。下游引用 Claude Code 行为时，必须先确认目标版本号。

**附带的时间敏感项。** 本轮资料里有三条产品退役信息：Windsurf 于 2026.6.2 更名 Devin Desktop、Gemini CLI 托管版于 2026.6.18 退役、`.cursorrules` 被 Cursor 标记 legacy。这类信息半衰期以月计，兼容矩阵应带检索日期，超过半年需重测。这也解释了为什么两张矩阵不该合并：合并会丢掉「哪条是什么时候的观察」这一维度。

## 6. 本项目的 AGENTS.md 是导航型而非指令型，缺的是命令段落，不缺约束段落

**观察。** 根 [AGENTS.md](../../../../AGENTS.md) 实测 23 行 / 844 字符 / 1890 UTF-8 字节（2026-10-04，PowerShell 计数）。内容是：项目定位一句话、当前阶段、行动边界四条、按任务读取的导航（指向 CONVENTIONS / STYLE / ARCHITECTURE / TRADEOFFS 及各子树 AGENTS.md）。**没有**构建、测试、Lint、复跑脚本的命令段落。

**推断。** 按本轮判据分项评估：

- **长度**：23 行远低于 100-200 行建议阈值与 32 KiB 上限，无膨胀风险，且短文件更易命中缓存。
- **内容类型**：几乎全部是「非可推断细节」——职责文件分工、各子树的约定入口、「允许破坏式重构、不要管安全门禁」这类项目特有许可，代理无法从目录结构推断。按判据这是高价值内容。
- **结构选择**：导航型（指向别处）而非指令型（内联全部）。这与第 5.2 节的知识升级流程方向一致——把细节留在 Spec／子树文件里，根文件只保留路由。它也部分规避了第 5.1 节的静默丢失：每轮注入的只有 23 行。
- **缺口**：仓库内有可执行脚本（`sources/papers/_scripts/pipeline.py` 补论文、`domain/repo-context/21read-pdf-vs-html/measure_read_cost.py` 复跑测量、`00docslist/_scripts/build_index.py`），但根 AGENTS.md 没有命令段落，各子树 AGENTS.md 也没有。代理要复跑时只能靠猜或全仓检索——这正是「探索性导航」，是 Lulla 研究里 AGENTS.md 应当消除的那部分成本。

**推断的边界。** 本项目是纯文档仓库，代理的主要动作是读写 Markdown，不是编译测试。两篇 arXiv 研究测的都是编码代理在真实代码仓库上的表现，其「减少探索性导航」的收益机制**未必成立**于本项目。所以这个缺口是「按判据推出来的一致性缺口」，不是「实测造成了损失」。

**待验证（需要模型在环，本轮未做）。** 给一个代理布置「补一篇论文入库」或「复跑 PDF/HTML 成本测量」，看它在没有命令段落时要花多少轮才能找到正确脚本与参数。这是本项目 [21read-pdf-vs-html](../../21read-pdf-vs-html/README.md) 已建立的实验范式的直接延伸，但需要隔离设计与预算，本轮没有执行条件。

**若验证成立的最小改动。** 在根 AGENTS.md 增加一个不超过 6 行的「可复跑脚本」段落，只列脚本路径与一句话用途（参数细节留在各脚本所在目录的 README），保持导航型风格。按第 4 条的位置策略，它应放在「按当前任务读取」之后、而不是文件末尾。

**反向自查：本项目是否违反了本轮的其他结论。** 第 5.1 节的规则膨胀（每次犯错加一条、从不删）需要纵向证据才能判断，本轮只有一次快照，无法评估——本项目 Git 历史里有 `AGENTS.md` 的演进记录，可作为后续检查对象。第 5.2 节的「定期审计」本项目尚未建立：没有任何机制检查根文件与六份子树 AGENTS.md（`sources/`、`sources/papers/`、`sources/repos/`、`domain/`、`domain/repo-context/`、`domain/repo-context/01docsclassify/`；`archive/` 下另有三份历史快照不计）之间是否出现重复或矛盾（`grep -rn` 审计动作未执行过）。
