## 1. 标准身份与定位：AGENTS.md 是给代理读的操作手册，不是给人的 README

### 1.1 它由谁托管、约束力有多强

**论点**：AGENTS.md 是 Linux 基金会下属 Agentic AI Foundation 托管的跨工具开放标准，采用纯 Markdown、无 Schema、无必填字段，其约束力来自代理对文本语义的解析而非格式校验。

**写作指导**：先说托管方与标准属性，再说明「无 Schema」带来的直接后果——不能靠校验器兜底，写法本身决定成败；最后点明与 README 的互补关系。

### 1.2 定位差异：README 给人看，AGENTS.md 给代理看

**论点**：AGENTS.md 与 README.md 是互补关系而非替代关系，README 承担项目介绍与快速上手，AGENTS.md 承担构建命令、反直觉约定与禁忌。

**写作指导**：用对照方式说明两份文件各自回答什么问题，并明确 README 不参与指令覆盖链。

## 2. 内容结构：只写代理推断不出来的东西

### 2.1 六个高信噪比段落

**论点**：官方规范与生产实践收敛出六个基础板块——项目概述、构建与测试命令、代码风格与约定、安全与权限边界、目录约定与禁区、PR 与提交规范，其中构建命令应放在文件靠前位置。

**表格1**：展示六个推荐段落的核心内容要求与编写要点

**写作指导**：先给出整体结构，再用表格逐段落说明内容要求与编写要点，最后强调祈使句与好坏代码对比优于文字描述。

### 2.2 隐形逻辑优先：什么不该写、什么 ROI 最高

**论点**：AGENTS.md 应仅包含「非可推断细节」，通用技术栈描述、标准目录结构说明、与既有文档重复的内容和抽象质量要求都是稀释注意力的噪声；非标准工具选型、反直觉架构决策、版本锁定与已知的坑才有高 ROI。

**表格2**：展示不应写入与应当写入的内容对照及其判定理由

**写作指导**：先立判据（代理能否自行发现），再分列两侧内容，最后落到「地图而非手册」原则。

## 3. 嵌套、覆盖与优先级链

### 3.1 层级加载与就近优先

**论点**：AGENTS.md 支持多层级配置，核心机制是「就近优先」——距离被编辑文件最近的 AGENTS.md 优先级最高；代理按全局层、项目根目录、子目录层级的顺序构建指令链。

**写作指导**：按加载顺序逐级说明四层结构，再解释非冲突配置自动合并、冲突配置由更具体者覆盖的合并规则。

### 3.2 Override 机制与其工具特异性

**论点**：`AGENTS.override.md` 优先级高于同级 `AGENTS.md`，且存在时同级文件被完全跳过而非合并，但它是 OpenAI Codex 特有实现，不属于官方规范的一部分。

**写作指导**：先讲覆盖语义（跳过而非合并）与三类适用场景，再明确其工具边界，避免被当作通用能力引用。

### 3.3 完整优先级链

**论点**：指令优先级从高到低为用户聊天中的显式指令、最近的子目录 AGENTS.md、根目录 AGENTS.md、工具默认配置，README 与其他文档不参与此覆盖链。

**写作指导**：以有序列表呈现四级链条，并补充「用户对话指令覆盖文件内容」这一最高优先级事实的含义。

## 4. 长度控制与 token 成本的实证量化

### 4.1 各工具的长度阈值与硬限制

**论点**：根目录文件建议控制在 100-200 行以内，超过 150-200 行应考虑拆分；各工具的硬限制差异显著，Codex 合并后指令总大小默认上限 32 KiB 且从末尾截断，Antigravity 单文件 12,000 字符，Claude Code 超过 4 MiB 会被跳过。

**表格3**：展示各工具对指令文件的行数建议或字符硬限制

**写作指导**：先给通用建议阈值，再用表格列出各工具的具体限制，区分「建议值」与「硬限制」两类性质不同的数字。

### 4.2 两篇实证研究的成本数据

**论点**：Lulla et al. (2026) 在 10 个仓库、124 个 PR 上测得开发者编写的 AGENTS.md 使运行时间中位数下降 28.64%、输出 Token 中位数下降 16.58%（均 p<0.05）；Gloaguen et al. (2026) 则测得 LLM 生成的上下文文件使任务成功率下降 0.5%-2%、推理成本上升 20%-23%。

**表格4**：展示两篇研究在样本规模、上下文类型、运行时间、输出 Token、推理成本、推理步骤与任务成功率上的对照

**写作指导**：先分列两篇研究的口径与数字，保留原始限定条件，再说明二者为何看似矛盾实则互补。

### 4.3 综合判断：净收益由内容质量决定

**论点**：AGENTS.md 降低的是输出侧消耗（探索性导航与重复请求），增加的是输入侧成本（额外上下文带来的输入 Token 与推理步骤），净收益取决于内容质量；缓存读取比标准输入便宜 90%，是缓解输入侧成本的手段。

**写作指导**：用输入侧/输出侧的分解解释两组数字如何共存，再落到「人工编写为正、自动生成为负」的分野与缓存缓解。

## 5. 失效模式与维护方式

### 5.1 四类失效模式

**论点**：实践中有四类失效模式——自动生成文件的负效应（在 8 个实验设置中的 5 个降低成功率）、规则膨胀与矛盾积累（更多规则并不产生更好表现）、长会话中的静默丢失（保留架构决策但丢弃具体约束）、过时结构描述的误导（增加推理成本并鼓励无效遍历）。

**表格5**：展示四类失效模式的成因与可观测后果

**写作指导**：逐类说明机制与后果，强调「每次犯错就新增规则但从不删除」是主动对抗上下文工程的行为。

### 5.2 维护流程与知识升级判据

**论点**：维护应从观察到的可复现失败中迭代而非预先堆砌，纳入 Git 版本控制并经 Review，用 CI 检查行数防膨胀，并建立「记录现象→判断可复现→验证解决方式→决定进入 Wiki、Skill 还是硬规则」的升级流程；能由 lint/CI/hooks 拦截的规则不应进 AGENTS.md。

**写作指导**：按维护动作的执行顺序组织，突出升级判据与定期审计（重复检查、移除失效约束、验证 Skill 是否真被触发），并说明修改后需开新对话才生效。

## 6. 跨工具兼容差异与桥接策略

### 6.1 没有任何两个工具以完全相同的方式读取 AGENTS.md

**论点**：尽管已有 20+ 工具支持 AGENTS.md，各工具在读取的文件名、嵌套支持、大小限制、每轮发送时机与特殊行为上均存在差异，没有任何两个工具以完全相同的方式读取它。

**表格6**：展示九款工具在读取文件、嵌套支持、大小限制、每轮发送与特殊行为上的对照

**写作指导**：先给「无一致性」这一总判断，再用表格逐工具列出差异，最后点出 Continue 文档未提及支持、Gemini CLI 需配置文件名这类容易踩空的项。

### 6.2 多工具环境下的兼容策略

**论点**：推荐以 AGENTS.md 为唯一事实来源，为 Claude Code 创建一行 `@AGENTS.md` 导入桥接文件或启用回退读取，为 Gemini CLI 配置 `context.fileName`，迁移已标记为 legacy 的 `.cursorrules`，并把需要 glob 作用域或 YAML frontmatter 的工具特定规则分离到各自专属目录。

**写作指导**：按策略清单逐条说明做法与适用条件，强调 AGENTS.md 只保留跨工具通用基线指令。
