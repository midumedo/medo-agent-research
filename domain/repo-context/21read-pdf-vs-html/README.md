# 05 · 读 PDF 与读 HTML，对 AI 哪个更省

同一份文档的两种格式表示，各读取路径在**上下文成本**上的确定性对比。与 [04how-agent-read-file](../04how-agent-read-file/README.md) 相邻：04 查的是 harness 有哪些读工具、怎么实现，这里问的是「同一内容、不同格式、不同模态，哪条读取路径更划算」。

## 为什么用这本书做对照

`sources/books/Agent-Memory-绿皮书.老刘说nlp/` 下有同名的 `.pdf` 与 `.html`，且**两者同源可证**：PDF 的 producer 是 `Skia/PDF m153`（Chrome 打印管线），每页页脚留着 `file:///…/Agent_Memory_绿皮书.html`，两版汉字量比值 0.987。内容相同、表示不同，这是格式对照里最干净的一种——排除了「两本书本来就不一样」这个混淆项。

## 「省」按什么算

分两个模态、四个口径。**模态维是关键**：PDF 可以当图像喂给原生视觉模型，也可以先抽成文本；HTML 可以当文本喂，也可以渲染成截图。成本模型完全不同。

| 模态 | 读取路径 | 计费变量 | 本轮状态 |
| --- | --- | --- | --- |
| 图像 | PDF 逐页渲染 → 视觉 token | 页面面积（与内容量无关） | 已测像素与字节；识别效果未测 |
| 文本 | PDF 抽取 / HTML 去标签 / HTML 结构化 | 字符数（与内容成正比） | 已测 |

C1 体积、C2 结构、C3 噪声由 measure_read_cost.py 一次跑完；C4 理解（模型答对率）未做。结果见 [2026-09-26 报告](results/2026-09-26.md) 与 [同名 JSON](results/2026-09-26.json)。

## 已完成：确定性测量

- **HTML 侧**：原样 → 去样式 → 去标签全文 → DOM 转结构化文本（带 98% 可见文本覆盖率断言，防「靠丢内容变短」）
- **PDF 侧**：文件体积 → PyMuPDF 文本抽取 → 页眉页脚与断行碎片统计 → 字体/字号信号 → 文字 bbox 面积覆盖率 → 逐页渲染的像素、字高与 PNG 体积

主要结论（详见结果报告）：

1. **打平点在 1.37×–1.64× 渲染倍率**（仅 patch 制：Claude / GPT / Gemini）。低于它视觉更省（1× = 29,392 tok），高于它文本更省（2× = 117,568 tok）。而正文只有 8.2 pt，「省」的那一档正是字最小的那一档。**固定预算的光学压缩（DeepSeek-OCR 一类）不适用此结论**——若每页压到 384 vision token，全书仅 16,896 tok，比文本路径省 3.4–4.7×，代价是保真度与"省的是哪一段"的区分。详见 [结果报告](results/2026-09-26.md)「例外：固定预算压缩」一节。
2. **成本模型不同**：图像按页面面积付费，这份文档文字只占页面面积 **20.0%**，另外 80% 的空白与版式照付；文本按字符付费，空白不付。载体体积差 38 倍（6.98 MB 图像 vs 184 KB 文本）。
3. **文本模态内部**：HTML 结构化文本 91,726 字符 vs PDF 抽取 92,530 字符，差 0.9%；HTML 用 +6.8% 的标记税带回 140 个标题、34 张表、271 处代码，PDF 抽取丢结构且不可恢复（610/615 字体是 Type3 子集）。

复跑（换一个未使用的输出前缀以保留原观察）：

```bash
python domain/repo-context/05read-pdf-vs-html/measure_read_cost.py \
  --out domain/repo-context/05read-pdf-vs-html/results/replication-01
```

依赖策略与项目一致（`pyproject.toml` 声明零第三方运行时依赖）：HTML 侧只用标准库 `html.parser`；PDF 侧的标准库无法完成（需解压内容流并处理字体映射），PyMuPDF 是**可选**依赖——缺失时脚本仍产出全部 HTML 侧结果，PDF 侧标 `unavailable` 并给出安装命令，不静默降级。

## 已探针：这条通道没有视觉

曾把 PDF 第 6 页渲染成 1190×1684 PNG 再 `read_file`，返回 `File is binary (.png format). read_file only reads text files.`——**图片不会作为视觉附件进入上下文**。因此本运行时无法实测「原生视觉读 PDF」的识别效果，脚本只测像素与字节，不宣称模型看得准。这是通道限制，不是对任何模型能力的判断。

## 待执行：模型在环的行为比较

下面是设计，不是已完成的实验；没有模型执行条件和预算前不预填结果。

**问题。** 打平点两侧（1× 与 3×）的视觉读取，在真实任务上答对率差多少？结构损失值多少 token？

**实验单位。** 一项任务 × 一种读取路径 × 一次独立尝试。同一持续对话里先喂一种再喂另一种会让历史泄漏答案，必须隔离。

**条件。** A = PDF 视觉 ×1；B = PDF 视觉 ×3；C = HTML 结构化文本；D = PDF 文本抽取。A/C 比模态，B/C 比"看得清"的代价，D/C 比文本模态内的格式差。

**任务取样。** 至少各一：只能靠表格回答的（本书 34 张表）、跨小节关系（140 个标题提供锚点）、代码片段（271 处 `code`）、简单事实负对照。**表格题是判别题**——它同时考验"视觉是否读得清"与"文本抽取是否丢结构"。

**必查项（从前一轮的待验证项升格）**：1× 渲染（8.2 px 字高）能否读准中文正文。若能，视觉路径确实更省；若不能，则视觉省下的 token 要以准确率偿付，打平点结论需按可读阈值上移。

**撤回条件。** 若 B 相对 C 的增益低于 5 倍成本，则对这类小字文本型文档，结论固定为"读 HTML 文本"；若 A 在表格题上与 C 持平且更便宜，则视觉路径应限定为"版式密集文档"的默认选择。若 D 并未劣于 C，则 HTML 的结构优势限定在生成端而非读取端。

## 不做的事

- 不把本目录的字符数或像素数当作任何具体 harness 的账单——token 均为估算，未装 tokenizer。
- 不因「HTML 更省」就建议删除 PDF 原件；PDF 是可打印、可归档的那一份，本实验只关心读取成本。
- 不把结论外推到扫描件 PDF（本书有完整文本层，`pdf_images=0`）。图像型 PDF 只能走视觉或 OCR，成本结构完全不同。
