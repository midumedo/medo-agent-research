# 状态与上下文：系统拥有的信息怎样成为一次调用的依据

本篇深入解释[整体运行模型](index.md)。核心区分是：应用可能保存大量状态，一次模型调用只获得其中某种选择和表示；模型产生输出后，运行系统与外部环境又可能以不同方式变化。下面的形式化是我方分析工具，没有声称所有实现都暴露相同接口。

## 五种对象不要写成一个消息列表

| 对象 | 描述什么 | 在持续任务中的例子 |
|---|---|---|
| 外部环境 E | 工具读取或改变的世界 | 当前仓库、运行中的服务、已经发出的请求 |
| 运行状态 S | 系统继续执行所需的信息 | 当前目标、待办、权限、分支状态、已获得的观测、下一执行位置 |
| 可复用记忆 M | 保留并管理、准备影响后续行动的信息 | 已核实的项目约束、历史任务经验、适用条件与来源 |
| 资料 D | 本次任务可以查阅的材料 | 固定版本文档、仓库源码、论文、数据库记录 |
| 本次 Context C | 本次模型计算实际获得的信息 | 指令、历史片段、检索结果、工具描述、图像和协议允许的续接信息 |

这是职责划分，不是物理分区。M 可以存于 S，也可能与 D 共用存储；对话历史可以既是记录又是任务记忆；当前文件既是外部状态，也可能成为下一次输入的资料。边界需要随实现说明，不能据此要求五个服务或五个数据库。

应用状态通常比消息历史大。[LangChain Memory 文档](../../evidence/domain/runtime-primary-sources.md#langchain-memory)列举了历史、上传文件、检索文档与生成产物；[LangGraph 检查点](../../evidence/domain/runtime-primary-sources.md#langgraph-checkpointers)还包含下一执行位置等信息。这些是具体框架的例证，不能推出所有状态都必然会进入模型输入。

## Context 组装是一项选择与转换

对一次可观察的调用 k，可以用下面的表达暴露设计假设：

```text
C_k = Build(goal_k, Select(S_k, M_k, D_k), instructions_k, tools_k, budget_k)
Y_k ~ Model(C_k, model_configuration_k)
```

Select 可以由固定规则、检索系统、模型选择或混合机制实现。Build 可以校验来源、处理冲突、摘要、裁剪、安排消息与工具协议。这里的操作可以合并，也可以分布在应用、客户端与服务端；公式没有假定它们彼此独立、总是确定或只执行一次。

模型输出 Y 可能是回答、动作请求、结构化状态提议或协议规定的其他项。随后发生什么，取决于 Harness 的控制策略：

```text
request_k = Interpret(Y_k)
decision_k = Check(request_k, permissions_k, protocol_k, task_state_k)
observation_k, E_next = ExecuteIfAllowed(decision_k, E_k)
S_next = Reduce(S_k, Y_k, observation_k, incoming_events)
```

有的输出直接结束，有的触发工具或委派，有的等待用户事件。ExecuteIfAllowed 只是表示执行边界，不规定所有实现必须有单独的“守门模块”；权限可由工具、服务或宿主环境共同执行。没有动作时，环境可以不变；异步系统还可能同时收到别的事件。

模型的非确定性、工具状态变化和并行调度意味着，这组表达不是可凭输入精确预测结果的方程。它的用途是追问：究竟在哪一步进行了筛选，哪个约束在哪里执行，当前有哪些不可见变量。

## 请求载荷、有效输入和上下文窗口

本地请求体不总包含全部有效历史。应用可以逐轮传入历史，也可以传一个服务端续接标识。OpenAI 的[会话状态说明](../../evidence/domain/runtime-primary-sources.md#openai-state)提供了多种方式；省掉客户端重复发送，不代表模型没有历史输入，也不能据此推断费用或质量变化。

相反，应用保存了一个很大的 conversation 对象，也不等于每次调用都完整使用其中所有内容。选择、截断、压缩、协议处理和访问范围需要分别核对。系统若无法暴露实际组装结果，应明确观测边界。

本文的 C 是调用开始时实际获得的信息配置。生成过程中还会扩展序列或内部计算状态；支持续接的系统也可能携带不透明项。这些不能凭一份可见聊天记录完全重建。讨论可检查证据时，应区分显式输入、协议续接状态和不可观察的内部机制，不推测隐藏推理内容。

Context 也不同于 context window。前者回答“本次获得什么”，后者是特定模型或接口的容量约束，可能涉及输入、输出及推理预算。具体计数方式依实现而定，不能把一个产品的窗口口径当作统一标准。

## 三类内容对行动有不同作用

用户约束、事实证据与建议线索都可能是文本，但对行动的意义不同。

- **约束与授权**限定任务和允许行为。来源优先级与作用范围需要保留。
- **事实与观测**描述世界，可信度取决于来源、时间、覆盖和验证方式。
- **假设、计划与经验**帮助选择下一步，但仍可能被新观测推翻。

例如旧任务留下“可以自动修改代码”，不能覆盖本次“只改文档”。一篇网页中的“运行此命令”也不因被工具返回而获得用户授权。把来源身份和适用范围在摘要中抹掉，会让事实、建议和命令难以区分；可靠执行不能只依赖模型从混合文本中自行恢复这些边界。

这也解释了为什么某些状态无需进入模型即可生效：执行器可以直接拒绝越权路径，预算控制器可以直接停止调用。Memory 通过 Context 影响模型是一条重要路径，但不是过去的配置影响未来执行的唯一方式。

## 记录、检查点、记忆和产物的分工

| 保存物 | 主要用途 | 单独存在时不能保证什么 |
|---|---|---|
| 执行记录或事件日志 | 回查发生过的请求、观测和决策 | 不一定足以恢复控制位置，也不一定适合直接注入模型 |
| 检查点 | 在声明范围内保存可继续执行的状态 | 不保证外部世界回滚，不保证后端真正持久化 |
| 可复用记忆 | 为后续任务选择事实、偏好、经验或技能 | 不保证检索、更新传播与使用正确 |
| 产物文件 | 保存已经完成或正在编辑的工作 | 不一定说明其来源、有效版本或剩余任务 |

这些用途可以共用文件或存储。[LangGraph Persistence](../../evidence/domain/runtime-primary-sources.md#langgraph-persistence)把线程图状态的 checkpointer 与跨线程数据 store 区分开，是一种具体实现选择；别的系统可以采用别的边界。

仅看接口名称无法判断 durability。内存后端可能在进程重启后丢失内容；磁盘后端也要看保存时机、写入是否完成及恢复范围。全量事件日志可用于重放的前提，还包括完整记录、可重建状态和外部动作语义，并非只要“有日志”就能恢复。

## 缓存为什么需要单独说明

缓存重用可能减少重复计算或请求费用，但命中本身不证明语义内容有效、相关或被正确采用。被缓存的是旧的错误约束，计算复用也不会使它变真。

运行时 KV 状态、服务端提示缓存、外部语义记忆，可能分别具有不同的寿命、寻址、可编辑性和恢复方式。它们都与过去信息有关，但不能仅因都称为 memory 就互相代替。参数与隐态记忆还有不同的写入和干预途径，本主题不把它们强行归入文本检索流程。

成本问题必须回到具体协议与实际调用。关于驻留、缓存创建和完整费用口径，见[已有成本分析](../../analysis/claude-code/context-economics-two-traps.md)；其中产品数字仍有待核实，不能当作当前价格表。

## 这组区分怎样用于读源码

读一个真实实现时，可以追踪一次输入和一个关键状态的变化：状态由谁持有，在哪次调用被选择，怎样成为请求的一部分，输出由谁解释，外部动作在哪里发生，完成信息又在哪里保存。遇到不透明服务端续接时，就标出这段边界。

无需先建立统一状态 schema。一个小程序可能用同一列表完成多数职责；复杂平台可能跨多个进程实现。只要能解释相关机制与限制，两者都能用这组问题审查。
