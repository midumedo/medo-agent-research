# 记忆的形成、更新与再次生效

本篇连接[整体运行模型](index.md)中的状态更新与未来使用。讨论重点是运行时可观察、可管理的外部记忆，不要求所有系统采用一个集中 Memory 服务。

## 从经历到记忆，中间有选择

系统读到资料、执行操作或收到用户更正后，会获得新的观测。把这些观测保存在日志中是一种记录；从中抽出适用于未来的事实、约束、经验或技能，则还发生了判断与表示转换。

例如一次工具调用失败，至少可能是临时网络故障、参数错误、权限不足或接口已变。若直接形成“这个工具不能用”的长期记忆，就把未诊断的事件推广成了规则。记忆形成应保留足够的来源与条件，使未来能够区分一次事件、重复模式和已验证做法。

本地论文对[情景、任务内状态与程序性记忆](../../evidence/domain/reviewed-local-passages.md)有不同范围的描述；本文采用这些区分帮助思考，不把一个 taxonomy 规定为唯一目录。

## 读、写和维护并不按单一时间表进行

下面是一组可以组合、循环或跳过的职责：

```text
观测或修正 → 候选内容 → 选择并形成表示 → 保存与建立访问入口
                                        ↕
下一次需求 ← 正确使用 ← 进入本次输入 ← 定位、读取与校验
                                        ↕
                         更正、冲突处理、失效、删除或重建
```

一次检索可以发现冲突并触发更新，保存过程可以拒绝候选，新的任务也可能直接读取原始记录而跳过事先提取。操作存在不等于每次必须执行，执行顺序取决于任务和实现。

“谁选择、谁批准、谁执行”是控制问题，可以分配给用户、模型、固定程序和后台服务的不同组合。[综述中的 control policy](../../evidence/domain/reviewed-local-passages.md#control-policy)已经讨论启发式、模型自控和学习控制，不能把这些视角据为本项目原创。

## 写入时机同时影响延迟和可见性

| 时机 | 为什么采用 | 需要面对的代价 |
|---|---|---|
| 当前调用或步骤的关键路径 | 让明确更正尽快影响下一次行动 | 增加本次工作与延迟；写错也会很快传播 |
| 任务收束时整理 | 获得更完整的事件与结果再判断复用价值 | 中途失败可能来不及整理，后续任务可能提前开始 |
| 后台异步形成与维护 | 把昂贵提取或整理移出当前响应路径 | 可见性延迟、资源竞争、任务触发与失败重试 |
| 后续读取时再解释 | 对未来未知用途保留原始材料 | 把分析成本和歧义处理推迟到使用时 |

[LangChain Memory 文档](../../evidence/domain/runtime-primary-sources.md#langchain-memory)明确讨论主路径与后台写入。它是实现例证，不能推出所有系统都应该异步，也不能把“移出关键路径”说成没有整体成本。

是否等待写入完成，要看下一次行动是否依赖这次更新。如果用户刚刚修正目标版本，下一步可能需要先让当前任务状态和输入采用新版本；后台长期记忆整理尚未完成，并不必然阻止当前任务正确继续。反之，若其他任务马上读取共享状态，就需要明确其看到哪个版本。

## 读取是一项任务相关的选择

检索命中回答“找到了什么”，不直接回答“本次应该相信和使用什么”。需要考虑相关性、来源身份、权限、时间、版本、适用任务和当前指令。检索排名靠前的旧事实，不能自然覆盖用户最新的明确更正。

也不要假定每次都先检索。系统可能预取常用背景，模型遇到缺口后再查询，或者直接读取一个已知路径。[Anthropic 的按需读取描述](../../evidence/domain/runtime-primary-sources.md#anthropic-context)说明了这类混合方式。指针使材料有机会被找到，但要有正确定位、访问权限、可用内容和触发读取的机制。

拿到材料之后，还可能需要重新构造关系。一个任务需要精确字段，另一个任务需要多个事件的先后因果；相同 top-k 结果不一定同样充分。长期保存原文、保留关系摘要和查询时综合，是不同成本与失效风险之间的组合，详见[留存分析](../../analysis/context-retention.md)。

## 更正要处理当前采用值及其派生关系

假设原记录说接口属于版本 A，随后获得可信修正：当前任务目标是 B。可能受影响的对象包括原始断言、提取的事实、摘要、检索索引、当前计划、已经分派的子任务和后续产物。

并非每次都需要维护完整依赖图。数据量小、重建便宜时，覆盖当前值并重建相关表示可能更简单；变化频繁、部分失效代价高时，明确来源与依赖可能更有价值。关键在于更新能否传播到真正使用信息的地方，而不在于是否存在一个叫“治理”的模块。

以下情形应分开：

- **新事实替代旧事实**：旧事实可能仍应保留历史位置，但不再作为当前采用值。
- **范围不同而同时成立**：版本 A 与 B 的接口差异未必构成冲突，可能需要按版本选择。
- **来源真正冲突**：需要检查出处、权限、时间或进一步核实，不能机械采用最后写入者。
- **暂时不能确定**：保留不确定与待查入口，比压成一个自信结论更忠实。

这些是设计判断，不是已验证的普适冲突算法。对具体实现，应记录哪些条件能使旧值继续被检索、注入或执行，并用实际路径解释。

## 删除、失效与不再注入有不同边界

从本次 Context 移走一段内容，并不等于删除持久记录；查询时过滤，也不等于摘要和产物中没有该信息。反过来，保留历史审计记录也不应使其自动重新成为有效知识。

删除或失效需要先确定目标：停止当前使用、停止未来检索、移除某项派生表示，还是在声明范围内删除持久副本。索引、摘要、后台任务和恢复路径都可能重新带回旧内容。系统必须说明实际完成的边界，不能由一个成功响应概括全部副本。

这不是要求所有任务都实现最复杂的全链路删除。只保存一个小文件的系统与跨多个索引的平台，需要处理的范围不同；比较时应给它们相同的目标语义。

## 从经验到技能还需要可用性与验证

事实记忆主要帮助判断世界，经验或技能还可能改变行动方式。将一次操作过程保存为指令、脚本或工具入口，只完成了某种表示和可调用性安排；适用条件、运行权限、结果检查与失效机制仍需说明。

[本地技能记忆段落](../../evidence/domain/reviewed-local-passages.md#procedural-memory)包含可调用、结果可验证及组合等讨论。它不能证明每次成功轨迹都值得沉淀成技能，也不能把文件存在当作后续调用正确的证据。

回到持续任务例子：某次迁移成功使用了一条脚本，后续应保留的可能是适用版本、输入条件、验证方法与脚本位置。若这些条件变了，重新运行同一脚本可能产生错误；复用的价值与核查成本需要一起看。

## 当前可形成的条件判断

信息很短且下一步频繁使用时，直接保留可能足够；材料很大但原文稳定可寻回时，按需读取值得比较；跨材料关系反复使用时，忠实摘要可能减少重复推理；高频修正时，多份派生表示需要额外关注一致性；任务间差异很大时，过早固化经验可能比保留出处更危险。

这些判断由机制和构造案例支持，仍需具体任务验证，不能据此宣布某种存储或策略普遍最佳。如何定位失败与设计对照，见 [失效定位](failure-modes.md)和[研究议程](../../analysis/research-agenda.md)。
