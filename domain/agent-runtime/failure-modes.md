# 从错误行动反查失效位置

“Agent 忘了”往往只是结果描述。[整体运行模型](index.md)把从信息产生到实际行动的路径拆开，是为了定位失败发生在哪里，并避免把所有问题都归结为更大的记忆库或更长的上下文。

下面是诊断性的构造案例与工程推断，没有报告实验结果。

## 一条信息没有起作用，可能坏在哪里

| 观察到的结果 | 可疑环节 | 应进一步检查的证据 |
|---|---|---|
| 后续完全找不到早期约束 | 保存、覆盖、失效或权限 | 原始输入、写入结果、状态版本、访问范围 |
| 原文存在，但从未被读取 | 查询触发、定位或检索 | 查询条件、候选结果、路径有效性、是否有补读信号 |
| 检索结果正确，模型仍没采用 | 组装遗漏、裁剪、冲突、表示或能力 | 真正送入本次调用的内容、顺序和来源边界 |
| 新值已保存，旧结论继续出现 | 派生摘要、索引、分支或后台更新 | 被使用的具体版本、传播时机与仍在运行的旧任务 |
| 模型提出了正确操作，但事情没完成 | 执行、权限、工具或结果解释 | 动作请求、外部响应、实际环境状态与失败信息 |
| 恢复后重复产生外部效果 | 检查点与外部动作语义不一致 | 恢复位置、操作标识、幂等范围、环境当前状态 |
| 主任务不知道子任务已发现的信息 | 回传、局部隔离或合并 | 子任务实际输入、返回物、未回传材料及主任务接收状态 |
| 输入变短，任务却更贵 | 工作量转移或返工 | 摘要、检索、委派、恢复、重试的全部调用和延迟 |

这张表不把一个症状绑定到唯一原因。例如重复询问既可能是没有获得信息，也可能是来源冲突、工具故障或主动核实。诊断应沿可观察轨迹缩小范围。

## 最小证据链应该连到实际结果

为了解释一次失败，通常需要连接任务目标与约束、实际采用的状态版本、调用输入、动作请求、工具观测、后续状态与任务结果。并非所有产品都暴露这些接口；看不到时应保留未定位区间，不能把日志没有记录当作机制没有发生。

原始输出可能很大或包含访问受限信息，记录范围应与任务相称。诊断目的在于让关键因果关系可回查，不等于无差别保存所有内容。无需记录或推断模型不可见的内部思考过程。

工具“成功”与任务“成功”应分别记录。写入完成可能写到了错误文件；测试通过也可能只覆盖部分条件；模型生成的完成声明可能遗漏尚未执行的检查。

## 区分信息策略与任务能力

比较留存或检索策略时，可以增加一个**诊断用的充分证据对照**：由任务设计者把完成任务所需的短而充分的正确材料直接放进输入。

如果这个条件仍失败，应检查任务本身、模型能力、工具和判分，不继续假定增加检索组件就能解决。如果它成功而某种记忆策略失败，再追查信息选择、表示、恢复和使用。但这个差异只能缩小可疑范围，不能单独证明哪一个组件造成了失败。

诊断条件包含了现实策略可能不知道的必要信息，所以不能把它放进正常策略成本排名，也不能把答案透露给待测方案。[研究议程](../../analysis/research-agenda.md#retention)保留了这个边界。

## 让不同策略面对可解释的比较

完整历史、摘要、按需检索与混合方案，本来就改变可见输入和总工作量。若同时固定这些结果变量，会消掉正在研究的机制。应保持原始信息供给、任务目标、模型及比较口径可解释，再分别观察：

- 同等质量要求下，全部调用与维护工作需要多少费用和时间。
- 固定可用资源下，任务完成、关键约束与失败恢复如何变化。

构建索引、生成摘要、子 Agent、失败重试和后续恢复均可能是策略的一部分，不能只比较主调用的输入长度。缓存命中、计费口径与实际质量也要分开。

[本地评测协议摘录](../../evidence/domain/reviewed-local-passages.md#evaluation-protocol)说明一篇论文报告过预算等条件对排名的影响。这里引用的是作者报告，不是本项目复现；它支持认真描述协议，不支持宣称所有评测没有价值。

## 用事件变化检验整个流程

在一个可检查的小任务中，可以逐渐加入以下变化。每次尽量只改变能够解释的一项条件：

| 变化 | 想观察什么 | 不能越界声称什么 |
|---|---|---|
| 原文保留或不可访问 | 摘要遗漏之后是否有恢复机会 | 一次恢复成功不能证明长期稳定可恢复 |
| 用户明确修正一个关键值 | 当前状态、派生表示和后续输入是否采用新值 | 当前任务通过不能证明所有跨任务更新正确 |
| 旧文档给出相反指令 | 来源与权限是否被保持 | 提示中写了安全原则不等于执行器真的限制动作 |
| 动作完成后、记录前中断 | 恢复是否识别已发生的效果 | 一个幂等文件写入不能代表所有外部操作 |
| 子任务开始后修改目标 | 分支是否收到更新、旧结果怎样处理 | 主任务知道新目标不代表全部分支同步 |
| 删除一项已被摘要的信息 | 当前读取、派生表示与恢复路径的边界 | 一个删除接口返回成功不等于所有副本清除 |

这些是可执行的研究设计方向，不是已完成的测试。若简单方案已经可靠，应报告其适用范围；负结果或无法区分也可以结束一次研究，不为得到预设结论不断追加复杂机制。

## 这个主题尚未回答什么

我们仍缺少完整对象的固定版本执行映射、真实失败轨迹和成对行为结果。官方文档有助于认识职责和语义，不能代替实现核验；逻辑反例有助于限制全称断言，不能估计生产任务中的发生率。

后续对象研究应优先让这些连接变得可定位：目标更正怎样传到输入，工具结果怎样改变状态，恢复位置怎样对应外部效果。新实现若呈现不同路径，修改模型，比给它强行套同一张流程图更有价值。
