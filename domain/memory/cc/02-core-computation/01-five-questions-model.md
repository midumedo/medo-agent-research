# Token-level Memory 的五问题模型

## 引言

从第一性原理推导,Memory 系统的本质是**在有限预算下的上下文组装决策**。Token-level Memory 作为最广泛使用的 Memory substrate,其核心计算可以分解为五个独立的子问题,每个问题都有独立的设计空间。

这个模型的核心洞察:**Token-level 记忆项目的核心是理解整个转换流程,而不是把注意力放在它怎么分类**。分类只是 Q1(写入管道)的辅助决策工具,真正决定系统行为的是这五个问题的设计选择组合。

---

## Q1: 写入管道 (Write Pipeline)

### 核心问题

交互流 → 怎么变成可存储的单元?

### 设计空间

#### 1.1 触发时机

**何时启动写入流程?**

- **每轮触发**:每次对话结束后立即处理
  - 优点:实时性强,不丢失信息
  - 缺点:处理频繁,成本高
  - 适用:高价值交互,需要精确记录的场景

- **事件驱动**:特定事件(用户明确表达偏好、任务完成、关键决策)触发
  - 优点:针对性强,只记录重要信息
  - 缺点:需要准确的事件检测机制
  - 适用:可定义明确事件的结构化场景

- **容量驱动**:累积到一定 token 数后批量处理
  - 优点:摊销处理成本,减少 LLM 调用
  - 缺点:延迟较高,可能丢失中间状态
  - 适用:成本敏感的应用

- **定时处理**:固定时间间隔(每小时、每天)批处理
  - 优点:可预测的成本,支持离线优化
  - 缺点:实时性最差
  - 适用:非实时场景,如每日总结

#### 1.2 处理范围

**处理哪些内容?**

- **全量对话**:完整的 user + assistant 交互
- **assistant 输出**:只记录 agent 的回复
- **显式标记**:只处理用户/系统明确标记为"需要记住"的内容
- **特定模式**:只提取特定类型(事实、偏好、任务)

#### 1.3 处理算子

**如何从原始交互中提取记忆?**

- **LLM 抽取**:用 prompt 让 LLM 抽取结构化信息
  - 灵活度高,可处理复杂语义
  - 成本高,延迟大
  - 典型实现:Mem0, MemGPT

- **LLM 摘要**:用 LLM 生成简化版本
  - 信息压缩,保留要旨
  - 可能丢失细节,摘要质量不稳定
  - 典型实现:大部分对话式记忆系统

- **规则提取**:正则表达式、NER 等固定规则
  - 成本低,可控性强
  - 只能处理结构化/半结构化内容
  - 适用:明确格式的信息(联系方式、日期、专有名词)

- **图谱构建**:实体-关系提取,构建知识图谱
  - 支持复杂查询,保留语义结构
  - 构建成本高,需要实体消歧
  - 典型实现:HippoRAG, Zep, A-MEM

- **混合流水线**:组合多种算子
  - 例:规则提取 + LLM 验证
  - 平衡成本与质量

#### 1.4 压缩深度

**处理到什么程度?** (见"处理深度连续谱"专题)

- **近原文**:轻度清理,保留几乎所有细节
- **事实单元**:抽取独立事实,丢弃冗余表述
- **抽象概念**:泛化为更高层级的模式
- **可执行形式**:编译为代码/workflow

选择由下游需求决定,不是理论上的"级别"。

#### 1.5 元信息标注

**记忆单元附加什么元数据?**

- **时间戳**:创建时间、最后访问时间、过期时间
- **来源**:会话 ID、用户 ID、触发事件
- **重要性评分**:预估未来访问概率
- **语义标签**:类型、主题、实体
- **provenance**:从哪条原始交互派生
- **置信度**:抽取/推理的可靠程度

## Q2: 存储组织 (Storage Organization)

### 核心问题

单元之间怎么组织,让后续检索高效?

### 设计空间

#### 2.1 存储结构

**记忆单元如何组织?**

- **扁平列表**:所有记忆平铺,无显式层级
  - 简单,易实现
  - 检索时需全局扫描
  - 适用:小规模(<1000条)

- **分层存储**:按类型/主题/时间分层
  - 检索可剪枝,效率高
  - 需要维护层级关系
  - 典型:MemGPT 的多层架构

- **图结构**:记忆单元间显式建模关系
  - 支持关联查询、路径推理
  - 构建与维护成本高
  - 典型:HippoRAG, A-MEM, Zep

- **多库分离**:不同类型记忆用不同物理库
  - 各库可独立优化
  - 增加跨库查询复杂度
  - 典型:MIRIX 的六类记忆分管

#### 2.2 索引方式

**如何加速检索?**

- **向量索引**:embedding + ANN 检索
  - 语义相似度查询
  - 需要 embedding 模型,存储开销大

- **关键词索引**:倒排索引
  - 精确匹配查询
  - 不支持语义理解

- **时间索引**:按时间戳组织
  - 支持时序查询
  - 不支持语义查询

- **图索引**:图数据库的原生索引
  - 支持关系遍历
  - 图遍历成本较高

- **混合索引**:多种索引共存
  - 灵活支持多种查询模式
  - 存储与维护成本高

#### 2.3 单元粒度

**一条记忆的最小/最大边界?**

- **对话级**:一次完整对话作为一个单元
- **轮次级**:一轮 user-assistant 交互
- **事实级**:一条独立事实
- **原子事实级**:不可再分的最小陈述
- **文档级**:一份完整文档/报告

粒度越细,检索精度越高,但单元数量越多,管理成本越大。

## Q3: 检索决策 (Retrieval Decision)

### 核心问题

当前任务需要哪些单元?

### 设计空间

#### 3.1 触发时机

**何时启动检索?**

- **每轮查询**:每次推理前都检索
- **需求驱动**:检测到特定意图(如"我之前说过...")时检索
- **混合**:基础上下文 + 按需检索

#### 3.2 检索策略

**如何找到相关记忆?**

- **向量检索**:语义相似度 top-k
  - 优点:语义匹配,召回泛化能力强
  - 缺点:可能检索到主题相关但事实无关的内容

- **关键词检索**:BM25 等传统 IR
  - 优点:精确匹配,可解释性强
  - 缺点:需要字面匹配,召回受限

- **图遍历**:从当前实体出发,沿关系边遍历
  - 优点:能发现隐含关联
  - 缺点:遍历深度难控制,成本高

- **时间过滤**:按时间窗口筛选
  - 近期记忆优先
  - 适合时序敏感任务

- **重要性排序**:按预估的价值排序
  - 需要准确的重要性评分机制

- **融合检索**:多路检索结果融合
  - 例:向量 + 关键词 + 时间
  - Reciprocal Rank Fusion (RRF) 等方法

#### 3.3 预算控制

**检索多少?**

- **固定 top-k**:返回前 k 条
- **阈值截断**:相似度/相关性超过阈值的全部返回
- **token 预算**:检索到填满预算为止
- **动态调整**:根据任务复杂度调整检索数量

## Q4: 维护机制 (Maintenance)

### 核心问题

单元集怎么保持质量?

### 设计空间

#### 4.1 更新触发

**何时启动维护?**

- **矛盾检测**:新信息与旧记忆冲突时
- **定期维护**:每天/每周批处理
- **容量驱动**:记忆库达到容量上限时
- **Sleep-time 处理**:用户空闲时后台运行

#### 4.2 更新操作

**如何处理信息演化?**

- **覆盖更新**:新信息直接替换旧记忆
- **版本保留**:保留历史版本,标记最新
- **合并**:新旧信息融合为一条记忆
- **冲突标记**:保留冲突记忆,交由后续决策

#### 4.3 淘汰策略

**如何决定删除哪些记忆?** (Forget 操作,详见专题)

- **容量驱动**:FIFO, LRU, LFU
- **时间衰减**:按 Ebbinghaus 曲线降低权重
- **矛盾消解**:删除被证明错误的记忆
- **显式标记**:用户/系统明确要求删除
- **效用预测**:删除预估未来价值低的记忆

#### 4.4 重组策略

**如何优化记忆结构?** (Consolidate 操作,详见专题)

- **去重**:合并语义重复的记忆
- **摘要**:多条细节记忆压缩为一条概述
- **泛化**:多个具体案例抽象为一条规律
- **编译**:重复执行的步骤固化为技能

## Q5: 渲染方案 (Rendering)

### 核心问题

被选中的单元 → 怎么变成 context 片段?

### 设计空间

#### 5.1 注入方式

**记忆如何进入 context?**

- **System prompt 前缀**:在系统提示词后追加
  - 模型高度重视
  - 占用系统提示词预算

- **User message 前缀**:在用户消息前插入
  - 作为"已知信息"呈现
  - 可能干扰用户意图理解

- **独立 message**:作为独立的"记忆"角色消息
  - 结构清晰
  - 部分模型不支持自定义角色

- **工具调用结果**:伪装成工具返回的结果
  - 符合 agent 工作流
  - 需要工具调用机制

#### 5.2 格式化

**记忆以什么形式呈现?**

- **自然语言**:流畅的句子/段落
  - 可读性强
  - token 消耗较多

- **结构化**:JSON/YAML/键值对
  - 信息密度高
  - 可读性较差

- **列表**:bullet points
  - 简洁
  - 适合多条独立事实

- **对话式**:模拟过去的对话片段
  - 保留交互情境
  - 占用 token 多

#### 5.3 优先级与取舍

**预算不足时如何取舍?**

- **截断**:按相关性排序,保留 top-k
- **压缩**:对低优先级记忆进行二次摘要
- **分层**:核心记忆完整保留,次要记忆只给摘要
- **动态调整**:根据任务动态分配各类记忆的预算

## 五问题的交互与依赖

这五个问题不是孤立的,它们之间存在设计上的依赖与权衡:

### Q1 ← Q3 的反馈

检索日志反映"什么被查询",指导写入时的压缩深度与元信息标注。例如,如果发现某类记忆的检索召回率低,可能需要调整 Q1 的抽取策略。

### Q2 ← Q3 的适配

存储结构必须支持检索策略的高效执行。例如,如果检索策略依赖图遍历,存储就必须是图结构;如果依赖向量检索,就需要向量索引。

### Q3 → Q5 的约束

检索返回的记忆数量与质量直接影响渲染的复杂度。如果检索返回大量低相关度记忆,渲染阶段需要做更激进的过滤与压缩。

### Q4 ← Q1+Q3 的驱动

维护机制的触发由写入与检索的行为模式决定。例如,如果发现同一记忆被反复更新,说明需要更好的合并策略;如果某些记忆从未被检索,说明可以淘汰。

### Q1 ↔ Q4 的循环

写入时的处理深度影响后续维护的必要性:写入时压缩不足,后续需要更多 Consolidate;写入时压缩过度,后续可能需要重新展开或补充细节。

## 五问题模型的研究价值

### 1. 完备性

任何 Token-level Memory 系统的行为,都可以用这五个问题的设计选择组合来描述。没有遗漏的维度。

### 2. 正交性

五个问题相对独立,可以独立设计与优化。修改 Q2(存储结构)不必然要求修改 Q1(写入流程)。

### 3. 可比性

用这个模型分析不同系统,可以清晰识别它们的设计差异:

| 系统 | Q1 关键选择 | Q2 关键选择 | Q3 关键选择 |
|------|------------|------------|------------|
| MemGPT | 每轮触发 + LLM 抽取 | 分层存储 | Agent 主动调用 |
| Mem0 | 事件驱动 + LLM 抽取 | 图结构 | 向量检索 |
| Letta | 用户标记 + 规则提取 | 扁平列表 | 关键词检索 |

### 4. 设计空间映射

每个问题的设计空间是有限且可枚举的。这为系统性探索设计空间、识别未被探索的组合提供了基础。

### 5. 评测维度对齐

Benchmark 可以针对每个问题设计独立的评测:

- Q1: 抽取准确率、信息保留率
- Q2: 存储效率、索引构建成本
- Q3: 检索召回率、精确率、延迟
- Q4: 更新正确性、淘汰合理性
- Q5: 渲染后的任务性能、token 消耗

## 与"分类"的关系

传统的 Memory 分类(episodic/semantic/procedural)在五问题模型中的定位:

- **分类是 Q1 的辅助决策工具**:决定"这条交互应该抽取什么类型的记忆"
- **分类影响 Q2 的组织方式**:不同类型可能用不同的存储结构
- **分类影响 Q3 的检索策略**:不同类型的检索优先级与方式不同

但**分类不是第一性的**。同一个系统可以不使用任何显式分类,只要五个问题的设计选择合理,系统就能有效运作。相反,即便有精细的分类,如果五个问题设计不当,系统依然会失效。

---

## 小结

Token-level Memory 的核心计算不是"如何分类",而是如何在五个子问题上做出正确的设计选择:

1. **Q1 (写入)**:交互流 → 可存储单元
2. **Q2 (存储)**:单元集 → 高效组织
3. **Q3 (检索)**:当前任务 → 相关单元
4. **Q4 (维护)**:保持质量 → 更新/淘汰/重组
5. **Q5 (渲染)**:选中单元 → context 片段

这个模型的价值在于:**它把"Memory 系统是什么"的问题转化为"Memory 系统在五个决策点上做了什么选择"的问题**。这是从本质主义到操作主义的转变,也是研究框架与理解框架分离的关键。
