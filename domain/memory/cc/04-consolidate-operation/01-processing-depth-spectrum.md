# 处理深度:从连续谱到实用停靠点

## 引言

在早期讨论中,我们曾尝试将记忆的处理深度离散化为"Raw / Summarized / Abstract / Compiled"四个级别。这个尝试最终被推翻,原因在于:**处理深度本质上是一个连续谱,而非离散的级别**。

将连续过程人为离散化会导致两个问题:
1. 边界模糊:一条"摘要"可能深度相差巨大,它不是稳定的级别
2. 过程误判:"处理到一半"的状态不是独立的级别,而是**处理未完成**的状态

本文档重构处理深度的概念模型,建立"连续谱 + 实用停靠点"的框架。

---

## 第一部分:处理深度是连续谱

### 定义

**处理深度**(Processing Depth)是记忆相对于其源信息的**信息压缩程度**的连续度量。

形式化表达:
```
原始交互流 I (信息量 H(I))
    ↓ 处理算子 P
记忆单元 M (信息量 H(M))

处理深度 d = (H(I) - H(M)) / H(I)
```

- d = 0: 无压缩,近原文保留
- d → 1: 极度压缩,只保留核心要旨
- d 是连续变量,不是离散类别

### 为什么是连续的

**经验证据**:

场景:用户与 Agent 讨论一次项目会议

可能的处理结果:
- d≈0.1: "2026-10-24 团队会议,讨论了 Q4 路线图,Alice 提出延迟发布,Bob 反对,最终决定保持原计划"
- d≈0.3: "Q4 路线图会议:Alice 建议延期被否决,维持原计划"  
- d≈0.5: "团队决定 Q4 按原计划发布"
- d≈0.7: "Q4 发布时间表:按计划"
- d≈0.9: "Q4: 正常轨道"

**关键观察**:这五条记忆之间没有清晰的"级别"边界,它们是同一条信息在压缩率连续谱上的不同位置。

### 处理的本质:信息损失的权衡

每一次处理都是一次**有损压缩**:

| 压缩率提升 | 获得 | 损失 |
|----------|-----|-----|
| 更高 | token 预算节省<br>检索效率提升<br>泛化能力增强 | 细节丢失<br>情境缺失<br>可验证性降低 |

**不存在"最优深度"**——只有在特定下游需求下的最优深度。这是经济决策,不是技术决策。

## 第二部分:实用停靠点由下游需求决定

### 核心洞察

虽然处理深度是连续的,但在实际系统中,某些深度会成为**稳定的停靠点**(Stable Anchors),原因是它们被特定的下游需求锚定。

**停靠点不是理论划分的,而是被使用模式发现的。**

### 四个主要停靠点

基于现有 Memory 系统的实证分析,四个停靠点反复出现:

#### 停靠点 1: 事件可重放 (Event Replay)

**下游需求**:用户可能需要回顾"当时发生了什么",支持审计、纠纷解决、上下文重建

**处理深度**:低压缩 (d < 0.3)

**典型形态**:
- 时间戳 + 参与者
- 近原文的对话/行为记录
- 保留关键细节(谁说了什么、何时、为什么)

**工程实现**:
- MemGPT 的对话历史层
- Letta 的 archival memory
- 大部分系统的"对话日志"

**ROI 判断**:
- 高价值:合规场景(医疗、法律)、关键决策可追溯
- 低价值:日常闲聊、重复性操作

#### 停靠点 2: 事实可查询 (Fact Retrieval)

**下游需求**:Agent 需要查询"用户偏好是什么"、"某实体的属性"等独立事实

**处理深度**:中压缩 (0.3 < d < 0.6)

**典型形态**:
- 独立的事实单元:"用户偏好暗色主题"
- 实体-属性-值三元组:`(Alice, role, Product Manager)`
- 已消歧、已泛化的陈述

**工程实现**:
- Mem0 的核心记忆
- 大部分系统的"semantic memory"
- 知识图谱的节点与边

**ROI 判断**:
- 高价值:频繁查询的事实(用户偏好、常用联系人、配置参数)
- 低价值:一次性事实、易过时的状态

#### 停靠点 3: 策略可参考 (Strategy Reference)

**下游需求**:Agent 需要知道"遇到类似情境时该怎么做"

**处理深度**:高压缩 (0.6 < d < 0.85)

**典型形态**:
- 情境-策略映射:"当 API 调用失败时,先检查 rate limit,再重试,最多 3 次"
- 抽象的经验规律:"用户倾向于在周一上午处理邮件"
- 失败教训:"不要在未确认库存前承诺交付日期"

**工程实现**:
- ReasoningBank 的策略记忆
- AWM 的抽象动作序列
- Agent 的"经验池"

**ROI 判断**:
- 高价值:可迁移的模式、反复出现的情境
- 低价值:高度情境特定的策略

#### 停靠点 4: 操作可执行 (Executable Operation)

**下游需求**:Agent 需要直接调用某个已固化的操作序列

**处理深度**:形态转换 (不再是压缩率的维度)

**典型形态**:
- 代码/脚本:`def deploy_to_staging(): ...`
- Workflow 定义:YAML/JSON 的步骤序列
- API 调用模板

**工程实现**:
- Voyager 的技能库
- Memp 的 procedural memory
- 任何 Skill/Tool 库

**ROI 判断**:
- 高价值:高频操作、可编程的环境
- 低价值:低频操作、不可编程的环境

### 停靠点的属性

| 属性 | 说明 |
|-----|-----|
| **稳定性** | 停靠点是稳定的,因为有明确的下游需求锚定 |
| **非等距** | 停靠点在连续谱上不是均匀分布的,由实际需求分布决定 |
| **可跳跃** | 处理可以直接跳到某个停靠点,不必经过所有中间状态 |
| **可共存** | 同一条源信息可以在不同停靠点都有实例(多级索引) |

## 第三部分:停靠点之间的"中间状态"

### 处理未完成 vs 独立级别

当一条记忆处于两个停靠点之间时,它不是"第 2.5 级",而是**处理进行中**的状态。

**具体场景**:

一次 30 分钟的会议刚结束,系统开始处理:
1. **t=0s**: 原始对话流 (停靠点 1 的原材料)
2. **t=10s**: LLM 生成摘要 (d≈0.4,但还未提取独立事实)
3. **t=20s**: 从摘要中抽取事实 (到达停靠点 2)
4. **t=60s**: 识别出可泛化的策略 (到达停靠点 3)

**t=10s 的状态不是"Summarized 级别"**——它是"从停靠点 1 前往停靠点 2 的半成品"。

如果此时检索到这条记忆,会发生什么?
- 它既不足以支持事件重放(细节已丢)
- 也不足以支持事实查询(还未结构化)
- **它是一个不稳定的中间态**

### 摘要的特殊性

"摘要"(Summary)不是停靠点,而是**工具**——一个处理算子,可以把记忆从任何深度推向更深:

```
Raw (d=0.1) --[Summary]--> d=0.4
Fact (d=0.5) --[Summary]--> d=0.7 (多事实合并)
Strategy (d=0.75) --[Summary]--> d=0.9 (策略集压缩为原则)
```

"摘要"的深度取决于参数(压缩目标、token 预算、保留细节),它不锚定任何固定位置。

## 第四部分:处理深度的 ROI 模型

### 基本原则

> **每一次处理都有成本且必然有信息损失。处理的 ROI 由下游使用频率和价值决定,不是由"应该处理到什么级别"的规范决定。**

### 成本-收益分析

设:
- C_process: 处理成本(LLM 调用、延迟)
- L_info: 信息损失(无法恢复的细节)
- S_storage: 存储节省
- G_retrieval: 检索效率提升
- V_use: 预期使用价值(频率 × 任务价值)

ROI = (S_storage + G_retrieval + V_use) / (C_process + L_info)

**推论**:

1. **高频查询的记忆值得深度处理**
   - V_use 高 → ROI 高
   - 例:用户偏好应该处理到停靠点 2(事实),支持高效检索

2. **低频记忆保持近原文即可**
   - V_use 低 → 即便 S_storage 和 G_retrieval 正向,ROI 仍可能为负
   - 例:一次性的临时对话,不值得抽取事实

3. **永远不被引用的记忆,连存储都是浪费**
   - V_use = 0 → ROI 必然为负
   - 这是 Forget 操作的理论依据

### 动态调整策略

处理深度不应在写入时一次性确定,而应根据访问模式动态调整:

```
初始写入 → 停靠点 1(事件级,保险)
    ↓
第 1 次访问 → 触发延迟处理到停靠点 2(事实)
    ↓
第 5 次访问 → 触发深度处理到停靠点 3(策略)
    ↓
长期未访问 → 降级回停靠点 1 或 Forget
```

**实现方式**:
- 访问计数器作为触发器
- Sleep-time 后台处理
- 成本预算分配:高频记忆获得更多处理预算

## 第五部分:与"记忆类型"的关系

### 类型 ≠ 深度

传统分类(episodic/semantic/procedural)与处理深度**不是一一对应的**:

| 类型 | 可能的深度范围 | 说明 |
|------|--------------|------|
| Episodic | 停靠点 1~2 | 事件记录,通常保留细节,但也可以是"事件摘要" |
| Semantic | 停靠点 2 | 独立事实,中度压缩 |
| Procedural | 停靠点 3~4 | 策略或可执行代码,高度抽象 |

**关键区别**:
- **类型**回答"这是什么知识"(内容的语义性质)
- **深度**回答"压缩到什么程度"(信息的密度)

两者正交:一条 episodic 记忆可以是原文(d=0.1)也可以是高度摘要(d=0.6)。

### 类型与停靠点的映射

| 停靠点 | 主要对应类型 | 但也可以包含 |
|--------|------------|------------|
| 1: 事件可重放 | Episodic | 保留细节的 Semantic(如完整的知识条目) |
| 2: 事实可查询 | Semantic | 结构化的 Episodic(如"会议结论列表") |
| 3: 策略可参考 | Experiential | 抽象的 Procedural(如"部署检查清单") |
| 4: 操作可执行 | Procedural | 编译的 Experiential(如"常用调试步骤") |

**结论**:类型是内容维度,深度是压缩维度,两者是不同轴上的投影。

## 第六部分:工程设计指南

### 指南 1: 不要预设固定深度

**反模式**:
```python
def write_memory(content, type):
    if type == "episodic":
        depth = 0.2  # 固定深度
    elif type == "semantic":
        depth = 0.5
    ...
```

**正确做法**:
```python
def write_memory(content, estimated_future_use):
    if estimated_future_use == "high_frequency":
        target_anchor = Anchor.FACT  # 停靠点 2
    elif estimated_future_use == "audit_trail":
        target_anchor = Anchor.EVENT  # 停靠点 1
    ...
    process_to_anchor(content, target_anchor)
```

### 指南 2: 支持多级索引

同一条源信息可以在多个停靠点都有表示:

```
源:30 分钟会议
├─ 停靠点 1: 完整对话记录(支持审计)
├─ 停靠点 2: 提取的 5 条关键决策(支持查询)
└─ 停靠点 3: 1 条策略规律(支持未来决策)
```

**成本权衡**:
- 多级索引增加存储成本
- 但支持不同查询模式,提高检索精度
- 适用:高价值记忆(关键会议、重大决策)

### 指南 3: 延迟处理优于预处理

**原则**:在不确定未来用途时,保持较浅深度(停靠点 1),在第一次实际使用时再处理。

**理由**:
- 避免过早压缩导致信息不可逆丢失
- 实际使用时才知道需要什么深度
- 预处理可能浪费在永远不被访问的记忆上

**实现**:
- 写入时:轻度处理 + 元信息标注
- 首次检索时:触发 JIT 处理到目标深度
- 缓存处理结果,后续访问直接使用

### 指南 4: 监控并识别实际停靠点

不要假设四个停靠点是完备的。通过监控实际使用模式,识别系统特定的停靠点:

**方法**:
- 记录每次检索时的"需求类型"
- 聚类分析:哪些深度的记忆被同类需求反复访问
- 识别出的聚类中心 = 该系统的实际停靠点

**可能发现新停靠点**:
- 例:多模态系统可能有"可视化"停靠点(图表、图像)
- 例:协作系统可能有"可转发"停靠点(格式化为可分享的形式)

## 第七部分:理论拓展

### 与信息论的联系

处理深度本质上是信息论中的**率失真权衡**(Rate-Distortion Tradeoff):

- Rate: 存储/传输成本 (token 数量)
- Distortion: 失真度 (信息损失)
- 目标: 在给定失真约束下最小化 rate,或在给定 rate 约束下最小化失真

**Rate-Distortion Function** R(D):
- D=0: R 最大(无压缩)
- D→∞: R 最小(只保留最少信息)

停靠点对应 R(D) 曲线上的"拐点"——在这些点附近,微小的 rate 增加可以显著降低 distortion,或反之。

### 与机器学习的联系

处理深度的优化等价于**表示学习**(Representation Learning)中的维度约减:

- 原始交互 = 高维数据
- 记忆单元 = 低维表示
- 处理算子 = 编码器

停靠点对应"有意义的潜在空间维度"——不同的下游任务需要不同的表示维度。

### 记忆与知识的连续过渡

**深刻洞察**:"记忆"与"知识"不是两类东西,而是**处理深度连续谱的两端**:

- 记忆(d < 0.6): 情境依赖,个体特定,保留细节
- 知识(d > 0.8): 情境独立,可泛化,高度抽象

中间地带(0.6 < d < 0.8)是"经验"——既有具体情境,又开始泛化。

**推论**:
- Memory 系统的终极目标不是"存储",而是**将经验蒸馏为知识**
- Consolidate 操作的本质是**沿深度谱向知识端推进**
- 最成熟的 Memory 系统应该能够自动识别"何时该泛化"

---

## 结论

处理深度不是离散的"级别",而是信息压缩的连续谱。实用停靠点不是理论划分的,而是被下游需求锚定的稳定位置:

1. **事件可重放** (d < 0.3): 支持审计与情境重建
2. **事实可查询** (0.3 < d < 0.6): 支持高效检索
3. **策略可参考** (0.6 < d < 0.85): 支持经验迁移
4. **操作可执行** (形态转换): 支持自动化

停靠点之间的中间状态不是独立的级别,而是**处理进行中**的状态。处理深度的选择是经济决策,由下游使用频率和价值的 ROI 模型决定,而非规范性的"应该处理到什么级别"。

记忆与知识是处理深度连续谱的两端,Memory 系统的演化方向是**从被动存储走向主动蒸馏**——自动识别何时该泛化,将经验转化为知识。
