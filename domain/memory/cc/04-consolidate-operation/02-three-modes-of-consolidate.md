# Consolidate 操作的三种模式

## 引言

Consolidate 是 Memory 系统中的核心操作之一,但它不是单一的操作,而是**三种不同模式的统称**。早期讨论中的一个关键错误就是试图将"Summary/Generalize/Compile"合并为单一的"C 操作",结果丢失了三个完全不同的工程设计空间。

本文档重构 Consolidate 的概念模型,明确三种模式的本质差异、各自的设计空间、以及它们在处理深度连续谱上的定位。

---

## 第一部分:三种模式的本质区分

### 核心洞察

Consolidate 不是"压缩"的同义词,而是**记忆重组**的总称。三种模式在以下维度上有本质差异:

| 维度 | 去重 (Dedup) | 摘要 (Summarize) | 泛化 (Generalize) |
|------|------------|----------------|-----------------|
| **输入数量** | 多条(≥2) | 单条或多条 | 多条(≥2) |
| **输出数量** | 1条 | 1条 | 1条 |
| **信息保留** | 完整(无损) | 有损压缩 | 抽象提升 |
| **处理深度变化** | 不变 | 增加 | 显著增加 |
| **可逆性** | 高(原信息可恢复) | 中(部分可恢复) | 低(不可逆) |
| **触发条件** | 检测到冗余 | 容量压力 | 识别出模式 |

---

## 第二部分:模式一 - 去重 (Deduplication)

### 定义

**去重**:识别并合并语义重复的记忆单元,保持信息完整性。

### 本质特征

- **无损操作**:合并后的记忆包含原记忆的全部信息
- **深度不变**:如果原记忆都在停靠点2(事实),合并后仍在停靠点2
- **目标**:减少存储成本与检索噪声,不改变语义

### 场景示例

```
记忆1: "用户偏好暗色主题" (2026-10-20)
记忆2: "用户喜欢 dark mode" (2026-10-22)

合并后: "用户偏好暗色主题(dark mode)"
元数据: 首次记录 2026-10-20,最后确认 2026-10-22
```

### 设计空间

#### 2.1 冗余检测策略

**语义相似度**:
- 向量余弦相似度 > 阈值(如 0.95)
- 优点:能捕捉同义表达
- 缺点:可能误判细微差异

**实体-属性匹配**:
- 如果两条记忆涉及同一实体的同一属性 → 可能冗余
- 例:`(Alice, role, PM)` 与 `(Alice, job, Product Manager)`
- 优点:精确控制
- 缺点:需要结构化记忆

**LLM 判断**:
- Prompt: "这两条记忆是否表达同一事实?"
- 优点:处理复杂语义
- 缺点:成本高,延迟大

**混合策略**:
- 向量初筛(召回) + LLM 精排(精确度)

#### 2.2 合并策略

**保留最新**:
- 假设:新信息更准确
- 适用:时序敏感的事实

**保留最详细**:
- 比较 token 长度或信息熵
- 适用:细节重要的场景

**智能融合**:
- 用 LLM 生成融合版本
- Prompt: "将这两条记忆合并为一条,保留所有信息"
- 适用:高价值记忆

**时间戳聚合**:
- 保留首次记录时间 + 最后确认时间
- 增加"确认次数"计数

#### 2.3 触发时机

**写入时检测**:
- 新记忆写入前,检查是否与已有记忆冗余
- 优点:实时,库保持精简
- 缺点:每次写入都要检索,成本高

**定期批处理**:
- 每天/每周扫描库,识别冗余对
- 优点:摊销成本
- 缺点:短期内存在冗余

**容量驱动**:
- 记忆库接近容量上限时触发
- 优点:只在必要时做
- 缺点:可能积累大量冗余

### 去重的价值

- **减少检索噪声**:同一事实多个版本会降低检索精度
- **降低存储成本**:尤其在向量检索系统中,每条记忆都有 embedding 开销
- **提高一致性**:单一事实源,避免矛盾

### 去重的风险

- **误合并**:细微差异被忽略
  - 例:"用户偏好咖啡(2020年)" vs "用户偏好茶(2026年)" 不应合并
  - 需要时间感知的冗余检测

- **信息丢失**:合并逻辑不完善时
  - 例:只保留最新,丢失了历史演化信息

## 第三部分:模式二 - 摘要 (Summarization)

### 定义

**摘要**:将一条或多条记忆压缩为更简洁的形式,牺牲细节换取空间效率。

### 本质特征

- **有损压缩**:细节被丢弃,只保留要旨
- **深度增加**:从停靠点1(事件) → 停靠点2(事实),或从停靠点2 → 更抽象的形式
- **目标**:节省 context 预算,提高检索效率

### 场景示例

```
原始对话(停靠点1):
用户: "我需要一份Q4的财报"
Agent: "好的,包括哪些部门?"
用户: "工程和销售"
Agent: "明白,我会生成工程和销售的Q4财报"

摘要后(停靠点2):
"用户需要Q4财报,范围:工程部门和销售部门"
```

### 设计空间

#### 3.1 摘要算子

**抽取式摘要**:
- 从原文中选择关键句子/片段
- 优点:忠实原文,可验证
- 缺点:可能不够简洁,语义不连贯

**生成式摘要**:
- LLM 重新生成简化版本
- 优点:灵活,语义连贯
- 缺点:可能引入幻觉,不可验证

**混合**:
- 先抽取关键信息点,再用 LLM 组织为流畅文本

#### 3.2 压缩率控制

**固定 token 预算**:
- Prompt: "将以下内容压缩到 50 tokens 以内"
- 优点:可预测的成本
- 缺点:可能过度压缩或浪费预算

**信息保留目标**:
- Prompt: "保留所有可操作的信息,省略背景与细节"
- 优点:内容驱动,灵活
- 缺点:输出长度不可预测

**多级摘要**:
- 生成多个版本:简版(20 tokens)、标准版(50 tokens)、详版(100 tokens)
- 检索时根据可用预算选择版本

#### 3.3 何时摘要

**Never**: 保持原文
- 适用:已经很简洁、需要精确引用、法律/合规场景

**Lazy**: 首次检索时才摘要(JIT)
- 优点:避免对永远不被访问的记忆做无用功
- 缺点:首次检索延迟高

**Eager**: 写入时立即摘要
- 优点:检索时低延迟
- 缺点:可能浪费在低价值记忆上

**Adaptive**: 根据访问频率动态决策
- 访问 > N 次 → 值得提前摘要
- 访问 = 0 → 保持原文或直接 Forget

### 摘要的价值

- **节省 context 预算**:更多记忆可以塞进有限窗口
- **提高检索效率**:更短的记忆,更快的处理
- **降低注意力稀释**:简洁的记忆更容易被模型关注

### 摘要的风险

- **信息不可逆丢失**:细节一旦压缩,无法恢复
- **摘要质量不稳定**:LLM 生成的摘要可能偏离要点
- **过早压缩**:在不知道未来需求时,可能丢失关键细节

## 第四部分:模式三 - 泛化 (Generalization)

### 定义

**泛化**:从多个具体案例中抽象出通用规律或模式,形成更高层级的知识。

### 本质特征

- **抽象提升**:从"具体事件"到"通用规律"
- **深度显著增加**:从停靠点1/2 → 停靠点3(策略)
- **目标**:提高经验的可迁移性与复用性

### 场景示例

```
具体案例1: "当 API 返回 429 错误时,等待 60 秒后重试,成功了"
具体案例2: "当 API 返回 429 错误时,等待 30 秒后重试,失败了,等待 120 秒后重试,成功了"
具体案例3: "当 API 返回 429 错误时,等待 90 秒后重试,成功了"

泛化后(停靠点3):
"当遇到 429 Rate Limit 错误时,应等待至少 60 秒后重试。如果再次失败,加倍等待时间。"
```

### 设计空间

#### 4.1 模式识别算法

**频率统计**:
- 识别重复出现的(情境, 操作, 结果)三元组
- 优点:简单,可解释
- 缺点:只能识别完全相同的模式

**聚类分析**:
- 将相似案例聚类,从聚类中心抽象规律
- 优点:能识别近似模式
- 缺点:需要合适的相似度度量

**LLM 归纳**:
- Prompt: "从以下案例中总结通用规律"
- 优点:处理复杂语义,生成自然语言规则
- 缺点:可能过度泛化或幻觉

**对比学习**:
- 同时提供成功与失败案例,让 LLM 识别决定性差异
- 优点:更准确的因果推断
- 典型实现:ReasoningBank 的失败经验纳入

#### 4.2 泛化的触发条件

**样本数阈值**:
- 同一情境下积累 N 个案例(如 N=3)后触发
- 优点:确保有足够统计显著性
- 缺点:可能错过早期明显模式

**相似度聚集**:
- 检测到多个高度相似的案例时触发
- 例:向量相似度 > 0.85 的案例集 > 3个

**显式请求**:
- 用户/系统明确要求"总结经验"

**Sleep-time 批处理**:
- 用户空闲时,扫描记忆库,识别可泛化的案例集

#### 4.3 泛化层级

**单步操作 → 多步流程**:
- 例:"复制文件" → "备份项目:复制 + 验证 + 压缩"

**具体参数 → 参数化模板**:
- 例:"等待 60 秒" → "等待 T 秒,其中 T 根据错误类型调整"

**领域特定 → 跨领域**:
- 例:"API 重试策略" → "任何网络操作的通用重试策略"

**步骤 → 原则**:
- 例:"先检查库存再承诺交付" → "永远不做无法履行的承诺"

### 泛化的价值

- **经验复用**:一次学习,多处应用
- **迁移能力**:规律可应用于未见过的情境
- **知识积累**:从"记忆"演化为"知识"

### 泛化的风险

- **过度泛化**:规律不成立的边界不清晰
  - 例:"API 重试总是有效" → 忽略了某些错误不可重试

- **样本偏差**:从有限案例泛化,可能不代表总体
  - 例:只遇到过 429 错误,泛化为"所有 API 错误都该重试"

- **因果混淆**:相关性 ≠ 因果性
  - 例:"等待后成功" 不一定因为"等待",可能是其他因素

## 第五部分:三种模式的交互

### 去重 vs 摘要

**区别**:
- 去重处理冗余,摘要处理冗长
- 去重无损,摘要有损
- 去重输入必须是多条,摘要可以是单条

**组合使用**:
```
1. 先去重:合并"用户偏好 X"的 5 个冗余版本 → 1 条
2. 再摘要:压缩这条记忆的详细描述 → 简洁版
```

### 摘要 vs 泛化

**区别**:
- 摘要是同一内容的简化,泛化是跨内容的抽象
- 摘要输出仍然是"这件事的要旨",泛化输出是"这类事的规律"
- 摘要深度增加适中,泛化深度增加显著

**组合使用**:
```
1. 先摘要:将 10 次详细的故障排查对话 → 10 条简洁的"问题-解决方案"对
2. 再泛化:从这 10 对中识别通用故障排查模式
```

### 去重 + 摘要 + 泛化的完整流程

```
原始记忆库: 100 条详细交互记录

Step 1 [去重]: 识别并合并语义重复 → 70 条独立记忆

Step 2 [摘要]: 压缩每条记忆的细节 → 70 条简洁记忆

Step 3 [泛化]: 从相似记忆中抽象规律 → 70 条记忆 + 10 条通用策略

最终库: 80 条记忆(70 事实 + 10 策略),信息密度显著提升
```

## 第六部分:与处理深度的关系

### 三种模式在深度谱上的位置

| 操作 | 深度变化 | 停靠点转换 |
|------|---------|-----------|
| 去重 | 不变 | 保持原停靠点 |
| 摘要 | 增加(Δd ≈ 0.2~0.4) | 1→2, 2→2(更简洁), 或 2→3 |
| 泛化 | 显著增加(Δd ≈ 0.4~0.6) | 1/2 → 3, 或 3 → 更高层原则 |

### 可逆性递减

| 操作 | 可逆性 | 恢复路径 |
|------|--------|---------|
| 去重 | 高 | 如果保留 provenance,可恢复原记忆 |
| 摘要 | 中 | 部分可恢复(如果保留原文引用) |
| 泛化 | 低 | 无法从规律反推具体案例 |

**工程含义**:
- 去重可以激进一些(可逆)
- 摘要需要权衡(保留原文引用 vs 节省空间)
- 泛化需要谨慎(不可逆,且可能过度泛化)

## 第七部分:何时用哪种模式

### 决策树

```
是否有多条语义重复的记忆?
├─ 是 → 去重
└─ 否 → 继续

记忆是否过于冗长?
├─ 是 → 摘要
└─ 否 → 继续

是否有多个相似案例?
├─ 是 → 检查是否可泛化
│   ├─ 能识别出通用模式 → 泛化
│   └─ 模式不明显 → 保持原样
└─ 否 → 保持原样
```

### 优先级

在资源有限时(如 Sleep-time 处理预算不足),优先级:

1. **去重** - 收益明确,风险最低
2. **摘要** - 针对高频访问的长记忆
3. **泛化** - 最耗时,但收益也最高(如果做对了)

### 反指示

**不要去重**:
- 记忆涉及时间演化(如偏好变化)
- 细微差异有意义(如不同情境下的微调策略)

**不要摘要**:
- 已经很简洁
- 需要精确引用(法律、合规)
- 从未被访问过(先 Forget 而非摘要)

**不要泛化**:
- 样本量不足(<3个案例)
- 案例差异大于相似性
- 规律不稳定(成功率<80%)

## 第八部分:评估 Consolidate 的质量

### 去重的评估指标

- **精确率**:合并的记忆对中,真正冗余的比例
- **召回率**:所有冗余记忆对中,被识别的比例
- **信息保留率**:合并后信息完整性

### 摘要的评估指标

- **压缩率**: token_after / token_before
- **Rouge/BLEU**: 与人类摘要的相似度
- **任务保持率**:摘要后,下游任务成功率是否下降

### 泛化的评估指标

- **迁移成功率**:规律应用于新案例的成功率
- **适用范围**:规律能覆盖的情境比例
- **过度泛化检测**:规律在边界外失效的频率

---

## 结论

Consolidate 不是单一操作,而是三种有本质差异的模式:

1. **去重**(Dedup): 无损合并冗余记忆,深度不变,可逆性高
2. **摘要**(Summarize): 有损压缩冗长记忆,深度适度增加,部分可逆
3. **泛化**(Generalize): 从具体案例抽象规律,深度显著增加,不可逆

三者的设计空间完全不同:去重关注冗余检测,摘要关注压缩质量,泛化关注模式识别。将它们合并为单一"C 操作"会丢失关键的设计维度。

在工程实践中,三种模式常常组合使用,形成从"原始记忆"到"知识"的演化路径:
```
Raw Events → [去重] → Unique Events → [摘要] → Concise Facts → [泛化] → Strategies
```

理解三种模式的本质差异,是设计高质量 Memory 系统的关键。
