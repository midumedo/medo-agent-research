# Experiential-Skill 谱系:编译-解释连续谱

## 引言

在讨论中形成的一个核心判断是:**Experiential 与 Skill 不是两种记忆类型,而是同一条"经验"在编译-解释连续谱上的不同位置**。

这个判断的深刻之处在于,它将看似正交的两个概念统一到了一个连续维度上,并发现了决定"经验可以编译到什么程度"的关键因素——**环境的 Action Space 可编程化程度**。

本文档重构对经验记忆的理解,建立编译-解释谱系模型,并探讨其对系统设计的含义。

---

## 第一部分:核心论断

### 论断的表述

**Skill = 被编译的经验,Experiential = 被解释的经验。**

两者的本质差异不在"内容类型",而在**执行方式**:

| 维度 | Experiential | Skill |
|------|-------------|-------|
| 存储形式 | 自然语言描述 | 代码/结构化步骤 |
| 执行方式 | 每次由 LLM 解释 | 直接调用/执行 |
| 延迟 | 高(需推理) | 低(预编译) |
| 灵活性 | 高(可即时调整) | 低(需修改代码) |
| 可迁移性 | 中(依赖 LLM 理解) | 高(跨模型复用) |
| token 消耗 | 每次都消耗 | 一次编译,多次零成本 |

### 编译的本质

**编译**(Compilation)是将"如何做"从依赖 LLM 推理的自然语言描述,转化为可直接执行的形式化操作序列。

类比编程语言:
- **解释型语言**(Python, JavaScript):每次运行都要解析源代码
- **编译型语言**(C, Rust):一次编译为机器码,后续直接执行

Experiential 是"解释型经验",Skill 是"编译型经验"。

## 第二部分:分界线由 Action Space 决定

### 核心洞察

一个经验能否从 experiential 端滑向 skill 端,取决于**环境的 Action Space 可编程化程度**——这是环境属性,不是记忆系统属性。

### 三种典型环境

#### 环境 1: 完全可编程(Voyager / Minecraft)

**Action Space**:
- Minecraft 提供完整的 Python API
- 每个动作都可以表达为函数调用
- 状态可查询,结果可验证

**经验形态**:代码型技能

```python
def mine_iron_ore():
    """挖掘铁矿石的技能"""
    # 找到铁矿
    iron_pos = find_nearest_block('iron_ore')
    # 移动到位置
    navigate_to(iron_pos)
    # 使用镐子挖掘
    equip('iron_pickaxe')
    mine_block(iron_pos)
    # 收集掉落物
    collect_nearby_items()
```

**特征**:
- 100% 编译化
- 跨会话复用无损耗
- 可组合为更复杂的技能

#### 环境 2: 部分可编程(AWM / WebArena)

**Action Space**:
- Web 环境的动作可枚举:点击、输入、选择
- 但内容是动态的,元素定位不稳定
- 需要一定的适应性

**经验形态**:抽象动作序列

```yaml
task: 在购物网站下单
steps:
  - action: search
    target: 搜索框
    input: "商品关键词"
  - action: click
    target: 第一个搜索结果
  - action: click
    target: "加入购物车"按钮
  - action: click
    target: "结算"按钮
  - action: fill_form
    target: 配送信息表单
    data: from_user_profile
```

**特征**:
- 部分编译化(步骤固定,内容参数化)
- 需要运行时适配(元素定位)
- 介于完全编译与完全解释之间

#### 环境 3: 开放推理(ReasoningBank / 通用对话)

**Action Space**:
- 没有可编程 API
- 动作是自然语言交互
- 推理路径高度情境依赖

**经验形态**:自然语言策略

```
情境:用户表达需求模糊

策略:
1. 先复述理解,确认大方向
2. 识别 2-3 个关键不确定点
3. 逐一询问,每次只问一个
4. 根据回答调整后续问题

为什么:
- 用户通常不清楚自己需要澄清什么
- 一次问太多会让用户困惑
- 逐步澄清能建立共同语境
```

**特征**:
- 无法编译(没有固定步骤)
- 每次都需 LLM 解释与调整
- 价值在"何时用这个策略",而非"怎么执行"

### 分界线可视化

```
编译化程度 ←————————————————————————————————————————————→ 解释化程度
100%                                                      0%

Voyager         AWM             ReasoningBank        通用对话
(代码)          (抽象步骤)      (自然语言策略)       (即时推理)

Action Space:
可编程 API   →   可枚举动作   →   结构化交互    →    开放推理
```

### 推论

**同一个任务,在不同环境下,编译化程度不同**:

| 任务 | 环境 A | 环境 B | 编译化差异原因 |
|------|--------|--------|---------------|
| 部署到生产环境 | Kubernetes API | 手动 SSH | A 有 API,可编译为脚本;B 依赖人工操作 |
| 查询数据库 | SQL 数据库 | 自然语言数据库 | A 有结构化查询语言,可编译;B 需每次理解 |
| 调试代码 | 可编程 IDE | 文本聊天 | A 有 LSP 协议,可编译工具链;B 只能给建议 |

## 第三部分:经验的抽象层级金字塔

即便在同一环境下,经验也可以存在于不同的抽象层级。抽象层级越高,可迁移性越强,但对具体情境的适配能力越弱。

### 五层金字塔

```
                    原则(Principles)
                  /               \
              策略(Strategies)       ← 高抽象,强泛化
            /                   \
        工作流(Workflows)           ← 中抽象,平衡
      /                       \
    步骤(Steps)                   ← 低抽象,强适配
  /                           \
原始轨迹(Raw Trajectories)          ← 零抽象,完全具体
```

### 各层级的特征

#### L0: 原始轨迹(Raw Trajectory)

**形态**:完整的交互记录,几乎无处理

```
[2026-10-20 14:32] User: API 返回 429 错误
[2026-10-20 14:33] Agent: 检查 rate limit 配置...
[2026-10-20 14:35] Agent: 发现每分钟 100 次限制,当前 150 次
[2026-10-20 14:36] Agent: 建议降低请求频率
[2026-10-20 14:38] User: 改为每分钟 80 次
[2026-10-20 14:40] Agent: 问题解决
```

**特征**:
- 抽象度:0
- 可迁移性:极低(情境高度特定)
- 信息量:最大(保留所有细节)

#### L1: 步骤指令(Step Instructions)

**形态**:从轨迹中提取的操作步骤

```
解决 429 Rate Limit 错误:
1. 检查 API 配置中的 rate limit 设置
2. 对比当前请求频率与限制
3. 如果超过限制,降低请求频率至限制的 80%
4. 验证错误是否消失
```

**特征**:
- 抽象度:低
- 可迁移性:低(只适用于相同的 API)
- 信息量:中(丢失了对话细节,保留操作要点)

#### L2: 工作流(Workflow)

**形态**:参数化的流程,可应用于同类任务

```yaml
name: 解决 API Rate Limit 错误
inputs:
  - api_name
  - error_code
steps:
  - 查询 {{api_name}} 的 rate limit 配置
  - 监控当前请求频率
  - if 频率 > 限制:
      调整请求间隔至 限制 * 0.8
  - 重试请求
  - 验证成功
```

**特征**:
- 抽象度:中
- 可迁移性:中(适用于所有有 rate limit 的 API)
- 信息量:中低(参数化,但保留结构)

#### L3: 策略(Strategy)

**形态**:情境-响应模式,不规定具体步骤

```
当遇到 Rate Limit 类错误时:
- 首要原则:不要立即重试,会加剧限流
- 诊断:检查当前请求频率是否超过 API 限制
- 响应:如果超过,降低频率至限制的 70-80%
- 备选:如果未超过,可能是突发流量,等待一段时间(指数退避)
- 长期:考虑实现请求队列与平滑器
```

**特征**:
- 抽象度:高
- 可迁移性:高(适用于所有限流场景)
- 信息量:低(只保留关键决策点)

#### L4: 原则(Principle)

**形态**:跨领域的指导思想

```
面对资源限制类错误:
- 不要与限制对抗,而是适应限制
- 理解限制的目的(保护系统,公平分配)
- 在限制下优化行为(削峰填谷,请求合并)
- 必要时与服务方协商提升限制
```

**特征**:
- 抽象度:极高
- 可迁移性:极高(适用于所有资源受限场景)
- 信息量:极低(只保留哲学)

### 抽象层级的权衡

| 维度 | 低抽象(L0-L1) | 高抽象(L3-L4) |
|------|-------------|-------------|
| 可迁移性 | 差 | 强 |
| 适配精度 | 高 | 低 |
| token 消耗 | 高 | 低 |
| 理解成本 | 低(具体明确) | 高(需推理应用) |
| 容错性 | 差(细节不匹配就失效) | 强(抽象可适配变化) |

## 第四部分:失败经验是决策边界的负样本

### 核心洞察

成功经验告诉你"什么可行",失败经验告诉你"什么不可行"。两者共同定义了决策边界。

只学习成功经验的系统,不知道"可行解空间"的边界在哪里,容易过度泛化。

### 失败经验的价值

**场景**:API 重试策略

仅有成功经验:
```
案例1: API 超时,等待 1 秒重试,成功
案例2: API 429 错误,等待 10 秒重试,成功
案例3: API 503 错误,等待 30 秒重试,成功

泛化策略: "遇到 API 错误就等待后重试"
```

**问题**:这个策略会在遇到 401(未授权)、403(禁止)、404(不存在)时失效——这些错误重试无意义。

加入失败经验:
```
案例4: API 401 错误,等待后重试,仍失败(失败)
案例5: API 404 错误,重试 3 次,全部失败(失败)

修正策略: "可重试的错误:超时、429、503;不可重试:4xx(除了 429)"
```

### ReasoningBank 的创新

ReasoningBank 是首个系统性纳入失败经验的 Memory 系统:

**传统做法**:
- 只蒸馏成功轨迹
- 失败轨迹被丢弃

**ReasoningBank**:
- 成功与失败都记录
- 对比分析:什么导致了差异
- 学到的是"决策边界",不只是"成功路径"

**示例**:

```
任务:回答用户关于"如何优化数据库查询"的问题

成功轨迹:
1. 先询问数据库类型(MySQL / PostgreSQL / MongoDB)
2. 询问查询耗时与数据量
3. 根据类型给出针对性建议
→ 用户满意

失败轨迹:
1. 直接给出通用优化建议(索引、缓存、分页)
2. 用户追问"我用的是 MongoDB,这些适用吗?"
3. Agent 需要重新解释
→ 用户不满意,认为 Agent 没听懂

对比学习:
- 成功点:提前澄清情境(数据库类型)
- 失败点:假设通用建议适用
- 决策边界:当解决方案依赖技术栈时,必须先澄清技术栈
```

## 第五部分:Memp 的迁移实验与启示

### 实验设计

Memp 论文的关键实验:

1. 用强模型(GPT-4)在 Minecraft 中收集交互轨迹
2. 从轨迹中蒸馏 procedural memory(技能)
3. 将技能迁移给弱模型(GPT-3.5)
4. 测试弱模型在同类任务上的表现

### 实验结果

**关键发现**:强模型蒸馏的技能,迁移给弱模型后,弱模型在同类任务上的成功率显著提升(从 30% → 65%)。

### 深刻启示

**高质量经验与模型能力部分解耦**。

传统理解:
- 强模型之所以强,是因为参数中编码了更多知识
- 弱模型缺乏这些知识,所以表现差

Memp 的证据:
- 即便参数能力有差距,**结构性知识**(如"如何分解任务"、"先做什么后做什么")可以通过显式记忆传递
- 经验不是某个模型的私有产物,而是**关于世界的结构性知识**

### 工程含义

**Skill 库可以跨模型复用**:
- 用最强模型蒸馏技能
- 迁移给成本更低的模型
- 实现"强模型的智慧 + 弱模型的成本"

**类比**:
- 参数能力 = 智商
- 显式技能 = 受过的训练
- 即便智商有差距,训练可以显著缩小表现差距

## 第六部分:MaTTS - 用推理算力购买记忆质量

### 核心思想

**MaTTS**(Massive Test-Time Sampling):给每个任务分配更多 test-time 算力,生成更多样化的交互轨迹,从中蒸馏更高质量的策略。

### 流程

```
传统方法:
任务 → 1 次执行 → 成功/失败 → 记录 → 蒸馏

MaTTS:
任务 → N 次执行(N >> 1) → 多条轨迹(成功 + 失败)
      ↓
对比分析 → 识别"哪些决策导致成功/失败"
      ↓
蒸馏高质量策略(包含决策边界)
```

### 为什么有效

**对比信号丰富**:

单次执行:
- 只知道"这样做成功了"
- 不知道"换个做法会怎样"

多次执行:
- 可以对比"做 A 成功,做 B 失败"
- 识别关键决策点

### 与 Scaling Law 的关系

**传统 Scaling**:增加训练算力(数据量 × 模型参数 × 训练 FLOPs)

**Test-Time Scaling**(MaTTS):增加推理算力(采样次数 × 对比分析)

**关键区别**:
- 训练 scaling 改变模型参数,成本高,不可逆
- Test-time scaling 不改参数,成本按需,可即时调整

**新的 scaling 路径**:
```
传统: 更大模型 → 更强能力
MaTTS: 更多采样 → 更好记忆 → 间接提升能力
```

## 第七部分:谱系模型的统一视角

### 统一公式

经验在编译-解释谱上的位置,由两个因素决定:

```
编译化程度 = f(Action Space 可编程性, 抽象层级)
```

- Action Space 可编程性:环境因素,决定"能编译到什么程度"
- 抽象层级:设计选择,决定"要编译到什么程度"

### 四个象限

```
                抽象层级高
                    ↑
                    |
可迁移原则    |    通用策略
(可编译,高抽象)|(解释型,高抽象)
                    |
编程性强 ←——————————|——————————→ 编程性弱
                    |
代码型技能    |    自然语言经验
(可编译,低抽象)|(解释型,低抽象)
                    |
                    ↓
                抽象层级低
```

### 设计含义

**不要强求编译不可编译的**:
- 在开放推理环境,强行"编译"经验为固定步骤,会失去灵活性
- 应保持为自然语言策略,让 LLM 每次解释

**不要过度抽象可执行的**:
- 在可编程环境,把代码"抽象"为自然语言描述,浪费可编译性
- 应直接编译为可执行代码

**最优点是动态的**:
- 早期:经验样本少,保持低抽象(具体步骤)
- 成熟期:样本丰富,泛化为高抽象(策略/原则)

## 第八部分:对 Memory 系统设计的启示

### 启示 1: Experiential 与 Procedural 不是分离的类型

**传统分类**(CoALA):
- Episodic:事件记录
- Semantic:事实知识
- Procedural:操作技能
- Experiential:经验策略

**问题**:Procedural 与 Experiential 的边界在哪里?

**谱系视角**:
- 它们是同一类知识(经验)的不同编译化程度
- 不需要人为划分,系统应支持经验在谱上自由移动

### 启示 2: 支持经验的"编译升级"

Memory 系统应该支持:

```
原始轨迹 --[第1次使用]--> 步骤指令
            ↓
      --[积累3+案例]--> 工作流
            ↓
      --[识别模式]--> 策略
            ↓
      --[跨领域泛化]--> 原则
```

**工程实现**:
- 初次遇到成功轨迹:保存为 L1(步骤)
- 同类轨迹出现 3 次:自动泛化为 L2(工作流)
- 检测到跨情境模式:提示用户是否泛化为 L3(策略)

### 启示 3: 环境感知的编译策略

Memory 系统应该检测:

```python
def should_compile(experience, environment):
    action_space = detect_action_space(environment)
    
    if action_space == "programmable_api":
        return "code"  # 编译为代码
    elif action_space == "enumerable_actions":
        return "workflow"  # 编译为工作流
    elif action_space == "open_reasoning":
        return "strategy"  # 保持自然语言策略
    else:
        return "adaptive"  # 混合形式
```

### 启示 4: 失败经验的系统性纳入

**不只记录成功,还要记录失败**,并对比分析:

```
MemoryUnit {
  task: "优化数据库查询"
  successful_approaches: [...]
  failed_approaches: [
    {
      approach: "直接给通用建议",
      why_failed: "未先澄清数据库类型",
      lesson: "技术栈依赖的建议必须先澄清情境"
    }
  ]
  decision_boundary: "当解决方案依赖技术选型时,先问清技术栈"
}
```

### 启示 5: 跨模型的技能复用架构

```
                强模型
                  ↓
          [经验蒸馏服务]
                  ↓
            Skill 库(共享)
          /      |      \
      模型A    模型B    模型C
      (弱)     (中)     (强)
```

**关键**:Skill 库是独立于模型的资产,可以在不同模型间迁移。

## 结论

Experiential 与 Skill 不是两种记忆类型,而是同一条"经验"在**编译-解释连续谱**上的不同位置。谱上的位置由两个因素决定:

1. **环境的 Action Space 可编程性**(环境属性):决定"能编译到什么程度"
   - 可编程 API → 代码型技能
   - 可枚举动作 → 结构化工作流
   - 开放推理 → 自然语言策略

2. **抽象层级**(设计选择):决定"要编译到什么程度"
   - 原始轨迹 → 步骤 → 工作流 → 策略 → 原则
   - 抽象层级越高,可迁移性越强,但适配精度越低

经验的质量由三个因素提升:
- **失败经验的纳入**:定义决策边界,防止过度泛化
- **跨模型迁移**(Memp):经验是关于世界的结构性知识,可在模型间复用
- **MaTTS**:用推理算力直接购买记忆质量,开辟新的 scaling 路径

Memory 系统应该支持经验在谱上的**自由移动**:根据使用频率、环境变化、样本积累,动态调整经验的编译化程度与抽象层级,而不是将它们固化为两个独立的"类型"。
