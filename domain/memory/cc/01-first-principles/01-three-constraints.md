# 三个不可回避的约束

## 引言

Memory 不是锦上添花的功能特性,而是被 LLM 作为计算引擎的结构性约束逼出来的必然产物。任何基于 LLM 的 Agent 系统,无论其应用场景如何,都必须面对这三个基础约束。

## 约束一: LLM 无状态

### 约束描述

LLM 本质上是无状态的函数:`output = f(context)`。每次推理只依赖当前输入的 context,调用结束后一切清零。没有任何信息会在两次推理调用之间自动保留。

### 工程含义

- **跨轮一致性无保证**:同一对话的第 10 轮无法自动"记住"第 1 轮发生了什么
- **会话间完全隔离**:今天的对话与昨天的对话之间没有任何天然的连接
- **身份认知缺失**:Agent 不知道"我是谁"、"我服务的用户是谁"、"我们之前做过什么"

### 推论

如果希望 Agent 表现出"记忆"——即能够引用过去的交互、保持一致的行为模式、积累经验——这些能力**不能依赖模型本身**,必须通过外部机制实现。

---

## 约束二: Context Window 有限且成本高

### 约束描述

即便是百万 token 级别的长上下文窗口,仍然存在三个维度的有限性:

1. **容量上限**:物理上不可能将所有历史信息塞入
2. **注意力稀释**:上下文越长,模型对每个 token 的有效注意力越分散
3. **成本线性增长**:token 数量与推理成本、延迟成正比

### 工程含义

- **全量注入不可扩展**:把所有历史对话塞进 context 在经济上和效果上都不可行
- **位置敏感性**:同样的信息放在 context 的不同位置,模型的关注度显著不同
- **每次推理都是预算决策**:每个 token 的注入都需要权衡"价值 vs 成本"

### 推论

即便技术上可以提供无限长的 context,仍然需要一个决策机制来回答:**这次推理应该把哪些信息放进去?** 这个决策机制就是 Memory 系统的核心职责之一。

---

## 约束三: 环境与用户持续变化

### 约束描述

Agent 运行的环境不是静态的:

- **事实会过时**:今天记住的用户偏好明天可能改变
- **知识会冲突**:同一实体的不同时间点的信息可能互相矛盾
- **需求会演化**:用户的目标、角色、关注点随时间推移发生变化

### 工程含义

- **不能只写不删**:无限累积的记忆会导致噪声淹没信号
- **需要冲突消解**:当新旧信息矛盾时,必须有机制判断"保留/更新/作废"
- **时效性管理**:某些记忆有"保质期",过期后反而有害

### 推论

Memory 系统不能是简单的"只增不减"的日志,必须是**活的、可演化的、有生命周期管理的**动态系统。这要求 Memory 系统必须具备:更新、遗忘、整合等操作能力。

---

## 三约束的交汇: Memory 的第一性定义

从这三个约束出发,我们可以推导出 Memory 的本质定义:

> **Memory 的第一性本质:在有限预算下,决定什么信息、以什么形态、在什么时候进入上下文。**

这个定义的每个部分都对应一个约束:

| 定义部分 | 对应约束 | 核心问题 |
|---------|---------|---------|
| 在有限预算下 | 约束二(容量与成本) | 不能全塞,必须选择 |
| 什么信息 | 约束一(无状态) | 要保留什么 |
| 以什么形态 | 约束二(注意力稀释) | 如何压缩与组织 |
| 什么时候进入 | 约束三(动态演化) | 检索与淘汰时机 |

---

## 关键洞察

### 洞察一: Memory 是决策问题,不是存储问题

存储只是 Memory 系统的物理载体。Memory 的核心价值在于**组装决策**:给定当前任务,从历史信息中选出"这次推理需要知道的",并以合适的形式注入 context。

存储可以是无限的,但每次推理的 context 是有限的。Memory 系统的智能体现在这个"无限→有限"的映射过程。

### 洞察二: 约束不可绕过,只能交易

- 长上下文技术的进步(如百万 token 窗口)缓解了约束二,但不能消除——成本和注意力稀释依然存在
- Fine-tuning 可以把某些知识"烧入"参数,但代价是训练成本、无局部性、不可删除
- RAG 可以从外部知识库检索,但这只是把决策问题外包给了检索系统

**不存在"完美 Memory"**,只有在不同约束之间做的不同权衡。

### 洞察三: 分类不是本质,操作才是

现有文献对 Memory 的分类(episodic/semantic/procedural 等)是有用的速记,但不是第一性的。从约束出发,Memory 系统的第一性特征是**它支持哪些操作**:

- Write(写入):如何从交互流中提取可保留的信息
- Read(检索):如何根据当前需求找到相关信息
- Update(更新):如何处理信息冲突与演化
- Forget(遗忘):如何防止噪声累积
- Consolidate(整合):如何压缩与抽象

分类是为了更好地实现这些操作,而非目的本身。

## 与相邻概念的区分

基于三约束,我们可以清晰界定 Memory 与相邻概念的边界:

### Memory vs RAG

- **RAG**:检索静态外部知识库(世界常识、企业文档)
- **Memory**:管理 Agent 自身动态产生的交互经验
- **关键区别**:RAG 的知识独立于特定 Agent 实例,Memory 的内容与特定 Agent-User 关系绑定

### Memory vs Context Engineering

- **Context Engineering**:单轮内的信息组织与提示词设计
- **Memory**:跨时间的状态维持
- **关键区别**:Context Engineering 在约束二内优化,Memory 解决约束一和三

### Memory vs 参数化知识

- **参数化知识**(pretrain 权重):模型在训练时习得的世界常识
- **Memory**:运行时累积的私有历史
- **关键区别**:参数化知识的写入成本极高且无局部性,Memory 强调低延迟的增量更新

### Memory vs Long-context

- **Long-context**:扩大约束二的上限(从 4k 到 1M tokens)
- **Memory**:在给定约束下的组装决策
- **关键区别**:Long-context 改变约束的参数,Memory 解决"如何利用有限容量"

## 研究含义

从第一性约束出发的研究路径与从"如何分类 Memory"出发的路径有本质不同:

### 传统路径(自上而下)

认知科学分类 → 套用到工程 → 为每类设计存储与检索 → 评测各类的准确率

**问题**:容易产生"为了分类而分类"的设计,约束的本质被掩盖

### 第一性路径(自下而上)

三约束 → 推导操作需求 → 设计操作的实现空间 → 以操作为轴评测系统

**优势**:直接对准约束,设计决策可追溯到第一性原理

---

## 小结

Memory 不是 Agent 的"锦上添花",而是被三个不可回避的约束逼出来的**必然产物**:

1. **LLM 无状态** → 需要外部机制保留历史
2. **Context 有限且贵** → 需要决策机制选择注入内容
3. **环境持续变化** → 需要生命周期管理

这三个约束共同指向一个统一的本质:**Memory 是在有限预算下的上下文组装决策系统**。

所有 Memory 系统的设计选择——分类方式、存储结构、检索策略、更新机制——都是在这三个约束的权衡空间中的不同位置。理解约束,就理解了为什么 Memory 必须存在,以及为什么它必然是现在这个样子。
