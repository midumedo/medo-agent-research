# Agent Memory Forms：参数记忆、Token Memory 与 Latent Memory

作者：Codex（基于 GPT-6；具体子型号未确认）  
日期：2026-11-02

## 摘要

过去的经验要影响未来，必须在系统中留下某种可以继续使用的东西。对以语言模型为核心的 agent，这种保留可以发生在三个不同位置：经验可以改变模型的权重；可以被保存为以后重新读取的符号记录；也可以被保存为模型能够继续使用的数值表征或计算状态。它们分别构成本文讨论的参数记忆、token memory 与 latent memory。

三者的区别会直接改变记忆的工作方式。参数记忆把经验的影响写入模型以后执行的计算；token memory 让经验保持为独立记录，在需要时交给模型理解和应用；latent memory 则保留与模型计算相适配的状态，使后续计算能够使用这些状态，而不必总从原始材料重新开始。本文分别展开三类记忆怎样形成、怎样被使用，以及其能力、更新方式和成本为什么会由此产生。分类的目的，是解释这三种机制，而不是仅给现有方法归类。

## 一、同一条经验，可以怎样被留下来

设想一个研究助手刚得知一条项目约定：**报告中的时间统一使用 UTC，并保留原始样本编号。** 这轮对话结束后，用户可能隔几天才要求它整理另一批实验。后来的请求未必重述这条约定，系统需要让过去的信息继续起作用。

一种做法是把相关经验用于训练或编辑模型。更新成功后，模型处理该项目的报告任务时，已经更倾向于保留编号并使用 UTC。另一种做法是把约定存成记录，在整理报告前查到它，再将它与任务一起提供给模型。还有一种做法是把项目资料处理成模型可以直接使用的状态，保存这些状态，后续处理报告时继续读取。这个例子用于比较机制，不预设某个具体模型已经能可靠完成三种实现。

第一种做法改变了模型的权重，属于**参数记忆（parametric memory）**。后两种做法保留了主体权重之外的材料或状态，属于本文所说的**外部记忆（external memory）**。外部记忆中，通过符号输入读取的内容称为 **token memory**；通过表征或状态输入使用的内容称为 **latent memory**。因此，本文先分参数记忆与外部记忆，再在外部记忆中区分 token 与 latent。

这里的“外部”相对于所研究模型的权重而言。它不要求离开模型所在的进程或显存。Token 也不要求磁盘上存的恰好是 tokenizer 的整数编号；自然语言、结构化条目和代码，只要最终作为符号内容交给模型读取，都可以沿这条路径发挥作用。Latent 指模型可使用的数值表征或计算状态，例如模型已经处理一段资料后形成、能够供后续计算继续读取的一组向量。

本文主要讨论跨模型请求的保留，包括同一会话内多次请求之间的保留。一次请求中产生、结束后即消失的激活，用于解释计算过程；它们尚未成为这里研究的持久记忆。分类也始终以同一个目标模型的实际实现为参照：LoRA 的矩阵作为权重增量起作用；连续前缀则是一组直接提供给模型的前缀向量或激活，作为输入状态起作用。二者即使都通过训练得到，仍分别属于参数与 latent 路径。[LoRA](index.md#source-lora)；[Prefix-Tuning](index.md#source-prefix-tuning)

这几项约定足以开始讨论。接下来真正要回答的是：**三种保存方式，为什么会让记忆的写入、使用与变化呈现不同性质？**

## 二、参数记忆：经验改变模型以后怎样处理输入

### 2.1 一条经验怎样进入权重

语言模型用权重执行计算。输入经过一系列变换，形成对后续输出的预测。训练改变这些权重，也就可能改变模型对相同输入的处理结果。参数记忆形成于这个过程中：过去的数据或反馈在权重中留下变化，后续任务再次使用这些权重，因而受到过去经验的影响。

继续看项目约定。若通过训练写入，系统需要把“时间用 UTC，保留样本编号”变成可优化的目标。例如，提供若干报告整理任务及符合约定的输出，使模型在这些输入下更倾向于生成所期望的结果。对于一种常见的监督训练形式，可以把目标简写为：

$$
\theta_{\mathrm{new}}
\leftarrow \operatorname{Update}\!\left(
\theta_{\mathrm{old}},
-\sum_{(x,y)\in D}\log p_\theta(y\mid x)
\right).
$$

这里，\(D\) 是用于更新的输入与目标输出，\(\theta\) 是模型权重。式子表达的含义很直接：根据这些例子调整权重，让目标输出在相应输入下更可能出现。采用梯度训练时，系统会计算可训练参数对误差的局部影响，据此确定更新方向；这种局部变化率就是梯度。实际更新还可以加入保持原有行为的约束，也可以只更新一部分参数。[LoRA §2、§4.1](index.md#source-lora)

从经验到训练目标的这一步至关重要。模型收到一条约定，并不意味着它自动知道应当在哪些场景中应用。若训练例子包含项目身份，更新就有机会学习“在这个项目中这样处理”；若训练只反复奖励 UTC 格式而没有区分项目，学到的变化可能更宽，影响原本使用其他时区的任务。**写入参数时，数据选择和训练目标共同决定哪些经验差异值得保留。**

因此，参数写入并非把一句话逐字放进某个权重地址。它是在用过去的经验改变未来计算。模型可能保留了某个事实的可回答性，也可能形成了处理一类任务的行为倾向，还可能保留了一些训练者没有预期的关联。具体保留了什么，要从更新目标、实际变化和后续行为共同理解。

### 2.2 以后回答时，模型怎样用到这些记忆

几天后，用户要求“整理这批实验结果”。如果相关经验已经写入模型，新的请求会经过更新后的权重。模型可能识别出项目、决定报告结构、生成时间字段并保留样本编号。这个过程不一定包含“先找到那句约定，再把它读一遍”的步骤。过去经验的作用可以分布在当前输入的识别、内部表征的形成和输出的生成过程中。

这解释了参数记忆的一项重要能力：**过去经验可以在模型处理新输入时直接参与计算，不必每次都重新提供完整来源。** 如果模型已经学会在不同表述下识别同一项目要求，那么“汇总本次结果”“补一份实验说明”“整理附件数据”等不同请求，都可能引出相应行为。

这种灵活性来自模型怎样表示输入和使用权重。两种提问方式若没有被模型处理为相关情境，同一经验的影响就可能无法在两种情况下都发挥作用。理解参数记忆的有效范围，需要继续看训练要求模型完成哪些任务，以及这些任务之间共享了什么。

普通语言模型也不承诺每个事实都有一个独立地址。对一条知识的使用可能依赖多个位置的计算；同一组权重又可能参与许多知识和行为。因此，能指出一个编辑位置，与能把所有有关知识完整列成条目，是不同程度的理解。ROME 展示了对特定事实关联进行局部权重编辑的机制，也让这个区别变得具体：可编辑的局部计算可以存在，原始来源却未必能被当作独立记录从权重中读回。[ROME](index.md#source-rome)

### 2.3 记住一条事实，与学会在任务中做事

“报告时间使用 UTC”可以至少以两种要求进入训练。一种要求模型在被问及时答出这条事实；另一种要求它在整理任意一批相关实验时，识别输入时间的含义、完成必要转换、选择正确输出格式，并同时保留样本编号。后者涉及多项计算在任务中的配合。

例如，原始记录是“sample-river-018，2026-11-02 09:30+08:00”。符合要求的报告需要保留 sample-river-018，并把时间写成 2026-11-02 01:30Z，其中 Z 表示 UTC。训练若要支持这种行为，目标就需要包含时间换算和编号保留，而不仅是回答“应该使用 UTC”。遇到缺少原始时区的记录，正确处理又应包括识别缺失，而不是擅自填入一个偏移量。

若只训练“问项目时区，答 UTC”，得到的证据首先支持这个问答关系。若训练覆盖不同来源的时间格式、不同报告任务和容易遗漏编号的情况，训练目标就进一步约束了应用过程。这种差别解释了为什么“知道规则”与“稳定按规则完成任务”应当分别研究：它们需要在不同输入上产生不同程度的正确行为。

参数记忆可以支持事实，也可以支持识别模式、选择步骤或生成动作的能力。两者都通过权重影响计算，不能仅凭“事实”或“技能”的内容名称，另判一种存储形态。真正不同的是训练要求保留哪些关系，以及成功需要覆盖怎样的输入范围。

这也给参数记忆的泛化一个具体含义：在没有逐项提供过答案的新输入上，已有权重变化仍能产生符合要求的结果。它可能来自新旧任务共同使用的特征和计算。例如，不同报告虽然内容不同，却都需要识别时间字段和样本标识。若更新改善的是这些可复用的处理关系，它就有机会同时改善多个任务。若更新仅适配训练样本的表面模式，效果便可能集中在相似样本上。

### 2.4 共享计算为什么同时带来迁移机会与干扰

同一组权重被多种输入使用，是理解参数记忆的重要起点。先只看一个线性层，固定进入该层的表示 \(x\)。权重从 \(W\) 变为 \(W+\Delta W\) 后，该层输出的变化是：

$$
\Delta h=\Delta W x.
$$

这说明一次权重更新对不同输入的影响取决于各自的 \(x\)。如果另一项任务也使用到被更新的计算方向，它就可能受到影响；如果其输入落在该更新不起作用的方向上，局部输出可以保持不变。

对项目报告来说，更新可能帮助模型更稳定地识别时间字段，从而改善多个相关任务；也可能过度加强某种格式偏好，把其他项目的报告一起改成 UTC。二者都需要从“哪些任务共享了哪些计算”来解释。共享计算提供了经验跨任务复用的条件，也形成了修改影响超出目标任务的可能性。

参数编辑和持续训练中的保护方法，正是在处理这个问题：一面改变需要改变的输入输出关系，一面保留其他关系。有的方法约束训练目标，有的方法限制更新位置，有的方法在选定表征上要求局部映射不变。AlphaEdit 给出了后一类机制的具体实例。保护哪组表征、实际覆盖哪些任务，会决定这种保护的有效范围。[AlphaEdit](index.md#source-alphaedit)

因此，参数更新的关键困难是**写入选择性**：不仅要让新经验起作用，还要控制它在哪些情况下起作用。把每次更新都描述成必然遗忘，会失去这个可研究的机制；把更新成功理解为旧能力自然不变，同样会忽略共享计算带来的影响范围。

### 2.5 原位更新、附加增量与定点编辑

参数记忆不只对应一次完整模型训练。不同写入方式改变的是参数系统中的不同部分。

**原位更新**直接改变现有权重。后续请求只要使用新版本，就使用这些变化。它可以把新的经验整合进原有计算，但更新与原有能力共享状态，因此需要关心新旧行为如何共同保持。预训练形成的知识与运行中追加的训练，在历史阶段上不同；就后续读取而言，都可以通过权重发挥作用。

**附加参数增量**把任务相关变化保存在可独立装载的模块中。LoRA 用两个较小矩阵的乘积表示某些层的权重修正，以这种低秩表示减少需要训练的参数。底座可以保持不变，系统按任务选择相应增量，也可以在适当条件下把增量合并进原权重。这使参数记忆能够按模块保留和切换：研究某个项目时装载其增量，离开该项目时不使用它。模块边界提供了操作上的隔离；模块内部各条经验是否相互独立，仍由更新方式决定。[LoRA §4.1](index.md#source-lora)

**定点编辑**尝试以较明确的目标修改特定计算。例如希望一个事实关联发生变化，同时尽量保留其他回答。ROME 为选定的前馈网络层构造权重修改：先求取该层对目标输入应产生的表示，再以有约束的矩阵更新把这个关系写入。它说明参数写入可以针对具体关系设计，而不必总以全模型常规训练实现。[ROME §3.1](index.md#source-rome)

三者都把变化留在模型参数中，却为更新粒度、装载和回滚提供不同条件。保留旧版本可以恢复更新前的权重；卸载独立增量可以停止使用该模块；回滚整个版本则可能一并撤销其中其他有价值的更新。要撤销的经验越细，所需的版本、模块或编辑控制通常也越细。

### 2.6 参数记忆把哪些工作提前完成了

在使用参数记忆的路径中，经验已经在写入阶段参与了模型调整。未来处理任务时，系统可以使用调整后的模型，而不必为每次使用都提供全部训练材料。这种安排有利于让反复使用的经验参与日常计算，也使写入质量格外重要：写入阶段错误地概括了适用范围，后续许多任务都可能继承这个偏差。

对于已经合并到原矩阵、且不改变计算结构的权重更新，该层推理仍执行原有形状的运算。经验增加并不必然使每次请求多出一段来源文本。但成本并未消失：构造更新、评估其影响、保留和切换版本，都需要资源；未合并模块还可能增加计算与装载开销。若事实变化频繁、每次只使用几次，写入的投入能否被后续使用抵消，就成为重要问题。

另一个代价是来源与行为之间的距离。文本记录可以直接保留“谁在何时提出了什么”；训练后的权重主要为后续计算提供数值条件。系统若还需要追溯依据，通常需要另外保留数据、版本关系或相应记录。能够生成正确答案，并不自动提供这次答案来自哪条经验的完整说明。

在有限精度、固定大小的参数状态中，可区别的信息总量也是有限的。实际瓶颈还可能更早发生在更新方法和读取能力上：状态仍有可表达空间，训练却没有找到合适的写入方式；某种关系已影响部分输入，却没有被另一种提问有效调用。因而参数记忆的有效容量，需要连同训练方法和任务要求来研究。

**参数记忆最值得把握的特点，是经验与模型计算的紧密结合。** 这种结合让经验能够影响多种后续输入，也使知识的写入范围、来源追溯和局部修正，比修改一条独立记录更依赖对模型行为的控制。

## 三、Token memory：保留经验的表达，在需要时重新理解和应用

### 3.1 记录本身是怎样一种记忆

若采用 token memory，系统可以把项目约定保存为一段文字：“本项目报告中的时间统一使用 UTC，并保留原始样本编号。” 后来的任务出现时，系统找到这条记录，将它与任务一起交给模型。这里长期保留的是一份可以再次读取的表达；模型权重可以在整个过程中保持不变。

记录可以是原话，也可以是整理后的事实、规则、步骤、代码或结构化字段。共同之处是：它们保留了一份独立于当前模型执行的符号内容。人或程序可以定位这份内容，模型则在读取时利用已有能力解释它。这使保存经验和使用经验之间保留了较明确的分界。

这种分界有实际意义。记录可以先保存下来，以后再决定怎样检索、怎样组合、交给哪个模型。更换模型后，文本通常仍能作为文本提供，虽然不同模型的理解与应用能力可能不同。修改读取策略，也不必重新训练或重写整份材料库。**Token memory 将“经验的表达”与“使用经验的计算”分开，使二者可以分别演进。**

但记录不是天然正确的事实。它可能记载了一个人的说法、一个暂时决定或一次失败尝试。保存这些内容并没有把它们变成永远成立的规则。记录应被怎样使用，要由其来源、时间、适用范围和当前问题共同决定。

### 3.2 写入时，首先要决定保留什么意义

同一次交互可以产生不同的记录。保存完整原话，可以保留条件、措辞和上下文；提取事实条目，可以让重要信息更容易被找到；形成操作规则，可以直接说明以后如何做。这些写法在后续任务中提供的帮助不同。

例如，原话是：“这次对外报告可以去掉样本编号，但内部实验报告仍要保留。” 若提炼成“报告可以去掉样本编号”，就丢失了报告类型和适用范围。以后即使准确检索到这条短记录，模型也可能据此删掉内部报告中的编号。问题发生在写入阶段：保存的表达已经不再支持正确区分。

相反，一份带条件的记录可以明确保留：“内部实验报告保留原始样本编号；本次对外版本例外。” 后续任务就有机会根据报告类型选择正确规则。这个例子说明，压缩的核心不是删掉多少字，而是哪些区分必须继续存在。时间、主体、对象、例外和决定状态，有时比一句规则的主干更决定行为。

原始材料与提炼记录也可以承担不同任务。原文支持追溯与重新解释；提炼后的条目降低选择和使用成本；面向任务组织的规则则突出行动条件。若只保留一种短摘要，系统是在用当前判断决定未来还能问哪些问题。若保留来源及其关系，以后发现摘要遗漏时，就有机会回到来源重新处理。

这不意味着每条记录都需要完整元数据或固定模板。需要保留哪些条件，来自未来任务可能需要区分什么。对一个恒定的项目设置，简单字段可能足够；对不断变更、包含例外的协作决定，时间和作用域就可能是内容本身的一部分。

### 3.3 大量记录怎样变成一次可用输入

长期保存的材料库可以远大于一次模型输入。当前任务到来后，系统必须决定拿出哪些材料。这一步可以是按项目读取固定文档，也可以是关键词搜索、向量检索，或 agent 在观察中继续查找。RAG 是其中一种机制实例：检索器用向量选择文档，生成模型再读取选中文本。[RAG §2](index.md#source-rag)

对项目报告任务来说，系统可能同时保存着旧约定、当前约定、另一个项目的约定以及一次性例外。仅找到“UTC”这个词还不够；需要找到当前项目、当前报告类型所适用的内容。选择过程实际上在解决“过去哪部分经验与现在有关”。其结果决定哪些记忆有机会影响这次任务。

选中之后，还需要组织输入。系统要把任务、资料、约定和必要的来源关系放在模型可读取的位置。如果旧规则和新规则都被放入，却没有注明哪条仍有效，冲突就被留给模型重新判断。如果只放入一个摘句，删掉了它的适用条件，正确的检索结果也可能在组装时失去意义。

因此，token memory 的使用包含几次不同的取舍：写入时决定保留哪些信息，选择时决定当前读取哪些记录，组装时决定以怎样的关系呈现它们。每次取舍都可以减少无关内容，也可能丢失任务所需的区分。有效的系统应让这些取舍服务于同一任务，而非各自只追求“更短”“更相似”或“更多命中”。

检索向量在这里帮助选择记录。若目标语言模型最终接收的是文本，则这份记忆仍沿 token 路径使用。选择工具所用的表示，与模型实际读取的内容可以不同；理解这一点，才能把检索失败和模型应用失败分别定位。

### 3.4 读到规则以后，计算仍然没有结束

一条记录进入输入，提供的是模型可以使用的条件。模型还需要判断它与当前任务的关系，并把它落实到输出中。

在报告例子里，模型需要识别输入中的样本编号、区分编号与行号、理解哪些时间已经是 UTC，以及决定报告哪些部分需要保留这些字段。记录给出了要求，却没有替模型完成每一步。若输入只有一个不带时区的时间值，文本规则也不能凭空提供缺失的原始时区；系统需要查找来源或保留不确定性。

这说明 token memory 的能力由记录与读取能力共同形成。记录可以补充当前模型原本没有的信息，也可以提醒模型调用已有步骤；而解释条件、执行转换和核对结果，则依赖模型及相关工具。如果模型无法完成时间转换，把约定存得更完整也不能单独补足这项计算能力。

这同时说明为什么保存程序、规则或示例可能有价值。它们不仅提供结果，还可以提供完成任务所需的步骤和约束。后续模型可以据此推理、生成动作或调用工具。经验于是能够从“上次发生了什么”，进一步变成“遇到这种情况应怎样处理”。其效果来自记录内容与执行过程的结合，不能只从记录类型判断。

Token memory 因而具有一种开放性：保存同一份项目资料，以后可以用于生成报告、检查报告、解释决定或发现冲突。它没有在保存时把所有未来用途固定成某个模型的数值状态。能够支持多大范围的用途，仍取决于保存内容的完整性与后续读取者的能力。

### 3.5 权重不变，系统怎样持续获得新能力

假设基础模型完全不知道这个项目的内部约定。保存并取回记录之后，完整系统就可以在相关任务中使用这项新信息。变化发生在外部记录及随后输入中，模型权重保持不变。这里获得的首先是对新信息的持续访问，以及在既有计算能力支持下使用它的能力。

这不是把“记住”缩减为一次提示。只要记录持续存在，之后多次任务都能重新访问它，经验就跨越了最初那次交互。若记录还会根据新经验修正，完整系统的行为就可以持续变化。例如项目新增了报告例外，系统更新相应条目；以后遇到该类报告时，读取的条件随之变化。

这种信息适应并不要求改变处理程序本身，其最小构造见[《推理》](推理.md#external-adaptation)。在报告任务中，语言模型使系统能够处理较丰富的表达，也使结果依赖于它能否正确理解规则、识别任务条件并完成应用。

记录还可以保存从多次经历中总结的规律。这里的规律是怎样得出的，与它后来怎样被使用，应分别研究。总结程序可能归纳得很好，也可能把偶然事件误当一般规律；读取模型可能正确应用，也可能忽略前提。称其为 token memory，只说明规律以符号形式被保留和使用，并没有预先裁定归纳过程的质量。

### 3.6 显式记录为什么容易修改，也为什么仍会过时

当约定作为独立记录存在时，系统可以明确定位它、检查措辞、修正字段，并保留更新前后的差异。把“本次例外”误写成“所有报告”的错误，可以在记录层直接更正。与调整模型权重相比，这种操作更直接地对应人想修改的那句话或那条事实。

显式记录也允许保留来源。读者可以看到规则来自哪次决定、与哪些材料有关；多个模型或使用者可以围绕同一条记录协作。它降低了检查保存内容的门槛，也使错误能够在进入模型前被发现。

不过，记录层的清楚并不自动使系统行为清楚。旧规则可能仍出现在摘要中，另一个工具可能读到旧版本，输入组织也可能把已经失效的内容重新带回任务。因而一次语义上的修正，要沿实际使用的记录关系传播。问题不是“文字不可修改”，而是系统究竟会从哪些地方重新读取这项信息。

更新还可能意味着保留多个有效值。例如内部报告与外部报告采用不同字段要求。此时直接覆盖旧值会丢失区分；正确做法可能是把条件写清，并让读取过程选择相应规则。Token memory 的可编辑性提供了完成这件事的手段，数据组织和选择策略决定它是否真的完成。

### 3.7 记忆库增长之后，困难会移到哪里

显式记录通常可以通过增加存储空间继续积累。新增一条记录不必覆盖旧条目，这使逐项保存经验成为自然的操作。但后续使用仍有有限的时间、输入空间和计算预算。记录越多，系统越需要从大量材料中找出当前有用的部分。

因此，token memory 的主要限制不只是能存多少。没有被选中的记录，本次没有机会发挥作用；选中的内容过多，可能增加计算并引入相互竞争的要求；经过摘要的内容更容易放入输入，却可能已失去某个未来任务所需的细节。存储、选择和使用之间必须共同决定保留粒度。

文本读取本身也需要模型计算。重新提供一段长资料，通常需要为这段输入构造相应表征；若已有相容缓存，系统可以复用其中一部分计算，这时就出现了与 latent 状态的实际分工。单纯把资料存成文本，并不会自动免去其后续处理成本。

**Token memory 的关键优势，是让经验作为独立、可重新解释的内容留下来。** 它提供直接检查、编辑、关联来源和按任务组合的空间。相应的主要任务，是在每次使用时把正确内容带到模型面前，并让模型正确理解和落实其中的条件。

<a id="latent"></a>
## 四、Latent memory：保留模型可以继续使用的表征与状态

### 4.1 模型读完一段资料后，留下了什么

模型读取项目约定时，不会始终以原始文字的形式计算。符号首先被转换成数值表示，再经过模型各层处理。某一位置的内部表示可以结合此前内容，成为后续计算所用的 hidden state，即模型运行中的内部向量状态。Attention，即按计算得到的权重组合可读取表征的机制，还会使用由有关表示构造的 keys 和 values；下一节展开它们怎样参与后续读取。

如果这些结果随着请求结束而消失，下次使用相同资料时，就需要重新完成相应计算。若把其中某种状态保留下来，并在后续请求中继续使用，就形成了本文讨论的 latent memory。对于这类保留计算结果的实现，后续计算不必重新把来源符号处理到这一保存位置，而可以从保存状态继续。

这给出 latent memory 最直接的来源：**让一次计算形成的状态跨越请求继续存在。** 过去的影响因此能够延续，后续任务也可能省去已完成的一部分计算。它不要求每次都重新训练一个模型，更不要求保存状态后立即丢弃来源文本。

但 latent memory 的来源不止缓存。数值状态还可以经过压缩、变换或直接优化，为某类后续任务提供更合适的条件。理解这一类记忆，需要先看状态怎样被读取，再看它怎样被构造。

### 4.2 以 KV 为例，过去的信息怎样参与新问题

在 Transformer 的 attention 中，query、key 和 value 都是向量。一个 head（注意力头）使用自己的一组 query/key/value 投影完成读取；多个 head 可以并行进行这种计算。对其中一个 head 的某个查询位置，可以把读取过程写成：

$$
\operatorname{Read}(q,K,V)
=\operatorname{softmax}\!\left(\frac{qK^\top}{\sqrt d}\right)V.
$$

\(q\) 是当前查询位置的向量；\(K\) 是可读取位置的 keys；\(V\) 是相应 values；\(d\) 是 query/key 的维度。计算先用 query 与 keys 得到分数，再把分数变成权重，最后用这些权重对 values 求和。这里的 query 是一层计算中的向量，不是自然语言问题本身；问题要经过模型处理，才会形成各层各位置的 query。[Transformer §3.2](index.md#source-transformer)

假设一段项目资料已经形成各层 KV。后来用户问“整理这批实验结果”，新输入在计算中产生查询，相关位置可以读取这段资料留下的状态。用户改问“检查报告是否符合项目要求”，后续查询会不同，对同一份 values 的加权也可以不同。保存状态因而可以支持多种后续计算，不只是重放某一个既定答案。

固定前缀的复用机会来自计算中的可见性限制。因果 attention 用遮罩禁止前缀位置读取后来才追加的内容。因此，在模型、前缀、位置及相关计算条件相容时，更换后续问题不会改变前缀本来应当算出的 KV。新问题可以读取这份 KV，无需先把它还原成原文。这里的复用条件由因果计算结构推出；因果遮罩的原始机制见 [Transformer §3.1、§3.2.3](index.md#source-transformer)。

这种复用保留了已完成的前缀计算，却没有替后续问题完成全部推理。新的请求仍需产生自己的表示，读取 KV，经过后续计算并生成结果。节省的是重新构造相应历史状态的工作；后续使用这些状态的计算仍然存在。

### 4.3 保存的位置不同，实际保留的东西就不同

保存输入 embedding，与保存深层状态，留下的是不同阶段的结果。Embedding 是符号进入模型时的数值表示；保留它可以省去对应的查表或编码步骤，但通常仍需执行后续模型层。较深的 hidden states 则包含经过相应层处理后的表示，但后续使用要求模型提供适当的继续计算方式。

KV 保存的是 attention 将要读取的特定状态。它通常按层、位置和 head 组织，适合后续 query 继续访问。完整 KV 的位置结构，也使“保留更多历史”往往意味着保存更多状态。源文本中的一句话可能分成多个 token，在不同层留下多组向量；它不是天然对应一个紧凑的事实字段。

循环状态采用另一种组织方式：模型持续用新输入更新一个状态，后续再以该状态参与计算。在固定大小的状态中，持续增长的历史需要被不断整合，哪些区分能够保持便取决于状态更新机制。它与按位置积累的完整 KV，在增长方式和信息选择上并不相同。

Transformer-XL 提供了复用历史 hidden states 的具体机制：上一段的状态参与下一段计算，并配合相对位置处理。它说明历史可以通过保留激活延续。论文的跨 segment 是该架构的计算边界；要成为跨请求的记忆，还需要运行系统实际保留并重新提供这些状态。[Transformer-XL §3](index.md#source-transformer-xl)

因此，研究 latent memory 不能只说“保存了一个向量”。需要说明向量对应哪个计算阶段、怎样进入后续模型、其规模怎样随历史增长。保存位置决定已经完成了什么，也决定以后还需要计算什么。

### 4.4 缓存、压缩和直接优化，分别怎样形成状态

**直接保留计算结果**最接近通常的缓存。模型处理资料后，把得到的 KV 或其他状态保存下来。写入过程主要继承正常模型计算；其作用首先是保持历史条件，并使以后能够复用。若使用条件相容，重新读取这些状态可以避免相应重算。

**压缩或变换状态**则进一步改变表示。系统可以选择部分状态、减少精度、压缩位置或形成新的摘要向量。这样做是为了在有限存储和读取预算中保留对任务重要的内容，但它必须决定哪些区别值得保留。若未来任务需要被压掉的样本编号，状态再小、读取再快，也无法单凭这些状态可靠恢复那个已丢失的区别。

这里需要注意，文本摘要与 latent 压缩都涉及选择，但选择的对象不同。文本摘要生成另一份可读表达；latent 压缩生成后续模型能够使用的数值表示。二者都可以围绕任务优化，只是对结果的检查方式、读取过程和模型依赖不同。

**直接优化状态**不必先得到一份完整缓存再删减。系统可以冻结主体模型，把一个连续前缀或一组 KV 作为可调整对象，用任务数据优化它们，使主体在读取这些状态后更容易完成目标。Prefix-Tuning 冻结语言模型并学习连续前缀；Cartridges 的一个具体实现直接优化可重复使用的 KV。[Prefix-Tuning](index.md#source-prefix-tuning)；[Cartridges](index.md#source-cartridges)

具体而言，每次训练让主体模型读取待优化状态和任务输入，再依据目标输出计算误差。误差通过模型的计算传回待优化状态，系统据此调整前缀或 KV，主体权重则保持不变。冻结权重限制的是哪些数值可以被修改，并不妨碍计算输出对输入状态的依赖。经过多次更新，后续 query 读取的便是一份被这些任务目标塑造过的状态；训练把工作落实在了外部数值状态上。

这种状态可能适合目标模型使用，却没有对应的一句自然语言原文。它保留的内容体现在对后续计算的作用中。例如某组优化状态可能帮助模型按项目格式生成报告，但是否同时支持逐字恢复原始约定，是另一项任务。优化时使用什么问题和目标输出，会影响状态保留哪些信息。

直接优化也解释了参数与 latent 的一个关键区别：二者都可以通过训练产生，但训练得到的对象以后在计算中做不同的事。LoRA 的增量改变层的权重计算；连续前缀和 KV 作为状态供模型读取。训练是构造方法，不能单独决定记忆属于哪一类。

### 4.5 数值表征为什么依赖产生和读取它的模型

文字“保留原始样本编号”具有可由不同读者重新解释的符号形式。某一模型为这句话产生的状态，则同时受到该模型的权重、层结构、位置处理和此前上下文影响。后续计算能够使用这些数值，是因为读取它们的操作与这种表示相配合。

两个模型即使使用相同维度的向量，也不意味着相同数值承担相同含义。一个维度、一个方向或某种组合怎样影响计算，来自各自模型的具体变换。把状态装载成功，只说明某些输入要求被满足；要继续获得预期结果，还需要产生与读取之间保持有效对应。

这使 latent memory 的可复用范围成为一个明确的技术问题。对于同一固定模型、同一前缀及相容位置安排，复用可以很直接。换模型、换编码方式或改变前置上下文之后，可能需要重新构造、变换状态，或验证近似使用是否仍满足任务要求。更新模型版本并不必然破坏所有旧状态，但需要查清改动是否触及相应计算。

这种依赖来自数值表示与读取计算之间的配合。对于复用已有计算的状态，这种配合让相应的前缀计算能够沿用；对于专门优化的状态，这种配合决定它能否发挥训练时形成的作用。两者都要求保存状态与当前模型的读取方式相匹配。

### 4.6 经验改变时，怎样修正已经保存的状态

若项目把某类报告的时区要求改了，修改原始文本并不会自动修改此前保存的 KV。旧状态仍由旧内容和旧计算产生，后续读取它时仍可能受到旧约定影响。因此，来源更新与状态更新需要联系起来。

直接由资料构造的缓存，可以根据依赖关系失效并重新计算。对于因果模型，如果前缀中间发生改变，后面位置的状态可能已经读过被改内容；重建范围因而不一定局限于被改动的几个 token。若更新仅在末尾追加，并且原有前缀保持相容，则原状态又可能继续使用。具体失效范围应从真实依赖确定。

经过压缩或直接优化的状态，修正方式可能不同。它可能需要重新优化，也可能允许局部更新，但不一定存在一个可直接改成“UTC”的字段。人可以定位和替换整个状态文件，却未必能像编辑文本那样指出其中哪几个数值只对应这条约定。

这并不使 latent 状态不可管理。系统可以按项目或资料分开保存，记录其来源与模型版本，在约定变化时替换相应状态。实例级的选择和撤销仍可以很明确；困难主要在于语义信息怎样分布于数值表示，以及某次内容变化需要改动多大范围。

### 4.7 计算节省、存储体积与可用信息怎样共同约束它

保存已经计算出的状态，不等于一定比保存来源更小。完整 KV 会为多个位置、多个层和多个 head 保存 key 与 value。以 32 层、32 个 KV heads、每头 128 维、每个数值 2 byte 的未压缩实现为例，一个位置对应 512 KiB；100,000 个位置约为 48.83 GiB。数值来自状态形状的直接计数，完整推导见[《推理》](推理.md#cost-and-reuse)。

这个体积之所以可能远大于文本，是因为保存的是计算过程中展开的多层状态。后续少做编码的收益，可能需要更多存储、装载和传输来换取。共享前缀使用很多次时，这笔交换可能有利；只使用一次或频繁失效时，收益就可能不足以覆盖新增费用。

后续读取也有成本。在普通稠密 attention 中，query 仍要与被保留的历史状态计算并聚合。保存更多位置，让更多历史保持可访问，同时增加所需存储和读取工作。压缩、筛选或限制状态窗口，可以减轻开销，也改变后续还能够利用哪些历史区别。

直接优化的状态有机会在较小空间中突出某类任务所需的信息，但效果与训练目标紧密相关。若未来问题偏离优化时关注的内容，原先被省略的区别可能重新变得重要。状态小、能回答某组问题和能保留全部来源，是不同的保存目标。

**Latent memory 的关键，是把历史以适合模型继续计算的状态留下来。** 它能够复用已经完成的处理，也允许针对后续任务构造表征。其主要代价则来自数值状态与模型的依赖、状态读写的资源需求，以及内容变化时如何保持这些状态有效。

## 五、三类记忆究竟改变了什么

### 5.1 经验在哪一步被加工，决定了以后怎样使用

现在可以回到同一条项目约定。参数方案把相关经验用于修改模型，使未来的输入经过更新后的计算。Token 方案保存约定的表达，让模型在处理未来任务时重新读取和应用。Latent 方案则把约定及相关资料变成可保存的状态，让未来计算直接使用这些状态。

这三个过程都让过去影响未来，但它们把工作放在不同位置。参数写入承担调整模型的工作；token 保存给未来保留较多重新解释的空间；latent 构造则完成特定表征处理或针对任务优化状态。由此，三者在后续读取、内容修改、来源检查和计算复用上出现不同性质。

| 要理解的问题 | 参数记忆 | Token memory | Latent memory |
|---|---|---|---|
| 长期留下什么 | 权重或权重增量中的变化 | 可再次读取的符号记录 | 可被模型继续使用的表征或计算状态 |
| 经验怎样影响后续任务 | 新输入经过已经改变的计算 | 相关记录进入输入，被模型解释和应用 | 后续计算读取或延续保存状态 |
| 主要给出了什么能力 | 将经验融入处理输入的方式 | 让经验独立保存、检查、修正和重新组合 | 复用已完成的处理，或提供为任务构造的状态 |
| 内容变化时主要处理什么 | 更新的目标与影响范围，以及版本或模块 | 记录中的条件、时间与相互关系，以及实际读取路径 | 来源依赖、状态重建或更新，以及读取兼容性 |
| 资源问题集中在哪里 | 写入与评估、模块和版本使用、有限参数的利用 | 内容组织与选择、输入预算、解释和应用 | 状态构造、存储与装载、后续读取和失效 |

表中的性质来自前面展开的机制。它们不能脱离具体实现简单排成优劣，但也不意味着三类只是名字不同。修改一条记录、调整一组权重和重建一份状态，确实对应不同的工作，并对后续使用提出不同要求。

### 5.2 同一信息有多个保存结果时，分工怎样发生

三类记忆可以同时服务于一项经验。例如保留项目约定的原文用于查阅和更新，同时为频繁使用的固定项目资料保存 KV；若长期处理同类报告，还可以训练模型改善相关任务能力。这里每一份保留对象都应有明确用途，而不是仅为了凑齐三种形态。

原文提供重新解释和重建的依据；状态支持特定模型下的重复使用；参数更新改变模型处理任务的方式。这种分工可以有价值，也会产生同步问题：原约定变了，哪些状态需要重建，哪些训练结果仍适用，都需要根据实际依赖回答。

普通文本输入在一次运行中产生 embedding 和 KV，并不自动意味着系统已经持久化了多种记忆。只有其中的状态被跨请求保留，才多出一份需要选择、更新和失效管理的记忆对象。相同信息出现于多个位置，也不意味着这些对象能逐项互相恢复。

是否值得采用一种分工，应由它在具体任务中的收益与代价决定。保留文本并缓存 KV，可以用节省的重复编码与新增保留、装载、重建费用直接比较；参数训练是否值得，则需要看写入成本、后续使用次数及行为变化。无需先证明所有系统必须混合，才能判断一个具体方案是否有效。

<a id="conclusions"></a>
## 六、结论

Memory forms 的研究对象，是经验在系统中以什么形式留下来，以及这种形式怎样参与未来计算。三类记忆各自有一条可以解释其性质的因果过程。

**参数记忆**通过经验改变权重，使后续输入经过改变后的计算。它让经验能够深入参与任务处理，也使写入选择性、跨任务影响和细粒度修正成为重要问题。

**Token memory**把经验保存为独立符号记录，在需要时选择、组织并交给模型使用。它让内容容易被检查、编辑和重新解释，系统的能力则取决于保存了哪些区分，以及能否把正确内容带入并落实到当前任务。

**Latent memory**保留模型可以继续使用的数值状态。它能够延续和复用历史计算，也能通过优化形成面向任务的表示；相应地，需要处理状态的模型依赖、资源需求和更新条件。

理解这三条过程，才能进一步讨论哪类信息适合怎样保存、写入时应保留哪些区别、读取为什么成功或失败，以及长期变化应怎样被处理。这些问题已经属于三类记忆自身的机制，而不是分类完成以后才开始考虑的附加事项。
